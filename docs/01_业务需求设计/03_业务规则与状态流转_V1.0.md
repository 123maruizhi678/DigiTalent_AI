# 2026 AI 数字化人才平台——业务规则与状态流转

- **文档编号：** 07
- **文档版本：** V1.0
- **文档状态：** 需求基线
- **编制依据：** 六份需求分析文件及第 1—36 项补充确认结果

> 本文件集中记录跨模块的业务规则、状态定义、状态转换、异常处理和人工介入边界。状态名称是需求层面的统一表达；具体代码值、状态机实现和数据库字段在详细设计阶段确定。未确认的数值或细则继续标记为待配置/待详细设计，不擅自推定。

## 1. 适用范围与基本原则

1. 业务状态由业务服务统一维护，不由前端或模型输出直接修改。
2. 状态转换必须校验当前状态、目标状态、操作人身份、角色权限和数据范围。
3. 关键状态变更应记录操作人、时间、原状态、目标状态、原因及关联任务。
4. 失败、重试、取消、恢复和人工介入均属于可追踪的业务过程。
5. AI 输出默认属于建议或草稿；需要人工确认的结果，在确认前不得作为正式业务结果生效。
6. 对会产生外部影响或不可逆影响的操作，应实施风险分级、审批、幂等及重复执行保护。

## 2. 统一身份与档案规则

### 2.1 账号、业务身份与系统角色

- 一个账号同一时点只能对应一种业务身份：候选人或员工。
- 一个自然人对应一份人才主档案。
- 候选人录用后，将原账号业务身份转换为员工身份，保留账号标识、人才主档案及候选人阶段历史业务记录。
- 一个用户可以拥有多个系统角色；角色权限按授权取并集，但仍受数据范围和明确禁止规则约束。
- 业务身份决定用户所处业务阶段，系统角色决定其可承担的职责，两者不得混为一谈。

### 2.2 重复档案处理

1. 系统根据可用身份信息识别疑似重复人才档案。
2. 系统展示重复判断依据及候选档案。
3. HR 确认后执行合并；系统不得未经确认自动合并。
4. 合并后保留来源记录、被合并档案标识及合并操作审计。
5. 具体重复识别字段、相似度阈值及冲突字段优先级在详细设计阶段确定。

## 3. 项目与岗位业务规则

- 项目可以独立存在，也可以归属于项目群。
- 项目群可以包含多个项目；项目包含一个或多个项目需求。
- 一个项目需求可以关联多个岗位；岗位之间可以共享部分条件，也可以保留独立条件。
- 项目关闭后保留历史数据，管理员可以重新开启。
- 项目关闭、重新开启均应记录操作人、时间和原因。

### 3.1 项目状态建议

| 状态 | 含义 | 允许的主要动作 |
|---|---|---|
| 草稿 | 项目尚未正式开展 | 编辑、提交/启用、删除（按权限） |
| 进行中 | 项目正在执行 | 业务处理、暂停、关闭 |
| 已暂停 | 暂时停止业务处理 | 恢复、关闭 |
| 已关闭 | 当前业务已关闭，历史数据保留 | 管理员重新开启、查看历史 |

> 状态名称用于统一业务语言；是否需要独立“已完成”状态，现阶段未单独确认，详细设计时根据项目交付流程判断，不擅自增加为强制状态。

## 4. 候选人与招聘业务规则

### 4.1 候选人招聘状态

候选人状态按招聘业务流程配置，保留每次状态变更记录。建议统一状态语义如下：

| 状态 | 含义 | 规则 |
|---|---|---|
| 待筛选 | 已进入候选人管理，等待筛选 | HR 可进行筛选处理 |
| 待邀约 | 满足初步筛选条件，等待发起邀请 | HR 可发起邀约 |
| 邀约中 | 已发送候选人邀请 | 受邀请有效期规则约束 |
| 面试中 | 正在进行一轮或多轮面试 | 按项目配置推进 |
| 测评中 | 正在进行测评 | 按项目配置推进 |
| 待决策 | 测评/面试环节已完成，等待业务决策 | 有权限人员作出结论 |
| 通过 | 当前招聘评估通过 | 可进入录用流程 |
| 淘汰 | 当前招聘流程不再推进 | HR 可填写原因重新激活 |
| 已录用 | 已完成录用 | 触发候选人账号身份转换为员工身份 |

以上状态不强制构成单一线性顺序。测评和面试的顺序可按项目或岗位配置；具体状态转换图在招聘流程详细设计阶段配置。

### 4.2 淘汰后重新激活

- 候选人被淘汰后，HR 可以重新激活。
- 重新激活必须填写原因，并记录操作人和时间。
- 重新激活后进入的具体招聘环节由项目流程配置决定。
- 不得覆盖原淘汰记录。

### 4.3 候选人邀请

- 邀请采用固定有效期。
- 邀请页面和相关通知应向邀请发起人及候选人展示有效期和具体失效日期、时间。
- 邀请过期后不得继续用于账号开通或授权登录，应提示重新邀请。
- 邀请记录至少关联候选人、发起人、创建时间、失效时间和当前状态。
- 具体有效时长尚未确认，作为可配置参数在详细设计阶段确定。

## 5. 简历解析与人才匹配规则

### 5.1 简历与档案

- 一个人才可以关联多份简历。
- 每份简历应记录来源、用途、有效状态、上传时间及历史版本。
- 原始文件保存在对象存储，业务元数据和解析状态保存在关系型数据库。
- 单次批量简历上传最多 20 份。

### 5.2 简历解析状态

| 状态 | 含义 | 转换规则 |
|---|---|---|
| 待处理 | 已创建解析任务 | 可被调度执行 |
| 处理中 | 解析任务正在执行 | 记录执行开始时间 |
| 待确认 | 解析成功，结果等待 HR 确认 | 不得直接写入正式人才档案 |
| 已确认 | HR 已确认解析结果 | 允许写入/更新正式人才档案 |
| 失败 | 自动重试达到上限或发生不可重试错误 | 允许人工重新发起 |
| 已取消 | 任务被有权限人员取消 | 保留取消记录 |

解析失败后自动重试；达到重试上限后标记失败，允许人工重新发起。重试上限和间隔在详细设计阶段配置。

### 5.3 人才岗位匹配

- 匹配结果包括硬性条件过滤结果、综合评分、匹配原因和推荐名单。
- AI 输出仅用于辅助筛选，最终筛选由 HR 决定。
- 匹配规则、评分权重及阈值需要业务配置或在后续规则设计中确定，不能由模型临时改变。
- 匹配结果应关联人才、简历版本、岗位及项目需求，保证可追溯。

## 6. 人才画像规则

1. AI 根据人才资料生成画像草稿。
2. HR 确认后，画像草稿才能成为正式画像。
3. 人才关键资料变化时，系统可以自动生成新草稿；HR 也可以手动触发重新生成。
4. 新画像不得直接覆盖旧画像；所有历史版本均需保留并可追溯。
5. 人工修改和确认应记录操作人、时间、修改前后内容及必要说明。

## 7. 测评与面试规则

- 测评与面试顺序由项目或岗位配置，可以先测评后面试、先面试后测评，也可以只安排其中一项。
- 客观题按配置规则自动评分。
- 主观题由 AI 提供评分，考官可以复核和调整。
- 测评结果、原始 AI 评分、人工复核结果及最终成绩分别留痕。
- 题库、试题、试卷、答卷、评分和测评结果之间应保留关联。
- 本期保留错题记录及管理，不建设错题复习计划。
- 测评和面试的具体状态、评分维度、通过阈值及复核触发条件，在对应业务规则配置中确定。

## 8. Agent、Workflow 与数字员工规则

### 8.1 Agent 执行

- Agent 执行任务时继承所属数字员工或任务的授权上下文，并受工具级权限限制。
- 普通且已授权的操作可以执行；敏感操作需要人工确认或审批。
- 单次 Agent 任务最长执行时间为 2 分钟。
- 失败后根据错误类型决定自动重试、人工介入或终止，并记录每次执行过程。
- 重试次数、间隔、错误分类和任务超时策略由详细设计配置。

### 8.2 Workflow 执行

- Workflow 采用固定主流程与动态分支相结合的方式。
- Workflow 支持从失败节点恢复，也允许有权限人员选择重新执行。
- 恢复或重新执行时，必须识别已成功完成的节点，防止重复执行产生重复业务结果。
- Workflow 记录节点状态、输入输出摘要、执行时间、错误信息及恢复操作。

### 8.3 任务状态建议

| 状态 | 含义 |
|---|---|
| 待执行 | 任务已创建，尚未开始 |
| 执行中 | 任务正在运行 |
| 等待人工 | 等待确认、审批或人工处理 |
| 重试中 | 任务按错误策略重新执行 |
| 已成功 | 任务执行成功 |
| 已失败 | 达到重试上限或不可重试错误导致失败 |
| 已暂停 | 任务被授权人员暂停或因权限变化暂停 |
| 已取消 | 任务被授权人员取消 |
| 已终止 | 因权限、风险或系统规则停止执行 |

### 8.4 权限变化处理

- 用户或任务授权变化后，运行中的 Agent / Workflow 必须重新校验授权。
- 权限撤销后，禁止后续未授权工具调用和业务操作。
- 根据任务风险和当前执行阶段决定暂停或终止。
- 暂停、终止及人工处理过程必须留痕。

## 9. 用户、组织与权限业务规则

1. 一个用户可以拥有多个系统角色，角色权限按授权取并集，但受数据范围和禁止规则约束。
2. 一个账号同一时点只能对应一种业务身份；候选人录用后转换为员工身份。
3. 用户停用时撤销登录及相关权限，保留历史业务数据。
4. 员工调部门时撤销原部门权限，按新部门重新分配。
5. 部门间默认数据隔离。
6. 跨部门项目授权由平台管理员审批和授权，并支持设置授权期限。
7. 敏感操作按业务类型和风险配置审批人、审批层级及审批规则；业务操作由相应业务负责人审批，系统级操作由平台管理员审批，特殊高风险操作可设置多级审批。
8. 候选人账号只能通过邀请获得，不允许自主注册。

## 10. 数据生命周期与治理规则

### 10.1 重复人才记录

系统识别疑似重复人才档案，由 HR 确认后合并；合并过程保留来源和审计记录。

### 10.2 逻辑删除与关联清理

人才档案删除先执行逻辑删除，关联数据进入待清理状态。经过规则校验后，统一清理 MySQL、MinIO、Milvus 和 Neo4j 中的关联数据，并记录清理结果。

### 10.3 个人信息删除请求

候选人提出删除个人信息请求时，由管理员审核；根据数据类别执行删除或匿名化，并处理各存储中的关联数据。依法或依业务要求需要保留的记录，其处理方式应在数据治理详细设计中明确。

### 10.4 历史版本及日志

- 人才画像保留所有历史版本。
- 简历原文件和解析结果保留历史版本及来源记录。
- 业务日志、系统日志、AI 调用日志和审计日志分类管理，分别配置访问权限和保留期限。

### 10.5 备份与恢复

- 数据每天备份一次。
- 定期验证备份可恢复性。
- 具体备份范围、全量/增量策略、保留期限、RPO / RTO 和恢复演练频率在数据治理详细设计中确定。

## 11. 异常处理与幂等原则

- 简历解析失败：自动重试，达到上限后标记失败，允许人工重新发起。
- Agent 失败：根据错误类型自动重试、人工介入或终止。
- Workflow 中断：支持从失败节点恢复或授权人员重新执行。
- 数据库写入或跨存储同步失败：记录异常并支持识别、补偿或人工处理；具体补偿策略在详细设计阶段确定。
- 对简历解析、人才建档、邀请发送、测评提交、任务执行及其他可能重复触发的业务操作，设计幂等键或等效的重复执行保护。
- 执行重试或恢复前，检查上一次执行是否已产生业务副作用，避免重复创建、重复发送或重复变更。
- 多人同时修改同一业务对象时，应识别版本冲突并提示处理；具体冲突解决策略在详细设计阶段确定。

## 12. 本期规模与非功能基线

| 指标 | 当前确认值/原则 |
|---|---|
| 初期注册用户 | 100 人以内 |
| 同时在线用户 | 20 人以内 |
| 单次批量简历上传 | 最多 20 份 |
| Agent 单次任务最长执行时间 | 2 分钟 |
| 系统可用性 | 本期不设固定百分比，建立核心服务监控、异常告警及恢复机制 |
| 数据备份 | 每天备份一次，并定期验证恢复 |

原设计中的页面响应、普通接口响应、向量检索耗时、召回率和报表生成时间等目标仍需确定测试环境、样本规模及统计口径后再作为正式验收门槛。
