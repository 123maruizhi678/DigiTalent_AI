## 一、设计目标与范围

本文件将平台前端概要架构落实为页面信息架构、菜单、路由、页面清单、页面布局、交互流程、组件组织、权限呈现、前后端API映射和页面验收标准，作为后续Vue
3前端开发和联调的设计基线。

本文件属于前端页面与交互详细设计，不代表页面已经完成原型、编码或部署。页面字段和交互可在实际开发阶段结合真实数据、接口实现、用户反馈进行调整，但调整不得破坏已经确认的业务边界、权限边界和数据一致性原则。

### 1.1 业务范围

前端覆盖七大业务模块：

1.  人才选拔；
2.  人才档案与人才画像；
3.  智能测评与面试；
4.  AI Agent与工作流管理；
5.  数字员工与任务调度；
6.  数据智能与运营决策；
7.  用户、组织与权限管理。

当前不纳入：岗前培养与培训课程、企业知识库。

候选人端采用独立门户界面，但共用平台账号认证体系。内部管理人员和候选人不共用同一套后台菜单。

### 1.2 已确认前端技术基线

  技术             用途
  ---------------- --------------------
  Vue 3            前端框架
  TypeScript       类型系统
  Vite             开发服务器与构建
  Element Plus     后台UI组件库
  Vue Router       页面路由与导航守卫
  Pinia            全局状态管理
  Axios            HTTP请求封装
  ECharts          数据可视化
  Vitest           单元测试
  Vue Test Utils   Vue组件测试
  Playwright       端到端测试

上述为设计技术基线，不代表当前工程已经全部安装或验证。进入实现前应检查实际前端工程和依赖状态；本步骤不扫描或假定任何本地项目目录内容。

### 1.3 设计原则

-   单一Vue应用，采用模块化单体架构，初期不采用微前端。
-   前端七大业务模块与后端七大业务模块保持业务对应。
-   内部管理端采用统一后台布局；候选人端采用独立门户布局。
-   页面、业务组件、公共组件、API调用和组合式逻辑分离。
-   菜单按业务模块组织，并依据用户权限动态展示。
-   首页采用统一平台首页与角色化工作台结合的方式。
-   页面标签支持固定、切换、关闭和刷新。
-   前端权限控制只改善交互体验，后端认证授权始终是最终安全边界。
-   耗时任务通过任务ID和HTTP轮询呈现状态，不假设页面必须保持打开。
-   AI生成、匹配、测评等结果应展示来源、状态和必要的人工复核入口。
-   本文所有页面方案暂按推荐方案确定，实际开发时允许经评估后调整。

### 3.3 首页与角色化工作台

采用"统一平台首页 + 角色化工作台"的组合：

-   统一首页提供平台级导航、通用待办、最近访问和必要的通知。
-   角色化工作台根据用户角色及权限展示对应统计、快捷操作和业务提醒。
-   不同角色看到的数据范围由后端决定，前端只展示服务端返回且有权访问的内容。
-   用户可有多个角色，首页工作台应明确当前业务上下文，避免把不同权限范围的数据混合展示。

工作台初步示例：

  用户类型                 工作台重点
  ------------------------ --------------------------------------------
  招聘业务人员             招聘需求、候选人阶段、待筛选简历、匹配任务
  人才管理人员             人才档案、画像待审核、人才结构
  测评/面试人员            待执行测评、待评价面试、报告状态
  Agent/Workflow运维人员   执行状态、失败任务、能力运行情况
  数字员工/任务调度人员    任务积压、调度计划、失败与重试
  运营分析人员             指标、分析任务、报告
  系统管理员               用户、组织、权限、系统状态和审计入口

以上为页面内容组织建议，不代表新增业务角色。实际可见内容由既有权限配置决定。

### 3.5 页面标签与导航

-   标签由路由元信息驱动。
-   支持固定标签、切换、关闭当前、关闭其他、关闭全部非固定标签和刷新。
-   标签标题与面包屑保持一致。
-   页面缓存按页面类型和业务状态决定，不缓存登录、权限变更、敏感表单等不适合缓存的页面。
-   标签状态不得保存密码、Token或敏感业务数据。
-   刷新页面后是否恢复标签由后续实现策略确定，不要求把所有页面状态持久化。

## 4.2 人才选拔模块

### 4.2.1 项目群管理

路由：`/selection/project-groups`

页面区域： - 搜索区：名称、状态、负责人； - 操作区：新建项目群； -
列表区：项目群名称、负责人、项目数量、状态、更新时间； -
行操作：详情、编辑、归档。

### 4.2.2 项目管理

路由：`/selection/projects`

列表字段建议： - 项目名称； - 项目群； - 项目负责人； - 状态； -
开始/结束时间； - 更新时间。

项目详情页采用标签页或分区布局： - 项目概览； - 项目需求； - 岗位； -
招聘需求； - 关联候选人或选拔进度（仅展示有明确业务关联的数据）。

项目、项目需求、岗位和招聘需求保留独立管理页面，同时允许从项目详情查看关联信息。关联视图不得替代独立资源接口。

### 4.2.3 项目需求、岗位和招聘需求

路由建议： - `/selection/project-requirements` -
`/selection/positions` - `/selection/recruitments`

各页面采用统一列表模式：筛选、分页、详情、创建和编辑。招聘需求详情作为招聘流程入口，提供候选人、筛选、匹配和阶段进度的关联视图。

### 4.2.4 候选人管理

路由： - `/selection/candidates` - `/selection/candidates/:candidateId`

列表页面： - 搜索：姓名、邮箱、电话、来源； -
筛选：状态、招聘需求、岗位、阶段； -
表格：候选人基本信息、来源、关联招聘需求、当前阶段、更新时间； -
操作：查看、编辑、归档； - 批量操作：只提供后端明确支持且有权限的操作。

详情页面： - 基本信息； - 简历； - 选拔记录； - 匹配结果； -
测评和面试关联摘要； - 相关文件。

候选人主体与人才主档案使用统一人才主体ID。候选人页面展示选拔场景信息，人才档案页面展示长期人才信息，不创建重复自然人记录。

### 4.2.5 简历管理

简历管理嵌入候选人详情的"简历"区域，不单独成为全局文件管理入口。

页面交互： 1. 用户选择文件并查看上传前校验结果； 2.
前端上传文件，后端创建文件资源； 3. 创建简历业务记录并关联文件ID； 4.
用户触发解析； 5. 后端返回解析任务ID； 6.
前端展示待处理、排队、解析中、成功或失败状态； 7. 前端轮询任务状态； 8.
解析完成后查看结构化结果； 9.
需要时由授权人员确认并将信息更新到人才档案。

解析结果区域建议： - 基本信息； - 教育经历； - 工作经历； - 项目经历； -
技能； - 解析状态和异常摘要。

原始简历不被解析结果覆盖。历史简历按业务记录查看。AI抽取内容不自动成为未经确认的正式人才信息。

### 4.2.6 简历智能筛选工作台

路由：`/selection/screening`

页面分区： - 筛选任务创建； - 招聘需求选择； - 候选人范围； -
筛选条件； - 任务列表和状态； - 筛选结果； - 人工复核。

典型流程：

``` text
选择招聘需求
  -> 设置候选人范围和筛选条件
  -> 提交筛选任务
  -> 返回task_id
  -> 展示任务状态并轮询
  -> 获取筛选结果
  -> 查看匹配依据和未满足条件
  -> 人工复核
  -> 记录业务处理结果
```

筛选结果展示建议： - 候选人； - 筛选等级/状态； - 满足条件摘要； -
未满足条件； - 依据摘要； - 模型或规则版本； - 人工复核状态。

不得仅凭AI筛选等级在前端自动执行淘汰、录用等最终业务决定。

### 4.2.7 人岗匹配工作台

路由：`/selection/matching`

页面区域： - 单人匹配； - 批量匹配； - 岗位/招聘需求选择； -
候选人范围； - 匹配任务列表； - 匹配结果排序； - 差距分析； - 人工复核。

交互流程：

``` text
选择岗位或招聘需求
  -> 选择单个或多个候选人
  -> 提交匹配
  -> 返回任务ID
  -> 轮询任务状态
  -> 获取匹配结果
  -> 按匹配分数或等级排序
  -> 查看技能/经历差距
  -> 人工复核
```

匹配分数应明确标识为AI/规则分析结果，显示必要的解释信息和版本，不将分数解释为录用概率或最终决定，除非后端业务定义明确支持该含义。

### 4.2.8 招聘阶段看板与表格视图

路由：`/selection/pipeline`

页面提供： - 看板视图：按招聘阶段分列； -
表格视图：按候选人、招聘需求、阶段和更新时间查询； -
筛选：招聘需求、岗位、阶段、负责人； -
阶段操作：进入详情、提交阶段变更。

阶段拖动： - 前端先进行目标阶段可用性提示； - 调用后端状态流转接口； -
后端验证当前状态、目标状态、用户权限和业务条件； -
成功后刷新或更新视图； - 失败时恢复原位置并展示错误原因。

不得只修改前端状态而不调用后端。

## 六、路由与菜单设计

### 6.1 路由组织建议

``` text
src/router/
├── index.ts
├── guards.ts
└── modules/
    ├── home.ts
    ├── selection.ts
    ├── talent.ts
    ├── assessment.ts
    ├── ai.ts
    ├── digital-employee.ts
    ├── analytics.ts
    ├── system.ts
    └── portal.ts
```

路由元信息建议：

``` ts
interface AppRouteMeta {
  title: string
  requiresAuth: boolean
  layout: 'main' | 'auth' | 'portal'
  permission?: string
  menuKey?: string
  breadcrumb?: string[]
  keepAlive?: boolean
  hidden?: boolean
}
```

此为前端类型设计建议，实际命名可随工程规范调整。

### 6.2 路由守卫流程

``` text
访问目标路由
  -> 读取路由元信息
  -> 判断是否需要认证
  -> 未认证：进入登录/邀请认证页
  -> 已认证：校验用户状态
  -> 获取或刷新权限信息
  -> 判断路由所需权限
  -> 无权限：进入403页面
  -> 有权限：加载页面组件
```

认证失败、Token过期和权限变更应与后端JWT协议一致。前端路由守卫不能作为后端授权的替代。

### 6.3 菜单配置

菜单配置包含： - 菜单标识； - 菜单标题； - 图标； - 路由名称； -
父级菜单； - 所需权限； - 排序； - 是否隐藏。

菜单由统一配置和当前用户权限计算生成。不得只通过隐藏菜单保护接口。

### 6.4 路由命名约定

-   路径使用小写英文和连字符；
-   资源详情使用`:resourceId`或明确业务标识；
-   列表、详情、创建/编辑优先采用同一资源路径结构；
-   候选人门户统一使用`/portal`前缀；
-   管理端统一使用模块前缀；
-   路由名称全局唯一；
-   不把Token、邀请凭据或敏感信息放入URL。

注意：API详细设计中已定义的资源路径作为页面调用依据。若个别页面需要的查询能力尚无对应接口，应先补充API契约，再开发页面，不得由前端绕过API直接访问数据库或文件系统。

## 八、交互状态与统一体验规范

### 8.1 页面通用状态

所有数据页面应考虑以下状态：

  状态         前端表现
  ------------ --------------------------------
  初次加载     Loading或Skeleton
  正常数据     表格、卡片或详情
  空数据       空状态说明和有权限的创建入口
  查询无结果   显示无匹配数据及清除筛选入口
  请求失败     错误提示、保留可恢复的筛选条件
  无权限       403提示，不显示敏感数据
  资源不存在   404页面或资源不存在提示
  数据冲突     显示业务冲突原因并引导刷新
  提交中       禁止重复提交，显示进度
  操作成功     明确反馈并刷新相关数据

### 8.2 表单交互

-   表单字段与后端Pydantic Schema保持一致。
-   必填、长度、枚举和格式规则前后端尽可能一致。
-   前端校验只用于即时反馈，后端必须再次校验。
-   创建和编辑表单区分字段默认值和未提交字段。
-   重要操作需确认；取消编辑时提示未保存变更。
-   业务状态字段不允许通过普通表单绕过后端状态流转。

### 8.3 表格与搜索

-   列表默认采用服务端分页，默认20条、最大100条，具体以接口约束为准。
-   搜索条件支持重置和查询。
-   排序字段必须是API允许的白名单字段。
-   筛选条件变化后按约定重置页码。
-   批量操作需检查每条数据的权限和业务状态。
-   不将全量数据加载到前端再自行分页。

### 8.4 文件上传和下载

-   上传前展示文件名、大小和类型。
-   上传过程展示进度和失败状态。
-   文件上传成功后保存后端返回的file_id。
-   业务关联使用file_id，不使用本地路径。
-   下载和预览通过后端鉴权接口完成。
-   前端不拼接服务器物理路径，不将永久文件URL暴露给未授权用户。

### 8.5 异步任务交互

适用于简历解析、筛选、匹配、画像生成、测评评分、报告生成、Agent/Workflow执行和数据分析。

统一流程：

``` text
用户提交
  -> 前端禁用重复提交
  -> API返回task_id或execution_id
  -> 页面展示已受理
  -> HTTP轮询状态
  -> 状态进入终态
  -> 停止轮询
  -> 成功：加载结果
  -> 失败：展示安全错误摘要和允许的重试操作
  -> 取消：展示取消结果
```

规则： - 不把浏览器页面是否打开作为任务生命周期依据； -
轮询间隔应可配置，并避免高频请求； -
页面卸载时停止本页面轮询定时器，但不默认取消服务端任务； -
返回页面后可根据任务ID恢复查询； -
任务取消、重试必须调用后端接口并遵守权限与状态机； -
进度无法准确计算时展示阶段，不虚构百分比。

### 8.6 多标签页与页面缓存

-   标签与路由绑定；
-   标签关闭不自动删除后端业务数据；
-   页面缓存需考虑数据权限和敏感信息；
-   用户退出登录或权限变更后清理不再适用的缓存；
-   详情页切换资源ID时避免复用上一个资源的数据。

## 十、状态管理与前端服务

### 10.1 Pinia全局Store

建议： - `userStore`：当前用户基本信息和认证状态； -
`permissionStore`：当前用户权限和可见菜单； -
`appStore`：布局、主题、侧栏和全局界面状态； -
`tabStore`：导航标签状态； -
`notificationStore`：通知摘要（若后端提供相应接口）。

### 10.2 模块状态

候选人筛选条件、当前人才详情、测评表单和分析页面临时结果优先放在模块Composable或页面局部状态，不把所有业务数据塞进全局Store。

### 10.3 API服务

各业务模块维护独立API文件，共用统一Axios实例。请求层统一处理： -
BaseURL和超时； - JWT认证请求头； - request_id关联； - 统一响应结构； -
HTTP和业务错误； - 401、403和网络异常； - 文件上传下载。

前端TypeScript类型应与后端Pydantic/OpenAPI保持一致。接口契约变化后应同步更新类型和测试。

## 十一、权限、安全和敏感信息呈现

### 11.1 三级前端控制

1.  路由级：无权限用户不能进入页面；
2.  菜单级：只展示有权访问的菜单；
3.  按钮/操作级：隐藏或禁用无权执行的操作。

后端必须对每次请求重新执行认证、资源授权和数据范围过滤。

### 11.2 数据展示控制

-   仅展示当前用户有权访问的数据；
-   敏感字段按后端返回的权限结果控制；
-   文件预览和下载每次重新鉴权；
-   不能通过前端隐藏列来代替后端字段级保护；
-   不在浏览器控制台、URL或普通错误提示中输出密钥和Token；
-   不在本地持久化存储中保存不必要的敏感业务信息。

### 11.3 AI结果呈现

AI筛选、匹配、画像、评分和面试分析应： - 明确标识AI生成或算法分析； -
展示必要的来源摘要和版本信息； - 区分模型建议与人工确认； -
对高影响业务动作保留人工审核； -
不允许前端把AI建议直接转换为最终录用或淘汰结论。

## 十四、开发实施注意事项与允许调整范围

### 14.1 可以在开发时调整

-   页面布局细节、卡片和表格列；
-   页面分区、标签页顺序；
-   搜索条件和筛选器表现；
-   弹窗、抽屉或独立详情页的选择；
-   组件拆分和复用方式；
-   页面缓存和交互反馈；
-   桌面端不同分辨率适配细节；
-   根据真实用户反馈调整导航和操作路径。

### 14.2 调整前必须重新评估

-   页面是否改变业务对象边界；
-   是否需要新增或修改API；
-   是否改变数据库字段或关联；
-   是否扩大用户数据可见范围；
-   是否改变AI任务的状态流转；
-   是否绕过人工审核；
-   是否让候选人门户访问内部管理数据；
-   是否与统一文件权限和审计规则冲突。

### 14.3 不得仅因页面方便而改变的约束

-   七大业务模块边界；
-   人才主档案与候选人主体统一标识原则；
-   邀请制账号策略；
-   JWT认证和后端数据范围控制；
-   Agent、Workflow和数字员工的对象边界；
-   MySQL业务状态与日志文件的存储边界；
-   AI分析结果与人工业务决定的区分；
-   文件资源必须由后端鉴权访问。
