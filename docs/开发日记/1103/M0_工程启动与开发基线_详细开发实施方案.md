### 1.4 已确认的技术和项目约束

-   后端：Python、FastAPI、Pydantic；采用模块化单体，不拆微服务。
-   后端分层：API、Schema、Service、Repository、Model；公共基础设施放在`core`和`common`。
-   前端：Vue 3、TypeScript、Vite；依赖清单中的Element Plus、Vue
    Router、Pinia、Axios、ECharts等按既定清单管理。

    Compose作为M0前置条件。
-   配置统一管理；真实密钥不得进入代码仓库、普通日志或文档。

# 任务一：P6-BASE-001 建立后端工程骨架

-   优先级：P0
-   复杂度：简单
-   前置依赖：无
-   目标：建立可启动、结构清晰、可扩展的FastAPI最小应用。

### 4.1.1 实施内容

1.  核对当前后端目录和已有FastAPI入口。
2.  确认Python解释器来自已确定的Conda环境`feiyu`；若当前解释器不符，先停止并反馈，不擅自创建新环境。
3.  按后端分层设计建立或补齐`app/`、`api/`、`core/`、`common/`等基础包。
4.  建立唯一FastAPI应用入口`main.py`。
5.  建立总路由注册器`api/router.py`。
6.  建立最小健康检查路由，例如`GET /api/v1/health`；如果项目现有健康检查路径已确定，则沿用现有路径，不重复新增。
7.  应用启动时只初始化M0所需资源，不连接MySQL、Milvus、Ollama或MinerU。
8.  明确应用启动和关闭生命周期入口，为后续数据库连接池、Worker等资源预留挂载位置，但不提前实现。
9.  为后端测试建立`tests/unit/`和`tests/api/`目录约定。

### 4.1.2 关键代码职责

`main.py`只负责应用组装：

-   创建FastAPI实例；
-   调用配置加载入口；
-   初始化日志；
-   注册请求中间件；
-   注册全局异常处理；
-   注册总路由；
-   配置应用生命周期。

`router.py`只负责路由聚合：

-   统一API版本前缀；
-   注册健康检查路由；
-   为未来业务路由保留明确注册位置；
-   不编写SQL、不放业务规则。

健康检查只用于判断应用进程和HTTP服务是否可用。数据库、模型、向量库等依赖健康状态在对应里程碑增加独立检查，不在M0健康检查中伪造为已验证。

### 4.1.3 验证步骤

在后端目录、Conda环境和依赖状态确认后执行：

``` powershell
conda activate feiyu
python --version
python -m pip show fastapi pydantic
```

启动命令按项目最终入口确定，建议统一为：

``` powershell
python -m uvicorn app.main:app --host 127.0.0.1 --port 8080 --reload
```

检查：

``` powershell
Test-NetConnection 127.0.0.1 -Port 8080
Invoke-RestMethod http://127.0.0.1:8080/api/v1/health
```

若现有路由前缀或启动入口不同，应以实际项目配置为准并同步更新README，不能为了照抄命令而重复挂载`/api`。

### 4.1.4 验收标准

-   [ ] FastAPI应用可从约定入口启动；
-   [ ] 健康检查返回成功状态和明确服务标识；
-   [ ] 应用路由统一注册；
-   [ ] 启动时不依赖MySQL、Milvus、Ollama、MinerU；
-   [ ] 业务逻辑未混入`main.py`或总路由注册器；
-   [ ] 已有目录和文件未被无故覆盖或迁移；
-   [ ] 有实际命令输出和接口响应作为验收证据。

-   优先级：P0

# 任务四：P6-BASE-003 建立日志与异常基础设施

-   优先级：P0
-   复杂度：中等
-   前置依赖：BASE-001、BASE-002
-   目标：建立请求级追踪、统一异常转换和安全日志基础。

### 4.4.1 实施内容

1.  在`app/core/logging.py`建立统一日志初始化入口。
2.  支持DEBUG、INFO、WARNING、ERROR等级。
3.  采用结构化日志字段，至少包含时间、级别、logger名称、消息和`request_id`（请求上下文存在时）。
4.  在`app/core/middleware.py`建立请求追踪中间件：
    -   接收可信的请求追踪标识或生成新的`request_id`；
    -   将请求标识放入请求上下文；
    -   在响应头返回`request_id`；
    -   记录请求方法、路径、状态码和耗时；
    -   不记录请求体、密码、Token或完整个人信息。
5.  在`app/core/exceptions.py`建立应用异常基类和明确的异常类型。
6.  在`main.py`注册全局异常处理器，将异常转换为统一错误响应。
7.  区分参数错误、业务错误、权限错误和系统错误的基础表达；M0不实现完整认证权限逻辑。
8.  对未预期异常记录受控堆栈信息，客户端只返回安全、简洁的错误信息。
9.  日志与安全审计概念分离：M0只建立应用运行日志和请求日志基础；安全审计事件的完整事件模型、完整性保护和审计查询按后续安全任务实施。
10. 日志输出位置遵循现有项目配置；未经用户明确指定，不写入或检查受限的`logs`目录。

### 4.4.2 统一错误响应约定

与API详细设计保持一致，普通JSON错误响应至少具有：

``` json
{
  "code": "SYSTEM_ERROR",
  "message": "系统处理失败",
  "data": {
    "errors": []
  },
  "request_id": "req_xxxxx"
}
```

具体错误码应沿用API详细设计中已确认的五大类别：认证、权限、参数、业务、系统。M0只建立通用异常转换机制，不提前实现所有业务错误码。

### 4.4.3 敏感信息保护

普通日志不得记录：

-   密码、Access Token、Refresh Token、Cookie；
-   API Key、数据库密码和完整连接串；
-   简历全文、身份证号及不必要的联系方式；
-   文件内容、模型完整上下文或未经脱敏的业务数据；
-   堆栈、内部绝对路径和数据库细节到客户端响应。

### 4.4.4 验证步骤

1.  正常健康检查请求产生请求日志；
2.  响应包含`request_id`；
3.  受控应用异常被转换为统一错误响应；
4.  未预期异常返回通用系统错误，服务端日志保留必要诊断信息；
5.  同一请求的日志与响应使用相同`request_id`；
6.  使用测试输入检查密码、Token和敏感字段不会出现在普通日志；
7.  日志初始化失败时能给出明确启动错误，不静默丢失日志。

### 4.4.5 验收标准

-   [ ] 日志初始化由统一模块负责；
-   [ ] 请求ID贯穿请求日志和响应；
-   [ ] 全局异常处理器已注册；
-   [ ] 错误响应符合统一契约；
-   [ ] 未预期异常不会把堆栈返回前端；
-   [ ] 敏感字段不会进入普通日志；
-   [ ] 没有擅自把安全审计日志简化为普通业务日志；
-   [ ] 相关测试有可复现证据。

-   记录：在开发日志写入文件名、修改内容、验证命令和结果；

若没有Git版本控制或工作区存在未提交修改，先保留备份/差异记录并向用户说明，不擅自覆盖。
