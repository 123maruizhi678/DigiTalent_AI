## 4. 任务状态与流转规范

| 状态 | 进入条件 | 退出条件与去向 |
| --- | --- | --- |
| 待开始 | 已分配唯一编号、来源与范围 | 用户授权且依赖满足、完成开发前检查后到开发中 |
| 开发中 | 开始按批准范围实施 | 实施完成到待测试；需暂停到已暂停 |
| 待测试 | 实施自述完成，验证清单明确 | 真实验证通过且证据齐全到待审核；失败到待整改；不适用项须说明并审核 |
| 待审核 | 测试证据、差异和报告齐全；文档任务完成适用检查 | 技术审核明确通过到已通过；不通过到待整改 |
| 待整改 | 测试失败、审核意见或用户退回 | 按明确整改范围实施，完成后到待测试，复验后重新待审核 |
| 已通过 | 技术审核人明确确认技术标准通过 | 用户正式确认且遗留项归属明确后到已关闭；退回则待整改 |
| 已关闭 | 用户明确验收确认，归档证据齐全 | 发现需重开问题时记录来源及授权，转待整改，保留关闭历史 |
| 已暂停 | 记录原因、影响、暂停前状态及恢复条件 | 条件解除并获继续授权后回原阶段；不得因时间经过自动恢复 |

正常流转：待开始 → 开发中 → 待测试 → 待审核 → 已通过 → 已关闭。任一未关闭执行阶段可记录暂停；取消任务以已暂停记录取消原因，是否另立任务由用户决定。

旧枚举映射仅用于理解：进行中/待联调/联调中对应开发中并记录联调子阶段；测试中对应待测试并记测试进度；待验收按证据区分待审核或已通过；旧“已完成”必须核查审核和用户确认，不能直接映射已关闭；阻塞对应已暂停并保留原阶段。历史原文不改。

四种结论独立记录：Codex 完成自述只能说明实施交付；自动化测试通过只覆盖已执行断言；技术审核通过需审核人意见及证据；用户正式确认需用户明确回复及日期。Git 提交、开始新聊天或沉默均不能代替确认，也不能仅凭这份规范将 M0 标记整体完成。

## 7. 开发过程与验收规范

1. 读取用户指定的依据及适用根规则，缺失则报告，不搜索受限目录替代品。
2. 检查相关工程状态、调用关系、文件和原 Git 状态。
3. 输出开发前检查结果、已有成果、差异与风险。
4. 输出拟新增和修改文件清单；删除单独列出授权依据。
5. 制定实施计划和验证方案，说明待确认事项。
6. 在授权范围内实施，保护共享文件和他人修改。
7. 执行适用自动化测试，记录命令、环境、预期、真实结果；不适用项说明原因。
8. 检查真实代码差异及新增文件，不能以未跟踪文件的空 diff 代替审查。
9. 在用户授权位置生成或增量追加开发记录，不覆盖历史测试及记录。
10. 提交技术审核，保留意见和审核身份、日期。
11. 根据已授权审核意见整改、复测、重新审核；越界修改先说明并取得授权。
12. 用户正式确认并明确授权后才进入下一项任务。

不得跳过前检查、把计划写成完成、以测试通过代替整体验收、擅自扩大范围、自动提交 Git 或自动进入下一阶段。本轮文档任务以内容覆盖和保护检查验证，业务测试不适用且未执行。
