# 数据库表设计 · 2026 AI 数字化人才平台

> 配套：PRD + 概要设计 + 详细设计 + 接口设计。
> 字段定义取自 `backend/app/infrastructure/*.py` 真实 ORM 模型（2026-09-27）。类型按 MySQL 映射（INT/VARCHAR/TEXT/JSON/DATETIME/…）。未逐字段展开但已建模的表见第 9 节。

---

## 1. 数据库选型与分布

| 存储 | 引擎 | 承载内容 |
|---|---|---|
| 业务主库 | MySQL（pymysql） | 全部结构化业务主数据（下表所有关系表） |
| 向量库 | Milvus（pymilvus 3.0） | 人才/简历/岗位/知识切片向量（`knowledge_chunks.milvus_id` 关联） |
| 图库 | Neo4j（额外引入） | 人才-技能-岗位-制度知识图谱 |
| 缓存/队列 | Redis（经 Celery，待补统一缓存层） | 任务调度、会话、限流（规划中） |
| 对象存储 | MinIO | 简历/知识库原文件（`object_key`） |

> 需求强制"四库协同"（MySQL+PgSQL+Milvus+Redis）；当前 MySQL+Milvus 已落地，PgSQL（分析/时序）与统一 Redis 缓存层待补（PRD 第 4 节）。

---

## 2. 命名规范

- 业务表：`snake_case` 复数（如 `resume_files`）；系统表前缀 `sys_`（如 `sys_users`）。
- 主键：`id` INT 自增；时间戳由 `TimestampMixin` 注入 `created_at`/`updated_at`（系统表部分用 `created_at`）。
- 软删除：业务表多用 `status` 字段（active/deleted）而非物理删除。

## 6. 测评域

### 6.1 `question_banks` / `questions`
`question_banks`：id, name(VARCHAR255), description(TEXT), total_questions(INT), status。
`questions`：id, bank_id(FK), serial_no(VARCHAR64), question_type(single_choice/multi_choice/fill_blank/essay), content(TEXT), options(JSON), answer(TEXT), score(INT), scoring_standard(TEXT), analysis(TEXT), knowledge_point(VARCHAR255), knowledge_category(VARCHAR255), knowledge_base_category(VARCHAR255), difficulty(easy/medium/hard), subjective(BOOL), operator(VARCHAR128), status。

### 6.2 `exams` / `exam_submissions` / `exam_interview_results`
`exams`：id, name, category(面试/内测), description, bank_ids(JSON), question_ids(JSON), total_questions(INT), total_score(INT), pass_score(INT), start_time(DATETIME), end_time(DATETIME), duration_minutes(INT DEFAULT 60), status(draft/published)。
`exam_submissions`：id, exam_id(FK), candidate_name, answers(JSON), score(INT), max_score(INT), pass_score(INT), result(passed/failed), recommendation(TEXT), detail(JSON)。
`exam_interview_results`：id, exam_id(FK), submission_id(FK), candidate_id(FK NULL), invite_id(FK NULL), candidate_name, score, max_score, pass_score, result, result_label, passed(BOOL), next_round_recommended(BOOL), candidate_status, notification_status, notification_message(TEXT), answers(JSON), detail(JSON)。

### 6.3 `wrong_questions` / `review_plans`
`wrong_questions`：id, exam_id/ submission_id/ question_id/ bank_id(INT NULL), candidate_name, content(TEXT), question_type, user_answer(TEXT), standard_answer(TEXT), analysis(TEXT), score(INT), max_score(INT), status(active/mastered/deleted)。
`review_plans`：id, wrong_question_id(FK), question_id(INT NULL), candidate_name, content(TEXT), question_type, review_time(DATETIME), reminder(BOOL), status(scheduled/completed/cancelled/deleted)。

## 10. 索引与性能建议

- 外键列均建索引：`resume_id`、`parsed_resume_id`、`job_profile_id`、`exam_id`、`bank_id`、`agent_id`、`user_id`、`role_id`、`menu_id`、`knowledge_id`。
- 列表/过滤高频列：`status`、`name`、`schedule_type`、`data_scope`、`category` 建普通/组合索引。
- 向量检索走 Milvus 独立集合（非 MySQL）；图谱查询走 Neo4j。
- 分页大表（parsed_resumes、match_lists、exam_submissions、sys_operation_logs）需覆盖索引 + 合理 `page_size` 上限。

## 11. 与需求"四库协同"差距

- ✅ MySQL：全部关系表已落地（上表）。
- ✅ Milvus：向量由 `knowledge_chunks.milvus_id` + 人才/简历向量承载。
- ➕ Neo4j：图谱增强（超出需求）。
- ❌ PgSQL：海量分析/时序数据暂落 MySQL，是否引入见 PRD 决策项 3。
- ⚠️ Redis：仅 Celery 任务调度使用，缺统一缓存/会话/限流层（PRD 决策项 4）。
