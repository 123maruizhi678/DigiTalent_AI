## 一、评估目标与范围

本步骤判断平台能否在用户身份、角色和业务数据范围受控的前提下，通过自然语言查询业务数据，并进一步形成统计分析、可视化、人才缺口分析、决策建议和分析报告。

本步骤正式评估 12 项：

1. 自然语言问题理解和查询意图识别。
2. NL2SQL 技术路线及候选方案。
3. 数据库 Schema、表关系和字段语义提供方式。
4. 查询范围与用户数据权限的关联。
5. SQL 生成、语法校验和安全校验。
6. 只读查询限制、危险语句拦截和资源限制。
7. 查询结果解释、统计和聚合分析。
8. 数据可视化及图表生成。
9. 人才缺口分析和运营指标分析。
10. 分析报告生成及结果溯源。
11. 查询超时、结果过大和异常处理。
12. 数据准确性、权限隔离和审计记录。

### 1.1 业务范围依据

已确认的业务对象与流程文件将数据智能与运营决策范围定义为：
- 自然语言数据查询。
- AI 将自然语言转换为只读 SQL。
- 查询前进行用户身份、角色和业务数据范围校验。
- SQL 安全检查，禁止通过 NL2SQL 新增、修改或删除业务数据。
- 业务数据统计及数据可视化。
- 人才缺口分析。
- 决策建议及分析报告生成。
- 运营及审计数据查看。

NL2SQL 只承担只读查询；业务数据修改不通过 NL2SQL 执行。

### 1.2 不在本步骤内完成的工作

- 不开发完整 NL2SQL 业务功能。
- 不直接创建或修改正式业务数据库表。
- 不在没有真实数据字典和业务指标口径的情况下宣称查询准确。
- 不把大模型生成的 SQL 直接交给数据库执行。
- 不将本步骤的技术路线评估视为安全、性能或生产验收；相关专项仍需在第二阶段第 8 步及后续实施中完成。

## 四、自然语言问题理解与查询意图识别

### 4.1 用户确认方案

AI 先识别用户问题意图、业务对象、统计维度和时间范围，再进入数据查询流程；不将用户原始问题直接交给模型生成 SQL。

### 4.2 建议识别结果结构

| 字段 | 说明 |
|---|---|
| intent | 查询意图，例如明细查询、统计、趋势、对比 |
| business_domains | 涉及的人才、岗位、技能、测评等业务领域 |
| entities | 问题中涉及的业务对象 |
| metrics | 需要查询的业务指标 |
| dimensions | 分组或对比维度 |
| time_range | 时间范围及其解释 |
| filters | 用户明确提出的筛选条件 |
| output_preference | 表格、统计摘要或图表等结果偏好 |
| ambiguity | 是否存在歧义及需要澄清的内容 |

### 4.3 示例

用户问题：“最近一个月，各岗位的人才缺口分别是多少？”

意图识别结果示例：

| 识别项目 | 结果 |
|---|---|
| 查询意图 | 人才缺口统计 |
| 业务对象 | 岗位、人才 |
| 统计指标 | 人才缺口人数 |
| 统计维度 | 岗位 |
| 时间范围 | 最近一个月 |
| 结果形式 | 分组统计及岗位间对比 |

若“最近一个月”的业务口径、时区或统计日期不明确，应采用平台统一规则或向用户澄清，不应由模型任意解释。

### 4.4 可行性结论

本地模型可以承担自然语言意图识别，但对复杂业务问题、歧义时间范围和复合指标的识别效果需要使用真实业务问题集评估。

**结论：可行，模型理解准确率待测试。**

## 五、NL2SQL 技术路线

### 5.1 用户确认方案

采用本地大模型生成候选 SQL，结合数据字典和 Schema 检索、程序化 SQL 校验及只读执行机制。

### 5.2 推荐流程

```text
用户自然语言问题
        ↓
问题理解与意图识别
        ↓
数据字典 / Schema 检索
        ↓
本地大模型生成候选 SQL
        ↓
SQL 解析与安全校验
        ↓
用户数据范围校验
        ↓
只读数据库账号执行
        ↓
结果结构化与结果校验
        ↓
统计解释 / 图表 / 报告
```

### 5.3 技术职责

| 组件 | 职责 |
|---|---|
| LangChain | 封装模型、Prompt、Schema 检索及查询工具 |
| LangGraph | 管理查询流程、分支、失败处理和人工澄清 |
| Ollama | 生成意图结构和候选 SQL |
| 数据字典服务 | 提供业务表、字段、关系和指标定义 |
| SQL 安全校验模块 | 独立解析和验证候选 SQL |
| 查询执行服务 | 通过只读账号执行已通过校验的 SQL |
| 结果分析模块 | 进行确定性统计和模型辅助解释 |

### 5.4 重要边界

- 大模型输出始终视为不可信候选内容。
- 模型自我检查不能替代程序化 SQL 安全校验。
- 不允许模型直接持有数据库连接或数据库凭据。
- SQL 通过校验后，仍由只读数据库账号和数据库权限提供最后一道保护。
- 对无法映射到数据字典、指标定义或授权数据域的问题，应拒绝生成可执行 SQL 或要求用户澄清。

### 5.5 可行性结论

当前 Python、LangChain、LangGraph、Ollama、MySQL 技术基线能够支撑该流程。实际可用性取决于本地模型生成质量、数据字典完整度和 SQL 校验覆盖率。

**结论：有条件可行。**

## 六、数据库 Schema、表关系和字段语义管理

### 6.1 用户确认方案

建立统一数据字典，管理表结构、字段含义、表关系和业务指标，并根据查询意图提供相关 Schema，而不是每次向模型提供完整数据库结构。

### 6.2 数据字典建议内容

| 类型 | 建议管理内容 |
|---|---|
| 业务域 | 人才、岗位、技能、测评、面试、组织、运营等 |
| 数据表 | 物理表名、业务名称、用途、所属业务域 |
| 字段 | 字段名、数据类型、业务含义、是否敏感 |
| 表关系 | 主键、外键、关联字段、允许的 JOIN 关系 |
| 指标 | 指标名称、定义、计算口径、数据来源 |
| 维度 | 时间、组织、岗位、项目、技能等 |
| 查询策略 | 允许查询的表、字段、关联关系及聚合规则 |
| 权限标签 | 数据域、组织范围、字段敏感等级和授权要求 |

### 6.3 Schema 检索方式

根据意图识别得到的业务域、指标和维度，检索最小必要的表结构及关系，再提供给模型生成候选 SQL。

不能仅凭表名相似就允许 JOIN；关联关系必须来自已登记且经过确认的数据字典。

### 6.4 可行性结论

MySQL 元数据可提供物理结构基础，业务字段含义、关系和指标口径需要结合已确认业务文档及后续数据库设计补充。

**结论：可行；数据字典建设是 NL2SQL 准确性的关键前置工作。**

## 七、用户数据权限与查询范围控制

### 7.1 用户确认方案

查询前结合用户身份、角色、组织和业务数据范围进行权限校验，并生成受限查询条件。

### 7.2 建议权限判断流程

```text
用户发起查询
    ↓
认证用户身份
    ↓
获取角色、组织和数据授权
    ↓
识别查询涉及的业务域、表和字段
    ↓
校验查询范围是否被授权
    ↓
生成受限查询条件
    ↓
进入 SQL 安全校验
```

### 7.3 权限控制层次

| 层次 | 控制内容 |
|---|---|
| 用户身份 | 确认当前请求主体 |
| 角色权限 | 判断允许使用的数据查询能力 |
| 组织范围 | 限定可查询的组织或部门 |
| 业务数据范围 | 限定项目、岗位、人才等业务对象 |
| 表权限 | 限定可访问的数据表 |
| 字段权限 | 限定可访问字段，尤其是敏感个人信息 |
| 聚合与导出权限 | 控制结果粒度、明细查看和导出能力 |

### 7.4 安全要求

权限条件不能仅通过 Prompt 告知模型。应由后端权限服务生成并验证，且在 SQL 执行前再次检查。对于涉及敏感数据的查询，应按平台既有用户、角色、数据范围和审批规则处理。

**结论：有条件可行；需与第 8 步安全专项统一验证。**

## 八、SQL 生成、语法校验和安全校验

### 8.1 用户确认方案

使用 SQL 解析器进行：
- 语法分析。
- SQL 语句类型检查。
- 表白名单校验。
- 字段白名单校验。
- 表关联关系校验。
- 用户数据权限条件校验。

### 8.2 校验项目

| 校验项目 | 处理要求 |
|---|---|
| SQL 语法 | 使用解析器解析，不能只靠字符串判断 |
| 语句类型 | 只允许符合策略的只读 SELECT 查询 |
| 多语句 | 默认拒绝多语句 |
| 表白名单 | 只允许访问已登记且授权的数据表 |
| 字段白名单 | 只允许查询授权字段 |
| JOIN 关系 | 只允许数据字典登记的关联关系 |
| 权限条件 | 验证组织和业务数据范围约束 |
| 子查询与 CTE | 按复杂度及允许规则校验 |
| 危险语法及函数 | 使用白名单或明确的拒绝策略 |
| 参数 | 使用参数化方式传递用户值，避免字符串拼接 |

### 8.3 候选工具

可以评估 SQLGlot 等 SQL 解析工具，验证 MySQL 方言、AST 节点分析和 SQL 重写能力。最终工具及版本应通过最小集成测试后确定。

### 8.4 重要限制

仅检查 SQL 是否以 `SELECT` 开头不构成安全校验。只读校验应基于解析后的语法结构，并结合数据库权限进行纵深防护。

**结论：有条件可行；解析器兼容性和规则覆盖需要专项测试。**

## 九、只读执行、危险语句拦截和资源限制

### 9.1 用户确认方案

使用独立只读数据库账号，限制查询表和字段，禁止危险语句，并设置查询超时、返回行数及资源限制。

### 9.2 建议防护措施

| 防护层 | 建议措施 |
|---|---|
| 数据库账号 | 独立 NL2SQL 只读账号，不使用管理员账号 |
| 数据库授权 | 仅授予允许查询的数据对象权限 |
| 事务 | 使用只读事务策略（结合数据库能力验证） |
| SQL 规则 | 只允许白名单查询结构，拒绝写操作和危险语句 |
| 查询超时 | 设置数据库和应用层超时 |
| 结果行数 | 设置最大返回行数 |
| 分页 | 对明细结果采用分页或受控游标策略 |
| 查询复杂度 | 限制关联数量、子查询层级及高成本查询 |
| 并发 | 限制查询服务和数据库连接池并发 |
| 字段保护 | 对敏感字段进行授权、脱敏或拒绝返回 |

### 9.3 可行性结论

MySQL 独立只读账号、应用层 SQL 校验和查询资源限制能够形成多层防护。

**结论：有条件可行；数据库权限配置和高成本查询控制需要实测。**

## 十、查询结果解释、统计和聚合分析

### 10.1 用户确认方案

AI 对查询结果进行解释、统计和聚合分析，输出关键指标、数据对比及结论。

### 10.2 处理原则

将确定性计算与模型解释分开：

1. 数据库执行授权查询。
2. 统计程序执行可复现的聚合、比率和差值计算。
3. 对结果进行结构及口径检查。
4. 大模型根据真实查询结果生成自然语言解释。
5. 输出结果时附带统计范围、指标口径和数据时间。

### 10.3 示例输出结构

| 内容 | 示例 |
|---|---|
| 统计范围 | 指定时间范围和授权组织 |
| 关键指标 | 岗位需求人数、符合条件人才人数、人才缺口 |
| 数据对比 | 不同岗位之间的缺口对比 |
| 趋势 | 与上一统计周期比较 |
| 结论 | 对实际统计结果进行解释 |
| 限制说明 | 数据缺失、口径差异或样本不足提示 |

模型不能自行补齐缺失数字，也不能把相关性直接描述为因果关系。

### 10.4 可行性结论

SQL 聚合和 Python 确定性计算可承担数值计算，Ollama 负责解释。模型解释质量仍需通过业务问题集和人工评审验证。

**结论：可行。**

## 十一、数据可视化及图表生成

### 11.1 用户确认方案

AI 根据数据类型和分析意图推荐图表类型，前端使用统一图表组件渲染。

### 11.2 推荐流程

```text
授权查询结果
    ↓
结果结构标准化
    ↓
识别数据类型和统计维度
    ↓
推荐图表类型
    ↓
生成受约束的图表配置
    ↓
Pydantic / 前端 Schema 校验
    ↓
统一图表组件渲染
```

### 11.3 图表适用场景

| 图表 | 适用场景 |
|---|---|
| 柱状图 | 不同岗位人才数量对比 |
| 折线图 | 人才数量、测评通过率趋势 |
| 饼图 | 人才类型或状态占比 |
| 条形图 | 岗位缺口排名 |
| 堆叠柱状图 | 不同技能的人才分布 |

### 11.4 安全与准确性要求

- 大模型只生成受约束的图表配置，不生成并执行任意前端代码。
- 图表数据只能来自本次已授权查询结果。
- 图表字段、系列和数据类型必须校验。
- 样本量过小或数据缺失时，应显示限制说明。
- 图表标题、时间范围、单位和指标口径应与数据结果一致。

### 11.5 可行性结论

采用前端统一图表组件和结构化配置可以实现。具体图表库及版本在前端工程实施时确定。

**结论：可行。**

## 十二、人才缺口分析和运营指标分析

### 12.1 用户确认方案

建立统一业务指标体系，结合人才、岗位、技能和测评数据开展缺口分析及趋势分析。

### 12.2 指标体系建议

| 指标类别 | 指标示例 |
|---|---|
| 人才指标 | 人才总量、有效人才数量、人才状态分布 |
| 岗位指标 | 岗位需求人数、岗位数量、需求变化 |
| 匹配指标 | 匹配人数、匹配率、符合硬性条件人数 |
| 技能指标 | 技能覆盖率、技能缺口、技能分布 |
| 测评指标 | 测评参与人数、通过率、平均成绩 |
| 运营指标 | 任务完成率、处理时长、异常任务数量 |

具体指标是否纳入正式范围，应以业务数据结构和指标口径确认结果为准。

### 12.3 指标定义要求

每项指标至少明确：
- 指标唯一编码及名称。
- 业务定义。
- 计算公式。
- 数据来源表和字段。
- 统计粒度。
- 时间口径。
- 过滤条件。
- 权限要求。
- 更新频率。
- 负责人或确认来源。

### 12.4 人才缺口计算示例

在岗位需求人数和符合岗位条件的人才人数采用同一统计范围、时间口径和去重规则的前提下，可定义：

\[
人才缺口人数 = \max(岗位需求人数-符合条件的人才人数, 0)
\]

“符合条件的人才”应沿用第四步人才与岗位匹配中已确认的硬性条件过滤及综合评分规则，不由大模型临时改变匹配标准。

### 12.5 可行性结论

统计分析和趋势计算技术上可实现。准确性依赖业务指标定义、数据完整性、岗位匹配规则及历史数据质量。

**结论：有条件可行；指标口径和数据质量是主要前置条件。**

## 十三、分析报告生成及结果溯源

### 13.1 用户确认方案

根据查询结果和统一指标体系自动生成分析报告，包含：
- 统计数据。
- 图表。
- 分析结论。
- 建议。
- 数据来源。

### 13.2 报告生成流程

```text
用户提出分析需求
      ↓
问题理解和权限校验
      ↓
查询及确定性统计
      ↓
数据质量和口径检查
      ↓
图表生成
      ↓
AI 生成分析说明和建议
      ↓
报告结构校验
      ↓
保存报告及来源引用
      ↓
用户查看或按权限导出
```

### 13.3 报告内容建议

| 部分 | 内容 |
|---|---|
| 报告基本信息 | 标题、生成时间、统计范围 |
| 执行摘要 | 主要发现和关键结论 |
| 指标说明 | 指标定义、公式和统计口径 |
| 数据概览 | 核心统计数据 |
| 图表分析 | 图表及对应解释 |
| 业务分析 | 人才缺口、岗位或技能趋势 |
| 决策建议 | 基于数据证据提出的建议 |
| 数据来源 | 查询范围、来源表、数据时间及查询记录 |
| 限制说明 | 数据缺失、样本不足和口径限制 |

### 13.4 结果溯源

建议为每份报告保存：
- report_id。
- 发起用户。
- 生成时间。
- 原始问题。
- 查询任务 ID。
- 指标定义版本。
- SQL 或规范化查询记录。
- 数据来源及统计时间。
- 图表配置。
- 模型及 Prompt 版本引用。
- 报告版本。
- 权限校验记录。

SQL 中可能包含个人信息筛选值或敏感条件。审计记录应进行必要脱敏和访问控制，不应为了溯源而无条件保存敏感原始数据。

### 13.5 可行性结论

通过结构化报告模板、确定性数据计算和模型辅助撰写可以实现。

**结论：有条件可行；报告版本、来源引用和导出权限需进一步设计。**

## 十四、查询超时、结果过大和异常处理

### 14.1 用户确认方案

设置：
- 查询超时。
- 最大返回行数。
- 分页。
- 结果集限制。
- 异常原因记录。
- 面向用户的可理解提示。

### 14.2 异常分类及处理

| 异常类型 | 建议处理 |
|---|---|
| 问题无法理解 | 请求用户补充条件或澄清 |
| Schema 无法匹配 | 不执行 SQL，提示当前问题涉及的数据范围未配置 |
| SQL 解析失败 | 拒绝执行，记录错误类别 |
| SQL 权限校验失败 | 拒绝执行，不向模型或用户暴露不必要的内部信息 |
| 查询超时 | 终止或取消查询，记录超时信息 |
| 结果过大 | 限制行数，提示缩小范围或使用分页 |
| 数据库连接失败 | 返回服务暂不可用提示，记录异常 |
| 结果为空 | 明确提示无匹配数据，不生成虚构结论 |
| 结果字段异常 | 停止后续图表和报告生成，记录结构校验错误 |
| 模型解释失败 | 保留原始统计结果，提示解释服务暂不可用 |

### 14.3 资源控制

查询超时和最大返回行数应由服务端强制执行，不能依赖模型遵守 Prompt。应用层和数据库层都应有相应限制。

对于分页，应固定排序字段并考虑稳定分页方式，避免数据变化导致重复或遗漏。大结果集不应全部传给模型；可先做数据库聚合，再对必要摘要进行解释。

### 14.4 可行性结论

应用层、数据库层和前端均有明确控制手段。

**结论：可行；具体超时、行数和并发阈值需在第 8 步及性能测试阶段确定。**

## 十五、数据准确性、权限隔离和审计记录

### 15.1 用户确认方案

建立统一指标口径、查询结果校验、权限隔离和完整审计记录，并保留 SQL、数据来源及分析依据。

### 15.2 数据准确性保障

| 保障点 | 建议措施 |
|---|---|
| 指标定义 | 使用统一指标字典，避免同名指标不同口径 |
| Schema | 数据字典与实际数据库结构定期核对 |
| SQL | 解析、白名单、权限和语义校验 |
| 结果 | 对关键统计值执行确定性复算或规则校验 |
| 时间范围 | 明确时区、统计截止时间和时间边界 |
| 去重规则 | 明确人才、岗位、测评等业务对象的去重口径 |
| 缺失数据 | 标注缺失和不完整情况，不推断为零 |
| 模型解释 | 解释内容必须引用查询结果，不得改写统计数值 |
| 报告 | 保留指标版本、查询记录和来源信息 |

### 15.3 权限隔离

- 每次查询均基于当前用户身份和授权范围。
- 不能复用其他用户的权限上下文。
- 查询缓存（如未来引入）必须按用户、权限范围、查询条件和数据版本隔离；当前不把缓存作为本步骤必选组件。
- 报告查看和导出重新执行权限检查。
- 敏感字段遵循字段级授权和脱敏要求。
- 批量导出继续遵循业务对象与流程文件中确认的分级控制及审批规则。

### 15.4 审计记录

建议记录：
- 请求用户及角色。
- 请求时间和请求 ID。
- 原始自然语言问题。
- 意图识别结果。
- 数据域、表和字段访问范围。
- 权限校验结果。
- 规范化 SQL 或安全审计所需的 SQL 记录。
- 查询执行时间和结果行数。
- 查询成功、拒绝或异常状态。
- 指标定义及版本。
- 图表和报告引用。
- 模型、Prompt 版本及执行链路标识。

审计记录应具备访问控制、脱敏、保留策略和必要的防篡改保护。完整审计不等于无限期保存所有原始输入输出。

### 15.5 可行性结论

可沿用平台用户权限、业务数据范围、操作日志和 AI 调用日志体系扩展实现。

**结论：有条件可行；权限隔离、审计完整性及敏感信息处理需要在第 8 步专项评估。**

## 十七、主要技术风险与验证计划

| 编号 | 风险 | 影响 | 建议处理及验证 |
|---|---|---|---|
| DI-01 | 本地模型误解业务问题 | 查询对象或统计范围错误 | 建立真实业务问题测试集，评估意图识别 |
| DI-02 | NL2SQL 生成错误 SQL | 查询失败或结果错误 | Schema 检索、SQL 解析和执行前校验 |
| DI-03 | 数据字典不完整 | 表字段映射和 JOIN 错误 | 数据字典与实际 Schema 对账 |
| DI-04 | 指标口径不统一 | 同一指标出现不同结果 | 建立指标注册和版本管理 |
| DI-05 | 权限条件遗漏 | 越权查询 | 后端生成权限约束，执行前强制验证 |
| DI-06 | SQL 解析规则存在绕过 | 危险 SQL 被执行 | AST 校验、数据库只读账号和安全测试 |
| DI-07 | 高成本查询 | 数据库资源耗尽 | 超时、行数、复杂度和并发限制 |
| DI-08 | 模型解释偏离数据 | 产生虚假结论 | 数值由程序计算，解释与结果绑定 |
| DI-09 | 图表字段映射错误 | 图表误导用户 | 图表配置 Schema 校验 |
| DI-10 | 人才缺口统计口径不一致 | 决策结果失真 | 复用岗位匹配规则，明确去重和时间口径 |
| DI-11 | 报告来源无法追溯 | 无法复核结论 | 保存查询、指标、数据时间和版本引用 |
| DI-12 | 敏感信息进入日志 | 个人信息泄露 | 脱敏、最小化记录和审计访问 |
| DI-13 | 结果集过大 | 内存和模型上下文资源消耗 | 分页、聚合和最大结果限制 |
| DI-14 | 模型服务不可用 | 查询解释或报告中断 | 保留结构化查询结果，支持降级展示 |

### 17.1 优先验证顺序

1. 建立覆盖人才、岗位、技能和测评的最小数据字典。
2. 建立一组经过业务人员确认的标准自然语言问题及标准 SQL/结果。
3. 验证本地模型意图识别和候选 SQL 生成质量。
4. 验证 SQL 解析器对 MySQL 方言的支持。
5. 测试多语句、写操作、未授权表字段、危险函数和复杂 JOIN 的拦截。
6. 测试不同用户、角色和组织范围下的查询隔离。
7. 测试只读账号的数据库权限。
8. 测试超时、分页、最大行数和高成本查询限制。
9. 对关键指标执行独立复算，核对统计口径。
10. 验证图表配置和数据系列绑定。
11. 验证报告中的数据、指标和查询来源可追溯。
12. 验证日志脱敏、访问控制和审计完整性。

## 十八、最终可行性结论

### 18.1 总体结论

**总体结论：数据智能与运营决策技术路线有条件可行。**

现有 Python、FastAPI、LangChain、LangGraph、Ollama、MySQL、SQLAlchemy 和 Vue 3 技术基线能够支撑自然语言查询、NL2SQL、权限校验、只读 SQL 执行、统计分析、图表生成和分析报告的整体技术路线。

本步骤已完成 12 项技术决策确认。推荐采用“本地大模型生成候选 SQL + 数据字典与 Schema 检索 + 程序化 SQL 安全校验 + 独立只读数据库账号 + 确定性统计计算 + AI 结果解释”的组合方案。

但当前不能认定 NL2SQL 已具备生产可用的准确率，也不能认定权限隔离和 SQL 安全已经通过测试。核心前置条件包括：
- 真实、完整且持续维护的数据字典。
- 经业务确认的统一指标口径。
- SQL 解析与安全规则覆盖。
- 用户、角色、组织及业务数据范围权限的强制执行。
- 只读数据库账号及数据库层授权。
- 本地模型在真实业务问题集上的效果测试。
- 查询性能、结果准确性、审计和敏感信息保护测试。

### 18.2 分项结论

| 编号 | 正式评估项 | 结论 |
|---|---|---|
| 01 | 自然语言问题理解和查询意图识别 | 可行，模型效果待测 |

| 04 | 查询范围与用户数据权限 | 有条件可行 |

| 06 | 只读限制、危险语句和资源限制 | 有条件可行 |

| 08 | 数据可视化及图表生成 | 可行 |

### 18.3 关键技术边界

1. NL2SQL 仅执行只读查询，不承担业务数据新增、修改和删除。
2. 大模型不直接连接数据库，也不持有数据库凭据。
3. 大模型生成的 SQL 必须通过独立程序化安全校验。
4. 查询权限由平台后端强制执行，不依赖 Prompt。
5. 数值计算以数据库和确定性程序为准，模型只负责解释。
6. 图表和报告必须绑定真实查询结果及指标口径。
7. 数据字典、指标定义、权限和审计是数据智能能力的基础依赖。
