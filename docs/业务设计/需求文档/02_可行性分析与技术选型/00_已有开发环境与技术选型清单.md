### 3.1 不同文件格式的解析方式

- **PDF：** 优先通过 MinerU 本地 HTTP API 解析，提取正文、标题、表格、图片引用和页码定位；扫描件使用 OCR 结果，并对低置信度内容标记人工核对。
- **Markdown：** 使用 Python 读取原文，使用 `markdown-it-py` 解析结构；保留命令、配置片段、错误码和代码块边界。
- **DOCX：** 使用 `python-docx` 读取标题、正文、段落和表格；图片、页眉页脚及复杂对象根据实际样本确定补充处理方式。
- 不同格式的解析器通过统一解析入口输出统一解析结果结构；具体解析逻辑不混入业务模块。

RAG 数据链路：

```text
技术资料
   │
   ▼
文档解析（MinerU / Markdown / DOCX 解析器）
   │
   ▼
清洗与统一结构化
   │
   ▼

   │

   │
```

技术知识资料进入 RAG；日志、告警、服务状态、进程信息和资源指标属于动态诊断数据，应通过受控工具或明确标注的脱敏/模拟样本读取，不能只存入 RAG 并当作实时事实。

## 9. 技术架构与数据流

### 9.1 总体技术架构

```text
用户 / Web Chat / API
        │
        ▼
      FastAPI
        │
        ▼
认证与会话上下文
        │
        ▼
   LangGraph 工作流
        │
        ├── IT 技术知识问答
        │       └── RAG → Milvus → Ollama Embedding
        │                         └── 证据组织与来源引用
        │
        └── 智能故障诊断
                ├── 只读诊断工具
                │     ├── 日志读取与过滤
                │     ├── 服务/进程/端口状态
                │     └── 资源/监控数据
                ├── RAG 技术知识检索
                └── 证据关联与诊断报告

MySQL：文档元数据、版本、任务和诊断记录
文件存储：原始技术资料、解析产物、脱敏/模拟样本
Ollama：Embedding 与对话生成模型服务
```

### 9.2 两类数据的技术边界

- **技术知识资料：** 规范、技术手册、命令说明、错误码解释和故障处理流程，经过解析、清洗、切片、Embedding 后进入 Milvus。
- **动态诊断数据：** 日志、告警、服务状态、进程信息和资源指标，通过受控工具或脱敏/模拟样本读取。
- **MySQL：** 管理文档元数据、版本、解析任务、诊断任务及必要的结构化样本/记录。
- **Milvus：** 存储技术知识 Chunk 的向量及检索元数据。
- **文件存储：** 保存原始技术资料、解析产物和脱敏/模拟诊断样本；项目内最终目录待确认。
- **Ollama：** 提供本地 Embedding 和对话模型服务。

## 10. 安全与开发环境边界

1. 首期不连接银行真实生产环境。
2. 不将真实客户数据、账号、密码、密钥、交易数据或未经授权的生产日志导入项目。
3. 诊断数据优先使用公开样例、脱敏样本或自行构造的模拟数据。
4. 日志和文档内容一律视为不可信数据，不能把其中的指令当作 Agent 系统指令。
5. Agent 不直接执行任意 Shell、任意 SQL 或任意文件访问。
6. 所有诊断工具实施路径白名单、参数校验、超时、输出限制和审计日志。
7. 可能改变系统状态的操作不属于首期默认能力；如后续扩展，必须增加权限、审批和人工确认。
