## 一、评估目标与范围

本专项评估智能测评与面试业务能否由平台已经确认的技术栈支撑，并形成后续详细设计和开发依据。

评估范围包括：

1. 题库与试题管理。
2. 题目分类及难度管理。
3. 智能出卷与规则组卷。
4. 在线测评。
5. 客观题自动评分。
6. 主观题 AI 辅助评分。
7. 测评结果管理及人工确认。
8. 面试邀约管理。
9. 多轮面试记录及综合结论。
10. 错题管理。

本期不包含独立错题复习计划，也不包含 AI 自动生成新题。

本报告属于技术可行性评估，不包含完整数据库建表、接口实现、代码开发、生产部署或性能验收。

## 二、已确认业务规则

### 2.1 题型范围

初期支持以下五种题型：

- 单选题
- 多选题
- 判断题
- 填空题
- 简答题

### 2.2 组卷方式

- 只从现有题库按照配置规则组卷。
- 本期不纳入 AI 自动生成新题。
- 组卷条件、题型数量、题目分类和难度等由业务配置决定。
- 已发布试卷应固定题目版本，避免题库后续修改影响已发布或进行中的测评。

### 2.3 评分及成绩确认

- 客观题采用自动判分。
- 主观题由 AI 辅助评分。
- AI 先产生评分建议，面试官或 HR 确认后形成正式成绩。
- 测评结果统一由 HR 确认后形成正式成绩。
- AI 评分结果不得未经人工确认直接成为正式成绩。

### 2.4 错题管理

- 自动记录错题。
- 支持按候选人、试卷和题目分类查询。
- 本期保留错题记录及管理。
- 本期不建设独立错题复习计划。

### 2.5 多轮面试

- 支持多轮面试。
- 每轮独立配置面试官和面试时间。
- 每轮独立保存面试记录及评价。
- 最后形成综合面试结论。

## 三、基础技术基线

本专项沿用已确认的基础技术组件，不重新选型。

| 技术层 | 已确认方案 | 在本专项中的用途 |
|---|---|---|
| 前端 | Vue 3 + TypeScript | 题库、组卷、在线答题、评分和面试界面 |
| UI | Element Plus | 管理端界面组件 |
| 后端 | Python 3.11 + FastAPI | 测评、题库、答卷和面试业务 API |
| 数据校验 | Pydantic | 请求、响应及 AI 评分结构校验 |
| ORM | SQLAlchemy | 业务数据访问和事务处理 |
| MySQL 驱动 | PyMySQL | MySQL 连接 |
| 业务数据库 | MySQL 8.0 | 题库、试卷、答卷、评分、测评结果及面试记录 |
| Agent 框架 | LangChain | 简答题 AI 辅助评分的模型调用和 Prompt 组织 |
| Workflow 框架 | LangGraph | 需要多步骤处理时组织评分流程和状态 |
| 模型服务 | Ollama + 统一模型适配层 | 初期本地模型推理 |
| 异步任务 | MySQL 持久化任务表 + 独立 Worker | AI 评分等耗时任务 |
| 任务调度 | APScheduler | 定时或周期任务触发，不直接执行耗时任务 |

说明：

- 题库维护、规则组卷、在线答题、客观题判分和错题记录属于确定性业务，不需要强行交给 Agent 或 LangGraph。
- AI 能力主要用于简答题辅助评分等需要模型理解的场景。
- 技术选型已确认不代表组件已经完成集成、性能或模型质量验收。

## 四、总体技术方案

### 4.1 逻辑架构

```text
Vue 3 + TypeScript
       │
       ▼
FastAPI 测评与面试业务接口
       │
       ├── 题库与试题管理
       ├── 规则组卷
       ├── 在线测评与答卷管理
       ├── 客观题自动判分
       ├── 测评结果与人工确认
       ├── 错题管理
       └── 面试邀约与多轮面试
       │
       ├───────────────┐
       ▼               ▼
MySQL             AI 辅助评分
业务数据          LangChain + Ollama
                       │
                       ▼
                  Pydantic 结构校验
                       │
                       ▼
                  人工审核确认
```

### 4.2 业务服务与 AI 能力边界

| 能力 | 业务服务负责 | AI 中台负责 |
|---|---|---|
| 题库与试题 | 创建、修改、分类、难度、状态和版本 | 不负责题库正式数据维护 |
| 规则组卷 | 按配置选择现有题目、校验试卷 | 本期不负责生成新题 |
| 在线测评 | 开始、答题、保存、提交和状态控制 | 不负责正式答卷状态 |
| 客观题评分 | 根据标准答案确定性判分 | 不需要调用模型 |
| 简答题评分 | 提供题目、答案、评分标准并保存结果 | 生成评分建议和评分理由 |
| 正式成绩 | HR 确认、成绩发布及历史记录 | 不直接发布正式成绩 |
| 面试管理 | 邀约、轮次、面试官、记录和评价 | 可按后续需求提供辅助分析，但不替代正式评价流程 |

AI 输出必须经过结构校验和业务校验；正式业务状态由测评与面试业务服务维护。

## 六、规则组卷技术评估

### 6.1 推荐处理流程

1. 管理人员配置组卷条件。
2. 配置题型、题目数量、分类、难度及分值等规则。
3. 后端从现有题库查询符合条件的题目。
4. Python 规则组卷逻辑选择题目。
5. 校验题量、题型、总分、题目状态及重复情况。
6. 保存试卷草稿。
7. 人工审核后发布。
8. 发布时固定试卷及题目版本。

### 6.2 技术实现

规则组卷采用 Python 确定性业务逻辑，MySQL 保存组卷条件、试卷及题目关联。

本期不采用 AI 自动生成新题，也不让大模型决定正式试卷内容。

### 6.3 风险与验证

- 可用题目数量不足。
- 题型或难度分布不符合规则。
- 题目重复。
- 总分计算错误。
- 题库修改影响已发布试卷。

应通过边界测试验证题量不足、题库停用、规则冲突和试卷版本固定等情况。

### 6.4 可行性结论

**技术方案可行。** 组卷规则的具体字段、优先级及冲突处理方式需在详细设计阶段明确。

## 七、在线测评技术评估

### 7.1 推荐处理流程

```text
候选人/员工进入测评
       ↓
身份与测评资格校验
       ↓
加载已发布试卷快照
       ↓
开始测评并记录开始时间
       ↓
在线答题与进度保存
       ↓
主动提交或到时自动交卷
       ↓
保存答卷及答题记录
       ↓
进入评分流程
```

### 7.2 技术实现

- Vue 3 负责答题界面和交互。
- FastAPI 负责测评业务接口。
- MySQL 保存测评任务、试卷快照、答卷、答题记录和提交状态。
- 后端负责测评时间、提交状态和重复提交控制。

### 7.3 可靠性要求

需要考虑：

- 答题进度保存。
- 自动保存与提交。
- 到时自动交卷。
- 重复提交控制。
- 网络异常恢复。
- 试卷和题目版本固定。
- 测评资格及访问权限校验。

具体防作弊、身份核验和监考要求尚未确认，本报告不将其视为已确认需求。

### 7.4 可行性结论

**技术方案可行。** 在线测评并发、自动保存、断网恢复和到时交卷需要通过集成及压力测试验证。

## 八、评分技术评估

### 8.1 题型与评分方式

| 题型 | 初期评分方式 | 是否使用 AI |
|---|---|---|
| 单选题 | 与标准答案比较 | 否 |
| 多选题 | 按预设答案规则判分 | 否 |
| 判断题 | 与标准答案比较 | 否 |
| 填空题 | 标准答案及允许答案匹配 | 初期不需要 |
| 简答题 | AI 辅助评分，人工确认 | 是 |

多选题部分得分规则、填空题答案容错规则仍需在详细业务设计阶段确认。

### 8.2 客观题自动评分

客观题采用确定性 Python 业务代码，根据标准答案和已确认评分规则计算分数。

客观题自动判分结果保存为评分记录，进入统一成绩确认流程。

### 8.3 简答题 AI 辅助评分

推荐流程：

1. 获取试题、参考答案、评分标准和考生答题内容。
2. 通过 LangChain 组织 Prompt 和模型调用。
3. 使用 Ollama 生成评分建议。
4. 将模型输出映射到 Pydantic 结构。
5. 校验分数范围、评分维度和必要字段。
6. 保存 AI 建议得分、评分理由和模型版本。
7. 提交给 HR 或面试官审核。
8. 人工确认或修改后形成正式评分记录。

建议保留：
- 原始答题内容。
- 参考答案和评分标准。
- 评分维度及分值。
- AI 建议得分。
- 评分理由及依据。
- 模型和 Prompt 版本。
- 人工确认得分。
- 人工修改记录。

AI 评分结果不直接成为正式成绩。

### 8.4 可行性结论

**技术方案可行。**

需要使用人工标注样本验证 AI 建议评分与人工评分的一致性、评分稳定性、理由可解释性和异常输出处理能力。

## 九、测评结果与错题管理

### 9.1 测评结果

测评结果需要关联：
- 测评任务。
- 候选人或员工。
- 试卷及版本。
- 答卷。
- 各题评分记录。
- 总分及结果状态。
- HR 确认记录。

测评结果统一由 HR 确认后形成正式成绩。AI 建议分数、自动判分结果和正式成绩应区分保存。

### 9.2 错题管理

- 自动记录错题。
- 关联候选人、答卷、试卷和试题。
- 支持按候选人、试卷、题目分类查询。
- 保留错题历史及相关评分信息。

本期不建设独立错题复习计划。

### 9.3 可行性结论

**技术方案可行。** 需要明确正式成绩状态流转、错题判定规则及成绩修改审计。

## 十、面试邀约与多轮面试技术评估

### 10.1 业务范围

- 面试邀约管理。
- 面试轮次管理。
- 面试官配置。
- 面试时间管理。
- 面试记录。
- 每轮面试评价。
- 综合面试结论。

### 10.2 推荐数据对象

逻辑上建议区分：
- 面试邀约。
- 面试轮次。
- 面试记录。
- 面试问题。
- 面试评价。
- 综合面试结论。

以上是逻辑数据对象，不是最终数据库表结构。

### 10.3 推荐流程

1. HR 创建面试邀约。
2. 记录候选人、岗位、面试时间和邀约状态。
3. 创建对应面试轮次。
4. 为每轮配置面试官和时间。
5. 面试结束后保存本轮记录和评价。
6. 根据各轮结果形成综合面试结论。
7. 关联人才主档案及招聘流程。

每轮面试独立保存面试官、时间、记录和评价，避免不同轮次内容相互覆盖。

### 10.4 技术实现

- MySQL 保存邀约、轮次、面试记录和评价。
- FastAPI 提供面试管理接口。
- Vue 3 提供面试安排、记录和评价界面。
- 权限体系控制候选人资料及面试评价的访问范围。

### 10.5 可行性结论

**技术方案可行。** 需要进一步确认面试邀约有效期、通知渠道、面试轮次状态及综合结论规则；未确认事项不得直接写成既定业务规则。

## 十一、与人才主档案模块的关系

智能测评与面试是独立业务模块，不合并进人才档案模块。

两者通过统一人才主档案 ID 关联：

- 人才主档案负责自然人身份和人才基础资料。
- 智能测评模块负责题库、试卷、答卷、评分、测评结果和错题。
- 面试模块负责邀约、轮次、面试记录和评价。
- 测评结果和面试结论可以作为人才业务历史记录关联查询。
- 是否将测评和面试数据纳入后续人才画像分析，应遵循已经确认的画像数据来源范围；本专项不擅自扩大画像数据来源。

技术边界：
- 两个模块拥有各自的业务服务和数据对象。
- 通过人才 ID 和明确的业务接口关联。
- 不复制一份人才主档案。
- 不由测评模块直接修改人才主档案核心字段。

具体量化阈值需在测试方案中结合真实业务样本和运行环境确定，本报告不虚构已经达成的指标。
