## 一、评估目标与范围

本步骤判断平台在个人信息保护、业务权限、AI 工具执行、并发访问和系统稳定性方面是否具备合理的技术保障。

依据第二阶段总流程，本步骤正式评估 15 项：

1. 用户认证和会话安全。
2. 用户、部门、角色和菜单权限。
3. 业务数据范围控制。
4. 候选人和员工个人信息保护。
5. 简历及上传文件的访问控制和安全检查。
6. Agent 工具调用权限和参数校验。
7. 数字员工执行权限及敏感操作控制。
8. NL2SQL 的只读边界和 SQL 安全机制。
9. 模型供应商密钥及敏感配置管理。
10. AI 输入输出、日志和文件中的敏感信息处理。
11. 操作日志、AI 调用日志和审计追踪。
12. 并发用户、批量任务和任务吞吐量。
13. API、模型调用及异步任务的响应时间和超时策略。
14. 数据备份、恢复、服务故障和降级机制。
15. 性能测试环境、指标口径和验收条件。

本步骤以安全方案、性能方案、稳定性建议和风险清单为交付目标，不代表已经完成渗透测试、负载测试、灾备演练或法规合规审查。

## 三、第一批：用户认证与权限体系（01～03）

### 3.1 用户认证和会话安全

**用户选择：A**

采用用户名密码认证、JWT 身份令牌和 Refresh Token 刷新机制，密码使用安全哈希算法存储。

建议实施控制：
- 密码只保存安全哈希，不保存明文或可逆加密密码。
- 访问令牌设置有效期。
- Refresh Token 设置独立有效期和撤销机制。
- 支持退出登录、令牌失效及刷新令牌轮换。
- 对登录失败、异常登录和暴力尝试进行限制及记录。
- 认证和令牌传输应使用 HTTPS。
- 密码重置、账号禁用等敏感操作应使相关会话按策略失效。

**可行性结论：可行。** JWT 与 Refresh Token 可通过应用层认证模块实现；具体令牌期限、轮换及撤销策略需在详细设计中确定。

### 3.2 用户、部门、角色和菜单权限

**用户选择：A**

采用统一 RBAC 权限中心，由后端统一校验菜单、接口和业务操作权限。

权限对象包括：
- 用户。
- 部门。
- 角色。
- 菜单。
- 操作权限。
- API 接口权限。

前端可依据权限展示菜单和按钮，但前端隐藏不能替代后端鉴权。所有受保护的 API 和业务操作都必须由后端验证当前用户权限。

**可行性结论：可行。** 可在统一用户、角色和权限模型上实现，避免各业务模块自行维护互不一致的权限规则。

### 3.3 业务数据范围控制

**用户选择：A**

采用全部数据、部门数据、个人数据三级范围，并结合业务对象和字段级权限进行后端强制过滤。

| 范围 | 含义 |
|---|---|
| all | 用户在授权范围内可访问全部数据 |
| dept | 用户可访问其授权部门范围内的数据 |
| self | 用户仅可访问本人或本人负责范围内的数据 |

补充控制：
- 数据范围应按业务对象执行，不能只按菜单控制。
- 字段级权限应覆盖身份证号、手机号等敏感字段。
- 查询、导出、报告查看和文件下载都应重新校验权限。
- 多部门、跨项目或临时授权应有明确授权关系和有效期。
- Agent、数字员工和 NL2SQL 不得绕过后端权限服务。

**可行性结论：可行。** 需要将权限校验统一封装为后端服务，并在各业务数据访问入口执行。

## 四、第二批：个人信息、文件及 Agent 工具安全（04～06）

### 4.1 候选人和员工个人信息保护

**用户选择：B**

只对身份证号、手机号等敏感字段进行脱敏，其他数据正常存储。

建议的展示脱敏示例：

| 字段 | 展示示例 |
|---|---|
| 手机号 | 138****5678 |
| 身份证号 | 440123********1234 |

该选择仅确认了字段展示脱敏策略，并未确认对全部个人信息实施加密存储。

**风险与待处理事项：**
- 脱敏展示不能替代传输加密、存储保护和备份保护。
- 简历正文可能包含住址、邮箱、教育经历、工作经历等个人信息。
- “其他数据正常存储”不意味着可以不受访问控制或无限期保存。
- 需要按实际适用的数据保护要求确认处理目的、访问授权、保存期限和删除机制。
- 对敏感字段的查看、导出和修改应保留审计记录。

**可行性结论：基础脱敏可行；个人信息全生命周期保护尚不充分，属于重要安全风险。**

### 4.2 简历及上传文件安全

**用户选择：C**

只检查文件扩展名和大小，上传后直接保存。

已确认的简历上传约束：
- 支持 PDF、DOCX、DOC、TXT 和图片。
- 单次最多上传 20 份。
- 每份文件最大 20MB。

本次选择不包含文件真实类型校验、病毒扫描或隔离存储。

**风险判断：高风险。** 扩展名可以被伪造，不能证明文件真实格式或内容安全。直接保存后再交给解析器处理，可能带来恶意文件、解析器漏洞、压缩炸弹、超大资源消耗和非预期内容等风险。

**本报告保留用户 C 选项，不擅自将其改为更严格方案；但不建议将“仅检查扩展名和大小”直接作为生产环境最终安全控制。**

建议整改项：
1. 增加文件真实类型及文件头校验。
2. 对上传文件进行恶意内容扫描。
3. 上传文件先进入隔离区，检查通过后再进入可解析区。
4. 文件存储与 Web 静态目录隔离，禁止直接执行或公开访问。
5. 下载和解析前执行用户、业务对象和文件权限检查。
6. 限制解压深度、页数、图片像素、解析时长和临时目录空间。
7. 对文件访问、下载、删除和解析操作进行审计。

**可行性结论：基础上传功能可行；按当前 C 方案的文件安全保障不足，生产使用前应解决上述高风险项。**

### 4.3 Agent 工具调用权限和参数校验

**用户选择：A**

建立统一工具权限管理：
- 工具白名单。
- 角色授权。
- 参数 Schema 校验。
- 执行权限校验。
- 调用审计。

工具执行不能只依靠 Prompt 限制。后端工具注册表和授权服务应在每次调用前验证工具是否启用、调用主体是否有权限、参数是否符合 Schema。

对有副作用的工具，应进一步配置确认、幂等和结果核验机制。

**可行性结论：可行。** 可沿用 LangChain 工具封装、LangGraph 流程编排和后端权限服务实现。

## 五、第三批：数字员工、NL2SQL 和密钥管理（07～09）

### 5.1 数字员工执行权限及敏感操作控制

**用户选择：A**

数字员工继承发起用户权限，并叠加自身职责范围和任务授权。

有效执行权限不得超过以下授权范围的交集：
- 发起用户权限。
- 数字员工职责范围。
- 任务授权。
- Agent、Workflow 和 Tool 的具体执行权限。

执行前及业务服务写入前均应校验权限。敏感操作应根据业务风险设置人工确认或审批，不能因数字员工已关联 Agent/Workflow 就自动获得全部能力。

**可行性结论：可行。** 与第 06 步数字员工权限方案和第 05 步 Agent 工具权限边界一致。

### 5.2 NL2SQL 只读边界和 SQL 安全机制

**用户选择：B**

使用独立只读数据库账号，不增加复杂 SQL 解析机制。

该项与第 07 步数据智能评估中已确认的“SQL 解析器、语句类型检查、表字段白名单及权限条件校验”存在差异。本报告记录本步骤最新选择 B，但不能将其解释为已解决全部 SQL 安全问题。

只读数据库账号可以降低写入风险，但不能单独防止：
- 查询未授权人才或部门数据。
- 读取敏感字段。
- 高成本查询导致数据库资源耗尽。
- 不合适的 JOIN 或聚合导致数据泄露。
- 通过复杂查询绕过应用层业务范围。

**必要的最低控制建议：**
1. NL2SQL 使用独立只读账号，不使用业务管理员账号。
2. 数据库账号只授予必要表或视图的 SELECT 权限。
3. 应用层必须执行用户身份、角色、组织和业务数据范围校验。
4. 设置查询超时、最大结果行数、分页和并发限制。
5. 对敏感字段实施字段级授权或受控视图。
6. 记录查询主体、查询对象、执行状态和结果规模。

由于用户明确选择不增加复杂 SQL 解析机制，AST 解析和复杂语法白名单不列为本次已确认必选方案；但应在实施前通过安全测试判断仅靠只读账号和应用层控制是否满足风险要求。

**可行性结论：基础只读查询可行；安全保障弱于第 07 步原先确认的方案，属于需要在第 09 步综合决策中明确的风险和方案冲突。**

### 5.3 模型供应商密钥及敏感配置管理

**用户选择：B**

密钥统一保存在项目 `.env` 文件中，不提交 Git。

实施要求：
- `.env` 加入 `.gitignore`。
- `.env.example` 只保留变量名和占位值，不放真实密钥。
- 限制 `.env` 文件系统访问权限。
- 禁止在日志、异常堆栈和 API 响应中输出密钥。
- 密钥泄露后应支持轮换和撤销。
- 不同环境使用不同密钥。

**可行性结论：初期开发环境可行。** 生产部署前应重新评估专用密钥管理、部署注入和轮换机制。

## 六、第四批：AI 数据、日志审计和并发任务（10～12）

### 6.1 AI 输入输出及敏感信息处理

**用户选择：C**

完整保存所有 AI 输入、输出和调用记录，方便后续排查。

这意味着可能保存：
- 用户原始问题。
- 模型输入和输出。
- Agent 工具调用参数及结果。
- Workflow 执行过程。
- 模型名称、调用时间和状态。
- 异常信息及必要上下文。

**风险判断：高风险。** AI 输入输出可能包含简历正文、个人联系方式、身份证信息、业务数据和内部配置。完整保存会扩大敏感信息暴露面和数据泄露影响。

本报告保留 C 选项，但完整保存必须理解为受控审计留存，而不是无限期、无差别、所有人员均可查看。

实施前必须明确：
- 保存目的和数据范围。
- 访问角色和最小权限。
- 加密、脱敏及密钥保护。
- 保存期限、归档和删除机制。
- 下载、检索和导出审计。
- 模型供应商及外部服务的数据处理边界。
- 密钥、密码、令牌等认证凭据不得作为普通日志内容保存。

**可行性结论：技术上可实现；在访问控制、保留期限和敏感信息保护规则未确定前，不宜认定为安全可上线方案。**

### 6.2 操作日志、AI 调用日志和审计追踪

**用户选择：A**

建立统一日志审计体系，覆盖：
- 用户操作。
- 权限判断。
- Agent 执行。
- Workflow 节点。
- Tool 调用。
- 数字员工任务。
- NL2SQL 查询。
- 异常和恢复操作。

建议每条记录包含请求 ID、用户 ID、任务 ID、执行主体、资源对象、操作类型、时间、结果和关联版本。

日志需要具备：
- 分级访问权限。
- 敏感字段处理。
- 统一时间和关联 ID。
- 保留期限和归档策略。
- 查询、导出和管理审计。
- 防止普通业务用户修改审计记录的控制。

**可行性结论：可行。** 初期可基于应用日志和 MySQL 审计记录实现，后续按吞吐量及保留要求评估集中日志平台。

### 6.3 并发用户、批量任务和任务吞吐量

**用户选择：A**

采用异步任务架构：
- FastAPI 接收请求并创建任务。
- 任务中心保存任务状态。
- 独立 Worker 认领和执行任务。
- 支持优先级和并发限制。
- 监控 Worker、模型及数据库资源。

该方案沿用第 06 步确认的 MySQL 任务中心、独立 Worker 和三级并发限制思路。不能仅依靠 FastAPI 异步接口承载所有耗时 AI 任务。

**可行性结论：有条件可行。** 任务原子认领、租约、幂等、Worker 故障恢复和模型并发资源限制需要压力及故障测试。

## 七、第五批：响应时间、备份恢复和性能验收（13～15）

### 7.1 API、模型调用及异步任务响应时间和超时策略

**用户选择：B**

统一设置一个超时时间，所有请求和任务使用相同限制。

本报告保留该选择。该策略简单，但 API、数据库查询、模型推理和批量异步任务的执行特征差异很大，统一超时时间可能造成：
- 普通 API 等待过久。
- 合理的长模型任务被过早终止。
- 数据库查询未及时释放资源。
- 异步任务被错误判定为失败。
- 重试和取消行为难以区分。

**可行性结论：基础统一超时可实现，但不适合作为复杂 AI 平台的最终精细化超时策略。**

实施时至少需要明确统一超时值的适用边界、任务状态查询、超时后的资源释放和重试行为。更细的 API、数据库、模型和任务分层超时可列为后续优化建议；本次不将其记录为用户已确认选择。

### 7.2 数据备份、故障恢复和服务降级

**用户选择：A**

建立：
- 自动备份。
- 定期恢复演练。
- 任务异常恢复。
- 核心服务降级机制。

建议覆盖：
- MySQL 业务数据及权限配置。
- 简历原始文件和业务附件。
- Agent、Workflow 和数字员工配置。
- 数据字典及指标定义。
- 任务记录和必要审计记录。
- 必要的模型配置（不以备份明文密钥为目标）。

需要明确备份频率、保留周期、异地或独立存储、恢复顺序及恢复验证。恢复演练应验证备份可用性，而不只是确认备份文件存在。

服务降级示例：
- 模型不可用时，保留普通业务查询和非 AI 功能。
- Agent 执行失败时，保存任务状态和错误信息。
- 图表或报告生成失败时，尽可能保留已完成的结构化统计结果。
- Worker 异常时，通过任务状态和租约机制恢复可安全重试的任务。

**可行性结论：可行；备份范围、恢复目标和演练频率需在详细设计中确定。**

### 7.3 性能测试环境、指标口径和验收条件

**用户选择：A**

建立统一性能测试方案，分别测试：
- 并发用户。
- API 响应。
- 数据库查询。
- 模型调用。
- 批量任务。
- 系统资源。

并制定量化验收指标。

建议测试指标：

| 测试类别 | 指标 |
|---|---|
| 并发访问 | 并发用户数、请求吞吐量、错误率 |
| API | 平均响应时间、P95、P99 响应时间 |
| 数据库 | 查询耗时、连接池占用、慢查询数量 |
| 模型 | 首 token 时间、完整响应时间、超时率 |
| 异步任务 | 排队时间、执行时间、成功率、重试率 |
| Worker | 活跃数、队列积压、任务恢复时间 |
| 资源 | CPU、内存、GPU 显存、磁盘空间和网络 |
| 稳定性 | 长时间运行错误率、服务重启和恢复情况 |

本步骤没有确认具体用户规模、目标吞吐量或响应时间数值，因此不在本报告中虚构固定验收阈值。量化阈值应在第 09 步结合部署环境、硬件配置、业务优先级和实际测试基线确定。

测试环境应尽量接近目标部署环境，并记录模型版本、硬件、数据量、并发模型和测试脚本版本。

**可行性结论：可行；具体验收数值待性能基线测试后确定。**

## 九、关键风险、冲突与整改优先级

### 9.1 高优先级风险

| 编号 | 风险 | 来源 | 影响 | 建议处理 |
|---|---|---|---|---|
| SEC-01 | 文件仅检查扩展名和大小，直接保存 | 第 05 项选择 C | 恶意文件、伪造格式、解析器攻击 | 生产使用前增加真实类型校验、病毒扫描和隔离区 |
| SEC-02 | 完整保存所有 AI 输入输出 | 第 10 项选择 C | 简历和个人敏感信息集中暴露 | 明确访问控制、加密、期限、删除和审计 |
| SEC-03 | NL2SQL 不增加复杂 SQL 解析机制 | 第 08 项选择 B | 越权查询、敏感字段访问和高成本查询风险 | 只读账号、数据库授权、应用层权限、资源限制并专项测试 |
| SEC-04 | 个人信息只对身份证号和手机号脱敏 | 第 04 项选择 B | 其他个人信息可能缺少相应保护 | 进行数据分类，明确其他个人信息的访问和存储要求 |

### 9.2 中高优先级风险及设计差异

| 编号 | 风险或差异 | 来源 | 建议 |
|---|---|---|---|
| SEC-05 | 第 07 步确认 SQL AST 校验，本步骤选择 B 不采用复杂解析 | 第 08 项 | 第 09 步必须统一最终 SQL 安全基线 |
| SEC-06 | 第 07 步确认细化 SQL 安全，本步骤只确认只读账号 | 第 08 项 | 明确数据库权限能覆盖哪些安全边界 |
| SEC-07 | 统一超时时间无法适配不同任务类型 | 第 13 项选择 B | 明确统一值及异常语义，后续评估分层超时 |
| SEC-08 | `.env` 作为密钥管理方式 | 第 09 项选择 B | 限制文件访问、禁止提交 Git，生产部署重新评估 |
| SEC-09 | 三级并发限制及 Worker 恢复尚未实测 | 第 12 项选择 A | 进行并发、重复认领、崩溃恢复和幂等测试 |
| SEC-10 | 性能验收阈值尚未量化 | 第 15 项选择 A | 在第 09 步确定目标负载和验收数值 |

### 9.3 必须解决与可后续优化事项

**建议作为进入生产使用前的必须解决项：**
1. 文件上传安全不能只依赖扩展名和大小检查。
2. AI 完整日志保存必须具备敏感数据访问控制和保留策略。
3. NL2SQL 必须验证组织及业务数据权限，不能只依赖只读账号。
4. 身份认证、角色权限和数据范围必须在后端执行。
5. 备份必须经过实际恢复验证。
6. 任务并发和故障恢复必须经过测试。

**可以在后续实施中逐步优化，但需要保留计划：**
- 专用密钥管理服务。
- 更精细的分层超时。
- 集中式日志平台。
- 更高级的审计防篡改能力。
- 更精细的性能自动扩缩容能力。

## 十、测试与验证计划

### 10.1 身份和权限测试

- 未登录访问受保护 API。
- 过期、伪造和撤销令牌。
- 不同角色访问菜单、接口和操作。
- 全部、部门、个人三级数据范围。
- 跨部门和跨项目数据访问。
- 字段级敏感数据访问。
- 报告查看、文件下载和数据导出权限。

### 10.2 文件与个人信息测试

- 扩展名伪造。
- 文件头与扩展名不一致。
- 超过 20MB 的文件。
- 单次超过 20 份的上传请求。
- 恶意文件和异常文档。
- 解析超时和资源耗尽。
- 未授权下载和跨用户文件访问。
- 身份证号、手机号展示脱敏。
- AI 输入输出和日志中的敏感信息访问控制。

### 10.3 AI 工具与数字员工测试

- 未授权工具调用。
- 工具参数类型错误和越界值。
- 数字员工调用超出职责范围的 Agent。
- 用户权限不足时发起数字员工任务。
- 敏感工具操作的人工确认。
- 工具调用重复执行和幂等。
- Workflow 中断、恢复和失败记录。

### 10.4 NL2SQL 测试

- 使用只读账号尝试写操作。
- 查询未授权表和字段。
- 跨组织和跨部门查询。
- 敏感字段访问。
- 超大结果集和高成本查询。
- 多语句和异常 SQL 输入。
- 查询超时及连接释放。
- SQL 记录和审计关联。

### 10.5 并发、备份与恢复测试

- 多用户并发登录和查询。
- 多 Worker 同时认领任务。
- 任务重复提交。
- Worker 异常退出和任务租约回收。
- 模型服务不可用时的降级。
- MySQL 备份恢复。
- 文件及配置恢复。
- 恢复后权限和任务状态一致性。
- 长时间运行和资源监控。

## 十一、最终可行性结论

### 11.1 总体结论

**总体结论：平台安全、权限和性能技术路线有条件可行，但当前确认方案存在若干必须在生产使用前处理的安全风险。**

现有 Python、FastAPI、MySQL、JWT、RBAC、LangChain、LangGraph、独立 Worker 和 Ollama 技术体系能够支撑本步骤提出的认证、权限、AI 执行控制、审计、并发和恢复方案。

其中：
- 用户认证和统一 RBAC 具备明确实现路径。
- 三级数据范围和字段级权限可由后端权限服务实现。
- Agent 工具白名单、参数校验和调用审计可实现。
- 数字员工可继承发起用户权限并叠加职责授权。
- 独立只读数据库账号可以作为 NL2SQL 的基础保护。
- 异步任务、Worker、并发控制和资源监控可沿用第 06 步方案。
- 自动备份、恢复演练和性能测试具有明确实施路径。

但文件安全、AI 敏感信息完整留存、NL2SQL 安全边界和统一超时策略仍有明显风险或设计差异。它们不能仅因用户已选择某个方案就被认定为满足生产安全要求。
