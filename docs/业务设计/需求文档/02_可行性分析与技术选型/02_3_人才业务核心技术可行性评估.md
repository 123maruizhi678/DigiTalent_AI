## 一、评估目标与范围

本报告评估人才业务核心技术能否由已确认的基础技术栈支撑，并形成后续详细设计和开发的技术依据。

本步骤分为五项：

1. 简历上传与解析技术可行性评估。
2. 简历信息抽取与结构化技术可行性评估。
3. 人才主档案技术可行性评估。
4. 人才与岗位匹配技术可行性评估。
5. AI 人才画像技术可行性评估。

本报告属于技术可行性评估，不包含完整数据库建表、接口实现、代码开发、生产部署或性能验收。

## 二、基础技术基线

本报告沿用《02_基础技术组件可行性评估》V1.1 已确认的技术路线，不重新选型。

| UI | Element Plus | 管理端界面组件 |
| 后端 | Python 3.11 + FastAPI | 业务 API、任务接口 |

| MySQL 驱动 | PyMySQL | MySQL 连接 |
| 业务数据库 | MySQL 8.0.44 | 人才、岗位、简历、测评、面试等业务数据 |
| Agent | LangChain | 模型调用、Prompt、工具组织 |
| Workflow | LangGraph | 多步骤 AI 工作流、状态管理 |
| 向量数据库 | Milvus 2.6.25 | 人才及岗位语义向量检索 |
| 图数据库 | Neo4j | 人才关系分析的目标组件，实际使用价值需专项验证 |
| 模型服务 | Ollama + 统一模型适配层 | 本地模型推理，保留外部模型接入能力 |
| 异步任务 | MySQL 持久化任务表 + 独立 Worker | 简历解析、画像生成、AI 评分等耗时任务 |
| 任务调度 | APScheduler | 定时、周期任务触发；不直接执行耗时任务 |
| 文件存储 | 本地文件系统 | 初期保存简历及相关业务文件 |
| 文件访问 | 统一 FileStorage 接口 | 屏蔽底层存储实现，未来可扩展对象存储 |
| 缓存 | 初期不引入 Redis | 遵循已确认约束 |
| 文档解析 | MinerU、python-docx 及格式专用解析器 | 简历文件解析 |

- MinIO 不作为人才平台业务文件存储的必选组件；Milvus 部署所需对象存储依赖与业务文件存储分开管理。
- Neo4j 虽纳入目标技术架构，但不应为了使用而使用；需要通过实际人才关系查询场景验证价值。
- 技术选型已确认不代表所有组件已经完成部署、集成或性能验证。

# 三、第一项：简历上传与解析技术可行性评估

## 3.1 已确认业务规则

| 项目 | 确认结果 |
|---|---|
| 支持格式 | PDF、DOCX、DOC、TXT、图片 |
| 图片初期建议范围 | JPG、JPEG、PNG；其他格式需另行确认 |
| 单次批量上传 | 最多 20 份 |
| 单份文件大小 | 最大 20 MB |
| 理论单批最大容量 | 400 MB（20 份均达到单文件上限时） |
| 文件保存 | 本地文件系统 |
| 文件元数据及任务记录 | MySQL |
| 解析执行 | 异步任务 |
| 失败处理 | 保存错误信息，支持重试和人工处理 |

400 MB 是理论批次容量，不代表已经通过该容量的上传压力测试。

## 3.2 推荐解析技术

| 文件格式 | 推荐解析技术 | 处理方式 |
|---|---|---|
| PDF | MinerU | 提取文本、版面和必要表格信息 |
| DOCX | python-docx | 提取段落、标题和表格 |
| DOC | LibreOffice 转换 | 转换为可解析格式后交给对应解析器 |
| TXT | Python 文件读取 | 识别编码并读取文本 |
| 图片 | MinerU OCR | 识别图片文字及版面 |

LibreOffice 属于需要补充安装和验证的组件；不能将 DOC 直接当作 DOCX 解析。图片 OCR 的识别效果需要使用真实样本验证。

## 3.3 推荐处理流程

1. HR 通过前端批量上传简历。
2. FastAPI 校验数量、大小、扩展名和实际文件类型。
3. 计算 SHA-256，辅助识别重复文件。
4. 保存原始文件。
5. 在 MySQL 创建文件记录及独立解析任务。
6. APScheduler 按调度规则触发任务认领流程。
7. Worker 领取并执行解析任务。
8. 统一文件解析入口识别格式并分发到注册的解析器。
9. 解析器输出统一解析结果。
10. 保存解析文本、页码、结构信息、状态及错误记录。
11. 解析结果进入信息抽取阶段。

## 3.4 统一解析器设计

统一解析入口只负责文件类型识别、解析器查找、调用和统一结果封装，不混入具体格式解析逻辑。

建议拆分：
- 文件类型识别模块。
- 解析器注册模块。
- 统一解析入口。
- PDF 解析器。
- DOCX 解析器。
- DOC 转换处理器。
- TXT 解析器。
- 图片 OCR 解析器。
- 统一解析结果模型。

以后增加格式时，原则上通过新增解析器和注册配置扩展，不改动统一入口核心逻辑。

## 3.5 可靠性、安全与风险

- 每个文件独立记录上传和解析结果，部分文件失败不应导致其他成功文件全部回滚。
- 文件扩展名和实际类型双重校验；限制文件大小和数量。
- 防止路径遍历、恶意文件上传和越权访问。
- 原始文件、解析任务和解析结果分别管理。
- 任务需支持幂等、超时、重试、失败恢复和人工重新执行。
- 对 OCR 质量差、文件损坏、格式不支持等情况记录明确错误。
- 文件访问必须经过权限控制，不能使用无保护的公开访问地址。

## 3.6 可行性结论

**结论：技术方案可行，部分组件和性能仍需验证。**

| 评估维度 | 结论 |
|---|---|
| 五种格式解析 | 方案可行 |
| 20 份批量上传 | 方案可行，需压力测试 |
| 单份 20 MB 限制 | 方案可行 |
| DOC 转换 | 需补充 LibreOffice 并验证 |
| 图片 OCR | 需真实样本验证 |
| 异步任务及重试 | 方案可行，需验证幂等和恢复 |
| 400 MB 批次承载 | 尚未验证 |

# 四、第二项：简历信息抽取与结构化技术可行性评估

## 4.1 已确认业务规则

| 确认事项 | 最终结果 |
|---|---|
| 信息范围 | 基础字段 + 完整教育经历、工作经历、项目经历 |
| 审核方式 | 所有简历必须经过 HR 确认后，才能进入正式人才档案 |
| 工作年限 | 只提取简历中明确写出的工作年限；没有则留空 |

## 4.2 信息抽取范围

### 基础信息
- 姓名。
- 联系方式。
- 性别、年龄（仅在简历明确提供时提取）。
- 最高学历、专业。
- 明确写出的工作年限。
- 技能、个人优势。

### 教育经历
建议每段经历独立记录学校、学历、专业、入学时间、毕业时间、学习状态及原始描述。

### 工作经历
建议每段经历独立记录公司、行业、岗位、入离职时间、工作职责、工作成果及原始描述。

### 项目经历
建议每个项目独立记录项目名称、角色、时间、背景、职责、技术栈、成果及原始描述。

以上是推荐结构字段；具体字段是否全部进入正式业务模型，应在详细设计阶段结合业务复核。

## 4.3 推荐技术方案

1. 读取第一项输出的统一解析文本。
2. 对长简历按章节或内容块分段。
3. 使用 LangChain 组织 Prompt 和模型调用。
4. 使用 Ollama 提取基础信息、教育经历、工作经历、项目经历。
5. 将模型输出映射到统一 Pydantic 模型。
6. 执行字段类型、格式和业务规则校验。
7. 保存 AI 抽取草稿及字段来源依据。
8. HR 查看、修改、补充并确认。
9. 只有确认后的信息才能写入正式人才档案。

## 4.4 数据质量控制

每个重要抽取字段建议保留：
- 字段名称和值。
- 原始文本依据。
- 来源页码（适用时）。
- 抽取状态。
- 模型参考置信度。
- HR 审核状态。

模型置信度不能直接当成真实准确率，必须通过人工标注样本校准。

缺失和异常信息建议区分：
- 已提取。
- 未提及。
- 无法识别。
- 存在冲突。
- 待人工确认。

不得让模型自行编造姓名、学历、学校、工作年限或项目经历。工作年限不根据起止时间自动计算，除非未来另行确认业务规则。

## 4.5 推荐数据对象

逻辑上建议区分：
- 简历解析结果。
- 人才基础信息草稿。
- 教育经历草稿。
- 工作经历草稿。
- 项目经历草稿。
- 字段抽取依据。
- 人工审核记录。

实际数据库表的拆分方式留待数据库设计阶段确定。

## 4.6 风险与测试要求

主要风险：
- 不同简历排版造成抽取差异。
- 模型遗漏或编造字段。
- 多段经历混淆。
- 长文本超出模型有效上下文。
- 模型结构化输出不稳定。

建议使用人工标注的真实简历测试字段准确率、完整性、来源可追溯率和人工修正率。此前提出的准确率目标属于建议验收指标，尚未通过测试，不作为已达成结果。

## 4.7 可行性结论

**结论：技术方案可行，模型抽取准确率需要真实简历样本验证。**

# 五、第三项：人才主档案技术可行性评估

## 5.1 已确认业务规则

| 确认事项 | 最终结果 |
|---|---|
| 人才主档案 | 一个自然人对应一份统一人才主档案 |
| 候选人与员工 | 分别保留业务身份，关联同一人才主档案 |
| 重复人才合并 | 选择一份主档案保留，其他档案标记为已合并，并保留映射及历史记录 |
| 账号业务身份 | 同一时点只能对应一种业务身份 |
| 多份简历 | 一个自然人可以关联多份简历 |
| 当前有效简历 | HR 手动指定，历史简历保留 |
| 删除 | 先逻辑删除，再按规则处理关联数据 |
| 画像 | 独立管理并保留历史版本 |

## 5.2 推荐数据架构

以 MySQL 中的人才主档案为统一关联对象，候选人身份、员工身份、简历、结构化资料、人才画像和标签分别管理。

建议逻辑对象：
- `talent_master`：人才主档案。
- `candidate_identity`：候选人业务身份。
- `employee_identity`：员工业务身份。
- `resume_file`：简历文件记录。
- `resume_version`：简历版本。
- `resume_extraction`：解析记录。
- `talent_merge_record`：人才合并记录。
- `talent_profile`：人才画像。
- `talent_tag`：人才标签。
- `talent_change_log`：人才资料变更记录。

以上是逻辑数据对象，不是最终建表方案。

## 5.3 候选人转员工

候选人录用后，不复制一份新的人才主档案，而是在原人才主档案下创建或激活员工身份，保留候选人阶段的招聘、面试、测评等历史业务记录。

身份转换应通过 MySQL 事务处理，并记录操作日志和异常恢复信息。

## 5.4 重复人才识别与合并

建议采用规则匹配、疑似重复检测和 HR 人工确认的方式。

- 手机号、邮箱等可作为辅助匹配信息。
- 姓名、教育经历、工作经历和简历相似度可用于发现疑似重复。
- 不允许仅凭姓名相同自动合并。
- HR 选择保留档案后，将关联业务数据迁移或建立关联。
- 被合并档案保留原 ID、目标 ID、合并原因、操作人和时间。
- 合并过程需考虑事务、关联完整性及异常恢复。

## 5.5 简历与资料更新

一个人才可以关联多份简历，由 HR 指定当前有效简历。原始文件、文件版本和解析记录分开管理；重新解析不得覆盖历史解析结果。

AI 抽取结果和画像草稿不得直接覆盖正式人才资料。正式资料变更应记录修改前后值、来源、操作人员和时间。

## 5.6 可行性结论

**结论：现有 MySQL + SQLAlchemy + FastAPI 技术栈能够支撑人才主档案管理。**

主要验证点是复杂档案合并、身份转换事务、并发修改和关联数据完整性。

# 六、第四项：人才与岗位匹配技术可行性评估

## 6.1 已确认业务规则

| 确认事项 | 最终结果 |
|---|---|
| 岗位条件维护 | HR 配置和维护；重要岗位由管理员或业务负责人审核 |
| 硬性条件不满足 | 判定不满足 |
| 信息不足 | 单独标记，不自动淘汰 |
| 评分权重 | 每个岗位独立配置 |
| 匹配合格线 | 每个岗位独立配置 |
| 人才多岗位匹配 | 允许一个人才同时匹配多个岗位 |
| 岗位条件修改 | 保留历史结果，由 HR 手动触发重新匹配 |

## 6.2 推荐技术架构

采用 MySQL + Milvus + Ollama + LangChain + LangGraph：

- MySQL：保存人才结构化数据、岗位条件、评分规则和匹配结果。
- Milvus：人才及岗位语义向量检索。
- Ollama：辅助语义分析和匹配解释。
- LangChain：组织模型调用及匹配工具。
- LangGraph：组织匹配工作流。
- 评分引擎：按照岗位规则执行确定性评分。
- HR：保留最终筛选决定权。

## 6.3 匹配处理流程

1. HR 创建岗位并配置岗位条件。
2. 配置硬性条件、软性评分维度、权重及合格线。
3. 重要岗位进入审核流程。
4. 发布岗位条件版本。
5. HR 发起匹配任务。
6. MySQL 执行硬性条件过滤。
7. 将满足条件的人才交给 Milvus 进行语义检索。
8. 汇总检索结果和结构化匹配依据。
9. 评分引擎计算综合分数。
10. 生成满足、不满足、信息不足及待核实名单。
11. 保存匹配任务、岗位版本、评分明细和解释。
12. HR 查看结果并决定后续招聘流程。

信息不足不得自动等同于不满足，也不得在缺少依据时给出确定性结论。

## 6.4 评分与版本管理

- 综合分数采用 0–100 分。
- 每个岗位独立配置评分维度和权重。
- 权重总和需通过配置校验。
- 每个岗位独立设置合格线。
- 一个候选人可参与多个岗位匹配，各岗位结果独立。
- 每次匹配保存岗位条件版本、评分规则版本、模型及相关检索配置。
- 岗位修改后保留历史匹配结果，由 HR 手动触发新一轮匹配。

## 6.5 风险与验证要求

主要风险：
- 结构化资料不完整。
- 向量检索遗漏。
- 模型解释不准确。
- 评分规则配置错误。
- 岗位版本变化导致历史结果无法解释。
- 多岗位匹配记录混淆。

建议用人工标注的人才—岗位样本验证硬性条件判断准确率、匹配排序质量、评分稳定性和解释可追溯性。

## 6.6 可行性结论

**结论：现有技术栈能够支撑人才与岗位匹配业务。** 主要待验证匹配准确率、评分稳定性和检索性能。

# 七、第五项：AI 人才画像技术可行性评估

## 7.1 已确认业务规则

| 确认事项 | 最终结果 |
|---|---|
| 画像内容 | 基础概况、专业能力、综合优势、待提升项、人才标签，以及教育、工作、项目经历分析 |
| 画像数据来源 | 初期只使用已经确认的人才档案资料 |
| 生成触发 | 人才关键资料变化时自动生成草稿；HR 也可手动触发 |
| 正式画像 | 必须由 HR 审核确认后发布 |
| 历史版本 | 保留画像历史版本，不覆盖旧版本 |

初期不使用测评、面试和岗位匹配记录作为画像生成依据。

## 7.2 人才主档案与画像的边界

人才主档案保存事实性资料，例如学历、学校、工作经历、项目经历和技能。

人才画像保存基于已确认事实形成的综合分析，例如专业能力分析、优势、待提升项和人才标签建议。

技能事实与技能能力评价必须区分；AI 生成的分析结论应能追溯到人才资料依据。

## 7.3 推荐技术架构

- MySQL：保存画像草稿、正式画像、版本及审核记录。
- Ollama：本地模型推理。
- LangChain：组织 Prompt、模型调用及结构化输出。
- LangGraph：组织数据获取、分析、生成、校验和草稿保存流程。
- Pydantic：画像结构校验。
- FastAPI：画像生成、查询、审核接口。
- Vue 3：画像展示、修改和审核。

## 7.4 画像生成流程

1. 人才关键资料发生变化，或 HR 手动触发。
2. 判断是否需要生成画像任务。
3. 获取已经确认的人才档案资料。
4. 组织基础信息、教育、工作、项目和技能数据。
5. 调用 Ollama 生成画像草稿。
6. 使用 Pydantic 校验结构。
7. 检查画像结论是否有来源依据。
8. 保存待审核草稿。
9. HR 查看、修改、确认或退回。
10. 确认后生成正式画像新版本。
11. 保留历史版本及审核记录。

## 7.5 画像更新和版本管理

关键资料变化时可自动生成草稿；HR 也可以手动触发。联系方式等普通资料变更是否触发，应通过关键字段配置控制。

建议记录：
- 人才 ID。
- 画像版本号。
- 来源人才资料版本。
- 生成方式（自动/手动）。
- 模型及 Prompt 版本。
- 画像结论及其来源依据。
- 审核状态、审核人和审核时间。
- 人工修改前后内容。

自动生成不等于自动发布；正式画像必须经 HR 确认。

## 7.6 风险与验证要求

主要风险：
- AI 编造能力或优势。
- 人才资料不完整。
- 资料变更事件遗漏。
- 重复触发生成任务。
- 多次生成结果不一致。
- 人工修改无法追溯。

建议测试画像事实准确性、来源可追溯性、内容完整性、重复生成一致性和自动触发可靠性。

## 7.7 可行性结论

**结论：现有技术栈能够支撑人才画像生成、审核、更新和版本管理。** 模型分析质量及自动触发可靠性需要真实数据验证。
