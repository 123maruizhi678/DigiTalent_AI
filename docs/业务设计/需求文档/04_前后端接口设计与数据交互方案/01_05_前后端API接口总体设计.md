## 一、设计目标与范围

本文档依据第四阶段第07步五批共30项确认结果，确定 AI 数字化人才平台前后端
API 的总体规范，包括 API
风格、版本、资源命名、请求与响应、错误编码、分页、排序、筛选、参数验证、幂等、七大业务模块

执行、异步任务、数据契约、OpenAPI 文档、安全、日志追踪、测试和验收要求。

本文档属于 API
总体设计，不等同于全部接口的逐项详细设计。具体接口字段、业务状态流转、请求和响应
Schema、权限矩阵、错误编码完整清单及数据库事务边界，应在后续接口详细设计和开发阶段补充。

### 1.1 业务范围

API 覆盖平台七大业务模块：

1.  人才选拔。
2.  人才档案与人才画像。
3.  智能测评与面试。
4.  AI Agent 与工作流管理。
5.  数字员工与任务调度。
6.  数据智能与运营决策。
7.  用户、组织与权限管理。

不纳入当前业务范围：岗前培养与培训课程、企业知识库。

### 1.2 前后端技术基线

  层次           技术或规范                                用途
  -------------- ----------------------------------------- --------------------
  前端           Vue 3 + TypeScript                        页面和类型定义
  前端路由       Vue Router                                页面访问控制
  前端状态       Pinia                                     认证和全局状态
  前端请求       Axios                                     HTTP 请求封装

### 1.3 总体设计原则

-   采用 RESTful API 风格。
-   统一 API 前缀 `/api/v1/`。
-   使用小写英文复数资源名表达资源。
-   使用 HTTP 方法表达资源操作。
-   普通 API 统一响应结构和错误编码。
-   HTTP 状态码表达真实 HTTP 处理结果。
-   JSON 作为主要请求和响应格式，文件传输单独定义。
-   统一分页、排序、筛选、参数验证和异常处理。
-   七大业务模块拥有清晰独立的 API 资源边界。
-   跨模块通过资源 ID 和明确的关联接口建立联系。
-   认证、权限和数据范围由后端最终执行。
-   耗时业务采用异步任务模式，避免长期占用普通 HTTP 请求。
-   初期采用 HTTP 轮询查询任务状态，后续按实际需要评估 SSE 或
    WebSocket。
-   Pydantic Schema 作为后端数据契约基础，通过 OpenAPI
    描述接口并同步前端 TypeScript 类型。
-   通过统一 `request_id` 关联请求、日志和异步执行。
-   建立自动化测试、接口联调和架构验收机制。

## 三、API 基础规范

### 3.1 统一前缀与版本

统一 API 前缀：

``` text
/api/v1/
```

示例：

``` text
/api/v1/candidates
/api/v1/talents
/api/v1/assessment-tasks
/api/v1/agents
/api/v1/digital-employees
/api/v1/metrics
/api/v1/users
```

版本号用于管理可能发生的不兼容接口变更。当前使用
v1，不意味着每次新增字段都需要升级版本；兼容性判断应纳入接口变更管理。

### 3.2 HTTP 方法约定

  方法     主要用途         约定
  -------- ---------------- ----------------------------------
  GET      查询             不应产生业务资源变更
  POST     创建或提交操作   创建资源、提交任务或执行明确动作
  PUT      完整更新         表示对资源进行完整替换式更新
  PATCH    部分更新         只更新指定字段
  DELETE   删除             删除或按业务规则执行逻辑删除

业务动作接口应明确动作语义和状态约束，不能仅为了形式上的 RESTful
而隐藏实际业务含义。

### 3.3 资源命名

-   使用小写英文复数资源名。
-   资源层级表达真实的从属关系。
-   路径参数使用明确的业务 ID。
-   查询参数采用统一命名。
-   不把任意业务操作都写成无规则的动词路径。

示例：

``` http
GET    /api/v1/candidates
GET    /api/v1/candidates/{candidate_id}
POST   /api/v1/candidates
PATCH  /api/v1/candidates/{candidate_id}
DELETE /api/v1/candidates/{candidate_id}
```

### 3.4 普通 API 统一响应结构

``` json
{
  "code": "0",
  "message": "success",
  "data": {},
  "request_id": "req_xxxxx"
}
```

字段含义：

  字段         含义
  ------------ --------------
  code         业务处理编码
  message      结果说明
  data         业务数据
  request_id   请求追踪标识

说明： - 上述结构用于普通 JSON API。 - 文件下载等二进制响应不强行包装成
JSON。 - HTTP 状态码应与实际处理结果一致。 -
错误响应也应尽可能保留统一错误结构和请求追踪标识。

### 3.5 全局错误编码

已确认错误类别和示例：

  错误类别   示例编码               说明
  ---------- ---------------------- --------------------
  认证错误   `AUTH_UNAUTHORIZED`    未认证或认证失效
  权限错误   `AUTH_FORBIDDEN`       无权执行操作
  参数错误   `VALIDATION_ERROR`     请求参数验证失败
  资源错误   `RESOURCE_NOT_FOUND`   资源不存在
  业务错误   `BUSINESS_ERROR`       业务规则不满足
  系统错误   `INTERNAL_ERROR`       未预期的服务端错误

后续应建立完整错误编码清单，包含 HTTP
状态码映射、错误描述、是否可重试和前端处理建议。不同业务场景不能复用同一编码表达不同含义。

### 3.6 请求与响应媒体类型

  场景                 媒体类型或格式
  -------------------- ------------------------------------------
  普通查询和数据提交   `application/json`
  文件上传             `multipart/form-data`
  文件下载             二进制响应，媒体类型按文件内容确定
  文件预览             根据预览方式返回文件内容或明确的预览资源
  日期时间             ISO 8601 字符串

字符编码统一采用
UTF-8。具体文件类型和下载响应头在文件接口详细设计中确定。

## 四、查询、分页、排序与筛选规范

### 4.1 页码分页

统一参数：

  参数        类型      说明
  ----------- --------- -------------------
  page        integer   当前页码，从1开始
  page_size   integer   每页记录数

请求示例：

``` http
GET /api/v1/candidates?page=1&page_size=20
```

分页响应数据示例：

``` json
{
  "items": [],
  "total": 100,
  "page": 1,
  "page_size": 20
}
```

分页参数必须设置合理上下限，避免单次请求返回过量数据。具体默认值和最大值由接口详细设计统一确定。

### 4.2 排序

统一参数： - `sort_by`：排序字段。 - `sort_order`：排序方向，使用 `asc`
或 `desc`。

示例：

``` http
GET /api/v1/candidates?sort_by=created_at&sort_order=desc
```

后端必须使用排序字段白名单，不能将客户端传入的字段未经校验直接拼接到
SQL。

### 4.3 简单筛选

简单筛选使用 Query Parameters：

``` http
GET /api/v1/candidates?status=active&keyword=Java
```

适用于关键词、状态、时间范围和其他简单条件。

### 4.4 复杂组合查询

复杂查询使用专门的 POST 查询接口：

``` http
POST /api/v1/candidates/search
Content-Type: application/json
```

请求体示例：

``` json
{
  "filters": {
    "status": ["active"],
    "skills": ["Python", "Java"]
  },
  "keyword": "AI工程师"
}
```

复杂查询的字段、组合规则和可查询范围必须由后端 Schema
与业务权限共同约束。

### 4.5 详情与关联资源

采用资源详情接口和关联资源接口结合的方式：

``` http
GET /api/v1/candidates/{candidate_id}
GET /api/v1/candidates/{candidate_id}/resumes
GET /api/v1/candidates/{candidate_id}/assessments
```

避免一个详情接口无边界地返回所有关联数据。对于页面确实需要的轻量汇总信息，可以在详细设计中定义明确的聚合响应。

## 五、参数验证、超时与幂等

### 5.1 Pydantic 参数验证

后端统一验证： - 必填参数。 - 数据类型。 - 字符串长度。 - 数值范围。 -
枚举值。 - 日期和时间格式。 - 分页参数。 - 复杂筛选结构。 -
文件元数据和业务关联参数。

前端可以进行即时表单校验，但前端校验不能替代后端验证。

### 5.2 超时策略

根据接口类别制定超时策略：

  接口类别              处理原则
  --------------------- ------------------------------------------
  普通查询              使用合理的短时超时
  普通写入              使用与业务处理相匹配的超时
  文件上传              考虑文件大小和上传过程设置超时
  长耗时 AI 任务        提交后返回任务标识，不让普通请求一直等待
  Agent/Workflow 执行   采用执行记录和异步状态查询

具体秒数应在实现和性能测试阶段根据实际服务耗时确定，不在总体设计中虚构统一数值。

### 5.3 幂等与重复提交

-   关键业务操作按业务需要设计幂等机制。
-   对可能重复提交的任务创建操作，评估使用幂等键。
-   后端应处理并发重复提交。
-   前端按钮禁用只是交互辅助，不能作为唯一防重复措施。
-   请求超时后，客户端应先查询原操作或任务状态，不应直接重新创建。

## 七、认证、权限与组织数据范围 API

### 7.1 认证 API

建议接口：

  方法   路径                     用途
  ------ ------------------------ --------------
  POST   `/api/v1/auth/login`     用户登录
  POST   `/api/v1/auth/logout`    用户退出
  GET    `/api/v1/auth/me`        获取当前用户
  POST   `/api/v1/auth/refresh`   刷新认证凭据

说明： - 刷新接口是否启用以及具体行为取决于最终认证方案。 -
认证凭据的存储、有效期、刷新和撤销策略必须前后端一致。 - 优先评估
HttpOnly、Secure、SameSite Cookie 等安全机制及相应 CSRF 防护要求。 -
不在浏览器端暴露服务端密钥。

### 7.2 权限和菜单 API

建议接口：

``` http
GET /api/v1/auth/permissions
GET /api/v1/auth/menus
```

用于前端获取当前用户可访问的权限和菜单信息。

前端可根据权限控制路由、菜单和按钮展示，但后端必须对每个受保护 API
重新执行授权检查。

### 7.3 组织数据范围

示例：

``` http
GET /api/v1/organizations/{organization_id}/members
```

后端必须根据当前用户的组织关系、角色和数据范围限制返回结果，不能只验证用户是否登录。

### 7.4 权限控制原则

-   身份认证确认调用者是谁。
-   角色和权限检查确认调用者能否执行某种操作。
-   组织数据范围确认调用者能访问哪些业务数据。
-   文件访问还需验证文件与业务对象的关联权限。
-   前端隐藏菜单和按钮不能代替后端授权。

## 八、统一文件资源 API

### 8.1 建议接口

  方法     路径                                 用途
  -------- ------------------------------------ ----------------
  POST     `/api/v1/files/upload`               上传文件
  GET      `/api/v1/files/{file_id}`            查询文件元数据
  GET      `/api/v1/files/{file_id}/download`   下载文件
  GET      `/api/v1/files/{file_id}/preview`    预览文件
  DELETE   `/api/v1/files/{file_id}`            删除文件

### 8.2 文件资源管理原则

-   文件通过统一文件资源管理。
-   业务对象通过文件 ID 关联文件。
-   文件元数据与文件实际内容的存储方式由文件存储设计确定。
-   上传接口采用 `multipart/form-data`。
-   下载接口返回二进制内容和适当的响应头。
-   预览接口根据文件类型和预览策略返回内容或预览资源。
-   删除操作必须校验文件归属、引用关系和用户权限。
-   不得仅凭文件 ID 就允许访问文件。

### 8.3 文件安全要求

后端重新验证： - 文件大小。 - 文件扩展名和实际内容。 - MIME 类型。 -
文件访问权限。 - 文件与业务对象的关联关系。 -
必要的恶意文件检测和安全处理。

前端文件校验仅用于改善用户体验，不能作为安全边界。

WebSocket。初期不为尚未明确的实时需求增加系统复杂度。

## 十、Pydantic、OpenAPI 与 TypeScript 数据契约

### 10.1 契约管理原则

-   后端以 Pydantic Schema 作为请求和响应数据契约基础。
-   FastAPI 通过 OpenAPI 描述 API
    路径、方法、参数、请求体、响应和认证要求。
-   前端根据 OpenAPI 生成或同步 TypeScript 类型。
-   API 类型变更必须经过检查和联调。
-   不允许长期依赖人工分别维护两套互不校验的类型定义。

### 10.2 数据契约示例

后端 Pydantic Schema 示例：

``` python
from pydantic import BaseModel


class CandidateResponse(BaseModel):
    id: str
    name: str
    status: str
```

前端 TypeScript 对应类型示例：

``` typescript
export interface Candidate {
  id: string
  name: string
  status: string
}
```

以上仅用于说明类型对应关系。实际字段、可空性、枚举和命名以最终后端
Schema 为准。

### 10.3 类型同步流程

``` text
后端定义 Pydantic Schema
          |
          v
FastAPI 生成 OpenAPI
          |
          v
前端类型生成或同步
          |
          v
类型差异检查
          |
          v
前后端接口联调
          |
          v
测试与验收
```

需要在工程实现阶段选定具体的 TypeScript
类型生成工具和命令，并纳入版本管理或 CI 检查。

### 10.4 OpenAPI 文档

FastAPI 自动生成 OpenAPI 文档，统一描述： - 接口路径和 HTTP 方法。 -
路径参数和 Query Parameters。 - 请求体 Schema。 - 响应 Schema。 -
错误响应。 - 认证要求。 - 接口说明和标签。

文档应与实际代码保持一致，不应将过期的手工文档作为唯一接口依据。

## 十一、API 安全与访问控制

### 11.1 统一安全要求

-   身份认证。
-   角色权限校验。
-   组织数据范围控制。
-   文件访问授权。
-   请求参数验证。
-   关键操作保护。
-   必要的接口限流。
-   敏感信息保护。
-   合理的跨域和传输安全配置。

### 11.2 认证和授权

所有受保护接口必须在后端验证认证状态和授权条件。不能仅依靠前端路由守卫、菜单隐藏或按钮隐藏。

### 11.3 数据范围

组织数据范围应在后端查询和业务处理过程中落实。不能只在前端过滤已经返回的数据。

### 11.4 限流与防重复

根据接口风险确定限流策略，重点评估： - 登录和认证相关接口。 -
文件上传接口。 - AI 任务提交接口。 - Agent/Workflow 执行接口。 -
其他可能消耗较多计算资源的接口。

限流阈值和策略由部署规模、用户规模和实际资源消耗决定。

### 11.5 敏感信息

-   不在响应中返回密码、密钥或不必要的内部信息。
-   不在日志中记录认证凭据。
-   不将服务端密钥放入前端构建变量。
-   错误信息避免暴露数据库结构、内部堆栈和服务秘密。
-   敏感操作应进入审计记录。

## 十二、日志、request_id 与请求追踪

### 12.1 统一请求追踪

统一使用 `request_id` 关联请求链路。

建议记录： - request_id。 - 请求路径。 - HTTP 方法。 -
请求发起用户或可审计的用户标识。 - 响应状态码。 - 请求耗时。 -
异常信息。 - 关联 task_id。 - 关联 execution_id。

日志记录必须遵循敏感信息保护要求，不记录密码、Token、密钥和不必要的个人敏感数据。

### 12.2 请求与任务关联

一次任务提交请求可以形成如下关联：

``` text
request_id
   |
   v
业务 API 请求
   |
   v
task_id
   |
   +----> execution_id（如适用）
   |
   v
任务状态与结果
```

请求结束后，异步任务可能继续执行，因此任务日志需要保留原始请求追踪关联，并为任务自身的后续处理记录必要的上下文。

### 12.3 审计日志

需要审计的操作由权限和审计设计确定，重点包括： - 用户和角色权限变更。 -
组织管理操作。 - 文件访问和删除等关键操作。 - Agent、Workflow
配置和执行控制。 - 关键业务数据变更。 - 其他需要追责或安全审查的操作。
