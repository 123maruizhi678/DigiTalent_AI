## 一、设计目标与范围

本文档根据第四阶段第09步五批共30项确认结果，定义 AI
数字化人才平台核心业务 Workflow
的组织方式、执行规范、主要业务流程、Agent 与 Tools 使用边界、输入输出
Schema、状态管理、异常处理、人工审核、数字员工调度、跨 Workflow
协作及端到端验收要求。

本文件是在第四阶段第01---08步总体设计基础上的业务流程详细设计。它明确流程节点和职责边界，但不替代后续开发阶段的数据库字段级设计、API
契约、Prompt 正文、评分权重、模型参数和部署验证。

### 1.1 平台业务范围

本设计覆盖已确认的七大业务模块：

1.  人才选拔。
2.  人才档案与人才画像。
3.  智能测评与面试。
4.  AI Agent 与工作流管理。
5.  数字员工与任务调度。
6.  数据智能与运营决策。
7.  用户、组织与权限管理。

明确不纳入本项目业务范围： - 岗前培养与培训课程。 - 企业知识库。

RAG
等能力如被业务流程调用，必须限定在经过授权的人才业务数据范围内，不代表新增企业知识库模块。

### 1.2 已确认技术基线

  技术                     流程设计中的定位
  ------------------------ ------------------------------------------------------
  FastAPI                  对外 API 和业务服务入口
  MinerU                   独立文档解析服务的底层引擎
  Ollama                   当前本地模型服务
  `qwen3.5:4b`             当前 Chat 模型
  `qwen3-embedding:0.6b`   当前 Embedding 模型
  Embedding 维度 1024      当前向量维度基线
  LangChain                模型、Prompt、Tools、Embedding 和检索组件集成
  LangGraph                Agent/Workflow 编排、状态流转和 Checkpoint
  MySQL                    业务关系数据持久化及待验证的 Checkpointer 持久化目标
  Milvus                   向量存储和检索，实际部署与 Collection 仍需验证

当前不将 Redis 作为初期必需依赖。MySQL Checkpointer
的兼容性和实际恢复行为必须通过技术验证后才能投入使用。

### 1.3 总体设计原则

-   按业务场景建立独立 Workflow，各流程可以组合调用。
-   按业务重要程度和实施依赖关系安排开发顺序。
-   支持 API、人工操作和内部任务调度三种触发方式。
-   同步与异步执行并存，根据任务耗时和场景选择。
-   统一基础输入输出规范，每种 Workflow 使用独立 Schema。
-   建立统一业务执行状态管理，不只依赖 LangGraph 内部状态。
-   MinerU 负责文档解析，Agent 负责业务信息提取和分析。
-   规则计算与 AI 分析分离，模型不能随意改变确定性规则。
-   AI 输出与人工最终决定分开记录。
-   原始业务数据、规则计算结果、AI 分析结果和最终报告分层管理。
-   人才画像不覆盖原始人才档案，支持版本和来源追溯。
-   Workflow 之间通过标准化输入输出协作，不直接共享任意内部 State。
-   关键节点支持人工审核、中断和授权恢复。
-   通过幂等、并发控制和执行追踪保证任务可靠性。
-   所有 AI 数据访问遵循身份、角色和组织数据范围权限。

  顺序   Workflow                 优先级
  ------ ------------------------ --------
  1      简历解析                 最高

### 3.3 触发方式

统一支持：

1.  **API 触发：** 前端提交业务请求，由 FastAPI 进入业务服务。
2.  **人工操作触发：** 授权人员手动启动、重试或重新生成。
3.  **内部任务调度触发：** 数字员工或内部服务发起任务。

所有触发方式进入统一任务和 Workflow 执行管理机制。

### 3.4 同步与异步执行

  场景             建议执行模式
  ---------------- ------------------------
  简单查询         同步
  单份简历解析     根据实际耗时选择
  批量简历筛选     异步
  人才画像生成     异步
  测评分析         根据复杂度选择
  面试分析         根据材料规模和耗时选择
  综合报告生成     异步
  数字员工长任务   异步

同步请求需要设置合理超时。异步任务通过 `task_id`
查询进度和结果。实际阈值在性能测试后确定。

## 四、统一任务与 Workflow 执行规范

### 4.1 统一基础字段

每次 Workflow 调用至少具有以下基础信息：

  字段           说明
  -------------- --------------------------
  task_id        业务任务标识
  workflow_id    Workflow 定义标识
  execution_id   一次具体执行标识
  input          当前 Workflow 的业务输入
  output         当前 Workflow 的业务输出
  status         执行状态
  error          错误分类和错误信息

根据具体流程补充候选人、岗位、测评、面试或报告等业务标识。

### 4.2 统一状态

  状态        含义
  ----------- --------------
  pending     待执行
  running     执行中
  waiting     等待人工处理
  completed   已完成
  failed      执行失败
  cancelled   已取消

状态流转应由统一任务服务管理，并与 LangGraph
执行状态建立关联。需要明确合法状态转换，避免已取消任务被意外恢复或重复完成。

### 4.3 执行记录

建议记录： - task_id、workflow_id、execution_id。 - 业务对象标识。 -
触发方式和发起主体。 - 当前节点。 - 开始时间和结束时间。 - 执行状态。 -
错误分类和错误信息。 - 重试次数。 - Checkpoint 关联信息。 -
模型、Prompt、Agent、Tools 和 Workflow 版本（适用时）。

### 4.4 State 与业务执行记录

-   每种 Workflow 使用独立 State Schema。
-   State 保存当前流程执行所必需的数据。
-   业务执行记录保存在业务持久化层。
-   LangGraph Checkpoint 保存工作流中间状态。
-   Checkpoint 不替代业务最终结果或业务审计记录。
-   Workflow 间通过 Schema 化输入输出传递数据，不直接依赖对方内部
    State。

## 五、简历解析 Workflow 详细设计

### 5.1 业务目标

接收候选人简历文件，通过 MinerU 解析文档，再由简历解析 Agent
提取业务字段，经过结构化校验后形成可供后续业务使用的简历数据。

### 5.2 节点设计

  ---------------------------------------------------------------------------------------------------
  节点              输入                   主要处理                                 输出
  ----------------- ---------------------- ---------------------------------------- -----------------
  1\. 接收简历      文件及候选人关联信息   接收上传请求，建立文件关联               文件标识

  2\. 文件校验      文件标识               检查格式、大小、可读性和必要的安全条件   校验结果

  3\. MinerU        已校验文件             调用独立文档解析服务                     文档解析结构
  文档解析                                                                          

  4\. 简历信息提取  文档解析结构           简历解析 Agent 识别业务字段              候选简历字段

  5\. 信息结构化    提取结果               映射到统一 Resume Schema                 结构化 Resume

  6\. 数据校验      Resume                 检查字段类型、格式、来源和必要完整性     校验结果

  7\. 保存解析结果  校验结果及原始内容     由业务服务持久化并关联候选人             解析结果标识
  ---------------------------------------------------------------------------------------------------

### 5.3 统一 Resume Schema

``` text
Resume
 ├── basic_info
 ├── education
 ├── work_experience
 ├── project_experience
 ├── skills
 ├── certificates
 └── raw_content
```

要求： - 支持字段缺失。 - 保留原始解析内容。 -
必要字段保留来源和页码定位。 - 区分原文明确记载和模型归纳信息。 -
不允许模型编造缺失字段。 - 对日期、联系方式、经历时间等进行格式校验。 -
原始文件、解析结果和候选人主档案分开管理并建立关联。

### 5.4 组件职责

  组件             职责
  ---------------- --------------------------
  文件管理服务     文件接收、存储和访问控制
  MinerU           文档内容和结构解析
  简历解析 Agent   识别和提取业务字段
  Schema 校验器    检查结构和字段格式
  业务服务         保存结果和维护业务关联

### 5.5 异常处理

  异常              处理方式
  ----------------- ------------------------------
  文件损坏          标记失败并返回明确原因
  文件格式不支持    拒绝进入解析节点
  MinerU 超时       按有限重试策略处理
  AI 提取异常       有限重试，保留失败记录
  Schema 校验失败   尝试受控修正或转人工复核
  关键字段缺失      标记缺失或待补充，不自动编造

## 十三、跨 Workflow 协作设计

### 13.1 标准化调用原则

Workflow 可以独立执行，也可以由其他 Workflow
或任务调度机制调用。调用时必须明确： - 目标 Workflow 标识和版本。 - 输入
Schema。 - 输出 Schema。 - 关联 task_id。 - execution_id。 -
调用状态。 - 错误和重试语义。 - 业务数据访问权限。

不允许调用方直接依赖被调用 Workflow 的内部 State 字段。

### 13.2 顺序组合示例：人才选拔

``` text
简历解析 Workflow
       |
       v
简历智能筛选 Workflow
       |
       v
岗位人才匹配 Workflow
       |
       v
人才画像生成/更新 Workflow
       |
       v
综合报告生成 Workflow（按业务需要）
```

流程中的每一步都可以独立执行。组合调用时通过标准化结果传递数据。

### 13.3 条件分支

例如： - 简历解析失败：结束当前任务或进入人工处理。 -
简历信息不足：标记待补充，不进入依赖缺失字段的分析。 -
筛选结果需要复核：进入人工审核节点。 -
匹配数据不完整：明确标记无法判断的维度。 -
测评或面试结果缺失：综合报告标记缺失，不生成虚构内容。

### 13.4 失败结果传递

下游 Workflow 必须能够区分： - 上游成功并有有效结果。 -
上游成功但部分字段缺失。 - 上游等待人工处理。 - 上游失败。 -
上游已取消。

不能将失败或缺失结果当作正常空数据继续生成结论。

## 十五、幂等、并发和任务取消

### 15.1 统一任务标识

建议区分： - `task_id`：业务任务标识。 - `workflow_id`：Workflow
定义标识。 - `execution_id`：一次执行标识。 -
`request_id`：请求链路标识。 -
`idempotency_key`：用于识别重复提交的幂等键。 -
`business_object_id`：业务对象标识。

### 15.2 幂等控制

-   对需要防止重复创建的操作使用幂等键。
-   同一请求重复提交时，按业务规则返回已有任务或执行状态。
-   外部调用重试前检查是否已经产生副作用。
-   业务结果保存需要防止重复写入。
-   对任务取消、恢复和重试操作进行状态校验。

### 15.3 并发控制

-   控制同一任务的并发执行。
-   对允许并行的子任务明确依赖关系。
-   避免多个执行同时覆盖同一业务结果。
-   对状态更新和结果保存采用适当的事务或并发控制策略。
-   具体锁、唯一约束和并发阈值在技术实施阶段确定。

### 15.4 任务取消

-   任务取消需要检查当前状态。
-   已完成任务不能被误标为取消。
-   取消后阻止不必要的后续节点启动。
-   对已执行的外部副作用记录结果，必要时走补偿处理。
-   取消操作需要权限校验和审计。

### 16.3 异常分类

  异常类型              处理方向
  --------------------- --------------------------------
  文件异常              校验失败或转人工
  MinerU 异常           有限重试或失败
  模型服务异常          按模型策略重试、降级或失败
  Schema 校验异常       受控修正或人工复核
  数据权限异常          拒绝访问，不盲目重试
  Milvus 检索异常       记录错误并按策略处理
  Agent/Tools 异常      记录节点失败，判断能否安全重试
  Workflow 节点异常     检查 State 和 Checkpoint
  Checkpoint 恢复异常   阻止不安全恢复，转人工处理

### 16.4 重试原则

-   按任务和节点类型设置重试策略。
-   区分可重试与不可重试错误。
-   设置最大重试次数。
-   记录每次重试原因。
-   考虑退避策略。
-   通过幂等避免重复写入。
-   不允许无限重试。
-   权限错误、参数错误和不兼容错误不应盲目重试。

## 十七、权限与数据保护要求

所有 Workflow 必须遵循统一权限体系。

### 17.1 访问控制

-   任务发起时校验用户身份和操作权限。
-   获取候选人、岗位、简历、测评和面试数据时校验数据范围。
-   Agent 和 Tools 调用必须执行权限检查。
-   数字员工不能继承超出发起人或授权策略的权限。
-   人工审核只能由有权限的人员完成。
-   Workflow 恢复、重试、取消和重新生成均需要权限检查。

### 17.2 数据保护

-   不在日志中记录密码、Token、密钥等认证凭据。
-   对个人敏感信息进行脱敏或限制记录。
-   控制模型输入输出的保存和访问。
-   云端模型接入时评估个人信息保护和供应商数据处理要求。
-   RAG 检索必须应用组织和业务数据范围过滤。
-   向量相似度不能替代业务授权。
-   AI 输出应区分事实、推断和未知信息。

### 17.3 人才业务公平性与可解释性

-   筛选和匹配只能使用合法、岗位相关的评价条件。
-   不使用受保护个人特征进行不当评价。
-   评分规则由业务配置管理。
-   重要结果保留证据和人工复核渠道。
-   AI 建议不能自动替代授权人员作出关键招聘决定。

## 十八、测试与端到端验收标准

### 18.1 分层测试

  幂等测试          重复请求和重复写入

  权限测试          越权访问和组织范围过滤
  端到端测试        从业务触发到最终结果的完整链路

### 18.2 各业务流程验收

  流程           核心验收内容
  -------------- ---------------------------------------------
  简历解析       文件解析、结构化提取、字段校验和来源追溯
  简历筛选       岗位要求分析、筛选依据、缺失信息和人工审核
  岗位人才匹配   多维度评价、规则权重、匹配依据和差距分析
  人才画像       画像生成、事实/推断区分、来源追溯和版本更新
  智能测评       原始数据、规则计算和 AI 分析分离
  面试分析       问答提取、能力分析、证据和审核状态
  综合报告       多来源数据汇总、完整性校验、报告版本和审核
  数字员工调度   任务识别、权限检查、分配、跟踪和结果回传

### 18.3 跨流程验收

必须验证： - Workflow 可以独立执行。 - Workflow 可以按标准 Schema
组合调用。 - 顺序组合和条件分支正常。 -
上游失败和数据缺失可以正确传递。 - State 状态流转正确。 - Checkpoint
保存和恢复有效。 - 人工审核任务能够关联原执行并授权恢复。 -
重复提交不会产生重复业务结果。 - 并发执行不会造成状态或数据覆盖错误。 -
任务取消能够阻止不必要的后续执行。 - request_id、task_id、execution_id
可以关联完整链路。 - 权限检查覆盖 API、Agent、Tools、RAG 和恢复操作。

### 18.4 AI 效果评估

建立固定样本集和人工标注基准，评估： - 简历字段提取准确性。 -
简历解析完整性。 - 筛选依据与岗位要求的一致性。 - 人才匹配评价合理性。 -
人才画像事实准确性和来源完整性。 - 测评分析质量。 -
面试分析证据支持程度。 - 综合报告完整性和可追溯性。

具体样本规模、指标和通过阈值应在测试方案中制定，不在本总体流程文件中预设未经验证的数值。
