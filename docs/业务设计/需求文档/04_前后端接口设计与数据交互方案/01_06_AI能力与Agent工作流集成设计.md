## 一、设计目标与范围

本文档依据第四阶段第08步五批共30项确认结果，明确 AI 数字化人才平台中 AI
技术组件的职责、统一 AI
能力服务层、模型适配、Prompt、Tools、Embedding、Milvus、RAG、Agent、Workflow、State、Checkpoint、Human-in-the-loop、七大业务模块
AI 能力集成，以及异常处理、模型切换、重试恢复、监控、测试和验收要求。

本文档属于 AI 能力与 Agent 工作流总体集成设计，不等同于所有
Agent、Prompt、Tools、Workflow
节点和数据库表的详细设计。具体字段、Prompt
内容、工具参数、状态结构、索引参数、重试阈值和模型效果指标，应在后续详细设计与实施阶段确定。

### 1.1 平台业务范围

AI 能力服务于已经确定的七大业务模块：

1.  人才选拔。
2.  人才档案与人才画像。
3.  智能测评与面试。
4.  AI Agent 与工作流管理。
5.  数字员工与任务调度。
6.  数据智能与运营决策。
7.  用户、组织与权限管理。

当前明确不纳入业务范围： - 岗前培养与培训课程。 - 企业知识库。

本设计中的 RAG
是面向经过授权的人才业务数据的可复用检索增强能力，不代表重新建设企业知识库业务模块。

  ------------------------ --------------------------------- -------------------------------------

  Ollama                   本地模型服务                      已部署

API 接入能力。

### 1.3 总体设计原则

-   建立统一 AI 能力服务层，避免业务模块直接依赖底层 AI 技术。
-   各技术组件职责明确，避免 LangChain、LangGraph、FastAPI 互相替代。
-   MinerU 通过独立文档解析服务接入。
-   本地和云端模型通过统一模型适配层接入。
-   Prompt、Tools、Agent 和 Workflow 定义与执行逻辑分离。
-   LangChain 提供 AI 基础组件，LangGraph 负责 Agent/Workflow 编排。
-   每种 Workflow 定义独立 State Schema。
-   Checkpoint 保存执行状态，不替代业务最终结果。
-   关键业务节点支持人工审核。
-   原始业务数据与 AI 分析结果分开保存。
-   模型、Prompt、Agent、Workflow、Tools 版本可追溯。
-   AI 输出仅作为业务辅助信息，关键业务决定由授权人员作出。
-   异常、重试、恢复、日志和测试纳入统一管理。
-   所有 AI 数据访问必须遵循身份认证、角色权限和组织数据范围控制。

## 四、统一模型服务与配置管理

### 4.1 模型适配层

建立统一模型服务入口，底层通过不同适配器连接模型提供商。

``` text
统一模型服务
      |
      +---- Ollama 适配器
      |
      +---- 云端模型适配器（预留）
```

业务模块只依赖统一模型调用接口，不直接依赖某个具体提供商的 API。

### 4.2 当前模型配置基线

  用途             当前模型                 提供方
  ---------------- ------------------------ --------
  Chat             `qwen3.5:4b`             Ollama
  Embedding        `qwen3-embedding:0.6b`   Ollama
  Embedding 维度   1024                     已确认

### 4.3 模型配置项

建议统一管理：

  配置项            说明
  ----------------- ------------------------
  provider          模型提供商
  model             模型名称
  purpose           模型用途
  temperature       生成参数
  timeout           调用超时
  max_tokens        输出长度限制（适用时）
  model_version     模型版本或标识
  enabled           是否启用
  fallback_policy   降级策略

Chat 和 Embedding 分开配置，不假定同一模型同时适合两种用途。

### 4.4 模型切换原则

-   支持本地和云端模型按配置切换。
-   支持不同业务场景选择不同模型。
-   记录实际调用的提供商和模型。
-   切换前验证输入输出 Schema、上下文长度、工具调用能力和其他必要能力。
-   不允许未经验证自动切换到不兼容模型。
-   模型不可用时按配置降级或明确失败，不进行无边界的自动切换。
-   云端模型接入时评估数据出境、个人信息保护、供应商数据处理和组织安全要求。

## 五、Prompt 管理设计

### 5.1 管理原则

Prompt
与业务代码分离，建立独立管理模块，支持模板、版本、变量、启用状态和使用场景管理。

### 5.2 初步 Prompt 范围

-   简历解析 Prompt。
-   简历筛选 Prompt。
-   人才画像 Prompt。
-   人才匹配 Prompt。
-   智能测评 Prompt。
-   面试分析 Prompt。
-   报告生成 Prompt。
-   Agent 通用 Prompt。

### 5.3 Prompt 管理字段

  字段         说明
  ------------ --------------
  prompt_id    唯一标识
  name         Prompt 名称
  scene        使用场景
  version      版本
  template     模板内容
  variables    模板变量定义
  status       启用状态
  created_at   创建时间
  updated_at   更新时间

### 5.4 执行追踪

每次 Agent 或 Workflow 执行应记录实际使用的 Prompt 标识和版本，避免
Prompt 更新后无法解释历史结果。

Prompt 修改应经过测试和版本管理，重要业务 Prompt 不应直接无记录覆盖。

## 六、Tools 注册与管理设计

### 6.1 统一注册机制

建立 Tools 注册与管理机制，供 Agent 和 Workflow 使用。

初步工具示例：

  工具名称                 用途
  ------------------------ --------------
  `candidate_search`       候选人查询
  `resume_parser`          简历解析
  `talent_profile_query`   人才画像查询
  `assessment_query`       测评结果查询
  `report_generator`       报告生成

以上为初步示例，实际工具清单应根据业务详细设计确定。

### 6.2 工具统一定义

每个工具至少需要定义：

-   唯一工具名称。
-   工具说明。
-   输入参数 Schema。
-   输出结果 Schema。
-   权限要求。
-   超时策略。
-   异常处理策略。
-   版本和启用状态。

### 6.3 工具安全

-   工具调用必须执行用户和业务权限校验。
-   Agent 不得绕过业务服务直接操作数据库。
-   文件读取必须检查文件归属和访问权限。
-   高风险或不可逆操作必须经过授权或人工确认。
-   工具执行记录应关联 Agent、Workflow、task_id 和 request_id。
-   对工具输入进行 Schema 验证，避免任意参数注入。

## 七、Embedding、Milvus 与 RAG 设计

### 7.1 统一 Embedding 服务

统一 Embedding 服务负责： - 文本向量化。 - 批量文本向量化。 -
模型配置。 - 输入长度控制。 - 向量维度校验。 - 模型版本记录。 -
失败处理和必要的重试。

当前向量维度为1024。更换 Embedding
模型时，需要评估维度、模型空间兼容性和历史向量重建需求。

### 7.2 Milvus 向量检索服务

独立向量检索服务统一管理：

-   Collection 创建和配置。
-   向量写入。
-   向量更新和删除。
-   相似度检索。
-   Top-K 查询。
-   元数据过滤。
-   检索结果与 MySQL 业务记录关联。

Milvus 的
Collection、索引类型、距离度量、分区和元数据字段需在向量数据详细设计中确定。1024
维是当前 Embedding 基线，不代表其他索引参数已经确定。

### 7.3 数据职责

-   MySQL：保存人才档案、候选人、岗位、测评等业务主数据及其关系。
-   Milvus：保存用于相似度检索的向量和必要的检索元数据。
-   原始文件：通过统一文件管理机制保存和授权访问。
-   AI 分析结果：由对应业务服务按业务模型持久化。

Milvus 不作为人才业务主数据的唯一存储位置。

### 7.4 可复用 RAG 流程

``` text
经过授权的业务数据
       |
       v
数据准备与清洗
       |
       v
文本切分
       |
       v
Embedding 向量化
       |
       v
Milvus 向量存储
       |
       v
检索请求
       |
       v
向量检索与元数据过滤
       |
       v
按需重排
       |
       v
Prompt 上下文组装
       |
       v
LLM 生成
       |
       v
结果校验与返回
```

### 7.5 RAG 使用边界

RAG
可以用于经过授权的人才档案、候选人、岗位、测评等业务数据检索和上下文增强。

必须遵循： - 先进行身份和数据权限校验。 -
检索时应用组织和数据范围过滤。 - 不因向量相似就自动授予数据访问权限。 -
检索结果应能关联原始业务记录。 - 生成结果应在需要时保留来源信息。 - 不将
RAG 作为绕过业务权限的通道。

本设计不新增企业知识库业务模块。

## 八、Agent 体系设计

### 8.1 Agent 组织模式

采用模块化专业 Agent。复杂场景再引入多 Agent 协作，不为使用多 Agent
而增加不必要的复杂度。

初步 Agent 规划：

  Agent            主要职责
  ---------------- --------------------------
  简历解析 Agent   简历信息提取与结构化辅助
  简历筛选 Agent   根据岗位要求分析候选人
  人才画像 Agent   人才特征归纳和画像生成
  人才匹配 Agent   岗位与人才匹配分析
  智能测评 Agent   测评结果分析
  面试分析 Agent   面试内容分析与评价辅助
  报告生成 Agent   综合分析报告生成

Agent 的最终清单、拆分粒度和调用关系在业务流程详细设计中确定。

### 8.2 Agent 配置管理

每个 Agent 建议管理：

  字段            说明
  --------------- --------------
  agent_id        唯一标识
  name            名称
  description     职责描述
  model_config    模型配置
  prompt_id       关联 Prompt
  tools           可使用工具
  input_schema    输入数据结构
  output_schema   输出数据结构
  version         Agent 版本
  status          启用状态

### 8.3 定义与执行分离

-   Agent 定义描述能力、配置和可用工具。
-   Agent 执行记录描述一次实际运行。
-   Agent 版本变更不应无记录覆盖历史执行信息。
-   执行记录关联实际模型、Prompt 和 Tools 版本。
-   Agent 的工具访问范围必须受权限控制。

## 九、LangGraph Workflow 与 State 设计

### 9.1 Workflow 编排方式

统一使用 LangGraph StateGraph 编排多步骤 AI 业务流程。

节点可以调用： - 普通 Python 业务服务。 - LangChain 模型和 Prompt
组件。 - 注册的 Tools。 - 专业 Agent。 - 文档解析服务。 - Embedding
和向量检索服务。

LangGraph
负责节点执行、状态流转、条件分支、中断和恢复，不替代普通业务服务。

### 9.2 Workflow 定义管理

Workflow 定义与执行记录分离管理。定义至少需要明确： - Workflow
标识和名称。 - 业务用途。 - 节点定义。 - 节点之间的连接关系。 -
条件分支。 - 输入和输出 Schema。 - 关联 Agent 和 Tools。 -
版本和启用状态。

### 9.3 独立 State Schema

每种 Workflow 定义独立 State
Schema，避免不同业务流程共用一个庞大的全局状态对象。

示例仅用于说明简历筛选 State 的概念：

``` python
from typing import TypedDict, Any


class ResumeScreeningState(TypedDict, total=False):
    task_id: str
    candidate_id: str
    resume_content: dict[str, Any]
    position_requirements: dict[str, Any]
    screening_result: dict[str, Any]
    current_step: str
    errors: list[str]
```

实际开发时根据 LangGraph 节点更新机制、字段可选性和持久化要求确定
TypedDict 或其他 Schema 实现。

### 9.4 State 设计要求

-   字段名称和类型明确。
-   节点输入输出有约束。
-   只保存 Workflow 执行必需的数据。
-   避免无必要复制完整个人敏感信息。
-   明确状态更新规则。
-   能关联 task_id、业务对象 ID 和执行标识。
-   对错误和当前步骤有明确表达。
-   对并发更新和恢复场景进行测试。

## 十、Checkpoint 与人工审核机制

### 10.1 Checkpoint 设计

使用 LangGraph Checkpointer 保存 Workflow 中间执行状态。

优先验证 MySQL 持久化方案。当前不将 Redis 作为初期必需依赖。

Checkpoint 主要用于： - 保存执行状态。 - 保存节点执行进度。 -
支持中断后恢复。 - 支持人工审核后继续。 - 支持符合条件的失败恢复。 -
追踪执行历史。

### 10.2 Checkpoint 与业务数据的边界

-   Checkpoint 保存工作流执行状态。
-   业务表保存人才、候选人、测评、筛选结果等业务数据。
-   任务表保存统一任务状态和任务关联。
-   Agent/Workflow 执行记录保存执行元数据和结果关联。

Checkpoint 不能替代业务结果持久化，也不能作为唯一业务审计记录。

### 10.3 MySQL 持久化技术验证

实施前需要验证： - 选定 Checkpointer 实现是否支持目标 MySQL
版本和驱动。 - 表结构初始化和迁移方式。 - 事务行为。 -
并发写入与锁行为。 - Checkpoint 清理和保留策略。 -
服务重启后的恢复能力。 - 人工中断与恢复的正确性。

如果目标实现不兼容，应先评估兼容适配方案或其他持久化方案，不应未经验证直接投入业务。

### 10.4 Human-in-the-loop

关键业务节点支持人工审核、中断、修改和恢复。

适用场景：

  场景       人工参与方式
  ---------- --------------------------
  简历筛选   重要筛选结果复核
  人才匹配   高影响匹配结果确认
  人才画像   关键画像内容审核
  智能测评   异常或争议结果复核
  面试分析   授权人员确认 AI 分析结果
  报告生成   正式报告发布前审核

### 10.5 人工审核流程

``` text
Workflow 执行
      |
      v
到达人工审核节点
      |
      v
保存 Checkpoint
      |
      v
创建人工审核任务
      |
      v
授权人员审核
      |
      +---- 驳回或要求修改
      |
      +---- 审核通过
                |
                v
          校验恢复权限
                |
                v
          恢复 Workflow
                |
                v
             继续执行
```

审核记录应保留审核人、审核时间、审核意见、处理结果和关联执行标识。人工修改应限定允许修改的字段，避免任意改变已完成的历史执行状态。

## 十一、七大业务模块 AI 能力集成

### 11.1 人才选拔

独立能力： - 简历解析。 - 简历智能筛选。 - 岗位人才匹配。

组合流程示例：

``` text
简历上传
    |
    v
文件管理服务
    |
    v
MinerU 文档解析
    |
    v
简历信息结构化
    |
    v
候选人信息校验
    |
    v
简历智能筛选
    |
    v
岗位人才匹配
    |
    v
按规则触发人工复核
    |
    v
保存业务结果
```

要求： - 简历解析、筛选和匹配可独立执行。 - 多个能力可以组合成
Workflow。 - 解析结果、筛选结果和匹配结果分开保存。 - AI
分析不能替代招聘人员最终决策。 -
对影响候选人机会的重要结果提供解释和人工复核渠道。

### 11.2 人才档案与人才画像

建立独立人才画像生成与更新 Workflow。

能力包括： - 人才信息提取。 - 技能归纳。 - 经历总结。 - 人才特征分析。 -
人才画像生成。 - 画像更新。 - 人工审核。

要求： - 原始档案与 AI 画像分开保存。 -
画像记录来源、生成时间和模型/Prompt 版本。 - 画像更新保留历史版本。 - AI
不直接覆盖原始档案。 - 画像访问遵循组织和角色权限。

### 11.3 智能测评与面试

分别建立： - 测评分析 Workflow。 - 面试分析 Workflow。

主要能力： - 测评结果分析。 - 答题表现分析。 - 能力维度分析。 -
面试文本分析。 - 面试评价辅助。 - 综合报告生成。

要求： - 原始答题记录独立保存。 - 面试材料与测评材料分开管理。 - AI
分析结果独立保存。 - 报告关联对应测评任务或面试记录。 - AI
评价不得未经复核直接成为最终录用决定。

### 11.4 AI Agent 与工作流管理

统一管理： - Agent 配置和版本。 - Prompt 模板和版本。 - Tools
注册和权限。 - Workflow 定义和版本。 - Agent 执行记录。 - Workflow
执行记录。 - Checkpoint 查询。 - 执行状态和错误信息。

要求： - 定义与执行分离。 - 执行时记录实际使用版本。 -
配置变更应可审计。 - 未经授权不得调用工具。 - 执行结果可以关联业务任务。

### 11.5 数字员工与任务调度

职责关系：

``` text
数字员工
    |
    v
任务分配与调度
    |
    v
Agent / Workflow
    |
    v
AI 能力执行
    |
    v
任务结果
    |
    v
数字员工任务记录
```

要求： - 数字员工负责业务任务承接与调度。 - Agent 负责专业 AI 能力。 -
Workflow 负责多步骤流程编排。 - 数字员工不直接实现模型推理。 -
Agent/Workflow 执行记录关联业务任务。 - 任务结果统一回传。 -
支持任务状态查询和异常处理。

数字员工、Agent 和 Workflow 是相关但不同的业务对象，不合并为同一资源。

### 11.6 数据智能与运营决策

建立独立数据分析和报告生成 Workflow。

分析范围： - 人才选拔效果。 - 人才结构。 - 测评结果统计。 - Agent
执行情况。 - 数字员工任务执行情况。 - 运营报告。

职责划分：

  工作             责任主体
  ---------------- --------------------
  基础指标计算     后端业务服务
  数据权限过滤     后端权限体系
  统计口径管理     业务服务和指标定义
  数据分析与解释   AI 能力
  报告生成         报告生成 Workflow
  重要业务决策     授权人员

AI 不负责替代确定性统计计算，报告应记录数据来源和生成时间。

### 11.7 用户、组织与权限管理

本模块为所有 AI 能力提供安全基础： - 当前用户身份认证。 -
角色权限检查。 - 组织数据范围控制。 - Agent 和 Tools 调用授权。 -
文件访问授权。 - 人工审核权限。 - 配置变更和关键操作审计。

前端隐藏菜单或按钮不能替代后端授权。RAG
检索和向量查询也必须执行业务数据访问控制。

## 十二、异常处理、重试与降级

### 12.1 统一异常分类

  异常类别         示例                      处理方向
  ---------------- ------------------------- ----------------------------
  模型服务异常     服务不可用、连接失败      按模型策略重试或降级
  模型调用异常     超时、输出不符合 Schema   受控重试或失败
  文档解析异常     文件损坏、解析超时        记录失败原因，按条件重试
  Embedding 异常   向量化失败、维度不符      校验输入和模型配置
  向量检索异常     Milvus 不可用、查询失败   记录检索错误，按策略处理
  Agent 异常       工具失败、模型异常        记录执行失败和上下文
  Workflow 异常    节点失败、状态异常        根据节点和 Checkpoint 处理

### 12.2 重试原则

-   按任务类型制定策略。
-   区分可重试和不可重试错误。
-   设置最大重试次数。
-   记录每次重试原因和结果。
-   对短暂性服务异常可采用退避策略。
-   参数错误、权限错误和不兼容错误不能盲目重试。
-   重试必须考虑幂等，防止重复创建或重复写入。
-   不允许无限重试。

具体重试次数、退避间隔和超时阈值应通过实施测试确定。

### 12.3 Workflow 恢复

-   先读取任务和执行状态。
-   确认 Checkpoint 与 Workflow 版本兼容。
-   检查节点是否已经产生外部副作用。
-   检查恢复用户权限。
-   对可能重复执行的写入操作进行幂等保护。
-   只有满足恢复条件才继续执行。

### 12.4 模型降级

-   模型不可用时按配置选择备用模型或明确失败。
-   备用模型必须满足当前任务所需能力。
-   切换后记录实际模型和版本。
-   不能把不同 Embedding 模型产生的向量视为天然兼容。
-   对工具调用、结构化输出和上下文长度等能力进行兼容性验证。

## 十三、AI 执行监控与日志追踪

### 13.1 统一关联标识

-   日志访问遵循组织权限。
-   对日志保留期限和删除策略进行统一管理。

## 十四、AI 测试与效果评估

### 14.1 分层测试体系

  测试层次     测试内容
  ------------ --------------------------------------------------
  基础组件     模型调用、Prompt 渲染、Embedding、Milvus、MinerU
  Tools        参数 Schema、权限、超时和异常
  Agent        输入输出结构、工具调用和执行结果
  Workflow     节点顺序、条件分支、状态更新和失败处理
  Checkpoint   持久化、中断、服务重启和恢复
  RAG          检索结果相关性、权限过滤和生成质量
  业务效果     简历解析、筛选、匹配、画像、测评和面试分析
  安全与异常   越权访问、重复提交、服务不可用和数据保护
  前后端联调   API 契约、任务状态和人工审核流程

### 14.2 固定样本集与人工标注

建立可重复使用的测试样本集，并由业务人员或具备相应判断能力的人员提供人工标注基准。

重点评估： - 简历字段提取准确性。 - 简历解析完整性。 -
智能筛选结果与岗位要求的一致性。 - 人才匹配结果的合理性。 -
人才画像内容的准确性和可追溯性。 - 测评分析结果的稳定性。 -
面试分析内容的完整性和证据支持。 - RAG 检索相关性和权限过滤正确性。

具体指标、通过阈值和样本规模需要在测试方案中定义，不在总体设计中预设未经验证的数值。

### 14.3 AI 输出评估原则

-   不要求模型自然语言输出逐字固定。
-   对结构化输出验证 Schema 和必填字段。
-   对业务结论验证事实依据和来源。
-   对模型效果使用固定样本集进行对比。
-   对关键业务输出保留人工复核。
-   对模型或 Prompt 更新进行回归测试。
