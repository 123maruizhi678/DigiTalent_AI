## 一、设计目标与范围

本文件明确 AI
数字化人才平台的核心业务对象、对象身份标识、权威数据归属、对象关联关系、生命周期、跨模块数据流转、版本追溯以及删除和归档原则，为下一步数据库总体设计提供业务模型依据。

本步骤定义的是业务对象及其关系，不等同于 MySQL
表结构设计。一个业务对象可以由多张数据表实现；具体字段类型、索引、约束、表拆分和物理存储方案将在数据库总体设计中确定。

### 1.1 业务范围

平台当前包含七大业务模块：

1.  人才选拔。
2.  人才档案与人才画像。
3.  智能测评与面试。
4.  AI Agent 与工作流管理。
5.  数字员工与任务调度。
6.  数据智能与运营决策。
7.  用户、组织与权限管理。

公共业务能力包括文件管理、通知管理、任务记录、操作审计、数据导入导出、通用状态能力和业务事件能力。

当前不纳入业务范围：岗前培养与培训课程、企业知识库。

### 1.2 设计原则

-   业务对象按七大业务模块划分权威归属。
-   每个核心对象拥有独立、稳定的业务标识。
-   候选人与正式人才分开管理，通过关联关系连接。
-   核心对象按业务含义独立建模，不将不同对象简单合并。
-   对象之间通过明确的关联关系协作。
-   跨模块数据通过业务服务接口和必要的业务事件传递。
-   需要追溯的对象保留版本或历史记录。
-   各类对象分别定义生命周期和状态，不强行采用全平台统一业务状态。
-   删除、停用、归档和保留策略按对象类型确定。

### 2.1 候选人转入正式人才档案

候选人通过选拔后，不直接把候选人对象改造成正式人才对象，而是通过明确的业务转入流程创建或关联人才档案。

转入时： - 保留原候选人记录及其选拔过程。 -
创建新的正式人才档案，或在身份核验后关联已有档案。 - 建立 candidate_id
与 talent_id 的关联。 - 记录转入时间、操作来源和处理结果。 -
对疑似重复人才进行身份核验，避免未经确认合并档案。

### 2.2 各对象独立管理生命周期

候选人、招聘需求、测评任务、Workflow
执行实例和数字员工任务等对象分别定义状态。状态名称、状态流转条件和终态规则应由所属业务模块确定，不能以一个全平台通用状态枚举替代所有业务状态。

### 2.3 跨模块数据传递

模块间通过业务服务接口和必要的业务事件传递数据。数据提供方负责提供其权威管理的数据；接收方只获取完成业务所需的数据，不直接修改提供方的核心业务记录。

### 2.4 历史版本与追溯

对简历、人才档案、人才画像、Agent、Prompt、Workflow、测评方案等需要追溯的对象保留版本或历史记录。执行实例应记录实际使用的定义版本，确保历史结果可解释、可复核。

### 2.5 删除、停用与归档

不同对象根据业务属性和保留要求分别制定策略。重要业务记录优先采用逻辑删除或归档；配置类对象可以停用；历史记录不因主对象状态变化而被无条件删除。文件删除还需要检查业务引用和访问权限。

### 2.6 最终评估结论

第五批补齐了前四批尚未明确的生命周期、跨模块数据传递、历史追溯及数据保留规则。第1---30项已覆盖对象范围、身份、属性组织、关联关系、模块归属、状态、流转和验收要求，不需要第六批。

## 五、核心对象关系设计

### 5.1 候选人、人才、岗位和简历

-   一个岗位可以关联多次招聘需求。
-   一个招聘需求可以关联一个或多个岗位候选范围，具体招聘组织规则在后续业务流程设计中确定。
-   一个候选人可以关联多份简历。
-   一个候选人可以产生多条选拔记录。
-   一个正式人才可以关联多个候选人记录。
-   候选人与人才档案通过独立关联对象连接，不合并两个对象身份。

``` mermaid
erDiagram
    POSITION ||--o{ RECRUITMENT : has
    RECRUITMENT ||--o{ SELECTION_RECORD : contains
    CANDIDATE ||--o{ RESUME : owns
    CANDIDATE ||--o{ SELECTION_RECORD : participates
    CANDIDATE ||--o{ CANDIDATE_TALENT_LINK : linked
    TALENT ||--o{ CANDIDATE_TALENT_LINK : linked
    CANDIDATE ||--o{ MATCH_RESULT : evaluated
    POSITION ||--o{ MATCH_RESULT : matched
```

### 5.2 人才档案、经历、技能、标签和画像

-   一个 Talent 可以关联多条 Education。
-   一个 Talent 可以关联多条 WorkExperience。
-   一个 Talent 可以关联多条 ProjectExperience。
-   Talent 与 Skill 通过 TalentSkill 关联。
-   Talent 与 Tag 通过 TalentTag 关联。
-   一个 Talent 可以拥有多个历史 TalentProfile 版本。
-   人才画像应记录来源数据和生成版本。

### 5.3 测评方案、任务、答题、评分和面试

-   一个测评方案可以创建多个测评任务。
-   每个测评任务记录实际使用的测评方案版本。
-   一个测评任务可以关联多条答题记录和评分明细。
-   一个测评任务可以关联多个面试对象。
-   测评报告与测评任务关联。
-   面试报告与面试对象关联。

### 5.4 Agent、模型、Prompt、Tools 与 Workflow

-   Agent 通过关联关系使用模型配置、Prompt 和 Tools。
-   一个 Tool 可以被多个 Agent 复用。
-   一个 Prompt 可以被多个 Agent 复用。
-   一个 Workflow 定义可以产生多次 WorkflowExecution。
-   WorkflowExecution 记录实际使用的 Workflow 版本。

``` mermaid
erDiagram
    AGENT ||--o{ AGENT_MODEL_CONFIG : configured
    MODEL_CONFIG ||--o{ AGENT_MODEL_CONFIG : used
```

## 六、关键业务数据流转

### 6.1 候选人进入平台至建立人才档案

1.  人才选拔模块创建或接收候选人记录，生成 candidate_id。
2.  候选人关联一份或多份简历。
3.  简历文件由公共文件管理能力保存，文档处理能力产生解析结果。
4.  人才选拔模块执行筛选、岗位匹配和选拔流程。
5.  候选人通过相应业务环节后，发起人才档案转入流程。
6.  人才档案模块执行身份核验。
7.  核验后创建新的 talent_id，或关联已有 talent_id。
8.  建立 candidate_id 与 talent_id 的关联，并记录转入时间和来源。
9.  原候选人和选拔记录继续保留。

### 6.2 测评与面试数据流转

1.  人才选拔模块发起测评需求。
2.  测评模块根据测评方案创建测评任务。
3.  测评任务记录方案版本。
4.  候选人完成测评，产生答题记录。
5.  测评模块形成评分结果和测评报告。
6.  如需面试，创建独立面试对象，可关联对应测评任务。
7.  测评模块向人才选拔提供必要状态和结论。
8.  测评模块向人才档案提供授权的测评摘要或报告引用。
9.  完整答题、评分和面试过程仍由测评模块权威管理。

### 6.3 人才画像生成与更新

1.  人才档案模块收集结构化人才信息。
2.  按授权规则关联测评结果摘要。
3.  规则能力处理结构化字段和确定性指标。
4.  Agent 提供经历分析、能力提取和画像总结等智能能力。
5.  形成独立人才画像对象。
6.  保存画像版本、生成时间、来源和人工修订信息。
7.  人工审核或修订后形成新的版本，不覆盖无法追溯的历史记录。

### 6.4 Agent 与 Workflow 执行

1.  业务模块或数字员工模块发起智能能力调用。
2.  Agent 根据其配置关联模型、Prompt 和 Tools。
3.  如需流程编排，调用指定 Workflow 定义和版本。
4.  创建 WorkflowExecution，记录实际使用的版本。
5.  记录节点执行状态和结果。
6.  返回执行结果给调用方。
7.  Agent 或 Workflow 不绕过业务模块直接修改其核心业务数据。

### 6.5 数字员工任务执行

1.  创建独立 Task。
2.  根据任务类型和配置分配数字员工。
3.  记录 TaskAssignment。
4.  调度执行并创建 TaskExecution。
5.  数字员工调用关联的 Agent 或 Workflow。
6.  保存执行结果、失败原因和必要的重试记录。
7.  更新任务状态并按需产生业务事件或通知。

### 6.6 数据智能分析

1.  数据智能模块确定指标定义、口径和统计周期。
2.  通过授权数据服务从各业务模块获取数据。
3.  计算并保存 MetricResult。
4.  根据分析任务生成 AnalysisReport。
5.  报告关联使用的指标及结果。
6.  保存报告版本、生成时间、统计周期和数据口径。
7.  用户查看报告时仍需执行相应数据权限检查。

### 6.7 用户授权与审计

1.  用户通过统一认证能力完成身份认证。
2.  系统根据用户、组织、角色和权限关联计算授权结果。
3.  业务模块在具体资源和数据操作时执行权限检查。
4.  关键操作产生 AuditLog。
5.  角色、组织和权限变更按审计要求保留历史记录。

本步骤确定各对象独立定义生命周期，不在此提前锁定所有状态枚举。详细状态值、流转条件和异常分支在业务流程与数据库设计中继续细化。

  -----------------------------------------------------------------------------------------------------
  对象类别                生命周期管理重点                           权威管理方
  ----------------------- ------------------------------------------ ----------------------------------
  招聘需求                创建、执行、暂停、结束或归档等业务阶段     人才选拔

  候选人                  待处理、筛选、邀请、测评、选拔结论等阶段   人才选拔

  简历                    上传、解析、审核、版本更新和归档           人才选拔；文件本体由文件管理支撑

  人才档案                创建、维护、变更、停用或归档               人才档案

  人才画像                生成、审核、修订、发布和历史追溯           人才档案

  测评任务                创建、待执行、执行中、完成或异常           智能测评

  面试                    创建、安排、执行、评价和完成               智能测评

  Agent                   配置、启用、停用和版本变更                 Agent 管理

  Workflow                定义、发布、停用和版本变更                 Agent 与工作流管理

  Workflow 执行实例       排队、运行、成功、失败或取消等执行状态     Agent 与工作流管理

  数字员工                创建、配置、启用、停用                     数字员工与任务调度

  任务                    创建、分配、执行、成功、失败、取消或归档   数字员工与任务调度

## 九、删除、停用与归档原则

  ----------------------------------------------------------------------------------------------
  对象类型                            建议处理原则
  ----------------------------------- ----------------------------------------------------------
  候选人、选拔记录                    依据业务和合规要求保留；重要过程优先归档而非直接物理删除

  人才档案                            谨慎处理删除请求，按数据保留要求执行停用、归档或受控删除

  简历和文件                          检查业务引用、权限及保留要求后处理文件

  测评答题和报告                      保留历史追溯所需记录，按适用规则处理

  Agent、Prompt、Tool、Workflow       优先停用或发布新版本，不因更新而破坏历史执行记录

  数字员工                            停用后保留必要任务和执行历史

  任务和执行记录                      按任务审计和追溯要求保留或归档

  用户                                优先停用账号和撤销授权，避免破坏历史操作主体关联

  角色和权限                          停用或撤销关联，保留必要授权变更历史

  指标和报告                          停用指标定义或归档报告，保留已产生的历史结果

  通知和审计记录                      按保留策略管理，不因业务对象删除而无条件删除

  业务事件                            保留重要事件及处理结果，按事件保留策略归档
  ----------------------------------------------------------------------------------------------

实际保留期限、物理删除条件、个人信息处理要求和文件清理机制，需结合平台适用的法律法规与组织制度进一步确定，本文件不擅自设定具体期限。

## 十、跨模块数据流转约束

1.  核心业务对象必须明确唯一权威管理模块。
2.  模块之间通过对外业务服务接口共享数据，不直接修改其他模块内部数据。
3.  跨模块传递遵循最小必要原则，只传递业务所需字段或结果摘要。
4.  关键状态变化可通过业务事件通知相关模块。
5.  事件应能关联来源对象、事件类型、发生时间和处理结果。
6.  需要可靠处理的事件应在后续详细设计中确定持久化、重试、幂等和失败补偿机制。
7.  接收模块不得将外部模块传来的数据误认为自身权威数据。
8.  对重要跨模块操作记录发起方、接收方、业务关联 ID 和处理结果。
9.  数据权限检查必须覆盖跨模块读取和分析场景。
10. 本步骤只确定事件机制原则，不据此强制引入消息队列或改变既定模块化分层单体架构。
