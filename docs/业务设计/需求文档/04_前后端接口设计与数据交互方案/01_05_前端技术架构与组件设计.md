本文档依据第四阶段第06步五批共30项确认结果，明确 AI
数字化人才平台前端的整体架构、目录组织、页面布局、路由和菜单管理、状态管理、API

前端覆盖平台七大业务模块：

### 1.3 总体设计原则

-   采用 Vue 3 + TypeScript 模块化单体前端架构。
-   一个前端应用统一运行，初期不采用微前端。
-   前端七大业务模块与后端七大业务模块保持业务对应。
-   页面、业务组件、公共组件和组合式逻辑职责分离。
-   建立统一主布局和独立认证布局。
-   使用 Vue Router 集中管理路由，按业务模块拆分路由配置。
-   统一菜单配置，根据用户权限动态生成可见菜单。
-   使用导航守卫进行路由访问控制。
-   使用 Pinia 管理全局状态，模块状态和页面局部状态按需管理。
-   使用统一 Axios 实例和统一 API 响应规范。
-   建立统一文件上传与下载服务。
-   公共组件分为基础组件和业务通用组件，业务专属组件归属对应模块。
-   前端权限控制不能替代后端认证和授权。
-   采用懒加载、按需加载和合理缓存策略。
-   建立组件、工具函数、页面交互和关键业务流程测试体系。
-   使用 Vite 构建，开发、测试和生产环境配置隔离。

## 三、前端整体架构

### 3.1 架构模式

采用 Vue 3 + TypeScript 模块化单体前端架构：

-   一个前端应用统一运行。
-   七大业务模块独立组织。
-   公共组件和公共能力集中管理。
-   页面通过 API 与 FastAPI 后端协作。
-   初期不采用微前端，避免不必要的工程复杂度。
-   后续是否拆分前端应用，根据实际团队和业务规模决定。

### 3.2 前端总体结构

``` mermaid
flowchart TB
    User[用户浏览器]
    App[Vue 3 应用]
    Router[Vue Router]
    Layout[主布局 / 认证布局]
    Views[七大业务模块页面]
    Components[公共组件与业务组件]
    Stores[Pinia Store]
    API[模块 API]
    Axios[统一 Axios 请求实例]
    Backend[FastAPI 后端]

    User --> App
    App --> Router
    Router --> Layout
    Layout --> Views
    Views --> Components
    Views --> Stores
    Views --> API
    API --> Axios
    Axios --> Backend
```

### 3.3 前端与后端的关系

  前端职责              后端对应职责
  --------------------- ------------------------------
  页面展示和用户交互    业务规则和数据处理
  Vue Router 路由控制   API 认证与授权
  Pinia 状态管理        用户、权限和业务数据服务
  Axios 请求封装        FastAPI API 接口
  TypeScript 类型定义   Pydantic Schema
  文件上传交互          后端文件接收、安全校验和存储
  图表展示              后端统计和分析服务

前端不能代替后端执行业务规则、权限判断和数据完整性校验。

## 五、页面布局与路由管理

### 5.1 整体布局

采用后台管理系统经典布局：

-   顶部导航栏：平台名称、用户信息、通知和快捷操作。
-   左侧菜单：七大业务模块导航，支持折叠。
-   主内容区：展示当前业务页面。
-   页面辅助区域：标题、面包屑和导航标签。

### 5.2 布局组件

  组件               职责
  ------------------ ------------------------------
  `MainLayout.vue`   登录后的平台主布局
  `AuthLayout.vue`   登录、邀请接受等认证页面布局

后续如有独立全屏工作台等需求，再按实际业务扩展布局，不为每个普通页面重复编写布局。

### 5.3 路由组织

-   使用 Vue Router。
-   每个业务模块维护独立路由定义。
-   统一路由入口汇总注册。
-   支持嵌套路由和路由元信息。
-   业务页面按需使用动态导入实现懒加载。

建议路由元信息包括： - 页面标题。 - 是否需要认证。 - 所需权限标识。 -
菜单关联信息。 - 面包屑信息。 - 是否缓存等页面展示配置。

### 5.4 菜单管理

统一菜单配置，支持： - 菜单分组。 - 多级菜单。 - 菜单图标。 -
路由关联。 - 权限关联。 - 根据当前用户权限生成可见菜单。

菜单配置和路由配置应保持一致，避免菜单指向不存在或无权限的路由。

### 5.5 导航守卫

基本访问流程：

``` text
用户访问页面
  -> 判断是否需要认证
  -> 检查当前认证状态
  -> 未认证：跳转登录或认证入口
  -> 已认证：检查页面权限
  -> 无权限：进入无权限页面
  -> 有权限：进入目标页面
```

认证状态失效时，应统一清理或更新前端状态，并按后端认证协议执行重新认证流程。

### 5.6 标题、面包屑和导航标签

通过路由元信息统一管理页面标题、面包屑和导航标签。避免每个页面自行维护重复的导航展示逻辑。

## 六、Pinia 状态管理

### 6.1 全局 Store

建议至少规划：

  Store          职责
  -------------- ----------------------------
  `user`         登录状态、当前用户基本信息
  `permission`   角色、权限标识和可访问资源
  `app`          全局界面状态和系统级配置

### 6.2 状态划分原则

  状态类型                   管理方式
  -------------------------- -------------------------------------
  用户、权限和全局界面状态   Pinia
  多组件共享的模块状态       模块 composables 或必要的模块 Store
  页面临时状态               Vue `ref`、`reactive`
  后端权威业务数据           通过模块 API 获取和更新

不要将所有业务列表、详情和表单数据永久放入全局
Store。需要缓存时，应明确缓存范围、失效条件和刷新策略。

## 七、API 请求与前后端数据规范

### 7.1 统一 Axios 请求实例

建议建立 `src/api/request.ts`，统一配置： - BaseURL。 - 请求超时。 -
请求拦截器。 - 响应拦截器。 - 认证凭据。 - 统一错误处理。

各模块通过独立 API 文件调用统一请求实例。

### 7.2 模块 API 文件

``` text
src/api/modules/
├── candidate.ts
├── talent.ts
├── assessment.ts
├── agent.ts
├── employee.ts
├── analytics.ts
└── system.ts
```

每个 API 文件只负责对应模块的接口调用和类型关联，不在 Vue 页面中直接散落
Axios 请求。

### 7.3 API 响应契约

建议统一响应结构示例：

``` typescript
interface ApiResponse<T> {
  code: string
  message: string
  data: T
  request_id?: string
}
```

分页响应示例：

``` typescript
interface PageResponse<T> {
  items: T[]
  total: number
  page: number
  page_size: number
}
```

以上为前端契约设计示例，最终字段名称、可空性、分页约定和错误编码必须与后端
Pydantic Schema
和统一响应规范逐项对齐，不能未经确认直接视为最终接口标准。

### 7.4 异常处理

  状态或错误   前端处理原则
  ------------ --------------------------
  401          统一处理未认证或认证失效
  403          提示无权限
  404          提示资源不存在
  422          展示参数验证错误
  500          提示服务端异常
  网络异常     提示连接失败
  业务错误     根据业务错误编码进行处理

错误提示应避免重复弹出。内部堆栈、数据库细节和敏感信息不应暴露给普通用户。

### 7.5 文件上传与下载

建立统一文件服务，负责： - 上传请求。 - 下载请求。 - 上传进度。 -
文件类型和大小的前端预检查。 - 上传和下载错误处理。 -
必要的文件元数据类型定义。

适用场景包括简历、人才附件、测评材料和报告。后端必须重新验证文件类型、大小、内容和访问权限，不能信任浏览器提交的文件名或
MIME 类型。

## 十、认证、权限与前端安全

### 10.1 统一认证状态

-   Pinia 统一管理当前认证状态和必要的用户信息。
-   Axios 拦截器按后端认证方案携带认证凭据。
-   路由守卫处理认证状态和页面访问。
-   退出登录时清理前端认证和用户状态。
-   登录失效时统一处理重新认证。

### 10.2 Token 存储与刷新

Token
的存储位置、有效期、刷新方式和撤销策略必须与后端认证方案共同确定。优先评估
HttpOnly、Secure、SameSite Cookie 等机制及其 CSRF 防护要求。

不得在未评估风险的情况下，将长期有效凭据随意存放在可被页面脚本读取的位置。前端不能自行假定后端支持某种刷新协议。

### 10.3 三级权限控制

  权限层级   前端职责
  ---------- ----------------------------------
  路由权限   控制用户是否可以进入页面
  菜单权限   控制用户可以看到哪些导航菜单
  按钮权限   控制用户界面中可见和可操作的功能

敏感数据展示也应遵循最小必要原则。隐藏按钮或菜单不能阻止用户直接构造
HTTP 请求，因此后端必须对每个受保护 API
执行身份认证、权限和数据范围校验。

### 10.4 敏感数据保护

-   不在前端日志中记录密码、Token 和密钥。
-   不将服务端密钥放入 Vite 暴露给浏览器的环境变量。
-   对个人敏感信息按业务授权展示。
-   不将前端校验作为后端安全控制的替代。
-   对敏感操作使用后端审计记录。

## 十一、性能与组件加载优化

### 11.1 路由懒加载

业务页面按需加载，避免初始加载整个七大模块的所有页面代码。

### 11.2 组件按需加载

-   Element Plus 按需加载。
-   大型图表按需初始化。
-   复杂编辑器和预览组件按需加载。
-   避免重复引入大型依赖。

### 11.3 数据和组件缓存

-   根据业务需要决定是否使用页面缓存。
-   明确缓存失效条件。
-   对可能变化的权限和敏感业务数据谨慎缓存。
-   避免重复 API 请求。
-   对长列表采用服务端分页或虚拟滚动等适当方案。

### 11.4 性能验收

具体首屏时间、页面响应时间、资源体积和并发访问目标，应结合部署硬件和实际业务场景在性能测试阶段制定，不在本概要设计中虚构数值。

## 十三、构建、环境配置与部署

### 13.1 Vite 构建

使用 Vite 进行开发和生产构建。生产构建输出静态资源，由实际部署的 Web
服务或静态资源服务提供访问。

不将 Vite 开发服务器作为生产部署方式。

### 13.2 环境配置

建议区分： - `.env.development` - `.env.test` - `.env.production`

环境配置用于管理： - API BaseURL。 - 应用运行环境标识。 -
必要的前端公开配置。

任何会被打包到浏览器端的变量都不应包含数据库密码、模型 API Key
或其他服务端秘密。

### 13.3 前后端访问方式

开发环境可以通过 Vite 代理访问 FastAPI；生产环境应明确静态资源服务与后端
API 的访问地址、反向代理或跨域策略。

具体域名、端口、HTTPS、代理配置和部署服务应在部署设计阶段结合实际环境确定。

### 13.4 构建验收

-   开发环境能够正常启动。
-   测试环境配置正确。
-   生产环境构建成功。
-   静态资源路径正确。
-   API BaseURL 指向对应环境。
-   刷新嵌套路由时能够正确返回前端入口页面。
-   不包含服务端密钥和开发调试信息。
