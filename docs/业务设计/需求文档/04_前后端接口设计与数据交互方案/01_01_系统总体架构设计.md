## 一、设计目标与原则

本文件记录系统总体架构的确认结果，明确前端、后端、业务模块、AI
能力、数据访问、基础设施、部署及运行管理之间的职责边界，为后续业务模块设计、数据设计、接口设计和服务交互设计提供依据。

本步骤确定的是总体架构方向，不代表所有组件均已部署、接入或通过生产验证。

设计原则： 1. 前后端分离，后端采用模块化分层单体架构。 2.
按七大业务模块组织后端代码。 3. API、Service、Repository、AI
能力和基础设施适配职责分离。 4. 模型供应商与 Agent 解耦。 5.
Agent、Workflow、文档处理、RAG、文件存储分别建立清晰边界。 6.
同一后端进程内优先使用进程内调用，独立服务之间通过 HTTP 等接口通信。 7.
当前不引入未经确认或暂不采用的中间件。 8.
区分技术选型、安装、启动、接入和验证状态。

## 四、总体架构决策

### 4.1 架构模式

采用**前后端分离的模块化分层单体架构**： - Vue 前端独立运行和部署。 -
FastAPI 作为统一后端应用入口。 -
七大业务模块在同一个后端应用中按模块组织。 - 后端内部通过 Service
接口协作。 - 暂不拆分为微服务。

## 六、AI 能力架构

### 6.1 模型适配

通过统一模型适配接口管理模型调用。当前模型服务为
Ollama；未来可增加云端模型提供方。Agent 不直接绑定具体供应商。

### 6.2 Agent 管理

Agent
独立实现并统一注册、配置和调用。管理信息可包括标识、名称、用途、能力说明、模型配置、工具、输入输出结构、版本和启用状态。

注册管理不等于必须实现动态插件加载，具体机制留待详细设计。

### 6.3 Workflow 管理

LangGraph 负责具有状态流转、条件分支、多节点协作等需求的工作流。Workflow
可以调用 Agent，但不替代普通业务
Service，也不要求所有业务逻辑都实现为工作流。

### 6.4 文档处理

建立独立文档处理层，通过统一入口识别文件类型并分发到相应解析器。MinerU
作为独立解析服务接入；Markdown、HTML、DOCX
等格式按解析策略配置适配器。输出统一文档结构，再进入清洗、切片等后续处理。

### 6.5 RAG 与向量检索

独立管理 Embedding、Milvus 访问、向量写入与检索、元数据过滤、结果整理和
RAG 上下文组装。业务模块通过服务接口使用检索能力，不直接操作 Milvus
SDK。

## 七、数据、文件与基础设施

### 7.1 MySQL

MySQL 8.0
作为业务关系型数据库，保存用户、组织、岗位、候选人、人才档案、测评、任务及执行记录等结构化业务数据。采用
SQLAlchemy + Repository + Service 分层访问。

### 7.2 Milvus

Milvus
用于向量数据存储和检索。业务实体的权威数据仍由业务数据库或文件存储管理，向量记录通过稳定业务标识关联。

### 7.3 文件存储

文件内容由独立文件存储适配层管理；MySQL
保存文件元数据、存储引用、状态和业务关联。实际介质（本地文件系统或对象存储）、目录、生命周期和备份策略留待详细设计。

### 7.4 适配器

``` text
infrastructure/
├── database/        # MySQL / SQLAlchemy
├── vector_store/    # Milvus
├── model/           # Ollama 或其他模型服务
├── document_parser/ # MinerU HTTP 客户端
└── file_storage/    # 文件存储实现
```

各适配器独立管理连接、配置、超时和异常，避免业务模块依赖底层 SDK 细节。

## 八、通信与异步任务

### 8.1 通信方式

  场景                    方式
  ----------------------- ---------------------------
  Vue 到 FastAPI          HTTP API
  FastAPI 内部模块        进程内 Service / 函数调用
  Service 到 Repository   进程内调用
  Repository 到 MySQL     SQLAlchemy
  AI 层到 Ollama          统一模型适配接口
  文档处理到 MinerU       HTTP API
  检索层到 Milvus         Milvus 适配器
  文件业务到文件存储      文件存储适配接口

### 8.2 异步任务

当前不引入独立消息队列。建立统一任务管理机制，至少记录任务
ID、类型、来源、业务对象标识、状态、创建/开始/结束时间、结果引用、异常摘要和重试信息。

需要在详细设计中解决： - 任务执行器是否独立于 Web 请求进程。 -
并发控制、超时、重试和幂等。 - 服务进程崩溃后的任务恢复。 -
服务重启后的待执行任务扫描。 -
高可靠性任务未来是否需要消息队列或其他持久化执行机制。

**注意：** MySQL
中存在任务记录，不代表任务执行天然具备进程崩溃后的自动恢复能力。当前确认的是暂不引入独立消息队列，不是已经确定具体生产级执行器。

## 九、部署与运行管理

### 9.1 部署边界

前端、FastAPI 和基础技术服务独立部署、独立运行。业务模块仍在同一个
FastAPI 应用中，不因独立部署而拆分为微服务。

  组件         当前技术方案   部署决策
  ------------ -------------- ----------------------
  前端         Vue 3 + Vite   独立运行和构建
  后端         FastAPI        独立 Python 应用进程
  业务数据库   MySQL 8.0      独立数据库服务
  向量数据库   Milvus         Docker Run 独立部署
  模型服务     Ollama         独立模型服务
  文档解析     MinerU         Conda + pip 独立服务
  AI 工作流    LangGraph      集成在后端 AI 能力层

当前不采用 Docker Compose，不使用 Redis，不将 Celery 作为已采用组件。

### 9.2 配置管理

统一配置管理机制建议采用 Pydantic Settings，通过环境变量或 `.env`
注入。配置包括应用参数、数据库、Milvus、模型、MinerU、文件存储、日志和超时等。

第26项选择 B
的含义待进一步澄清。不得在未确认前将其改写为多环境隔离；同时应避免不同环境误用同一业务数据或生产凭据。

### 9.3 敏感信息

-   数据库密码、API Key、访问令牌不得写入源代码。
-   `.env` 应加入 Git 忽略规则。
-   `.env.example` 只保留变量名称和非敏感示例。
-   生产环境通过安全环境变量或密钥管理方式注入。
-   日志不得输出密码和完整令牌。

### 9.4 服务生命周期

各服务独立启停，并提供统一启动、停止和状态检查脚本。总控脚本协调服务，不把多个服务合并到同一进程。

## 十、健康检查

健康检查对象： - FastAPI - MySQL - Milvus - Ollama - MinerU

必须区分应用自身状态和依赖服务状态。检查结果建议包括服务名称、状态、检查时间和必要的异常摘要。FastAPI
本身可用不代表所有依赖服务正常。

前端状态页面应从后端健康检查接口获取真实结果；未接入时明确显示"未连接""未检测"或"演示数据"，不得伪造在线状态。

## 十一、系统边界约束

1.  前端不直接连接 MySQL、Milvus、Ollama 或 MinerU。
2.  API 层不承载复杂业务逻辑。
3.  业务模块不直接操作底层基础设施 SDK。
4.  Agent 不承担全部业务流程管理。
5.  Workflow 不替代普通业务 Service。
6.  Agent、Workflow、数字员工和任务是不同业务对象。
7.  文件内容与业务元数据分开管理。
8.  同一后端进程内的模块优先使用进程内调用。
9.  不因模块化设计而提前拆分微服务。
10. 不未经确认引入 Redis、Celery 或其他中间件。
11. 不把演示数据或模拟执行结果描述为真实运行结果。
12. 如实区分技术选型、安装、启动、接入和验证状态。
