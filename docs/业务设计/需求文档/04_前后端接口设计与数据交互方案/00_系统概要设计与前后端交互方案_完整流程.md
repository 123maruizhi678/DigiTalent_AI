# AI 数字化人才平台

# 第四阶段：系统概要设计与前后端交互方案------完整流程

**文档版本：** V1.0\
**阶段性质：** 系统设计阶段，不直接开展业务功能编码。

## 一、阶段目标

在完成项目需求梳理、技术可行性评估、技术栈与依赖确认、前端原型工程化之后，开展系统概要设计。

本阶段明确前端、后端、数据库、AI
Agent、Workflow、数字员工及基础技术服务之间的职责边界、数据关系和交互方式，为详细设计、开发任务拆分和系统实现提供统一依据。

## 二、阶段输入与约束

### 2.1 主要输入

-   项目定位与用户场景
-   业务对象、功能与流程说明
-   功能范围说明
-   数据设计说明
-   权限设计说明
-   验收标准
-   综合技术可行性评估与方案确认
-   技术栈最终确认成果

-   基础设施、部署方式与环境确认成果
-   前端原型及第二轮优化报告

本阶段应以已确认的原始成果为准。若文件内容与本流程概述不一致，应核对原始成果，不得凭推测覆盖既有决策。

## 四、各步骤详细说明

### 第 01 步：系统总体架构设计

**目标：** 明确系统整体技术架构、分层结构、组件职责和系统边界。

**主要工作：** 1. 梳理前端、后端、数据层、AI 能力层和基础设施层。 2.
明确 Vue 前端与 FastAPI 后端的职责边界。 3.
明确业务服务层、数据访问层、Agent 层和 Workflow 层的职责。 4. 明确
MySQL、Milvus、Ollama、MinerU 等组件的位置。 5.
明确同步调用、异步处理和外部服务调用边界。 6.
识别内部组件与外部服务的依赖关系。 7.
检查架构是否符合已确认技术栈和部署约束。

**待确认重点：** 系统逻辑分层、各层职责、组件边界、前端访问边界、Agent
与 Workflow 的架构位置、文档解析和模型调用方式。

**交付物：**
系统总体架构说明、分层架构图、技术组件关系图、系统边界与职责说明。

**完成标准：**
各层次、核心组件、依赖关系和职责边界明确，无明显职责重复或架构冲突。

### 第 02 步：业务模块与功能边界设计

**目标：** 将七大业务范围落实为系统模块设计，明确模块职责和依赖关系。

**主要工作：** 1. 梳理七大业务模块及其子功能。 2.
明确每个模块的业务入口、主要操作和输出结果。 3. 明确模块内部功能边界。
4. 明确跨模块调用和数据依赖。 5. 识别公共能力，避免重复实现。 6.
检查前端原型、业务需求和模块划分是否一致。

**待确认重点：** 模块功能、模块间交互方式、公共服务、人工审核节点、Agent
辅助与普通业务逻辑的边界。

**交付物：**
七大模块设计说明、模块功能清单、职责边界表、模块依赖关系图。

**完成标准：**
模块职责、功能边界和依赖关系明确，与已确认需求和前端原型一致。

### 第 03 步：核心业务对象与数据流转设计

**目标：** 明确核心业务对象、对象关系、状态变化和业务数据流转过程。

**重点对象：** - 用户、组织、角色 - 岗位、候选人、简历 -
人才档案、人才画像、人才标签 - 测评、试卷、测评结果、面试及面试评价 -
Agent、Workflow、Workflow 节点 - 数字员工、任务、任务执行记录 -
运营指标、统计结果和分析报告

**主要工作：** 1. 梳理核心对象及属性边界。 2.
明确对象之间的一对一、一对多或多对多关系。 3.
明确对象创建、更新、归档和失效等生命周期。 4.
梳理简历上传、解析、结构化、审核到形成档案的过程。 5.
梳理岗位与候选人的匹配过程。 6.
梳理测评、面试及评价结果与人才档案的关联。 7. 明确
Agent、Workflow、数字员工和任务之间的关系。 8.
明确业务数据如何支撑运营分析和决策。

**必须区分的四种对象：** - Agent：具有特定能力的智能体。 -
Workflow：管理多个节点、执行步骤和条件分支的工作流。 -
数字员工：具有角色、能力配置和任务职责的数字化执行主体。 -
任务：需要被执行、调度、跟踪和记录的具体工作。

**交付物：**
核心业务对象清单、对象关系图、关键数据流转图、生命周期说明。

**完成标准：**
核心对象、关联关系、状态变化和跨模块数据流转清晰，可作为数据库和接口设计依据。

### 第 04 步：数据库总体设计

**目标：** 明确数据库职责、核心实体及存储策略。

**主要工作：** 1. 明确 MySQL 与 Milvus 的职责边界。 2.
梳理核心业务实体。 3. 分析实体之间的关系。 4. 确定核心数据持久化方式。
5. 明确简历原始文件、解析结果、结构化数据和向量数据的存储关系。 6.
明确业务数据与向量索引之间的关联标识。 7.
设计必要的创建时间、更新时间、状态和审计字段。 8.
考虑索引、唯一性、事务和数据一致性。 9.
检查数据库设计与权限、数据生命周期是否一致。

**交付物：** 数据库总体设计、数据存储职责划分、核心实体与表清单、ER
图、索引及一致性设计原则。

**完成标准：** 核心对象有明确存储方案，MySQL 与 Milvus
职责清楚，可支持后续详细表结构设计。

**说明：** 本步骤是数据库总体设计，不等同于立即创建全部生产业务表。

### 第 05 步：前后端接口设计

**目标：** 建立 Vue 前端与 FastAPI 后端之间统一、明确的接口契约。

**主要工作：** 1. 梳理七大业务模块需要的接口。 2. 确定 API
路径与命名规范。 3. 确定 HTTP 方法使用规则。 4. 统一请求参数和响应结构。
5. 设计分页、排序、筛选和搜索规范。 6. 设计统一错误码和错误响应。 7.
设计文件上传、下载和解析状态查询接口。 8.
设计身份认证、权限校验和用户上下文传递方式。 9.
明确接口幂等性、超时和重复提交处理要求。 10.
为长时间运行任务设计提交、状态查询和结果获取接口。 11. 建立前端页面、API
函数和后端路由映射关系。

**交付物：** API
设计规范、七大模块接口清单、请求与响应定义、错误码规范、页面与接口映射表。

**完成标准：**
前后端对接口路径、参数、返回值、权限要求和异常处理达成一致，可据此分别开展开发。

### 第 06 步：系统内部服务交互设计

**目标：** 明确 FastAPI
如何协调数据库、文档解析、模型服务、向量检索、Agent 和 Workflow。

**主要工作：** 1. 明确 FastAPI 与 MySQL 的交互方式。 2. 明确 FastAPI 与
Milvus 的交互方式。 3. 明确 FastAPI 与 MinerU 的调用方式。 4. 明确
LangChain 与 Ollama 的调用方式。 5. 明确 LangGraph 与 Agent、Workflow
的关系。 6. 明确数字员工如何使用 Agent 能力和执行任务。 7.
明确长时间运行任务的调度、状态跟踪和结果回传。 8.
明确服务调用超时、失败和重试要求。 9.
明确服务间数据传递和结果持久化方式。

**重点流程：** - 简历上传 → 文件解析 → 结构化处理 → 人才档案。 -
候选人信息 → 岗位要求 → 匹配分析 → 匹配结果。 - 测评任务 →
试卷生成或分配 → 测评执行 → 评分分析。 - 用户请求 → Agent → Workflow →
工具或服务 → 执行结果。 - 任务创建 → 数字员工接收 → 执行 → 结果记录。

**交付物：** 服务交互图、核心调用流程图、异步任务处理方案、Agent 与
Workflow 协作说明。

**完成标准：**
服务调用方、被调用方、输入输出和失败处理边界明确，无明显职责混乱或循环依赖。

### 第 07 步：权限、安全与数据隔离设计

**目标：** 明确用户身份、组织、角色、功能权限和数据访问范围。

**主要工作：** 1. 明确用户身份认证流程。 2.
落实邀请制账号和后台创建用户的要求。 3. 明确用户、组织、角色关系。 4.
明确功能权限和接口权限。 5. 明确行级数据权限。 6. 明确字段级数据权限。
7. 明确简历、人才档案和测评数据的访问控制。 8.
明确文件上传、下载和预览权限。 9. 明确 Agent
及数字员工执行任务时的权限边界。 10. 明确操作审计和敏感数据保护要求。

**交付物：** 身份认证设计、RBAC
权限模型、组织与数据范围设计、行级和字段级权限方案、文件访问控制方案、操作审计设计。

**完成标准：**
用户可访问的功能、数据和操作均有明确规则，前后端权限控制职责清晰，符合已确认需求。

### 第 08 步：异常处理与系统运行机制设计

**目标：** 建立统一的异常处理、任务恢复、日志记录和服务运行机制。

**主要工作：** 1. 设计统一 API 异常响应。 2.
设计数据库连接和事务异常处理。 3. 设计 MinerU 解析失败和超时处理。 4.
设计 Ollama 或模型调用失败处理。 5. 设计 Milvus 连接与检索异常处理。 6.
设计 Agent 执行失败处理。 7. 设计 Workflow 中断和恢复机制。 8.
设计任务超时、重试和失败记录。 9. 区分业务日志、运行日志和审计日志。 10.
明确服务健康检查和运行状态监控方式。 11.
明确关键异常告警和人工介入机制。

**交付物：** 统一异常处理规范、服务超时与重试方案、Workflow
恢复方案、任务失败处理方案、日志与监控设计。

**完成标准：**
关键服务和业务流程发生异常时，系统能够记录原因、反馈状态，并明确重试、恢复或转人工处理方式。

### 第 09 步：系统概要设计整合与评审

**目标：** 整合前八步成果，形成统一的系统概要设计基线。

**主要工作：** 1. 汇总系统总体架构。 2. 汇总七大业务模块及职责边界。 3.
汇总核心业务对象和数据流转。 4. 汇总数据库总体设计。 5. 汇总前后端 API
规范和接口清单。 6. 汇总内部服务交互方案。 7.
汇总权限、安全与数据隔离方案。 8. 汇总异常处理和系统运行机制。 9.
检查需求、架构、数据库、接口和权限的一致性。 10.
识别尚未确认的技术或业务问题。 11. 形成评审结论和后续详细设计任务。

**交付物：**
系统概要设计说明书、总体架构图、模块设计汇总、对象关系图、数据库总体设计、接口总清单、服务交互图、权限与安全设计、异常处理方案、待确认问题清单和评审记录。

**完成标准：**
各项设计互相一致，关键问题有明确结论或待办责任，可作为第五阶段系统详细设计和开发任务拆分依据。

## 五、步骤依赖关系

1.  第 01 步确定总体架构，为后续设计提供技术边界。
2.  第 02 步明确业务模块，为对象、数据库和接口设计提供业务边界。
3.  第 03 步明确核心对象和数据流转，是数据库设计和接口设计的重要输入。
4.  第 04 步与第 05 步分别从数据存储和前后端交互角度展开。
5.  第 06 步基于总体架构、业务对象和数据存储设计服务交互。
6.  第 07 步将权限要求落实到接口、数据和服务调用。
7.  第 08 步为接口、服务和业务流程补充异常与运行机制。
8.  第 09 步统一整合并评审全部设计成果。

第 04 步和第 05 步可以在第 03 步完成后分别推进，但两者必须保持一致。

## 六、统一执行方式

### 6.1 每一步的执行流程

1.  说明当前步骤目标和边界。
2.  列出本步骤全部待确认事项。
3.  每批提供 6 个问题。
4.  用户逐批选择或补充意见。
5.  记录每批确认结果。
6.  完成全部问题后进行整合分析。
7.  生成该步骤的 Markdown 成果文件。
8.  检查文件与既有需求、技术选型是否冲突。
9.  进入下一步骤。

### 6.2 确认原则

-   推荐方案结合当前项目实际环境和已确认决策。
-   不重复询问已经明确确认的内容。
-   不擅自修改已确认的业务范围。
-   不将尚未部署的技术组件描述为已运行。
-   不为增加技术复杂度而引入不必要的中间件。
-   发现需求冲突时先列出冲突，再由用户确认。
-   暂时无法确定的内容标记为待确认，不强行给出结论。
