## 3. Element Plus 组件方案

以 Element Plus 为唯一主要后台 UI 框架。使用表单与校验提示、分页表格、树形组织、菜单、面包屑、对话框、抽屉、上传及消息反馈等能力；表单前端校验改善输入体验，后端仍须校验业务数据。通用业务组件放 components，业务布局放 layouts，不提前封装庞大的通用框架。

**推荐手动按需引入**：在使用处显式导入 ElButton 等组件，并引入对应组件样式；消息、通知等服务式 API 也显式引入及配套样式。图标按名称从 @element-plus/icons-vue 导入，在局部模板中使用，按需用 ElIcon 包装；动态图标通过受控名称映射解析，不遍历注册整个图标集。

无需全局 app.use(ElementPlus)，也无需全局注册所有图标。全量注册加完整样式是可行备选，但会增加初始资源，不作为本项目默认方案。自动按需导入需要额外工具；本阶段不用 unplugin-vue-components、unplugin-auto-import，不修改 Vite/TS 配置。未来若引入自动化工具，另行确认开发依赖、声明文件和样式策略。[Element Plus 官方使用说明](https://element-plus.org/en-US/guide/quickstart.html)

样式统一由 styles 管理：基础重置、主题变量、全局覆盖和布局规则分开；加载顺序为基础样式、组件库样式、项目主题/覆盖，避免懒加载组件样式覆盖项目主题。统一品牌色、语义色、字体、间距与层级；优先 CSS 变量，覆盖选择器保持最小范围。通过 ElConfigProvider 统一中文语言、尺寸等配置。初期不为主题额外引入 Sass，深度编译定制和暗色模式待实际需求确认。

## 4. Vue Router 路由方案

采用按业务域分组的静态路由配置、布局嵌套及组件动态 import 懒加载。先用静态路由配合后端权限码，不引入动态路由管理库，也不让后端返回可执行组件路径。router/index.ts 创建实例；routes.ts 聚合路由，规模增长时在 router/modules 下拆分；guards.ts 只组织访问控制，不直接实现底层 HTTP。

| 分组 | 建议路径 | 组织职责 |
| --- | --- | --- |
| 登录与认证 | /login | 公共认证布局，与业务布局隔离 |
| 人才选拔 | /selection | 选拔流程相关路由 |
| 人才档案与人才画像 | /talent | 档案、画像子路由 |
| 智能测评与面试 | /assessment | 测评、面试子路由 |
| AI Agent 与工作流管理 | /agents | Agent、工作流子路由 |
| 数字员工与任务调度 | /digital-employees | 数字员工、调度子路由 |
| 数据智能与运营决策 | /analytics | 分析与运营子路由 |
| 用户、组织与权限管理 | /system | 用户、组织、角色和权限子路由 |
| 访问异常 | /403、/404 | 无权访问、地址不存在；最终 catch-all 指向 404 |

业务域共享受保护的 layouts 业务布局。meta 规划 title、requiresAuth、permissionCodes、permissionMode（all/any）、hidden 等类型明确的字段。默认业务路由需认证；公共白名单显式列出。嵌套路由沿 matched 逐层检查，避免父子权限字段覆盖导致遗漏；权限码命名与组合规则由后端契约统一。

守卫顺序：公共路由判定 → 等待唯一认证初始化 Promise → 未登录则转登录并记录站内目标地址 → 检查权限 → 允许或转 403。已登录访问 /login 时转向首个可访问业务入口；无任何业务权限则展示无权限结果，避免重定向循环。403/404 不要求业务权限码。返回目标仅允许站内合法路径，拒绝外部 URL、协议相对 URL 和登录循环。

登录恢复期间显示初始化状态，避免页面闪现；初始化失败区分无会话与网络故障，网络故障提供重试。懒加载失败通过 router.onError 提示重试，避免无限刷新；未知路径与权限不足分别处理。导航守卫用于导航流程控制，其机制参考 [Vue Router 官方导航守卫](https://router.vuejs.org/guide/advanced/navigation-guards.html)；上述权限策略为本项目建议。

建议 HTML5 history，未来生产服务器需将前端页面路径回退到 index.html，并将 /api 排除在页面回退外；此项仅记录，不修改部署配置。

## 5. Pinia 状态管理方案

入口后续创建并安装单一 Pinia 实例，再安装路由，确保守卫在组件外访问 Store 时使用正确实例。按职责使用 defineStore、state/getters/actions；共享访问方式依据 [Pinia 官方 Store 说明](https://pinia.vuejs.org/core-concepts/)。

| 规划 Store | 状态与职责 | 清理与持久化 |
| --- | --- | --- |
| auth | Access Token、到期时间、初始化/刷新状态、登录恢复与退出协调 | Token 只在内存，不进入 storage 或日志 |
| user | 用户基本信息、当前组织等后端返回资料 | 会话变化时重置；不持久化敏感档案 |
| permission | 后端角色、权限码；基于路由与权限派生可见菜单 | 登录/组织切换重新获取，退出清空 |
| app | 非敏感系统基础配置、侧栏折叠、主题、跨页面全局 UI 状态 | 仅主题/折叠等非敏感偏好可选择 localStorage |

菜单展开、活动项按路由及 UI 偏好管理，权限菜单优先 getter 派生，避免路由、菜单、权限各维护一份不一致的数据。角色只作展示和粗粒度 UI 辅助，按钮和路由使用后端权限码；数据范围标签可展示，不能据此推断真实可读写数据。

页面筛选、表单、临时弹窗、一次性列表请求结果由组件管理。确有跨页共享需求才引入业务 Store，并明确生命周期。敏感人才数据、Token 和完整认证状态均不做通用持久化；不增加 pinia 持久化插件。退出时重置全部会话相关 Store，避免切换账户后残留上一用户资料。

## 6. Axios 请求封装方案

### 6.1 实例、地址与调用边界

api/request.ts 提供唯一业务 API 实例，api/modules 按业务域封装接口，api/types 定义请求和响应契约。页面不散落创建实例，也不硬编码后端域名。认证刷新使用隔离的轻量实例/传输路径，避免业务响应拦截器再次触发刷新。

建议 baseURL 为 `/api`，模块 URL 写 `/auth/login` 等相对端点，不再重复 `/api`。例如浏览器访问 `/api/auth/login`，当前 Vite 转发至 `http://127.0.0.1:8080/api/auth/login`。代理 target 不应再附加 `/api`。现状与任务目标一致，但后端是否真实挂载 `/api`、是否改为 `/api/v1` 尚待确认；不据此宣称接口可用。Vite 代理只用于开发，生产优先同源反向代理，Vite preview 不替代生产网关。

若未来支持环境变量控制地址，只放公开 API 地址，禁止放任何密钥。业务实例仅访问受控后端，绝不将 Authorization 发送给任意第三方 URL。

### 6.2 请求与响应

- 请求拦截器按端点策略附带 `Authorization: Bearer <Access Token>`；登录/刷新等端点不附过期 Token。附必要的请求标识，禁止日志输出认证头和敏感请求体。
- 普通 JSON 默认建议 15 秒超时；上传、导出和长任务按接口覆盖。长时间 AI 作业优先后端任务 ID 加查询/后续事件协议，不简单无限延长普通请求。
- 响应封装返回类型化结果，统一错误结构保留 HTTP 状态、业务码、信息及追踪 ID；具体响应外层格式等待后端确认，不预设所有接口一定有 code/data/message。分页、空响应、Blob 单独处理。
- 401 进入受控刷新流程；403 展示无权限而不刷新；400/422 显示字段/业务校验；404 显示资源不存在；429 按响应提示限流；5xx 提示服务异常。超时、断网、取消分别识别，取消通常不弹错误。提示只由一层负责，防止页面与拦截器重复弹窗，不直接展示服务端堆栈。
- 不默认自动重试写请求。网络错误或超时不意味着后端未执行，重试必须考虑幂等契约。

Axios 的 baseURL、timeout、withCredentials、paramsSerializer、responseType、signal 等属于请求配置能力，参考 [Axios 官方请求配置](https://axios-http.com/docs/req_config)；以上默认值和错误策略是本项目建议。

### 6.3 文件与取消

上传使用 FormData，浏览器生成 multipart boundary，不手工写死 Content-Type；不强制所有请求使用 JSON。文件类型、大小的前端限制仅作体验校验，后端必须再次验证。下载使用 Blob，解析 Content-Disposition 并清理文件名，创建的对象 URL 使用后释放；Blob 返回错误时按响应类型解析，不误存为文件。跨域读取下载文件名须后端暴露该响应头；大文件/异步导出协议另行设计，暂不加 file-saver。

使用 AbortController/signal 取消离开页面后的请求，以及搜索框旧查询；必要时增加请求序号避免旧结果覆盖新结果。**不做全局无差别重复请求取消**：同 URL 不代表同业务意图，取消也不能撤销服务端操作。按场景用方法、URL、规范化参数及必要请求体识别重复查询；写操作先按钮防重复，关键提交由后端幂等键保障。不为此新增依赖。

## 7. 登录认证与权限配套

### 7.1 Token 保存方式比较

| 方式 | 生命周期 | 安全差异 | 本项目选择 |
| --- | --- | --- | --- |
| 内存（auth Store） | 刷新/关闭页面即丢失 | 活跃 XSS 仍可访问运行状态或代发请求，但不留下长期浏览器存储副本 | 短期 Access Token 推荐位置 |
| sessionStorage | 通常按标签页，刷新保留 | JavaScript 可读，XSS 可窃取；关闭窗口不等于服务端撤销 | 不保存认证凭据 |
| localStorage | 长期、同源共享 | JavaScript 可读，XSS 可窃取且残留时间长 | 不保存认证凭据，仅允许非敏感偏好 |
| HttpOnly Cookie | 由 Cookie 有效期与服务端会话控制 | JS 不能直接读，但浏览器自动携带，需防 CSRF；不能消除 XSS 代发请求风险 | Refresh Token 推荐位置，由后端 Set-Cookie 管理 |

这些存储的安全属性依据 [OWASP 会话管理指南](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。本项目推荐短期 Access Token 保存在内存、Refresh Token 保存在 HttpOnly Cookie；不把 Refresh Token 放响应 JSON、Pinia 或 Web Storage。不额外引入 Cookie 操作包，前端不能也不应设置/读取 HttpOnly 属性。

生产 Cookie 使用 Secure、HttpOnly、合适 SameSite，优先同源部署，按需求评估 Lax 或 Strict；不随意设置宽域 Domain。Path 必须同时覆盖刷新与退出端点，例如契约采用 /api/auth；Path 只减少发送范围，不构成安全隔离。真正跨站才考虑 SameSite=None; Secure，并需评估第三方 Cookie 限制。开发地址为 HTTP，不能假定生产 Secure Cookie 可原样联调，应明确采用本地 HTTPS 或严格隔离的开发 Cookie 策略，不能让开发例外进入生产。

Cookie 刷新、登录、退出等流程由后端校验 Origin/Referer，并按架构落实 CSRF Token 等防护；不能只依赖 HttpOnly 或 CORS。跨域凭据请求需 withCredentials、后端精确允许源和凭据响应，不允许用通配源搭配凭据。默认走同源 /api 代理，Cookie 的 Domain/Path 必须适配浏览器看到的前端源。

### 7.2 生命周期建议

1. **登录**：提交登录请求；后端校验并 Set-Cookie 写入 Refresh Token，返回短期 Access Token。前端仅存内存，再获取当前用户、角色、权限与必要配置。示例 `/auth/login`、`/auth/me`、`/auth/refresh`、`/auth/logout` 均相对 baseURL，未视作已存在接口。
2. **恢复**：页面重新加载后无内存 Token，进入 initializing；调用刷新端点，成功后获取用户与权限。所有守卫等待同一初始化 Promise。刷新返回明确无会话再进入匿名态；网络/5xx 故障展示重试状态，不直接误判会话已过期。
3. **身份认证**：业务请求使用 Bearer Access Token；前端最多根据到期时间提前刷新以改善体验，不签发 JWT，不将本地解码、角色判断或本地缓存视为可信授权。
4. **并发刷新**：可刷新业务请求遇 401 时共享一个刷新 Promise，其他请求等待。刷新成功更新内存 Token，原请求最多重放一次，标记已重放；登录、刷新、退出端点排除递归刷新。仅在后端保证 401 在业务执行前返回、请求可重放时重试写操作，否则提示用户处理，避免重复提交。
5. **失败处理**：刷新明确失效/撤销时清理状态、取消待处理请求、一次性提示并进入登录页。刷新超时/断网不无限循环、不重放队列，保留可重试状态。后端必须支持 Refresh Token 轮换、重用检测及会话撤销；前端不管理签名或刷新令牌库。
6. **退出**：请求后端撤销刷新会话并通过匹配作用域的 Set-Cookie 删除 Cookie；前端清空内存 Token、用户、权限、菜单与敏感缓存。退出失败也清理本地状态，但提示服务端撤销未确认，禁止把本地清理视作完整注销。
7. **竞态处理**：使用会话代次/退出标记，阻止退出或换账户后迟到的刷新/用户请求重新写入 Store。多标签页共享 Cookie 时需用浏览器原生能力协调刷新及退出，例如 Web Locks 和 BroadcastChannel（只传会话事件，不广播 Token），并与后端轮换并发策略配套；单页 Promise 不能解决跨标签页竞态。

### 7.3 RBAC 与数据范围权限边界

路由守卫检查后端权限码；菜单过滤、按钮隐藏/禁用使用同一权限数据和 all/any 规则，不能只过滤菜单而遗漏直接 URL 访问。角色/组织变化后重新拉取权限并刷新界面；任何时刻后端返回 403 都按拒绝处理，不以旧 Store 状态覆盖后端决定。

前端权限逻辑只负责界面和路由体验，用户可修改全部前端状态。接口授权、RBAC、组织/租户边界、记录级数据范围和字段级敏感信息均由后端逐次验证；禁止先拉取全部人才数据再在浏览器筛选，禁止信任前端提交的角色或数据范围。列表、详情、导出、上传和修改接口都需后端独立授权。
