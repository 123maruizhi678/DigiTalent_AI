# 第三阶段：技术栈、依赖与部署方式确认流程

- **项目名称：** 2026 AI 数字化人才平台
- **阶段编号：** 第三阶段
- **文档类型：** 阶段流程与工作计划
- **版本：** V1.0
- **阶段目标：** 将第二阶段已确认的技术可行性结论转化为可执行、可验证、可部署的技术环境基线。
- **工作原则：** 沿用已确认的技术方向；对尚未明确的版本、依赖、兼容性、服务参数和部署细节逐项确认；不把“技术选型已确认”误认为“环境已验证”或“部署已完成”。

---

## 一、阶段背景与目标

第二阶段已完成总体技术架构、基础技术组件、七大业务领域、安全权限、性能及综合技术可行性评估。

第三阶段不重新开展业务技术路线评估，也不随意更换已确认的技术选型。重点是回答以下问题：

1. 每一层具体使用哪些技术、框架和工具？
2. 各技术组件采用什么版本？
3. Python 与前端分别需要安装哪些依赖？
4. 各组件之间是否兼容，如何验证？
5. MySQL、Milvus、Neo4j、Ollama 等基础服务如何安装和运行？
6. 开发环境、测试环境及后续部署环境如何配置？
7. 如何形成可复现的依赖安装、服务启动和部署流程？

本阶段最终形成一套统一的技术栈、依赖版本和部署方案，为后续详细设计及开发提供依据。

## 三、步骤 01：技术栈最终确认

### 3.1 目标

将第二阶段已确认的总体架构和基础组件整理为一份逐项明确的技术栈清单，确认每项技术的用途、边界、当前状态及是否属于当前版本必需组件。

### 3.2 确认范围

1. 前端技术栈：Vue 3、TypeScript、Element Plus 及相关构建工具。
2. 后端技术栈：Python、FastAPI、Pydantic、SQLAlchemy、数据库驱动。
3. AI 技术栈：LangChain、LangGraph、模型适配层、Ollama。
4. 数据存储：MySQL、Milvus、Neo4j、本地文件系统。
5. 文档解析：MinerU 及格式专用解析器。
6. 异步任务：MySQL 任务中心、独立 Worker、APScheduler。
7. 安全与运维：认证授权、日志、配置管理、备份和监控基础能力。

### 3.3 已有技术方向

以下为第二阶段已确认方向，第三阶段需核对其具体版本和实施边界：

| 领域 | 已确认方向 |
|---|---|
| 前端 | Vue 3 + TypeScript + Element Plus |
| 后端 | Python 3.11 + FastAPI |
| 数据校验 | Pydantic |
| ORM | SQLAlchemy |
| MySQL 驱动 | PyMySQL |
| 关系数据库 | MySQL 8.0 |
| 向量数据库 | Milvus 2.6 |
| 图数据库 | Neo4j，按业务模块验证使用范围 |
| 文件存储 | 初期本地文件系统 |
| 文档解析 | MinerU |
| Agent | LangChain |
| Workflow | LangGraph |
| 模型服务 | Ollama + 统一模型适配层 |
| 定时调度 | APScheduler |
| 异步执行 | MySQL 持久化任务表 + 独立 Worker |
| 缓存 | 初期不使用 Redis |
| 独立消息队列 | 初期不引入 |
| 业务对象存储 | MinIO 不作为当前版本强制依赖 |

### 3.4 需要确认的内容

- 每项技术是否继续保留。
- 技术用途和模块边界。
- 具体版本或版本范围。
- 是否为当前版本必需。
- 是否存在备选方案。
- 是否需要进行最小化验证。

### 3.5 完成标准

形成完整技术栈清单，所有技术项均标记为“已确认”“待验证”“暂缓”或“取消”，不得将待验证项写成已验证。

## 四、步骤 02：Python 依赖确认

### 4.1 目标

明确后端和 AI 相关 Python 依赖，建立可复现的 Python 环境及依赖版本约束。

### 4.2 确认范围

1. Python 版本及 Conda 环境。
2. FastAPI 服务依赖。
3. Pydantic 配置与数据校验依赖。
4. SQLAlchemy、PyMySQL 数据访问依赖。
5. LangChain、LangGraph 及模型集成依赖。
6. Milvus 客户端及向量检索依赖。
7. MinerU 调用方式及相关客户端依赖。
8. APScheduler 和 Worker 相关依赖。
9. 日志、配置、测试和开发工具依赖。

### 4.3 重点工作

- 检查已有环境中已经安装的依赖。
- 区分运行时依赖、开发依赖、测试依赖和可选依赖。
- 确认直接依赖与传递依赖。
- 检查依赖版本约束和冲突。
- 确认 GPU、CUDA、PyTorch 等依赖是否与实际模型服务部署方式相关。
- 建立依赖锁定和环境复现方式。
- 明确安装顺序和安装失败时的处理方法。

### 4.4 主要成果

`02_Python依赖确认.md`

内容至少包括：
- Python 版本。
- Conda 环境名称。
- 依赖分类清单。
- 依赖版本及约束。
- 兼容性检查结果。
- 安装命令。
- 环境验证命令。
- `requirements.txt` 或其他锁定文件的维护方式。

### 4.5 完成标准

在指定开发环境中能够按文档安装依赖，依赖检查无未解决冲突，核心模块能够通过导入和最小启动验证。

### 5.2 确认范围

1. Node.js 版本。
2. npm、pnpm 或其他包管理工具。
3. Vue 3。
4. TypeScript。
5. Vite。
6. Element Plus。
7. Vue Router。
8. Pinia。
9. HTTP 请求客户端。
10. 表单、图表、日期和其他业务组件。
11. ESLint、Prettier、类型检查及测试工具。

### 5.3 重点工作

- 确认 Node.js 版本和包管理器。
- 确认核心依赖版本。
- 区分生产依赖和开发依赖。
- 确认锁文件及安装命令。
- 明确前端环境变量。
- 确认开发服务器与 FastAPI 的本地联调方式。
- 确认构建、类型检查和代码规范命令。

### 5.4 主要成果

`03_前端依赖确认.md`

内容至少包括：
- Node.js 版本。
- 包管理器及版本。
- 核心依赖清单。
- 开发依赖清单。
- 版本约束和锁文件。
- 环境变量规范。
- 安装、启动、构建及验证命令。

### 5.5 完成标准

能够从锁定依赖文件恢复前端依赖，成功启动开发服务器并完成生产构建，前端能够与后端开发接口联调。

## 六、步骤 04：基础设施与中间件确认

### 6.1 目标

确认应用运行所需的数据库、向量服务、图数据库、模型服务、文档解析服务及其他基础设施的版本、部署方式和连接参数。

### 6.2 确认范围

| 组件 | 需要确认的内容 |
|---|---|
| MySQL | 版本、端口、数据库、用户、字符集、备份 |
| Milvus | 版本、部署依赖、端口、数据持久化、客户端连接 |
| Neo4j | 是否启用、版本、端口、数据持久化和实际使用范围 |
| Ollama | 版本、模型清单、端口、GPU/CPU 资源使用 |
| MinerU | 版本、服务模式、API 地址、模型和运行资源 |
| 文件系统 | 存储目录、权限、容量、备份和文件安全 |
| Worker | 进程形态、并发、任务状态及日志 |
| APScheduler | 调度进程、任务持久化和多实例防重复机制 |

### 6.3 重点工作

- 区分业务组件与组件自身部署依赖。
- 确认各服务是否本机安装或通过 Docker 运行。
- 明确端口、连接地址和凭据管理方式。
- 明确数据卷、持久化目录和备份范围。
- 明确服务启动顺序及健康检查方式。
- 检查服务之间的网络连通性。
- 验证数据库客户端与服务端版本兼容性。
- 验证 GPU、模型和文档解析资源占用。

### 6.4 主要成果

`04_基础设施与中间件确认.md`

### 6.5 完成标准

每项当前版本必需的基础服务都有明确版本、部署形态、连接配置、数据持久化和健康检查方法；可选组件明确标注是否启用。

## 七、步骤 05：部署方式确认

### 7.1 目标

确定开发环境和后续部署环境中，各应用、数据库、AI 服务和任务执行进程的部署形态及运行方式。

### 7.2 确认范围

1. 前端开发和构建部署。
2. FastAPI 服务部署。
3. MySQL 部署。
4. Milvus 部署。
5. Neo4j 部署及启用条件。
6. Ollama 部署。
7. MinerU 部署。
8. Worker 部署。
9. APScheduler 运行方式。
10. 配置文件、环境变量和密钥管理。
11. 网络、端口、防火墙和服务访问边界。
12. 日志、数据卷、备份和恢复。

### 7.3 重点工作

- 确认开发环境的本地服务与 Docker 服务分工。
- 确认每个服务的启动、停止、重启和健康检查命令。
- 确认 API、前端和基础服务之间的访问地址。
- 确认环境变量和 `.env.example` 管理规范。
- 确认开发、测试和生产环境的配置隔离。
- 确认数据库和文件持久化路径。
- 确认 Worker 与 API 服务的进程隔离。
- 确认日志目录、轮转和异常排查方式。
- 确认部署失败、服务异常和数据恢复处理方式。

### 7.4 主要成果

`05_部署方式确认.md`

### 7.5 完成标准

形成可执行的部署拓扑、配置规范、服务启停流程和故障处理说明。当前开发环境和未来生产环境的差异必须明确标注。

## 八、步骤 06：技术环境与部署方案汇总

### 8.1 目标

将前五步确认结果整合成一份统一的技术环境和部署实施文件，作为开发阶段的执行依据。

### 8.2 汇总内容

1. 最终技术栈清单。
2. Python 及前端依赖版本。
3. 基础设施和中间件版本。
4. 服务部署拓扑。
5. 端口和网络规划。
6. 环境变量及配置规范。
7. 数据持久化和备份方案。
8. 服务启动和停止顺序。
9. 环境验证与健康检查。
10. 常见问题及故障排查。
11. 待验证项和后续优化项。
12. 开发环境与生产环境差异。

### 8.3 主要成果

`06_技术环境与部署方案汇总.md`

必要时同步维护：
- `requirements.txt` 或 Python 锁定文件。
- `package.json` 和前端锁文件。
- `.env.example`。
- 服务启动脚本。
- 部署配置文件。
- 环境检查脚本。

### 8.4 完成标准

- 前五步确认结果已汇总。
- 依赖版本和部署参数没有未解释的冲突。
- 必需服务有明确部署和启动方式。
- 环境变量不包含真实密钥。
- 核心服务具有健康检查和验证方法。
- 所有未验证内容明确标记。
- 开发人员能够按文档复现环境。

## 十一、阶段完成与进入开发的判断

完成本阶段不等于系统已经开发完成，而是开发所需的技术环境和部署基础已经明确。

### 阶段完成检查表

- [ ] 技术栈已逐项确认。
- [ ] Python 依赖和版本约束已确认。
- [ ] 前端依赖和版本约束已确认。
- [ ] 基础设施和中间件版本已确认。
- [ ] 必需服务部署方式已确认。
- [ ] 服务连接地址、端口和持久化目录已确认。
- [ ] 环境变量及密钥管理规范已确认。
- [ ] 关键组件兼容性验证已完成。
- [ ] Python 环境可以复现。
- [ ] 前端环境可以复现。
- [ ] 必需基础服务可以启动并通过健康检查。
- [ ] 最终汇总文件已生成。

### 进入后续开发阶段的条件

满足以下条件后，可以进入详细设计后的分阶段开发：

1. 核心技术栈和依赖版本已锁定。
2. 必需基础服务部署方式明确。
3. 核心组件最小集成验证通过。
4. 开发环境能够复现。
5. 配置、密钥、数据持久化和备份方案明确。
6. 尚未验证的组件和风险均有负责人或后续处理计划。

## 十二、执行规则

1. 按六个步骤顺序推进。
2. 每次集中确认一批问题，避免一次性提出过多问题。
3. 已在第二阶段确认的技术方向不重复讨论，除非发现冲突或兼容性问题。
4. 版本号、端口、目录和命令必须有实际依据，不凭空认定。
5. 每一步确认完成后生成对应 Markdown 成果文件。
6. 发现技术冲突时先列明冲突、影响和候选处理方式，再由用户确认。
7. 用户确认的方案与实际环境验证结果分别记录。
8. 最后生成第六份汇总文件，并检查六份文件之间的一致性。

**阶段最终目标：形成一套版本明确、依赖可复现、服务可启动、部署可执行、风险可追踪的技术环境基线。**
