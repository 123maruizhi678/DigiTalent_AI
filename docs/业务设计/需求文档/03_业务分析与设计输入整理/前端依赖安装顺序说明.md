## 2. 五批准备与验收顺序

以下分批按功能组织确认与检查，不保证 npm 物理安装隔离。完整 package.json 已声明全部22项，npm 安装某一批时可能同时处理其他声明以及 peerDependencies。不要为了实现隔离删除正式清单，也不要把五批验收解释为五次独立解析。建议选版后对完整清单统一安装一次，再按以下顺序验收。

表中 npm ls 检查包是否存在、解析版本与依赖问题；它本身不证明功能正确。第一至三批的运行冒烟检查需已有可用应用入口；本次不创建入口或测试文件。

## 3. 后续统一安装及回归方案

统一选版并更新经确认的版本声明后，在后续授权的首次安装阶段执行 `npm install`（本次不执行）。这一步将解析整份清单并生成 node_modules 和 package-lock.json，必须属于后续阶段的明确范围。保留所确认版本与安装结果，检查锁文件及顶层依赖，没有缺失、无效版本或未满足的 peerDependencies；后续已有锁文件的重复环境安装才考虑 `npm ci`。

按第二节五批顺序执行检查，再完成以下验收：

1. `npm ls --depth=0`：核查顶层直接依赖与22项正式清单一致；传递依赖不加入直接依赖统计。不能仅看终端无报错。
2. `npm run type-check`：确认 app/node 两个引用项目均覆盖；后续可在隔离验证副本对两类文件分别引入临时类型错误，确认能检出后恢复，不污染正式业务代码。
3. `npm run lint` 和 `npm run format:check`：检查现有配置可加载及实际文件结果，不自动运行写入型 lint:fix 或 format，不将失败自动归因于依赖缺失。
4. `npm run test:run`：复用后续已有代表性纯函数/组件用例，核对行为断言及实际用例数量；尚无用例时记录“未具备验收条件”，不得用 passWithNoTests 掩盖或宣称通过。
5. `npm run test:coverage`：核对 V8 provider 加载、text/html/lcov 报告、源码范围与排除项；当前无阈值，不声称已有覆盖率门禁。
6. `npm run build`：检查类型检查及 Vite 打包均完成，查看产物和警告；若入口仍为空，先记录应用实现前提未满足，不擅自扩展任务补代码。
7. 构建成功后 `npm run preview`，人工检查静态页面与资源；开发时用 `npm run dev` 检查开发服务器。preview 不代表生产网关，也不能用来证明 /api 联调成功。

记录每项实际命令、测试数量、结果、失败文件及原因；需要新结果时独立保留，不覆盖已有原始结果。组件真实布局、ECharts 绘图与尺寸变化须在浏览器人工验收，jsdom 断言不能代替；后端契约、权限与业务正确性需后续相应验收。未选版、未安装、入口/用例未就绪均应如实列为限制。
