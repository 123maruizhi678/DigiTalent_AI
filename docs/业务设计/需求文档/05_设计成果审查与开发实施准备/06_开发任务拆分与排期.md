## 一、目标与实施边界

### 1.1 本步骤目标

将系统设计成果拆解为可独立执行、可追踪、可测试和可验收的功能任务，明确：

1. 开发阶段和首期范围；
2. 任务编号、任务粒度和优先级；
3. 数据库、后端、前端、AI及基础设施之间的依赖；
4. 可并行任务及其前置条件；
5. 每项任务的交付物和验收标准；
6. 里程碑、风险和变更管理方式。

### 1.2 七大业务范围

1. 人才选拔；
2. 人才档案与人才画像；
3. 智能测评与面试；
4. AI Agent与工作流管理；
5. 数字员工与任务调度；
6. 数据智能与运营决策；
7. 用户、组织与权限管理。

明确不纳入本项目当前业务范围：岗前培养与培训课程、企业知识库。RAG等技术能力若被业务流程使用，限于已授权的人才业务数据，不据此新增企业知识库业务模块。

### 1.3 开发范围分层

**首期优先形成的业务闭环：**

- 基础平台和公共能力；
- 用户、组织、认证与权限；
- 文件管理和文档解析接入；
- 项目、岗位、招聘需求和候选人；
- 简历上传、解析、智能筛选和人岗匹配；
- 人才主档、经历、技能、标签、画像及审核；
- 与上述闭环直接相关的前端页面、任务状态和测试。

**后续逐步扩展：**

- 智能测评与面试；
- 完整Agent/Workflow管理和执行监控；
- 数字员工与任务调度；
- 数据智能与运营决策；
- 系统管理增强、监控和报表扩展。

后续模块并非取消，而是按依赖和资源条件分阶段交付。

## 三、任务拆分、编号与优先级规则

### 3.1 任务粒度

每项任务应满足：

- 有明确业务目标和范围；
- 有明确输入、前置条件和输出；
- 可由开发人员独立执行；
- 可通过测试或检查验收；
- 有可识别的交付物；
- 不把无关业务对象或多个无法独立验收的功能塞进同一任务。

任务可以跨多个代码文件，但不按单个文件机械拆分。

### 3.2 编号规范

采用：

`P6-{模块代码}-{三位序号}`

模块代码：

| 代码 | 含义 |
|---|---|
| BASE | 项目基础设施与公共能力 |
| IAM | 用户、组织、认证与权限 |
| FILE | 文件管理与文档处理 |
| SEL | 人才选拔 |
| TAL | 人才档案与人才画像 |
| ASM | 智能测评与面试 |
| AI | 模型、Agent、Tools与Workflow |
| DIG | 数字员工与任务调度 |
| DATA | 数据智能与运营决策 |
| FE | 前端工程与页面 |
| QA | 测试、质量和验收 |
| REL | 集成、部署与交付 |

示例：`P6-BASE-001`、`P6-SEL-004`、`P6-FE-003`。

### 3.3 优先级规则

| 优先级 | 含义 | 判定原则 |
|---|---|---|
| P0 | 阻塞性基础任务 | 不完成就无法安全启动后续开发或核心业务 |
| P1 | 首期核心任务 | 直接构成基础平台、人才选拔、人才档案闭环 |
| P2 | 后续业务任务 | 首期闭环后扩展测评、AI管理、数字员工、数据智能 |
| P3 | 增强任务 | 非首期必需的体验、报表、性能或管理增强 |

优先级不是任务状态。任务优先级可因依赖、风险和范围变更调整，调整需记录原因。

### 3.4 复杂度估算

| 等级 | 判断参考 |
|---|---|
| 简单 | 单一职责、依赖少、规则明确、验证方式直接 |
| 中等 | 涉及多个组件或服务，需要接口协作、数据转换或多类测试 |
| 复杂 | 跨模块、AI流程、权限/事务/异步恢复、技术不确定性或复杂集成 |

本计划按用户选择只标记复杂度，不给出未经人员和工程状态校准的开发天数。复杂任务应先做技术验证或拆分子任务。

### 3.5 依赖类型

- **强依赖（FS）：** 前置任务完成后才能开始。
- **弱依赖（SS/接口依赖）：** 可先并行开发，但必须先明确接口、Mock或边界。
- **可并行：** 任务之间无直接阻塞，或共享契约已经稳定。
- **外部条件：** 依赖服务、模型、部署、凭据、样本或业务规则确认。

### 3.6 统一任务状态

建议状态流：

`待开始 → 进行中 → 待联调 → 联调中 → 待测试 → 测试中 → 待验收 → 已完成`

异常状态：`阻塞`。

- 阻塞必须记录原因、影响任务和解除条件；
- 任务从阻塞恢复后回到适当的原工作状态；
- 不能仅因代码提交就标记已完成；
- 已完成任务必须有验收记录或可追踪的测试结果。

## 四、总体开发阶段与里程碑

### 4.1 里程碑总表

| 里程碑 | 阶段 | 主要交付 | 优先级范围 |
|---|---|---|---|
| M0 | 工程启动与基线 | 工程骨架、规范、配置与任务看板 | P0 |
| M1 | 基础平台 | 配置、日志、异常、数据库、认证权限、文件和任务基础能力 | P0 |
| M2 | 人才选拔闭环 | 项目/岗位/招聘需求、候选人、简历解析、筛选、匹配 | P1 |
| M3 | 人才档案与画像 | 人才主档、经历、技能标签、画像生成和审核 | P1 |
| M4 | 测评与面试 | 题库、方案、任务、答题评分、面试和报告 | P2 |
| M5 | AI管理与执行 | 模型适配、Agent、Tools、Workflow、执行监控 | P2 |
| M6 | 数字员工与调度 | 数字员工、能力关联、任务调度和执行管理 | P2 |
| M7 | 数据智能与运营 | 指标、分析任务、驾驶舱和报告 | P2 |
| M8 | 全面集成与验收 | 端到端测试、权限与安全验证、部署和交付 | P0/P1/P2 |

M0至M3构成首期优先交付主线。M4至M7按依赖逐步推进。M8贯穿各阶段并在阶段末完成整体验收。

### 4.2 里程碑验收原则

- M0：工程可启动，质量工具和目录边界明确。
- M1：用户可认证，权限有效，文件和任务公共能力可供业务模块调用。
- M2：从招聘需求到简历解析、筛选、匹配和人工复核形成端到端闭环。
- M3：候选人主体可关联人才主档，人才经历、技能、画像和审核可用。
- M4：测评任务、答题、评分、面试和报告流程可用。
- M5：Agent/Workflow可注册、执行、跟踪和受控恢复。
- M6：数字员工可关联Agent/Workflow并承接任务。
- M7：授权范围内的指标、分析和报告可用。
- M8：关键业务、安全、可靠性和交付检查通过。

```text
M3 人才档案与画像
  ├─ 人才主档/经历/技能/标签

  └─ 数据智能与运营决策

```

### 6.2 可以并行的工作

| 并行组 | 可并行任务 | 并行前提 |
|---|---|---|
| P0工程组 | 后端骨架、前端骨架、开发规范 | 目录和仓库约定先明确 |
| 基础平台组 | 用户/权限模型、文件适配、前端布局 | 公共模型字段和API契约稳定 |
| 人才选拔组 | 项目岗位API、候选人页面、简历解析适配 | 业务对象和接口Mock已确定 |
| AI接入组 | 模型适配、MinerU客户端、向量服务验证 | 配置接口和输入输出Schema明确 |
| 人才档案组 | 经历/技能模型、档案页面、画像Schema | 人才主体ID和数据库字段稳定 |
| 后续业务组 | 测评页面与服务、Agent管理页面、任务中心 | M1公共能力和相关API契约已具备 |

并行不代表可以绕过强依赖。涉及同一数据库表、API Schema或共享组件时，应先约定负责人和变更流程，避免多人同时修改造成冲突。

### 6.3 API契约与Mock先行

前后端并行必须遵循：

1. 从API详细设计确定资源、方法、路径、请求和响应Schema；
2. 将契约落实为OpenAPI或可共享的接口定义；
3. 前端使用与契约一致的Mock数据开发；
4. 后端按同一契约实现；
5. 接口可用后执行契约测试和真实联调；
6. 契约变更时同步更新前端类型、Mock、后端Schema和测试。

若详细设计中的接口路径或字段尚有歧义，先登记接口澄清任务，不得由前端和后端各自猜测。

## 七、核心业务闭环实施顺序

### 7.1 首期闭环一：基础平台与访问控制

```text
用户后台创建/邀请
  -> 登录与JWT认证
  -> 获取当前用户和权限
  -> 菜单/路由按权限展示
  -> 后端资源和数据范围授权
  -> 重要操作审计
```

验收：邀请制策略有效；无权限用户无法通过直接请求访问受限资源。

### 7.2 首期闭环二：简历解析

```text
招聘需求/候选人
  -> 上传简历文件
  -> 文件元数据和文件本体保存
  -> 创建解析任务
  -> Worker调用MinerU
  -> 解析结果校验
  -> 人工确认
  -> 保存最新解析结果
```

验收：文件与业务记录关联正确；任务失败可查询；原始简历不被解析结果覆盖。

### 7.3 首期闭环三：简历筛选与人岗匹配

```text
招聘需求和岗位条件
  -> 选择候选人范围
  -> 提交筛选/匹配任务
  -> AI Workflow执行
  -> 生成结构化结果、依据和差距
  -> 人工复核
  -> 更新选拔业务记录
```

验收：规则和评分口径可追溯；AI建议与人工决定区分；重复提交和失败处理符合幂等规则。

### 7.4 首期闭环四：人才档案与画像

```text
候选人主体
  -> 关联人才主档
  -> 经历/技能/标签维护
  -> 触发画像生成
  -> 生成待审核版本
  -> 人工审核
  -> 发布正式画像
  -> 保留历史版本
```

验收：候选人与人才主体不重复；画像事实、推断和来源有区分；历史版本可追溯。

## 八、数据库、文件、日志和AI基础设施实施约束

### 8.1 数据库实施

- MySQL数据库名：`agent_service`。
- ORM：SQLAlchemy；迁移：Alembic。
- 按数据库详细设计逐步建立公共表和首期业务表。
- 不一次性创建所有后续业务表。
- 不因Agent、Prompt、Tool、Workflow静态定义而新增配置表。
- 人才主档与候选人主体统一；员工身份独立。
- 简历及版本文件化，MySQL保存文件引用和最新解析结果，不建独立简历版本表。
- 教育、工作、项目经历合并为经历表，以类型区分。
- 测评方案保存最新配置，测评任务保存执行时快照。
- 题库与试题统一表；不建立独立试卷表。
- 答题与评分合并；测评报告独立。
- Agent/Workflow执行摘要入MySQL，节点明细进入结构化日志文件。
- 取消Workflow节点执行专用表；Checkpoint独立持久化并专项验证。
- 邀请/登录记录、通知/业务事件/导入导出过程、操作审计和系统日志按已确认决定采用日志文件方式，不额外建立专用数据库记录表。
- 具体DDL实施前仍须进行字段级评审和迁移审查。

### 8.2 文件与日志

- 文件本体首期存本地文件系统，元数据存MySQL。
- 业务模块只通过文件服务访问，不直接拼接物理路径。
- 日志使用结构化格式并按日期滚动，按业务类别和安全审计逻辑分开。
- 日志应包含可关联的request_id、task_id或execution_id。
- 不记录密码、Token、API密钥和不必要的完整个人敏感信息。
- 文件化记录需要验证写入失败、磁盘不足、日志轮转、检索和备份恢复。

### 8.3 AI与向量服务

- 建立统一模型适配层，当前先接入本地Ollama，保留云端适配能力。
- MinerU通过独立HTTP服务接入，不将文档解析逻辑塞入普通CRUD接口。
- LangChain用于模型、Prompt、Tools、Embedding和检索组件集成。
- LangGraph负责Agent/Workflow状态编排、条件分支、Checkpoint和人工审核节点。
- Milvus承担向量存储和相似度检索，不作为业务主数据权威来源。
- Neo4j保留为可选组件，只有明确关系查询需求和收益后再启用。
- Checkpoint持久化、模型切换、并发、效果阈值和资源使用均须在实施中验证。

## 十一、开发排期与里程碑检查点

### 11.1 排期方法

用户选择按里程碑和依赖确定顺序，再根据实际进度细化到周和日期；本文件不虚构具体日期或工期。

每个里程碑开始前：
- 检查前置任务是否完成；
- 检查API契约和数据库字段是否稳定；
- 检查外部服务是否可用；
- 检查任务是否具备明确验收条件。

每个里程碑结束时：
- 执行对应测试；
- 检查未完成任务和阻塞项；
- 检查新增需求和变更；
- 决定进入下一里程碑或调整范围。

### 11.2 无固定缓冲的风险处理

不单独添加固定缓冲时间，但应执行：
- 每个里程碑设置检查点；
- 复杂任务先完成最小技术验证；
- 外部服务问题及时登记为阻塞；
- 优先保证P0和P1任务；
- 发生延期时调整后续任务顺序或版本范围；
- 不压缩必要的安全、数据保护和测试验收活动。

### 11.3 里程碑出口检查表

| 里程碑 | 出口检查 |
|---|---|
| M0 | 后端、前端工程可启动；规范和配置机制可用 |
