## 一、审查目的

本次设计文档一致性检查旨在核对 AI
数字化人才平台已形成的业务、架构、数据、前后端、AI、权限安全和部署设计，识别不同文档之间的冲突、遗漏和表述不统一问题，并通过分批确认形成统一的设计基线。

本步骤重点解决：

1.  不同阶段的技术选型是否一致。
2.  系统总体架构与前后端分层是否一致。
3.  七大业务模块及核心业务对象是否保持统一。
4.  MySQL、Milvus、Neo4j 和文件存储之间的职责是否明确。
5.  API、异步任务、Agent 和 Workflow 的职责边界是否明确。
6.  AI 生成结果与人工最终业务结果是否区分。
7.  权限、安全、审计和数据保护是否覆盖 AI 执行链路。
8.  数据库迁移、工程规范、接口安全和服务部署是否具备可实施性。
9.  历史文档中已废弃或已调整的技术描述是否需要统一修订。

### 1.1 审查原则

-   已确认的用户决策作为本报告的设计基线，不擅自改变。
-   发现冲突时，优先采用后续确认的技术栈和设计决策。
-   不把可选组件写成首期强制依赖。
-   不把设计确认等同于代码实现或测试通过。
-   对尚未完成的文档修订、专项验证和实施细节，列入整改清单。
-   对原始资料未明确的内容，不擅自补充为已确认事实。

**选择A：保持现有方案，补充一致性规则。**

**选择A：保持现有分层。**

**选择A：HTTP + SSE 分工。**

  场景           通信方式

  实时执行进度   SSE

SSE 需要考虑断线重连、状态恢复、消息权限和用户权限撤销后的推送控制。不将
WebSocket 作为默认通信方式。

  技术             职责

  LangGraph        Agent、Workflow、状态流转和 Checkpoint
  MinerU           文档解析
  Milvus           向量存储与检索

保留模型切换、异常处理、重试、幂等和执行记录等后续实施要求。

### 5.5 第11项：核心 AI 业务流程

**选择A：保持现有流程，补充结果确认边界。**

明确区分：

-   AI 生成的草稿。

-   Workflow 执行、停止、重试和恢复均进行权限检查。
-   权限撤销后，运行中的任务在后续敏感操作前重新校验权限。
-   人才个人信息和 AI 处理结果受组织、角色和业务归属约束。

## 八、第五批整合结果：最终冲突收敛与验收

### 8.1 第25项：文件存储方案

**选择A：本地文件系统 + 统一适配层，预留 MinIO。**

最终确定：

-   首期采用本地文件系统。
-   通过统一接口屏蔽文件存储实现。
-   文件元数据由 MySQL 管理。
-   MinIO 作为未来扩展方案。
-   首期不强制部署 MinIO。

### 8.2 第26项：历史技术方案冲突

**选择A：以最新确认的技术栈和设计文档为准，统一修订旧文档。**

历史文档中的旧方案不能继续作为当前技术基线。

重点统一： - Redis 暂不使用。 - Docker Compose 不采用。 - MinerU 使用
Conda + pip。 - Milvus 使用 Docker Run。 -
文件存储首期采用本地文件系统。 - Neo4j 为可选组件。

### 8.3 第27项：Neo4j 定位

**选择A：保留为可选组件，不作为首期强制部署依赖。**

MySQL 继续作为业务权威数据源。Neo4j
只在关系图谱需求得到明确验证后启用，不影响核心业务运行。

### 8.4 第28项：环境配置风险管理

**选择A：保留所有环境配置值相同，增加安全与隔离控制。**

配置值相同的决定保持不变。后续部署时增加： - 配置一致性检查。 -
服务连通性检查。 - 数据访问隔离。 - 部署目标确认。 - 敏感配置保护。 -
防止误操作的部署确认机制。

该决策仍然存在环境资源混用风险，必须在实际部署验证中重点检查。

### 8.5 第29项：多存储一致性

**选择A：MySQL 权威数据源，辅助存储异步同步与补偿。**

最终数据职责：

  组件           职责                   权威性
  -------------- ---------------------- ----------------
  MySQL          业务主数据和关系数据   业务权威数据源
  Milvus         向量数据和检索         辅助存储
  Neo4j          关系图谱               可选辅助存储
  本地文件系统   原始文件和业务附件     文件内容存储
  MinIO          未来对象存储扩展       首期不启用

一致性处理要求： - 业务主数据先在 MySQL 中完成必要的事务提交。 -
辅助存储通过异步机制同步。 - 同步失败需要记录。 - 失败任务支持重试。 -
对无法自动恢复的异常提供补偿处理。 -
删除、更新和重建必须考虑关联数据。 - 辅助存储失败不得错误覆盖 MySQL
中的正式业务数据。

本方案采用可恢复的最终一致性思路，不承诺跨 MySQL、Milvus、Neo4j
的单一强一致性事务。

1.  业务范围与模块职责。
2.  系统总体架构。
3.  核心业务对象。
4.  数据库和文件存储。
5.  后端与前端分层。
