## 一、阶段目标

第五阶段承接第四阶段已经完成的系统概要设计，进一步检查设计成果、补齐可直接用于开发的详细设计，并将设计成果转换为可执行的开发任务和测试验收方案。

本阶段重点完成：

1. 检查业务、架构、数据、接口、AI、安全和部署设计之间的一致性。
2. 明确数据库表、字段、关系、约束、索引及迁移方案。
3. 将 API 总体规范细化为具体接口契约。
4. 将 Agent、Tools 和 Workflow 总体设计细化为可实现的定义、输入输出和执行机制。
5. 将前端总体架构细化为页面、路由、组件和交互设计。
6. 将设计工作拆分为开发任务，明确依赖、优先级和验收条件。
7. 建立覆盖单元、接口、集成、端到端、安全和性能的测试计划。
8. 完成本阶段出口评审，为第六阶段系统开发提供依据。

本阶段以设计、审查、任务规划和测试准备为主，不以完成业务功能代码为目标。

## 二、阶段输入与设计基线

### 2.1 主要输入

- 第一阶段形成的项目需求、功能范围、业务对象和业务流程资料。
- 第二阶段《09_综合技术可行性评估与方案确认》及专项技术评估成果。
- 第四阶段10项系统概要设计成果。
- 第五阶段第01步《01_设计文档一致性检查报告》。
- 当前已确认的技术栈和技术边界。
- 用户在本阶段执行过程中新增的明确决策。

### 2.2 必须保持一致的业务范围

1. 人才选拔。
2. 人才档案与人才画像。
3. 智能测评与面试。
4. AI Agent 与工作流管理。
5. 数字员工与任务调度。
6. 数据智能与运营决策。
7. 用户、组织与权限管理。

当前版本不纳入岗前培养与培训课程、企业知识库。

### 2.3 必须保持一致的技术与架构基线

- 前后端分离。
- 模块化单体业务应用。
- 统一 AI 中台。
- 独立异步任务执行层。
- MySQL 作为核心结构化业务数据的权威来源。
- Milvus 承担向量存储和检索。
- Neo4j 保留为可选组件，不作为首期强制部署依赖。
- 首期采用本地文件系统，通过统一文件存储适配层访问；MinIO 作为未来扩展。
- LangChain 负责模型、Prompt、Tools 等能力集成。
- LangGraph 负责 Agent / Workflow 的状态流转、Checkpoint、中断和恢复。
- Ollama 通过统一模型适配层接入。
- APScheduler + MySQL 任务中心 + 独立 Worker 承担首期任务调度与执行。
- 首期暂不使用 Redis，不强制引入独立消息队列，不采用 Docker Compose。
- MinerU 使用 Conda + pip 方式部署，不采用 Docker 部署。
- 各环境配置值相同的既定决策保持不变；部署时必须增加配置检查、数据隔离、部署目标确认和敏感配置保护。

### 2.4 设计与实现状态区分

- 设计文档完成，不等于代码已经实现。
- 技术选型确认，不等于组件已经完成集成验证。
- 接口契约完成，不等于接口已经开发。
- 测试计划完成，不等于测试已经执行或通过。
- 第五阶段完成，表示具备进入系统开发阶段的设计和计划条件，不表示系统已经具备生产上线条件。

8. Vue、Node.js、npm 和前端依赖。

## 六、第03步：数据库详细设计

### 目标

将第四阶段数据库总体设计和业务对象设计落实为可直接用于 SQLAlchemy 模型、Alembic 迁移脚本和数据库实现的详细结构。

### 主要工作

#### 1. 数据库表清单与模块归属

- 按七大业务模块梳理数据表。
- 识别公共基础表。
- 识别跨模块关联表。
- 明确每张表的业务归属和权威管理模块。
- 区分正式业务数据、AI 草稿、执行记录和审计数据。

#### 2. 字段字典设计

对每张表逐字段定义：

- 字段名称。
- 中文含义。
- 数据类型。
- 长度或精度。
- 是否允许为空。
- 默认值。
- 主键、外键和唯一性要求。
- 是否敏感字段。
- 是否需要脱敏展示。
- 字段来源和业务约束。

#### 3. 主键与关系设计

- 主键生成策略。
- 外键关系。
- 一对一、一对多和多对多关系。
- 唯一约束。
- 非空约束。
- 删除和更新策略。
- 跨模块关联规则。

#### 4. 索引与查询设计

- 高频查询条件。
- 组合索引。
- 唯一索引。
- 排序和分页场景。
- 任务认领与状态查询索引。
- 审计查询索引。
- 避免不必要索引及其写入开销。

#### 5. ER关系设计

- 输出核心业务实体关系图。
- 标记实体之间的基数关系。
- 标记核心业务主数据归属。
- 标记跨模块关联关系。

#### 6. SQLAlchemy 模型映射规范

- 模型文件组织方式。
- 字段类型映射。
- 关系映射。
- 公共字段和时间字段规范。
- 枚举和状态字段管理。
- Repository 层访问边界。

#### 7. Alembic 迁移与初始化策略

- 初始迁移。
- 增量迁移。
- 迁移脚本命名和审查。
- 开发环境初始化。
- 备份和回滚要求。
- 避免手工修改数据库后导致模型与结构不一致。

#### 8. 数据库设计审查

- 业务对象覆盖检查。
- 字段完整性检查。
- 关系和约束检查。
- 索引合理性检查。
- 权限与敏感数据检查。
- 与 API、Agent/Workflow 设计的一致性检查。

### 重点设计约束

- MySQL 是核心结构化业务数据的权威来源。
- Milvus 只承担向量存储和检索，不作为人才正式档案权威来源。
- Neo4j 为可选组件，不作为首期强制依赖。
- 文件本体保存在本地文件系统，文件元数据由 MySQL 管理。
- 辅助存储与 MySQL 之间采用可恢复的异步同步、重试和补偿方式。
- AI 生成草稿与人工确认后的正式业务数据应区分保存。
- 不应把概要设计中的示例表名直接当成最终物理表结构。

### 主要交付物

- 数据库表清单。
- 数据库字段字典。
- 表关系及 ER 图。
- 索引与约束设计。
- SQLAlchemy 模型设计说明。
- Alembic 迁移设计。
- 数据库详细设计文档。

### 完成标准

- 七大业务模块的核心数据对象均有明确存储归属。
- 核心表字段、类型、约束和关系明确。
- 关键查询场景有索引设计依据。
- 数据库模型可以据此实现。
- 数据库设计与业务对象、API 和权限设计不存在明显冲突。

**当前状态：当前进入本步骤。**

## 七、第04步：API 接口详细设计

### 目标

将第四阶段 API 总体规范落实为逐接口的详细契约，使前端、后端和 AI 能力模块可以依据统一定义并行开发和联调。

### 主要工作

#### 1. API 清单与模块归属

按七大业务模块梳理接口，明确：

- 接口名称和用途。
- HTTP 方法。
- URL 路径。
- 所属业务模块。
- 调用方。
- 依赖服务。
- 是否异步。

#### 2. 请求参数设计

明确：

- Path 参数。
- Query 参数。
- Header 参数。
- Request Body。
- 字段类型、长度和格式。
- 必填与可选。
- 默认值。
- 参数校验规则。

#### 3. 响应结构设计

明确：

- 统一响应结构。
- 成功响应字段。
- 分页结构。
- 列表和详情结构。
- 异步任务受理响应。
- 错误响应结构。
- 字段脱敏规则。

#### 4. 认证和权限设计

- 是否需要登录。
- 需要的角色和权限点。
- 数据范围约束。
- 组织归属约束。
- 字段级权限。
- 下载和导出权限。
- Agent/Tool 执行权限。

#### 5. 业务状态与异常设计

- 接口涉及的业务状态。
- 允许的状态转换。
- 重复请求处理。
- 幂等要求。
- 并发冲突处理。
- 超时和重试。
- 业务错误码。
- 外部依赖失败处理。

#### 6. 文件和异步接口设计

- 文件上传、下载和访问接口。
- 文件处理任务创建与状态查询。
- Worker 任务状态查询。
- Agent/Workflow 执行启动、查询、停止和恢复。
- SSE 实时进度推送。
- SSE 断线重连和权限撤销处理。

#### 7. OpenAPI 与接口验收

- 更新 OpenAPI 描述。
- 请求和响应 Schema。
- 接口示例。
- 权限测试要求。
- 错误场景。
- 接口验收条件。

### 主要交付物

- API 接口清单。
- 接口详细设计文档。
- 请求和响应 Schema。
- 错误码清单。
- 权限要求矩阵。
- OpenAPI 规范或对应接口定义。

### 完成标准

- 核心业务功能均有对应接口定义。
- 请求、响应、权限和异常规则明确。
- 前后端对接口字段和状态理解一致。
- 异步任务与 SSE 使用边界明确。
- 接口定义可用于前后端实现和测试。

## 八、第05步：Agent、Tools 与 Workflow 详细设计

### 目标

将第四阶段 AI 能力与 Agent 工作流集成设计、核心 AI 业务流程设计落实为具体可实现的 Agent、工具和 Workflow 规格。

### 主要工作

#### 1. Agent 清单与职责定义

对每个 Agent 明确：

- Agent 名称和唯一标识。
- 业务用途。
- 责任边界。
- 输入参数。
- 输出结构。
- 使用模型。
- Prompt 版本。
- 可用 Tools。
- 权限要求。
- 超时和重试策略。
- 失败处理方式。

#### 2. Tools 详细设计

对每个 Tool 明确：

- Tool 名称和用途。
- 参数 Schema。
- 返回 Schema。
- 允许调用的 Agent。
- 所需权限。
- 数据访问范围。
- 输入校验。
- 执行副作用。
- 幂等要求。
- 超时、异常和审计规则。

Tool 不得仅依靠 Prompt 控制权限，必须由后端执行真实授权和参数校验。

#### 3. Workflow 节点设计

明确：

- Workflow 输入和输出。
- 节点定义。
- 节点执行顺序。
- 条件分支。
- Agent 和 Tool 调用。
- 状态结构。
- 人工审批节点。
- 超时和重试。
- Checkpoint。
- 中断和恢复。
- 失败和补偿处理。

#### 4. 核心 AI 业务流程细化

至少覆盖已确认的主要流程：

- 简历解析 Workflow。
- 简历智能筛选 Workflow。
- 岗位人才匹配 Workflow。
- 人才画像生成与更新 Workflow。
- 智能测评分析 Workflow。
- 面试分析 Workflow。
- 综合报告生成 Workflow。
- 数字员工任务调度与 Agent/Workflow 协作。

#### 5. 模型适配和版本管理

- Ollama 与统一模型适配层。
- 模型名称和版本。
- Prompt 版本。
- Embedding 模型版本。
- 模型切换条件。
- 超时、限流和降级。

## 十、第07步：开发任务拆分与排期

### 目标

将数据库、API、Agent/Workflow 和前端详细设计转化为可执行的开发任务，明确先后依赖和交付要求。

### 主要工作

#### 1. 建立开发工作分解结构

按层次拆分：

- 项目基础设施。
- 后端公共能力。
- 数据库和数据访问。
- 七大业务模块。
- AI 中台。
- Agent、Tools 和 Workflow。
- Worker 与任务调度。
- 前端页面。
- 系统集成。

#### 2. 明确任务依赖

建立依赖矩阵，例如：

- 数据库结构先于依赖该结构的 Repository 和 Service。
- API 契约先于前后端联调。
- 模型适配层先于依赖模型的 Agent。
- Tool 契约和权限设计先于 Workflow 集成。
- 认证和权限基础能力先于受保护业务页面。
- 文件存储适配层先于简历文件业务流程。

#### 3. 明确任务属性

每个任务至少记录：

- 任务编号。
- 任务名称。
- 所属模块。
- 任务描述。
- 前置依赖。
- 优先级。
- 输入和输出。
- 关联设计文档。
- 预计工作量或排期。
- 验收条件。
- 风险和阻塞项。

#### 4. 划分实施批次

建议按依赖关系组织：

1. 基础工程和公共能力。
2. 核心人才业务。
3. AI 能力和工作流。
4. 数字员工与任务调度。
5. 数据智能与运营决策。
6. 全面集成和系统完善。

具体批次和并行安排以实际任务依赖为准。

#### 5. 建立任务跟踪机制

- 任务状态。
- 负责人。
- 开始和结束时间。
- 代码提交或变更记录。
- 测试证据。
- 阻塞和风险。
- 任务验收结论。

### 主要交付物

- 开发工作分解结构（WBS）。
- 开发任务清单。
- 模块依赖矩阵。
- 优先级和排期。
- 任务验收标准。
- 风险与阻塞清单。

### 完成标准

- 每项核心功能均拆分为可执行任务。
- 任务有明确输入、输出和依赖。
- 任务有优先级和验收条件。
- 不存在关键基础能力尚未安排却被业务任务依赖的情况。

## 十五、阶段执行原则

1. 每一步先明确目标、输入、输出和待确认事项。
2. 待确认事项分批提出，每批控制在便于审查的数量范围内。
3. 用户确认后记录决策并完成整合评估，再进入下一批。
4. 不将推荐方案写成用户已经确认的事实。
5. 不将示例表结构、示例字段或示例接口直接视为最终设计。
6. 每一步完成后形成独立 Markdown 成果文件。
7. 后续步骤发现前序设计冲突时，记录影响并按变更流程修订。
8. 设计文档、代码实现和测试验收分别记录状态。
9. 第02步跳过的决定保持有效；只有遇到具体问题时才开展针对性环境核查。
10. 第五阶段完成后，依据开发任务和测试计划进入第六阶段，不提前把详细设计工作混同为业务开发。

**第五阶段的最终目的：让开发人员能够依据明确、统一、可验证的设计文档开展系统开发，而不是在编码过程中临时决定数据库结构、接口字段、权限边界和业务流程。**
