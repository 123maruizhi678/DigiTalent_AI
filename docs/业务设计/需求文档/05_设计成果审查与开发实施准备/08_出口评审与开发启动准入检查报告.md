- Pydantic Schema、OpenAPI与TypeScript同步；

API文档也明确将Token有效期、邀请有效期、限流阈值、文件大小、任务超时、权限枚举和Checkpoint兼容性等留到实施阶段确定，没有虚构固定参数。

### 5.2 安全权限设计完整性

安全文档明确：

- Access Token + Refresh Token认证；
- Refresh Token使用安全Cookie保存，并要求根据部署设置HttpOnly、Secure、SameSite；
- Cookie方式必须设计CSRF防护；
- 管理员创建账号、邀请链接激活，不开放公开注册；
- RBAC结合组织范围和业务对象归属；
- 后端认证中间件、API权限依赖和业务层校验；
- Agent独立授权、Tools白名单和执行前参数/权限校验；
- Workflow查看、执行、管理、停止、重试和恢复权限分离；
- 数字员工不得自行提升权限；
- 人才敏感字段、文件、测评和面试材料分级访问；
- Prompt Injection防护、模型输入脱敏和输出Schema校验；
- 审计日志、密钥管理、备份恢复、安全测试和应急响应。

### 5.3 必须统一：Refresh Token传递方式

**API文档现有表达：**

- 登录响应示例的`data`中包含`access_token`和`refresh_token`字段；
- `/api/v1/auth/refresh`接口说明为使用有效Refresh Token；
- API文档同时指出浏览器端Token存储方式尚需评估。

**安全文档现有表达：**

- Refresh Token通过安全Cookie保存；
- Cookie设置HttpOnly；HTTPS部署时设置Secure；SameSite按部署形态选择；
- 必须设计CSRF防护；
- Refresh Token轮换、撤销和重复使用检测。

**问题：** 如果前端把登录响应体中的`refresh_token`取出并自行保存、传递，就与安全文档规定的HttpOnly Cookie保存方式不一致。HttpOnly Cookie的设计目的正是避免前端脚本直接读取Refresh Token。

**建议统一方案（待用户确认或作为设计修订）：**

1. 登录成功时，响应体只返回Access Token及必要用户信息；
2. Refresh Token通过`Set-Cookie`设置为HttpOnly Cookie，不放入可被前端JavaScript读取的JSON响应体；
3. `/api/v1/auth/refresh`从Cookie读取Refresh Token，并执行轮换；
4. `/api/v1/auth/logout`撤销服务端会话并清除对应Cookie；
5. 对Cookie认证相关请求实施CSRF防护；
6. OpenAPI、Pydantic响应Schema、前端Axios拦截器和认证测试用例同步更新。

在该项统一前，不应同时按两种方式实现。
