## 1. 数据设计目标

明确平台业务数据的范围、归属、数据对象关系、存储分工和主要流转链路，为功能开发、权限控制、Agent 执行及验收提供统一的数据依据。

## 2. 数据存储选型与边界

| 存储组件 | 当前定位 | 主要数据 |
|---|---|---|
| MySQL | 结构化业务主数据库 | 用户、组织、角色、项目、岗位、候选人、人才档案、测评、面试、Agent、Workflow、数字员工、任务及审计记录 |
| Milvus | 向量数据存储 | 人才、简历及岗位向量 |
| Neo4j | 图关系存储 | 人才、技能、岗位之间的关系 |
| MinIO | 对象文件存储 | 简历原文件及相关业务附件 |

**明确的技术边界**

- MySQL 作为结构化业务主数据库。
- 当前不引入 PgSQL。
- 当前暂不使用 Redis，不将 Redis 作为本期缓存、会话或任务队列的前置依赖。
- 原始设计中出现 Redis，不代表本期仍需部署。
- 其他组件的最终部署形态以项目技术架构文件为准。

## 3. 核心业务数据对象

### 3.1 项目与岗位数据

- 项目群
- 项目
- 项目人才需求
- 岗位字典
- 岗位条件
- JD 草稿及发布记录

关系：项目可以独立存在，也可以归属于项目群；项目群可包含多个项目。项目关联一个或多个项目人才需求；一个项目需求可关联多个岗位。不同岗位可共享部分岗位条件，也可配置独立条件。

### 3.2 人才与招聘数据

- 统一人才主档案
- 人员业务身份及身份状态
- 候选人信息
- 员工信息
- 简历原文件及历史版本
- 简历来源、用途及有效状态
- 简历解析任务及重试记录
- 简历结构化解析结果
- 人才与岗位匹配结果
- 候选人邀请记录
- 面试邀约
- 多轮面试记录及结论

一个自然人对应一份人才主档案。候选人和员工身份作为业务身份记录关联该主档案；一个账号同一时点只能对应一种业务身份。候选人录用后账号身份转换为员工身份，保留候选人阶段的历史业务记录。账号业务身份与系统角色分别管理，一个用户可以拥有多个系统角色。

### 3.3 人才画像数据

- 人才能力维度
- 人才标签
- 人才优势
- 待提升项
- 画像生成记录
- 人工调整记录
- 画像依据及关联业务数据
- 画像历史版本、确认记录及变更记录

画像支持 AI 自动生成和人工维护。画像变更应能够追踪生成或修改来源。

### 3.4 测评数据

- 题库
- 试题
- 题目分类及难度
- 试卷
- 答卷
- 评分记录
- 测评结果
- 错题记录

本期不包含错题复习计划。

### 3.5 Agent 与 Workflow 数据

- Agent 注册信息
- Agent 能力描述及状态
- Agent 配置及版本信息
- Workflow 定义及版本
- Workflow 执行实例
- Agent 执行记录
- 工具调用记录
- 模型供应商及模型配置
- 任务触发规则
- 任务执行状态及结果

### 3.6 数字员工与任务数据

- 数字员工基本信息
- 数字员工职责
- 职责流程
- 数字员工与 Agent / Workflow 关联关系
- 任务定义
- 任务触发记录
- 任务执行记录
- 运行异常记录

### 3.7 用户、组织及权限数据

- 用户账号
- 人员身份关联
- 部门及组织关系
- 角色
- 角色与用户关联
- 菜单及功能权限
- 数据范围授权
- 项目授权
- 候选人邀请及失效时间
- 审批记录
- 操作审计日志

## 4. 关键数据关系

1. 项目群与项目：一对多。
2. 项目与项目人才需求：一对多。
3. 项目需求与岗位：多对多或通过需求岗位关联对象实现；一个项目需求可以关联多个岗位，岗位条件允许共享部分配置。
4. 项目人才需求与岗位条件：按业务需求关联，可复用共享条件。
5. 人才主档案与候选人 / 员工身份：一个人才主档案可关联候选人阶段和员工阶段的业务身份记录；一个账号同一时点只能对应一种业务身份，候选人录用后转换为员工身份。
6. 人才与简历：一对多，简历保留来源、用途、有效状态及历史版本。
7. 人才与人才画像：人才可有多次画像生成或更新记录，保留历史版本。
8. 人才与测评结果：一对多。
9. 人才与面试记录：一对多。
10. Agent 与 Workflow：按工作流节点和调用关系关联。
11. 数字员工与 Agent / Workflow：支持一个数字员工关联多个 Agent 或 Workflow。
12. 用户与角色：支持一个用户分配多个系统角色。
13. 用户与业务身份：一个账号同一时点只能对应一种业务身份；身份转换保留历史。
14. 用户与项目授权：支持跨部门项目范围授权及授权期限。

> 上述关系表达业务层面的关联要求，不等同于已经确定的数据库物理表结构、主外键字段或基数约束。物理模型在数据库详细设计阶段确定。

## 5. 数据存储分工

### 5.1 MySQL

存储业务主数据、流程状态和可审计的结构化结果。包括用户组织权限、项目岗位、人才档案、简历解析结果、匹配结果、测评面试、Agent / Workflow、数字员工、任务、邀请及审计数据。

### 5.2 MinIO

存储简历原文件及相关附件。MySQL 保存文件元数据、对象标识、所属业务对象及访问权限关联，不将大文件内容直接作为普通业务字段存储。

### 5.3 Milvus

存储人才、简历及岗位向量，用于相似度检索和人才匹配辅助。向量记录应保留可回查的业务对象标识，不能将向量库作为人才业务主数据来源。

### 5.4 Neo4j

存储人才、技能、岗位之间的关系，用于人才画像及关系分析。图谱节点应能够关联到 MySQL 中的业务主键。

## 6. 主要数据流转

### 6.1 简历解析与人才匹配

简历上传 → 原文件写入 MinIO → MySQL 创建简历记录及解析任务 → 解析能力提取结构化信息 → 解析结果写入 MySQL → 按需要生成向量并写入 Milvus → 岗位匹配 → 匹配结果写入 MySQL。

### 6.2 人才画像

人才档案及业务数据 → 信息整理 → 能力维度分析 → 标签关联 → AI 生成画像 → 人工确认或调整 → 保存画像及版本/变更记录。

### 6.3 测评与面试

题库及试题 → 试卷 → 答卷 → 评分 → 测评结果写入 MySQL → 关联人才档案；面试邀约及多轮面试记录关联候选人和招聘项目。

### 6.4 Agent 与数字员工

Agent 注册及配置 → Workflow 定义 → 数字员工关联职责与 Agent / Workflow → 任务触发 → 执行 → 保存任务状态、工具调用及执行结果。

### 6.5 智能问数

用户自然语言问题 → 身份及数据权限识别 → SQL 生成 → 平台校验 → 受限查询 MySQL 业务数据 → 结果整理及展示 → 保存必要的查询审计信息。

## 7. 数据管理要求

### 7.1 数据准确性与一致性

- MySQL 作为业务主数据来源。
- Milvus 和 Neo4j 中的数据应保留 MySQL 业务对象标识。
- 文件、向量和图关系数据应能够定位其对应业务对象。
- 数据更新、删除或状态变化时，应定义相关存储的同步处理规则。
- 同步失败应能够识别、记录并支持后续处理。

### 7.2 数据安全与隐私

- 按角色、部门、个人和项目授权控制数据访问。
- 候选人简历、联系方式、测评结果等个人信息仅向有权限的人员开放。
- 导出、批量查看和敏感字段访问应纳入权限控制及审计。
- 模型调用前应明确传输数据范围，避免不必要地发送个人敏感信息。
- 密码、模型密钥等敏感配置不得以明文方式暴露。

### 7.3 数据保留、备份、脱敏及删除

按照已确认的分类管理原则，后续需要为不同数据类别分别确定：

- 数据分类及敏感级别。
- 保存期限及到期处理方式。
- 备份频率、备份范围及恢复验证方式。
- 测试数据脱敏规则。
- 个人信息删除或匿名化规则。
- MySQL、MinIO、Milvus、Neo4j 之间的关联数据清理规则。

已确认的数据管理规则：

- 人才档案疑似重复时，由系统识别并提示，HR 确认后合并，不自动无审核合并。
- 人才画像保留所有历史版本，支持查看和追溯。
- 简历原文件及解析结果保留历史版本，并记录来源、用途和解析过程。
- 日志按业务日志、系统运行日志、AI 调用日志、审计日志等类别管理，分别配置访问权限和保留期限。
- 人才档案删除先执行逻辑删除，关联数据进入待清理状态；经规则校验后，统一处理 MySQL、MinIO、Milvus 和 Neo4j 中的关联数据。
- 候选人提出个人信息删除请求时，由管理员审核，按数据类别执行删除或匿名化，并处理各存储中的关联数据。
- 数据每天备份一次，并定期验证恢复能力。

具体保留年限、备份时间窗口、RPO / RTO、恢复演练频率及删除审核流程的细节仍需在数据治理详细设计中确定。

## 8. 当前不纳入的数据能力

- Redis 缓存、会话及队列数据。
- PgSQL 业务数据。
- 错题复习计划数据。
- 岗前培养与培训课程数据。
- 企业知识库数据。

## 9. 数据处理规模基线

- 初期注册用户规模：100 人以内。
- 初期同时在线用户规模：20 人以内。
- 单次批量简历上传最多 20 份。
- 每天执行数据备份，并定期验证恢复能力。

## 10. 数据验收要点

1. 核心业务对象能够正确创建、查询、更新及关联。
2. 候选人和员工能够关联统一人才主档案，同时保留业务身份差异。
3. 简历原文件能够在 MinIO 定位，结构化解析结果能够在 MySQL 查询。
4. 人才、简历及岗位向量能够关联回业务主数据。
5. 图谱节点和关系能够关联回人才、技能及岗位业务对象。
6. 测评、面试结果能够关联正确的人才和项目。
7. Agent、Workflow、数字员工及任务执行记录能够追踪。
8. 候选人邀请记录能够准确保存失效日期和时间。
9. 数据访问符合部门、个人及项目授权范围。
10. 数据更新、删除及跨存储同步异常能够被记录和处理。
