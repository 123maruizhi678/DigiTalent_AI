### 1.3 总体安全原则

-   默认拒绝：没有明确授权就不允许访问。
-   最小权限：用户、Agent、数字员工和服务仅获得完成任务所需权限。
-   后端强制校验：前端隐藏按钮不能代替后端认证和授权。
-   组织隔离：数据访问必须同时考虑组织范围和业务归属。
-   分层防护：身份、权限、数据、文件、AI、日志和运维均建立控制。
-   AI 不拥有隐式权限：模型输出、Prompt 和 Agent 自身不能授予系统权限。
-   不可信输入隔离：简历、HTML、PDF、检索内容和外部文本均视为不可信数据。
-   关键操作留痕：权限变更、敏感数据访问、AI 工具调用和管理操作可追溯。
-   安全配置与代码分离：密钥不写入源代码。
-   可恢复性：关键业务数据和执行状态有备份、恢复和验证方案。
-   人工复核：高风险业务操作按规则进入二次确认或人工审核。
-   隐私保护：只收集和处理业务所需个人信息，限制访问、使用和保留。

## 三、身份认证与账号邀请设计

### 3.1 Token 认证机制

采用 Access Token + Refresh Token。

  --------------------------------------------------------------------------------------------------
  凭证                    用途                    安全要求
  ----------------------- ----------------------- --------------------------------------------------
  Access Token            访问后端 API            短期有效，服务端验证签名、有效期和必要的身份状态

  Refresh Token           更新 Access Token       安全 Cookie 保存，支持轮换、撤销和重复使用检测
  --------------------------------------------------------------------------------------------------

安全要求： - Access Token 不设置为永久有效。 - Refresh Token
应具有明确有效期。 - Refresh Token 每次成功续期后执行轮换。 -
检测到已轮换 Refresh Token 被再次使用时，撤销相关 Token
家族或会话并产生安全事件。 -
用户注销、密码重置、账号停用或管理员安全处置时，可撤销相关会话。 -
Cookie 设置 HttpOnly；HTTPS 部署时设置 Secure；SameSite
根据前后端部署形态选择。 - 采用 Cookie 传递 Refresh Token 时，必须设计
CSRF 防护。 - Access Token
的具体存储方式应结合前端安全架构确定，避免不必要的长期浏览器持久化。

#### R09 认证安全细化（2026-11-04）

Access Token采用HS256 JWT，有效期900秒；固定算法验证iss/aud/sub/sid/iat/exp/jti，并逐请求检查会话撤销和用户启用状态。密钥至少32随机字节，由统一Settings敏感字段提供，无内置生产密钥。JWT及密码库在IAM任务中按现有架构落实，不在R09新增依赖。

Refresh Token为32字节密码学随机不透明值；数据库仅存SHA-256摘要、用户、会话族、代次、创建/绝对到期/消费/撤销时间，摘要唯一索引。登录起7日绝对到期，不滑动延期。事务锁或CAS原子轮换，保留旧摘要到绝对到期，重放撤销整族，无并发宽限；退出先提交撤销再清Cookie，重复退出200。

Cookie：dt_refresh、HttpOnly、host-only、Path=/api/v1/auth、SameSite=Lax，生产Secure=true，本机HTTP开发可false；初始Max-Age=604800，轮换取绝对期限剩余秒数。采用同源反向代理部署；实际生产拓扑待验收。登录/刷新/退出均验证精确白名单Origin和X-CSRF-Protection: 1，缺失/null Origin拒绝，不降级Referer；SameSite仅辅助。禁止通配凭据CORS。可信Origin、密钥等后续统一Pydantic Settings并提供中文说明、环境示例和配置测试。

前端共享刷新Promise、一次重放、generation隔离迟到响应、退出等待在途刷新；跨标签页锁接入前必须补齐。日志只记录必要事件和关联标识，不记录密码、Token或Cookie。字段和接口详见 [R09 API接口契约](../../../开发日记/1104/M1-GATE-R09_API接口契约.md)。上述策略为设计约束，JWT签发、密码验证、数据库与认证API尚未实现。

``` text
       v

       v
```

``` text

       |
       v

       |
       v
```

要求： - 不开放公开注册入口。 -

邀请链接页面显示有效期提示。 -

### 3.4 密码管理

-   使用 Argon2id 等专用密码哈希算法，并配置适当的计算成本。
-   密码不明文存储，不可逆加密不替代密码哈希。
-   设置合理密码长度和常见弱密码拦截策略。
-   支持用户修改密码和管理员发起重置。
-   重置凭证必须一次性且有有效期。
-   密码重置后撤销旧 Refresh Token 和相关会话。
-   不在日志、异常信息或审计详情中记录密码。

## 四、用户、组织、角色与权限模型

### 4.1 核心对象

  对象               职责
  ------------------ ----------------------
  User               用户身份和账号状态
  Organization       组织信息和组织状态
  Role               角色定义
  Permission         可执行的资源操作权限
  UserOrganization   用户与组织的关联
  UserRole           用户与角色的关联
  RolePermission     角色与权限的关联
  UserSession        用户登录会话
  Invitation         用户邀请及激活状态

### 4.2 关系示意

``` text
User
  |
  +---- UserOrganization ---- Organization
  |
  +---- UserRole ------------ Role
                                  |
                                  +---- RolePermission ---- Permission
```

关系设计支持一个用户关联多个组织和多个角色，但具体业务是否开放多组织使用由组织管理策略决定。

### 4.3 RBAC 权限结构

采用 RBAC 作为基础授权模型，并叠加组织范围、业务归属和资源级条件。

权限判断至少考虑：

1.  用户身份是否有效。
2.  用户是否处于启用状态。
3.  用户在目标组织中的关联是否有效。
4.  用户是否拥有对应角色。
5.  角色是否具有目标资源操作权限。
6.  业务对象是否属于用户可访问范围。
7.  是否存在额外的敏感字段或操作限制。

  模块                    权限范围示例
  ----------------------- ---------------------------------------------
  人才选拔                候选人查看、创建、筛选、审核
  人才档案与画像          档案查看、编辑、画像生成和审核
  智能测评与面试          测评任务创建、结果查看、面试分析和审核
  AI Agent 与工作流管理   Agent 查看和配置、Workflow 查看、执行和管理
  数字员工与任务调度      任务创建、分配、停止、查询和数字员工管理
  数据智能与运营决策      指标查看、分析和数据导出
  用户、组织与权限管理    用户、组织、角色、权限和会话管理

权限需要细化到实际 API 和业务服务操作，不能只依赖模块菜单级控制。

## 五、数据范围与敏感信息访问控制

### 5.1 组合授权模型

数据访问采用以下组合条件：

``` text
用户身份
   |
   v
角色与操作权限
   |
   v
组织数据范围
   |
   v
业务对象归属
   |
   v
字段敏感级别
   |
   v
允许访问的数据
```

例如： - 招聘人员只访问被授权招聘业务范围内的候选人。 -
面试官只访问分配给自己的面试任务及必要材料。 -
组织管理员只能管理授权组织范围。 -
普通业务人员不能因为登录系统就访问全部人才数据。

### 5.2 敏感数据分级

  数据类别           访问控制要求
  ------------------ ------------------------------
  普通人才业务信息   按角色、组织和业务归属授权
  联系方式           字段级授权，必要时脱敏显示
  身份证明信息       严格限制访问，非必要不收集
  简历原始文件       按候选人和业务归属授权
  测评结果           限定有业务需要的授权人员
  面试材料           限定面试任务参与者和授权人员
  批量导出数据       单独授权、二次确认和审计

### 5.3 字段级脱敏

-   API 响应根据调用者权限决定返回完整值、脱敏值或不返回字段。
-   脱敏逻辑在后端执行。
-   前端隐藏字段不能作为保护措施。
-   导出接口使用独立权限。
-   日志和错误信息不得意外输出敏感字段。

### 5.4 Milvus 与检索数据权限

-   向量检索必须携带业务对象和组织授权范围。
-   检索结果返回前再次校验访问权限。
-   向量相似度不能替代业务授权。
-   数据删除或权限撤销时，需要考虑同步处理关联向量数据。
-   不允许通过 Agent 或检索接口绕过 MySQL 中的业务授权关系。

## 六、Agent、Tools、Workflow 与数字员工安全

### 6.1 Agent 独立授权

每个 Agent 应定义： - Agent 标识和版本。 -
允许调用的用户、角色或业务服务主体。 - 允许访问的组织和业务范围。 -
允许调用的 Workflow。 - Tools 白名单。 - 允许处理的数据类别。 -
执行记录和审计要求。

Agent
不得自动继承管理员权限。每次调用应能追溯到真实用户或明确授权的服务主体。

### 6.2 Tools 统一注册和执行授权

``` text
Agent 请求调用 Tool
       |
       v
Tool 注册信息检查
       |
       v
识别调用主体与 Agent
       |
       v
检查 Tool 调用权限
       |
       v
参数 Schema 校验
       |
       v
组织与业务数据范围校验
       |
       v
风险等级检查
       |
       v
执行 Tool
       |
       v
记录审计事件
       |
       v
返回结果
```

每个 Tool 应定义： - 唯一标识和版本。 - 输入参数 Schema。 - 输出结果
Schema。 - 所需权限。 - 可访问业务范围。 - 超时和错误处理。 -
幂等要求。 - 是否属于高风险操作。 - 是否需要人工确认。

Prompt 中的工具使用说明不能替代后端权限检查。

### 6.3 Workflow 权限

Workflow 权限至少区分：

  权限   说明
  ------ --------------------------
  查看   查看定义和执行记录
  执行   启动 Workflow
  管理   修改 Workflow 定义或配置
  停止   停止执行任务
  重试   重新执行失败任务
  恢复   从 Checkpoint 恢复任务

Workflow 恢复时还必须检查原任务状态、Checkpoint
关联、恢复人权限和此前是否产生不可重复的外部副作用。

### 6.4 数字员工权限

数字员工只能： - 承接授权范围内的任务。 - 调用允许的 Agent 和
Workflow。 - 访问当前任务所需的业务数据。 -
在授权范围内分配和跟踪任务。 - 返回执行结果和状态。

数字员工不能自行提升权限、扩大组织数据范围或绕过后端业务服务。

### 6.5 高风险操作人工确认

根据操作风险确定二次确认要求，例如： - 批量导出人才数据。 -
修改用户角色或组织权限。 - 删除重要业务数据。 - 修改 Agent 或 Tools
的高权限配置。 - 执行可能产生重大业务影响的批量操作。

人工确认应关联任务、调用主体、操作内容、审核人、审核结果和时间。

## 七、账号保护、会话管理与安全告警

### 7.1 登录失败保护

-   记录失败次数和发生时间。
-   对高频失败请求进行速率限制。
-   达到阈值后执行临时限制。
-   对异常模式生成安全事件。
-   提供管理员查询和处理能力。
-   避免仅根据单个 IP 的异常行为误封整个组织。
-   具体阈值通过测试和风险评估确定。

### 7.2 会话生命周期

会话管理支持： - 登录创建会话。 - Access Token 过期。 - Refresh Token
轮换。 - 用户主动注销。 - 单设备注销。 - 全部设备注销。 -
管理员撤销会话。 - 密码重置后撤销旧会话。 - 账号停用后撤销相关会话。

### 7.3 多设备会话记录

建议记录：

  字段             说明
  ---------------- --------------
  user_id          用户标识
  session_id       会话标识
  device_info      设备信息
  login_ip         登录 IP
  login_time       登录时间
  last_active_at   最后活动时间
  session_status   会话状态
  revoked_at       撤销时间

设备信息应控制采集范围，避免不必要的设备指纹追踪。

### 7.4 安全事件监控

监控场景包括： - 连续登录失败。 - 异常设备或地点登录。 -
可疑会话活动。 - 短时间大量访问敏感数据。 - 角色变更和权限提升。 -
异常批量导出。 - 管理员高风险操作。 - Refresh Token 重复使用。 - Agent
或 Tools 异常调用。

安全事件需要记录等级、发生时间、关联主体、事件类型、处理状态和处理结果。

## 八、数据加密、文件安全与个人信息生命周期

### 8.1 数据加密

-   前后端通信使用 HTTPS。
-   数据库和文件存储按部署能力启用静态加密。
-   对高敏感字段按风险实施应用层加密。
-   密钥与业务数据分离。
-   密钥不写入 Python 源代码或版本控制。
-   限制密钥读取权限。
-   建立密钥轮换和变更审计。
-   加密算法、密钥长度、轮换周期和密钥托管方式在部署安全设计中确定。

### 8.2 文件上传安全

支持的文档类型包括 Markdown、PDF、DOCX 和 HTML 等经业务允许的格式。

统一处理流程：

``` text
文件上传
   |
   v
身份与业务权限检查
   |
   v
文件大小和扩展名检查
   |
   v
真实文件类型识别
   |
   v
文件名与路径安全处理
   |
   v
内容检测和恶意文件扫描
   |
   v
隔离存储
   |
   v
授权解析与业务处理
```

要求： - 检查扩展名与文件实际格式是否一致。 -
限制文件大小和必要的资源消耗。 - 防止路径穿越和危险文件名。 -
对压缩文件等特殊格式设置解压限制（如业务允许）。 -
恶意文件扫描失败时按安全策略拒绝或隔离。 - 文件存储目录与 Web
可执行目录隔离。 - 下载通过后端授权接口完成。 -
文件物理路径不直接暴露给用户。 - MinerU
只负责解析，不负责替代上传安全、恶意文件扫描和访问控制。

### 8.3 个人信息生命周期

``` text
收集
  ↓
使用
  ↓
授权访问
  ↓
保留与归档
  ↓
删除或匿名化
  ↓
记录处理审计
```

要求： - 明确每类个人信息的业务目的。 - 只收集业务必要信息。 -
按角色、组织和业务关系限制访问。 - 对不同数据类型设置保留策略。 -
处理删除请求时检查关联文件、测评、面试、报告和向量数据。 -
对依法或按业务规则需要保留的数据，按规定限制访问并记录原因。 -
删除和匿名化操作必须记录审计。 - 不因删除主档案而遗漏文件存储、Milvus
或其他关联副本。

### 8.4 数据删除与关联清理

删除人才数据时应识别： - MySQL 主记录和关联记录。 - 原始简历文件。 -
面试材料。 - 测评和报告数据。 - Milvus 向量及关联元数据。 -
缓存或临时文件（如未来引入）。 - 备份中的数据及其到期清理策略。

具体删除顺序、事务边界和备份到期处理需要在数据设计与运维方案中确定。

## 九、AI 输入输出安全与 Prompt Injection 防护

### 9.1 模型调用数据安全

``` text
业务请求
   |
   v
用户身份与权限校验
   |
   v
Agent 任务授权
   |
   v
读取授权业务数据
   |
   v
敏感信息识别与必要脱敏
   |
   v
LLM / Embedding 调用
   |
   v
输出安全检查
   |
   v
Schema 校验
   |
   v
业务规则与权限校验
   |
   v
保存或返回结果
```

要求： - 模型只能接收完成当前任务所需的数据。 -
不得将全部人才数据默认发送给模型。 -
云端模型调用前评估数据处理、传输和供应商策略。 -
记录模型、调用主体、任务和结果状态。 -
对模型输出中的敏感信息进行检查。 -
模型输出不得直接执行未经授权的业务操作。 -
需要保存模型输入输出时，按数据分类和保留策略处理。

### 9.2 Prompt Injection 防护

外部内容包括： - 简历正文。 - PDF 文本。 - DOCX 内容。 - HTML 页面。 -
用户上传的其他文档。 - 外部检索结果。 - 工具返回内容。

以上内容统一视为不可信数据。

防护要求： 1. 系统指令、开发者指令和业务数据分层传递。 2.
使用明确的数据边界标记外部文档内容。 3.
不因文档中出现"忽略之前指令"等文字就改变系统行为。 4. Agent
只获得任务所需的 Tools 白名单。 5. Tool
执行前由后端检查权限、参数和数据范围。 6. 对高风险操作执行人工确认。 7.
对模型输出进行 Schema、业务规则和敏感信息检查。 8.
记录可疑输入和安全处置结果，但避免在日志中复制不必要的敏感原文。

### 9.3 AI 输出校验

-   结构化输出必须符合指定 Schema。
-   字段类型和必要字段进行校验。
-   缺失信息应标记为未知或缺失，不得编造。
-   AI 推断与原始事实分开记录。
-   评分和确定性业务规则由规则模块执行。
-   模型不得通过输出文本自行声明已获得授权。
-   关键业务决定保留人工复核渠道。

## 十、统一审计日志设计

### 10.1 审计范围

  审计类别       主要事件
  -------------- ----------------------------------
  用户认证       登录成功、失败、注销、密码重置
  邀请管理       创建邀请、重发、过期、激活
  用户与组织     用户创建、停用、组织关联变更
  权限管理       角色变更、权限授权和撤销
  敏感数据访问   敏感字段查看、文件下载、数据导出
  Agent          Agent 调用、版本、调用主体和结果
  Tools          工具调用、权限检查、执行结果
  Workflow       启动、停止、失败、重试和恢复
  数字员工       任务创建、分配、调度和取消
  系统管理       配置变更、密钥管理操作和安全处置
  数据生命周期   数据归档、删除和匿名化

### 10.2 审计事件基础字段

建议包含：

  字段              说明
  ----------------- -------------------------------
  audit_id          审计事件标识
  event_type        事件类型
  actor_type        用户、服务或 Agent 等主体类型
  actor_id          操作主体标识
  organization_id   组织标识（适用时）
  action            执行动作
  resource_type     资源类型
  resource_id       资源标识
  request_id        请求链路标识
  task_id           业务任务标识（适用时）
  execution_id      Workflow 执行标识（适用时）
  result            操作结果
  occurred_at       发生时间
  source_ip         来源 IP（适用时）
  detail_summary    脱敏后的事件摘要

具体字段和索引在数据库详细设计阶段确定。

### 10.3 日志安全

-   审计日志与普通应用运行日志区分。
-   普通业务用户不能修改或删除关键审计日志。
-   审计日志访问本身也需要授权和记录。
-   对关键日志实施完整性校验和防篡改保护。
-   敏感字段、密码、Token、密钥不写入日志。
-   记录必要的事件摘要，不默认保存完整模型上下文或完整个人信息。
-   关键审计记录可采用独立存储、只追加策略或完整性校验机制。
-   日志保留期限按类别和业务要求配置。

### 10.4 日志查询与追踪

支持按以下维度查询： - 时间范围。 - 用户或服务主体。 - 组织。 -
事件类型。 - 资源类型和资源标识。 - request_id。 - task_id。 -
execution_id。 - 操作结果。

审计查询必须遵守组织和审计权限范围。

## 十一、系统配置与密钥管理

### 11.1 配置分类

  配置类别   示例                         管理要求
  ---------- ---------------------------- --------------------
  普通配置   服务端口、日志级别           配置文件管理
  环境配置   开发、测试、生产环境         按环境隔离
  敏感凭证   MySQL 密码、模型 API Key     安全存储和访问限制
  加密密钥   字段加密密钥、文件加密密钥   专门密钥管理和轮换
  签名密钥   Token 签名密钥               限制访问并支持轮换

### 11.2 当前开发环境要求

-   开发环境可使用 `.env` 保存本地敏感配置。
-   `.env` 必须加入 Git 忽略规则。
-   `.env.example` 只保留变量名称和非敏感示例值。
-   禁止在日志和终端输出真实密码、Token 和密钥。
-   禁止将真实密钥写入源代码、测试样例或文档。
-   生产环境优先使用专门的 Secret/密钥管理方案。
-   配置变更需要记录操作主体和变更时间。

### 11.3 密钥轮换

-   明确密钥用途、所有者和使用服务。
-   轮换前验证新密钥可用。
-   支持平滑切换和必要的旧密钥失效。
-   对 Token 签名密钥轮换制定兼容窗口和撤销策略。
-   对加密数据密钥轮换制定重新加密或密钥封装策略。
-   记录密钥轮换事件，不记录密钥内容。

## 十二、备份与灾难恢复设计

### 12.1 备份范围

  组件              备份内容
  ----------------- ----------------------------------------
  MySQL             业务数据、账号权限、任务和审计元数据
  Milvus            Collection 数据、索引及必要元数据
  文件存储          简历原件、面试材料、业务附件和报告文件
  Workflow 持久化   Checkpoint 和必要的执行恢复数据
  系统配置          非秘密配置、部署配置和恢复所需配置
  密钥材料          按密钥管理策略安全备份或托管

### 12.2 备份原则

-   根据数据重要性制定备份频率。
-   区分全量和增量备份（如组件支持）。
-   备份文件应限制访问并进行必要加密。
-   备份存储与运行数据适当隔离。
-   记录备份时间、范围、结果和校验信息。
-   失败备份产生告警。
-   对备份介质和历史版本实施保留期限管理。
-   备份密钥和恢复凭证不能与备份数据无保护地放在同一位置。

### 12.3 恢复验证

恢复演练应覆盖： 1. MySQL 数据恢复。 2. Milvus 数据恢复。 3.
原始文件恢复。 4. Workflow Checkpoint 和必要执行状态恢复。 5. 配置恢复。
6. 关联数据一致性检查。 7. 服务启动和健康检查。 8. 关键业务流程验证。

不能只验证备份命令成功，必须实际执行恢复测试。

### 12.4 RPO 与 RTO

恢复点目标（RPO）和恢复时间目标（RTO）需要根据业务重要性、数据变化频率、存储能力和本地硬件条件确定。本文件不预设未经验证的具体数值。

## 十三、安全测试与漏洞管理

### 13.1 测试范围

  测试类别        重点内容
  --------------- ------------------------------------------
  依赖安全        Python 包、系统组件和容器镜像漏洞
  身份认证        Token 验证、过期、轮换和撤销
  登录保护        暴力破解、频率限制和异常会话
  API 安全        未授权访问、越权、参数校验和注入
  RBAC            角色权限和组织范围校验
  数据安全        敏感字段泄露、数据导出和删除
  文件安全        文件类型伪装、恶意文件、路径穿越
  Agent 安全      Agent 调用授权和数据范围
  Tools 安全      工具越权、参数攻击和重复操作
  Workflow 安全   执行、停止、恢复和跨组织调用权限
  AI 安全         Prompt Injection、敏感信息泄露和输出校验
  审计安全        日志缺失、篡改和越权查询
  备份安全        备份访问、完整性和恢复能力

### 13.2 漏洞处理流程

``` text
发现漏洞
   |
   v
确认影响范围
   |
   v
评估严重程度
   |
   v

   |
```

### 13.3 持续测试要求

-   在依赖更新和版本发布时检查漏洞。
-   对关键 API 进行认证和授权测试。
-   对文件上传和下载开展安全测试。
-   对跨组织和跨候选人访问开展越权测试。
-   对 Agent、Tools 和 Workflow 执行链路开展授权测试。
-   建立 Prompt Injection 测试样本。
-   对修复过的安全问题保留回归用例。

## 十四、安全事件应急响应

### 14.1 事件分类

可按事件影响划分等级，具体等级定义和响应时限由运维安全策略确定。

  事件类别   示例
  ---------- ---------------------------------------------
  账号安全   账号被盗、异常登录、Token 泄露
  权限安全   越权访问、异常提权
  数据安全   敏感信息泄露、批量导出异常
  文件安全   恶意文件上传、文件存储暴露
  AI 安全    Prompt Injection 导致异常工具调用或数据泄露
  系统安全   漏洞利用、服务异常或配置泄露
  备份恢复   备份损坏、恢复失败

### 14.2 应急处理流程

``` text
发现安全事件
      |
      v
事件登记与分级
      |
      v
告警与通知
      |
      v
调查影响范围
      |
      v
冻结账号 / 撤销会话 / 停止任务
      |
      v
隔离受影响服务或数据
      |
      v
修复漏洞与恢复数据
      |
      v
安全验证
      |
      v
事件关闭与复盘
```

### 14.3 处置能力

根据事件类型支持： - 暂停或冻结账号。 - 撤销 Refresh Token
和相关会话。 - 停止异常 Agent、Tools 或 Workflow 执行。 -
暂停受影响的文件处理任务。 - 限制敏感数据访问或导出。 -
隔离受影响服务。 - 恢复经过验证的备份。 - 记录处置过程和复盘结果。

处置操作本身需要权限校验和审计记录。

## 十五、安全验收标准

### 15.1 身份与账号验收

-   [ ] 不存在公开自主注册入口。
-   [ ] 管理员可以创建账号并发起邀请。
-   [ ] 邀请链接有有效期且只能使用一次。
-   [ ] 密码使用专用哈希算法存储。
-   [ ] Access Token 和 Refresh Token 按策略工作。
-   [ ] Refresh Token 轮换、注销和撤销有效。
-   [ ] 登录失败限制有效。
-   [ ] 用户可以查看和注销设备会话。

### 15.2 权限验收

-   [ ] 用户、组织、角色和权限关系正确。
-   [ ] RBAC 授权生效。
-   [ ] 组织数据范围隔离有效。
-   [ ] 业务对象归属检查有效。
-   [ ] 七大业务模块权限独立。
-   [ ] 敏感字段脱敏由后端执行。
-   [ ] 数据导出有独立权限。
-   [ ] Agent 调用权限有效。
-   [ ] Tools 白名单和参数校验有效。
-   [ ] Workflow 查看、执行、停止、重试和恢复权限分别生效。
-   [ ] 数字员工不能越权访问数据或调度任务。

### 15.3 数据与文件安全验收

-   [ ] HTTPS 配置有效。
-   [ ] 敏感字段加密策略有效。
-   [ ] 密钥不出现在源代码和日志中。
-   [ ] 文件类型与真实格式校验有效。
-   [ ] 文件大小限制有效。
-   [ ] 恶意文件扫描和隔离策略有效。
-   [ ] 文件下载必须通过后端授权。
-   [ ] 个人信息保留、删除和匿名化策略有效。
-   [ ] 删除流程覆盖关联文件和向量数据。

### 15.4 AI 安全验收

-   [ ] Agent 只读取当前任务授权数据。
-   [ ] 模型调用前执行必要的数据检查和脱敏。
-   [ ] 外部文档作为不可信数据处理。
-   [ ] Prompt Injection 测试不能使 Agent 获得额外权限。
-   [ ] Tools 调用必须经过后端授权。
-   [ ] 高风险操作按规则要求人工确认。
-   [ ] 模型输出通过 Schema 和业务规则校验。
-   [ ] AI 输出不能直接替代关键业务授权决定。

### 15.5 审计与运维验收

-   [ ] 关键用户操作有审计记录。
-   [ ] 权限变更有审计记录。
-   [ ] 敏感数据访问和导出有审计记录。
-   [ ] Agent、Tools 和 Workflow 调用可追踪。
-   [ ] 普通用户不能修改关键审计日志。
-   [ ] 日志完整性校验有效。
-   [ ] 密钥轮换和配置变更可追溯。
-   [ ] MySQL、Milvus、文件和 Workflow 必要状态均有备份方案。
-   [ ] 实际恢复演练通过。
-   [ ] 漏洞测试和应急响应流程经过验证。

### 15.6 验收结论原则

只有相关测试用例实际执行并通过，才能判定对应安全能力验收通过。设计文件完成不等于系统已经具备全部安全能力。
