## 一、评估目标与范围

本步骤评估 AI 中台能否统一管理 Agent、Workflow、模型供应商及工具调用，并支撑平台各业务场景。

重点评估：

1. Agent 注册、配置、启停、发布和版本管理。
2. Agent 能力描述、输入输出及调用约定。
3. Agent 工具注册、参数校验和权限控制。
4. Workflow 定义、节点组织和执行分支。
5. LangChain 的适用性。
6. LangGraph 的适用性。
7. 多 Agent 协作、结果传递和上下文管理。
8. Workflow 状态持久化、Checkpoint、中断和恢复。
9. 模型供应商统一接入、切换和配置管理。
10. Agent 执行记录、耗时、Token、错误和调用链追踪。
11. 人工确认、异常处理和失败重试机制。
12. AI 中台与业务服务之间的调用及结果回写边界。

本报告属于技术可行性评估，不包含完整 Agent 开发、可视化 Workflow 编辑器开发、生产部署或性能验收。

## 二、业务依据与统一术语

### 2.1 已确认的业务关系

根据业务对象与功能流程文件：

- Agent：执行特定业务任务的智能体。
- Workflow：组织多个任务或智能体的工作流。
- Agent 执行记录：智能体运行过程及结果。
- 任务调度规则：控制定时、周期或手动任务触发。
- 数字员工：承担特定数字化业务职责的虚拟执行主体，可关联多个 Agent 和 Workflow。
- 数字员工负责业务职责和任务组织，Agent 提供专业任务能力，Workflow 组织具体执行过程。

目前已明确的业务 Agent 包括简历解析 Agent 和岗位匹配 Agent。其他业务能力是否拆分为独立 Agent，应在对应设计阶段根据职责边界决定，不因技术架构预先强制拆分。

### 2.2 核心概念边界

| 概念 | 职责 |
|---|---|
| 业务模块/业务服务 | 执行确定性业务规则、权限校验和正式数据写入 |
| Agent | 提供边界明确的专业任务能力 |
| Workflow | 按预设节点、条件和分支组织任务及 Agent 执行 |
| 数字员工 | 承担业务职责，可关联多个 Agent 和 Workflow |
| LangChain | 组织模型调用、Prompt、工具及结构化输出 |
| LangGraph | 实现有状态的流程编排、分支、中断和恢复 |
| 模型适配层 | 屏蔽不同模型供应商的调用差异 |
| Worker | 执行耗时的异步任务 |
| MySQL | 保存业务数据、配置、任务记录及运行元数据 |

## 三、已确认的 12 项技术决策

| 编号 | 评估事项 | 用户确认方案 |
|---|---|---|
| 01 | Agent 执行模式 | A：固定职责的专业 Agent，由 Workflow 控制执行步骤 |
| 02 | Workflow 定义方式 | A：后台配置节点、条件和分支，发布后由 LangGraph 执行 |
| 03 | 人工确认机制 | A：支持配置人工确认节点，根据业务权限决定是否需要审批 |
| 04 | Agent 工具权限 | A：继承所属数字员工或任务的授权范围，允许更细粒度配置，但不得超出上层授权 |
| 05 | Agent 版本管理 | A：支持创建、测试、发布、停用、历史版本查看和回滚 |
| 06 | 模型供应商接入 | A：统一模型适配层，初期使用 Ollama，预留外部模型接入 |
| 07 | 多 Agent 协作 | A：Workflow 统一调度，各 Agent 按固定职责执行，通过标准化输入输出传递结果 |
| 08 | Workflow 状态管理 | A：使用 LangGraph Checkpoint，结合 MySQL 持久化，支持中断、恢复和人工审核后继续 |
| 09 | Agent 运行监控 | A：记录执行时间、耗时、Token、模型、版本、工具调用、节点状态、错误及调用链 |
| 10 | 异常处理与重试 | A：自动重试、异常记录、超限转人工处理，并支持人工重新执行 |
| 11 | AI 中台与业务数据边界 | A：通过业务服务接口读取和提交处理结果，业务服务负责校验、权限和正式数据写入 |
| 12 | 初期部署架构 | A：模块化单体，AI 中台作为独立逻辑模块运行，后续按负载和边界评估服务拆分 |

以上 12 项是本轮用户确认的决策基线。后续如发现版本兼容、安全或业务冲突，应记录证据并提出变更，不应静默替换已确认方案。

## 四、总体技术架构建议

### 4.1 逻辑架构

```text
业务应用层
  ├── 人才选拔
  ├── 人才档案与人才画像
  ├── 智能测评与面试
  └── 其他已确认业务模块
          │
          ▼
AI 中台统一入口（FastAPI）
  ├── Agent 管理
  ├── Workflow 管理
  ├── 执行任务管理
  ├── 人工确认接口
  ├── 权限校验与审计
  └── 运行记录查询
          │
          ▼
执行与编排层
  ├── LangGraph：流程状态、节点、分支、中断和恢复
  ├── LangChain：模型调用、Prompt、Tools、结构化输出
  ├── Agent Runtime：专业 Agent 执行
  └── Worker：耗时异步任务
          │
          ▼
模型适配层
  ├── Ollama（初期优先）
  └── 外部模型供应商适配接口（预留）
          │
          ▼
基础设施
  ├── MySQL：配置、业务数据、任务元数据、运行记录
  ├── LangGraph Checkpoint 持久化实现
  ├── 日志与调用链记录
  └── 现有文件、向量及其他基础服务
```

该图表示逻辑职责，不意味着初期必须拆成多个独立部署服务。

### 4.2 初期架构形态

采用模块化单体：

- FastAPI 提供统一应用入口。
- AI 中台在代码结构和业务边界上独立划分。
- Agent、Workflow、模型适配、执行记录和人工确认分别组织为独立模块。
- Worker 与 Web API 可作为不同进程运行，但共享受控的配置、任务和持久化机制。
- 后续只有在并发、资源隔离、独立扩缩容或团队协作确有需要时，才评估拆分服务。

不建议初期为了“微服务化”增加不必要的网络调用、部署、服务发现和分布式事务复杂度。

## 五、Agent 管理技术方案

### 5.1 Agent 生命周期

建议生命周期：

```text
草稿
  ↓
配置完成
  ↓
测试中
  ↓
已发布
  ↓
运行中
  ↓
停用
```

状态名称及转换条件应在详细设计阶段固化。测试失败、发布失败和版本回滚应有明确记录。

### 5.2 Agent 配置内容

每个 Agent 建议配置：

| 配置项 | 说明 |
|---|---|
| agent_id | 稳定唯一标识 |
| name | Agent 名称 |
| description | 职责说明 |
| input_schema | 输入结构及校验规则 |
| output_schema | 输出结构及校验规则 |
| prompt_version | Prompt 版本 |
| model_config_id | 模型配置引用 |
| tool_ids | 可使用工具清单 |
| permission_policy | 权限策略引用 |
| version | Agent 版本 |
| status | 草稿、测试、发布或停用状态 |

Agent 输入输出使用 Pydantic 等结构化模型校验。Agent 不应以任意自然语言文本作为唯一的机器间接口。

### 5.3 版本管理

用户已确认支持创建、测试、发布、停用、历史版本查看和回滚。

建议：
- 已发布版本不可原位覆盖。
- 每次发布保存完整配置快照。
- 运行任务绑定明确的 Agent 版本。
- 回滚通过重新指定历史发布版本实现。
- 记录版本创建人、测试结果、发布人、发布时间和变更说明。
- Prompt、模型配置、工具集合和权限策略均需记录版本或不可变引用。

### 5.4 初期 Agent 范围

当前业务文件明确的 Agent 至少包括：

| Agent | 业务职责 | 主要输入 | 主要输出 |
|---|---|---|---|
| 简历解析 Agent | 处理简历信息抽取任务 | 解析文本及文件上下文 | 结构化简历草稿、来源依据和校验状态 |
| 岗位匹配 Agent | 执行岗位匹配分析 | 已确认人才资料、岗位条件 | 匹配明细、评分依据及结果 |

人才画像、简答题评分等能力是否独立成为 Agent，需在后续详细设计中按复用性、权限和生命周期决定。

## 六、Workflow 管理与 LangGraph 执行方案

### 6.1 用户确认的流程定义方式

采用“后台配置 + LangGraph 执行”：

- 后台配置层负责维护节点、连接、条件和分支。
- 执行层负责将已发布的流程定义解析为受控的 LangGraph 图。
- 流程发布后形成不可变版本。
- 正在运行的任务绑定启动时使用的 Workflow 版本。
- 修改流程应产生新版本，不影响历史任务的可追溯性。

### 6.2 受控节点类型

建议初期只支持经过开发和安全审核的节点类型，例如：

| 节点类型 | 职责 |
|---|---|
| Agent 节点 | 调用已发布的专业 Agent |
| 业务服务节点 | 调用明确登记的业务服务 |
| 条件节点 | 根据结构化状态选择分支 |
| 数据校验节点 | 校验输入输出及业务约束 |
| 人工确认节点 | 暂停流程并等待授权人员处理 |
| 结束节点 | 形成流程结束状态 |
| 异常处理节点 | 处理可预期的错误分支 |

后台配置不得直接执行任意 Python 代码、任意 SQL 或未经登记的工具调用。节点参数应经过 Schema 校验和权限校验。

### 6.3 LangChain 与 LangGraph 分工

| 技术 | 使用位置 | 主要职责 |
|---|---|---|
| LangChain | Agent 内部及模型适配层 | Chat Model、Prompt、Tools、结构化输出 |
| LangGraph | Workflow 执行层 | 节点编排、条件分支、状态传递、Checkpoint、中断和恢复 |
| FastAPI | AI 中台接口层 | 接收请求、身份鉴权、任务创建、结果查询 |
| Worker | 异步执行层 | 运行耗时 Workflow 或 Agent 任务 |

不要将所有普通业务代码都封装成 Agent。确定性业务规则应优先由业务服务执行。

### 6.4 Workflow 版本和执行绑定

每次执行任务至少绑定：
- workflow_id
- workflow_version
- agent_id 及 agent_version
- model_config_version
- input_schema_version（适用时）
- 任务创建时间及发起人

这样能够解释历史任务使用了哪一版流程、Agent 和模型配置。

## 七、多 Agent 协作方案

### 7.1 用户确认的协作方式

由 Workflow 统一调度；各 Agent 按固定职责执行；通过标准化输入输出传递结果。

不采用 Agent 自主发现并随意调用其他 Agent 的模式。

### 7.2 参考流程

```text
业务请求
   ↓
Workflow
   ↓
简历解析 Agent
   ↓
结构化输出及数据校验
   ↓
人工确认 / 业务服务处理
   ↓
岗位匹配 Agent
   ↓
匹配结果及解释
   ↓
HR 人工筛选
```

该流程仅为协作关系示例，实际是否连续执行及触发条件由业务流程决定。

### 7.3 标准化结果协议

建议 Agent 之间传递结构化对象，至少包含：

| 字段 | 说明 |
|---|---|
| task_id | 当前业务任务 ID |
| run_id | 当前 Workflow 运行 ID |
| agent_id | 执行 Agent 标识 |
| agent_version | 执行 Agent 版本 |
| status | 成功、失败、待确认等状态 |
| data | 结构化业务结果 |
| evidence | 结果依据或来源引用 |
| error | 错误类型及安全摘要 |
| metadata | 耗时、模型等运行元数据 |

传递必要结果和来源引用即可，不应在 Agent 之间无控制地复制完整简历、个人信息或其他敏感数据。

## 八、工具注册与权限控制

### 8.1 用户确认的授权原则

Agent 工具权限继承所属数字员工或任务的授权范围，并允许配置更细粒度权限，但不得超出上层授权。

建议权限链：

```text
用户及角色授权
      ↓
数字员工 / 业务任务授权范围
      ↓
Workflow 授权范围
      ↓
Agent 可用权限
      ↓
Tool 工具权限
      ↓
执行时再次校验
```

如某个 Agent 不属于数字员工执行场景，应由明确的业务主体或任务授权上下文提供上层权限范围，不能默认授予全局权限。

### 8.2 工具注册信息

每个 Tool 建议登记：
- tool_id、名称和用途。
- 输入参数 Schema。
- 输出 Schema。
- 允许调用的 Agent。
- 所需权限。
- 是否只读。
- 是否产生外部副作用。
- 超时和重试策略。
- 审计级别。
- 版本及启停状态。

### 8.3 敏感操作

以下操作应由业务服务执行并进行独立权限校验：
- 创建或修改正式人才档案。
- 发布岗位或改变岗位条件。
- 确认正式测评成绩。
- 发布正式人才画像。
- 修改用户、角色及权限。
- 执行其他具有业务副作用的操作。

Agent 不得直接绕过业务服务访问数据库并写入正式业务数据。

## 九、模型供应商统一接入方案

### 9.1 用户确认的方案

- 初期优先使用 Ollama。
- 建立统一模型适配层。
- 预留外部模型供应商接入能力。
- 具体场景是否适合由本地模型承担，以真实业务测试结果为准。

### 9.2 模型适配层职责

建议统一管理：
- 供应商标识和启停状态。
- 模型名称及能力类型。
- Chat Model 和 Embedding 模型配置。
- 温度、上下文长度等参数。
- 超时、重试和并发限制。
- 凭据引用及安全存储。
- 模型配置版本。
- 调用耗时、Token 和错误记录。

业务 Agent 通过统一接口申请模型能力，不直接依赖某个供应商的私有请求格式。

### 9.3 模型切换边界

统一适配层可以减少供应商差异，但不能保证任意模型完全等价。切换模型后仍需验证：
- Prompt 兼容性。
- 结构化输出能力。
- 工具调用能力。
- 上下文长度。
- 中文业务表现。
- 响应时延、并发和成本。
- 数据传输及隐私要求。

## 十、Checkpoint、状态持久化与恢复

### 10.1 用户确认的方案

采用 LangGraph Checkpoint，并结合 MySQL 持久化，支持：
- Workflow 中断。
- 服务重启后恢复。
- 人工审核后继续执行。
- 节点状态记录。
- 失败节点重试。
- 任务执行追踪。

### 10.2 重要技术验证事项

**LangGraph Checkpoint 与 MySQL 的具体集成方式必须通过版本和适配器验证。**

不能仅凭“使用 MySQL”就认定已经存在适用且兼容的官方 Checkpointer。应在实施前验证：
1. 当前 LangGraph 版本与 Checkpoint 接口兼容性。
2. 可用 MySQL Checkpointer 的来源、维护状态和许可。
3. 事务、并发写入和锁机制。
4. checkpoint 数据结构及迁移策略。
5. 断点恢复和人工中断恢复测试。
6. 数据清理、归档和保留周期。

如果没有经过验证的适配器，应实现并测试受控的持久化适配方案；不得把普通业务任务表误认为 LangGraph Checkpoint 的等价替代品。

### 10.3 任务状态建议

| 状态 | 说明 |
|---|---|
| PENDING | 等待执行 |
| RUNNING | 执行中 |
| WAITING_HUMAN | 等待人工处理 |
| RETRYING | 自动重试中 |
| SUCCEEDED | 执行成功 |
| FAILED | 执行失败 |
| CANCELLED | 已取消 |
| NEEDS_MANUAL_ACTION | 超过自动处理范围，等待人工处理 |

状态机的具体转换条件、并发锁和恢复策略在任务执行详细设计阶段确定。

## 十一、运行监控、日志与调用链追踪

### 11.1 用户确认的监控范围

需要记录：
- 执行时间。
- 执行耗时。
- Token 使用量。
- 模型及模型配置版本。
- Agent 及版本。
- Workflow 及版本。
- 工具调用。
- 节点状态。
- 错误及重试情况。
- 调用链关联信息。

### 11.2 建议的观测字段

| 记录类型 | 关键字段 |
|---|---|
| 任务记录 | task_id、run_id、发起人、业务来源、状态 |
| Workflow 记录 | workflow_id、版本、节点、开始和结束时间 |
| Agent 记录 | agent_id、版本、输入输出摘要、状态 |
| 模型记录 | provider、model、Token、耗时、错误 |
| Tool 记录 | tool_id、版本、参数摘要、执行结果、权限决策 |
| 异常记录 | error_code、错误摘要、重试次数、处理状态 |
| Trace 记录 | trace_id、span_id、parent_span_id |

### 11.3 敏感信息保护

监控不能以无条件记录完整原始输入输出为前提：
- 简历、联系方式和个人信息应脱敏。
- 日志优先保存摘要、业务 ID 和来源引用。
- 敏感原文按业务权限单独访问。
- 模型密钥不得写入日志。
- 对日志查询、导出和删除设置权限及审计。
- 设置保留期限和归档策略。

## 十二、异常处理、自动重试与人工介入

### 12.1 用户确认的方案

采用：

**自动重试 + 异常记录 + 超限后转人工处理 + 支持人工重新执行。**

### 12.2 推荐异常分类

| 异常类型 | 建议处理 |
|---|---|
| 网络暂时不可用 | 有限次数自动重试 |
| 模型服务暂时不可用 | 退避重试，超过上限转人工处理 |
| 模型输出格式错误 | 受限格式修复或重新请求，仍失败则转人工 |
| 参数校验失败 | 不盲目重试，记录原因并要求修正 |
| 权限不足 | 立即拒绝，不自动重试 |
| 业务规则不满足 | 走业务分支，不视为系统故障 |
| 工具执行超时 | 根据工具幂等性决定能否重试 |
| 数据库或 Checkpoint 写入失败 | 保护任务状态，记录异常并执行恢复流程 |

### 12.3 重试控制

必须具备：
- 最大重试次数。
- 重试间隔及退避策略。
- 超时控制。
- 幂等键或执行去重机制。
- 可重试与不可重试错误分类。
- 人工重新执行的权限和记录。
- 重试前检查外部副作用是否已经发生。

不能对所有失败一律自动重试，否则可能重复创建业务记录或重复执行敏感操作。

## 十三、AI 中台与业务服务的数据边界

### 13.1 用户确认的方案

AI 中台通过业务服务接口读取数据和提交处理结果；业务服务负责：
- 业务规则校验。
- 身份与权限校验。
- 数据完整性校验。
- 正式业务数据写入。
- 事务及审计处理。

AI 中台不直接绕过业务服务写入正式业务数据。

### 13.2 推荐调用流程

```text
业务模块
   ↓
AI 中台创建任务
   ↓
读取授权范围内的业务数据
   ↓
Agent / Workflow 执行
   ↓
产生结构化结果和依据
   ↓
业务服务接口接收结果
   ↓
业务规则及权限校验
   ↓
人工确认（如业务要求）
   ↓
业务服务事务写入
   ↓
返回处理结果
```

### 13.3 数据边界原则

- MySQL 业务数据仍由业务模块负责维护。
- AI 配置和执行元数据由 AI 中台管理。
- Agent 输出默认是建议、草稿或待处理结果，不自动成为正式业务数据。
- 正式写入必须经过业务服务。
- AI 中台只获取当前任务必要的数据。
- 业务服务接口必须验证调用身份、权限、参数及幂等性。
