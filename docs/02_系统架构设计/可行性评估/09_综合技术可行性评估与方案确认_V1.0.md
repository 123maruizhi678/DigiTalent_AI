## 一、综合评估摘要

### 1.1 最终结论

**总体结论：平台技术路线有条件可行，可以进入下一阶段的详细设计和技术验证；在 P0 安全风险整改、关键组件验证及必要验收完成前，不得据此认定具备生产上线条件。**

综合前八步评估和本步骤五批确认，当前平台可以采用以下总体技术方向：

**前后端分离 + 模块化单体业务应用 + 统一 AI 中台 + 独立异步任务执行层 + 分层数据存储 + 统一身份权限与审计体系。**

初期不全面拆分微服务；不将 Redis、独立消息队列、MinIO 业务对象存储作为当前版本的强制依赖。业务应用负责正式业务规则、业务状态和权威数据；AI 中台负责模型、Agent、Workflow 和智能执行；任务执行层负责定时、异步和批量任务。

## 三、最终总体技术架构

### 3.1 架构分层

```text
平台用户
   │
   ▼
前端表现层
Vue 3 + TypeScript + Element Plus
   │
   ▼
后端接入层
Python 3.11 + FastAPI + Pydantic
   │
   ▼
模块化单体业务应用层
   ├── 人才选拔
   ├── 人才档案与画像
   ├── 智能测评与面试
   ├── Agent / Workflow 管理
   ├── 数字员工与任务管理
   ├── 数据智能与运营决策
   └── 用户、组织与权限
   │
   ├───────────────┐
   ▼               ▼
统一 AI 中台        独立任务执行层
LangChain           APScheduler
LangGraph           MySQL 任务中心
模型适配层           独立 Worker
Ollama
   │               │
   └───────┬───────┘
           ▼
分层数据与文件存储
MySQL / Milvus / Neo4j / 本地文件系统

横向贯穿：
统一认证与 RBAC、数据范围权限、工具权限、日志审计、
敏感信息保护、资源监控、备份恢复和性能验收
```

### 3.2 架构决策

1. 前后端分离，统一平台账号体系和角色化工作台，不为每个角色建立独立门户。
2. 初期采用模块化单体，代码按业务领域划分清晰边界。
3. AI 中台与业务应用层职责分离，业务规则和正式业务状态由业务模块维护。
4. 简历解析、批量匹配、AI 评分和报告生成等耗时任务异步执行。
5. Worker 独立运行，不将耗时任务长期阻塞在 API 请求中。
6. 数据存储按职责分层，MySQL 作为核心结构化业务数据的权威来源。
7. 权限和审计贯穿用户请求、Agent、Workflow、数字员工、Tool 和数据访问链路。
8. 后续是否拆分微服务，以实际性能瓶颈、团队规模和运维需求为依据，不预先增加分布式复杂度。

### 3.3 业务应用层与 AI 中台边界

| 能力 | 业务应用层负责 | AI 中台负责 |
|---|---|---|
| 人才资料 | 正式资料、业务规则、审核和版本 | 简历内容理解、信息抽取建议 |
| 人才画像 | 草稿状态、人工确认、正式画像保存 | 画像分析和草稿生成 |
| 岗位匹配 | 岗位条件、硬性规则、匹配结果保存 | 语义分析、向量检索及解释建议 |
| 测评 | 题库、试卷、答卷、正式成绩 | 简答题辅助评分和解释 |
| 面试 | 面试安排、记录、评价状态 | 面试内容辅助分析 |
| 数字员工 | 职责、授权、任务状态和审计 | Agent / Workflow 执行 |
| 数据智能 | 指标定义、查询授权和结果管理 | NL2SQL 辅助生成、结果解释 |
| 用户权限 | 身份、角色、数据范围和授权决策 | 执行前接受授权上下文，不自行授予权限 |

AI 输出不得未经业务校验及必要人工确认直接写入正式业务数据。AI 中台不能绕过业务服务直接修改正式业务状态。

### 4.1 组件选型边界

- MinIO 不作为当前业务文件存储的必需组件；如果 Milvus 部署架构自身存在对象存储依赖，应与业务文件存储区分。
- 不使用 Redis 是当前版本的明确约束，不代表 MySQL 任务中心可以不做并发控制、任务认领和恢复设计。
- Neo4j 需通过实际人才关系查询场景验证其必要性和查询价值；未验证前不应把所有关系查询强制迁移到图数据库。
- Ollama 的模型质量、响应时间、并发和资源占用需使用真实业务样本验证。
- 组件版本最终以兼容性验证和依赖锁定结果为准，不因本报告列出版本就认定已完成集成测试。

## 五、七大业务领域最终技术路线

### 5.1 人才选拔

**核心流程：**

```text
简历上传
  ↓
文件类型、大小和权限校验
  ↓
文件隔离与安全检查
  ↓
本地文件存储 + MySQL 文件元数据
  ↓
创建异步解析任务
  ↓
MinerU / 格式专用解析器
  ↓
LangChain + 模型服务进行信息抽取
  ↓
Pydantic 结构校验和标准化
  ↓
人工审核
  ↓
人才主档案关联/创建
  ↓
岗位条件过滤与语义匹配
  ↓
保存匹配结果并供 HR 确认
```

已确认简历格式和限制：
- PDF、DOCX、DOC、TXT、图片。
- 单次最多 20 份。
- 每份文件最大 20MB。

技术职责：
- FastAPI 负责上传入口、权限校验和业务接口。
- 本地文件系统保存文件原件，MySQL 保存文件元数据和处理记录。
- MinerU 及格式专用解析器负责文档内容解析。
- LangChain 和模型负责辅助信息抽取。
- Pydantic 负责结构校验。
- MySQL 保存正式人才业务数据。
- Milvus 提供语义向量检索。
- Python 规则引擎负责岗位硬性条件过滤及规则计算。
- HR 对需要人工审核的抽取和匹配结果进行确认。

可行性结论：技术路线可行；解析质量、真实样本准确率、文件安全和批量性能需验证。

### 5.2 人才档案与人才画像

MySQL 中的人才主档案是统一关联对象。一个自然人对应一份人才主档案，候选人身份和员工身份分别管理并关联同一主档案。

逻辑数据对象建议包括：
- `talent_master`
- `candidate_identity`
- `employee_identity`
- `resume_file`
- `resume_version`
- `resume_extraction`
- `talent_merge_record`
- `talent_profile`
- `talent_tag`
- `talent_change_log`

以上是逻辑对象，不是最终物理建表方案。

关键规则：
- 候选人录用后在原人才主档案下创建或激活员工身份，不复制新主档案。
- 一个自然人可以关联多份简历，由 HR 指定当前有效简历。
- 历史简历和历史解析记录保留。
- 疑似重复人才通过规则识别并由 HR 确认，不仅凭姓名自动合并。
- 正式人才资料和画像不得被 AI 草稿直接覆盖。
- 画像生成后先保存为草稿，经 HR 确认后成为正式画像并保留历史版本。

可行性结论：MySQL + SQLAlchemy + FastAPI 能够支撑；档案合并、身份转换事务、并发修改和数据完整性需详细设计及测试。

### 5.3 人才与岗位匹配

采用“硬性条件过滤 + 软性条件评分 + 语义相似度”的组合路线。

- MySQL 保存岗位条件、权重、匹配结果和明细。
- Python 规则引擎执行硬性条件过滤和确定性评分。
- Ollama/模型服务辅助语义分析。
- Milvus 提供岗位与人才向量检索。
- LangChain 组织模型调用，必要时由 LangGraph 编排多步骤匹配。
- 保存综合评分、条件匹配明细、是否通过、合格线、匹配原因和未满足条件。
- HR 按业务规则复核匹配结果。

具体评分维度、权重和合格线数值在详细设计中确认，不在本报告中虚构。

### 5.4 智能测评与面试

题型已确认包括：
- 单选题。
- 多选题。
- 判断题。
- 填空题。
- 简答题。

技术路线：
- MySQL 管理题库、试题、试卷、答卷、评分和面试记录。
- Python 确定性规则引擎从现有题库规则组卷，本期不建设 AI 自动生成新题。
- Vue 负责在线答题界面，FastAPI 负责测评业务接口。
- 客观题采用确定性代码自动判分。
- 简答题由 Ollama + LangChain 辅助评分。
- AI 建议分数、评分依据、模型/Prompt 版本和人工确认结果分别留存。
- HR/面试官确认后形成正式成绩。
- 多轮面试保留面试官、时间、记录和评价。
- 保留错题记录；独立错题复习计划不纳入当前范围。

待详细设计确认：多选题部分得分规则、填空题答案容错、防作弊、身份核验及监考要求等。

### 5.5 AI Agent 与 Workflow

最终确认 LangChain 与 LangGraph 分工：

| 组件 | 职责 |
|---|---|
| LangChain | 模型调用、Prompt、Tools、Retriever、结构化输出 |
| LangGraph | 节点组织、条件分支、多 Agent 协作、人工审批、Checkpoint、中断和恢复 |
| 模型适配层 | 统一不同模型服务的调用接口 |
| FastAPI 业务服务 | 权限校验、业务规则校验、正式数据写入 |
| MySQL | 执行记录、业务状态及必要的 Workflow 状态持久化 |

原则：
- Agent 是具有明确职责的专业执行单元。
- Workflow 负责组织 Agent 和工具执行流程。
- Agent 工具调用必须经过后端权限和参数校验。
- Prompt 不是安全边界，不能代替后端授权。
- AI 输出先校验，再由业务服务保存。
- Workflow 需设计状态持久化、中断恢复、超时、重试和异常处理。

### 5.6 数字员工与任务调度

确认采用：

**数字员工管理 + APScheduler + MySQL 任务中心 + 独立 Worker + LangGraph Workflow + LangChain Agent。**

职责：
- 数字员工模块管理职责、能力、关联 Agent/Workflow 和授权范围。
- APScheduler 负责定时、周期任务触发。
- MySQL 保存任务定义、状态、执行记录和必要的调度信息。
- Worker 负责任务认领、实际执行、并发控制、重试和故障恢复。
- LangGraph 组织任务执行流程，LangChain Agent 完成具体智能能力。
- 平台内部消息用于任务完成、失败和待办通知。

数字员工有效执行权限不得超过发起用户权限、数字员工职责范围、任务授权及具体工具权限的交集。

不引入 Redis 和独立消息队列的前提下，必须重点验证：
- 任务原子认领和防止重复执行。
- Worker 多实例并发控制。
- APScheduler 多实例防重复触发。
- 任务幂等、租约、超时、重试和失败恢复。
- 用户或任务授权撤销后的执行处理。
- MySQL 任务表的容量、索引和锁竞争。

### 5.7 数据智能与运营决策

NL2SQL 最终采用完整 SQL 安全校验方案，解决专项评估之间的方案差异。

```text
用户自然语言问题
  ↓
用户身份与数据范围校验
  ↓
查询意图识别
  ↓
数据字典 / Schema 检索
  ↓
模型生成候选 SQL
  ↓
SQL AST 解析
  ↓
SQL 语法及安全校验
  ↓
表字段白名单检查
  ↓
用户数据权限条件校验
  ↓
独立只读数据库账号
  ↓
执行查询（超时、行数和资源限制）
  ↓
结果解释、统计与可视化
  ↓
保存查询审计
```

关键原则：
- 大模型不直接持有数据库凭据。
- 只读账号不能替代业务数据权限控制。
- SQL AST、表字段白名单和用户数据范围校验共同构成安全边界。
- 对高成本查询设置超时、最大结果行数、分页和并发限制。
- 查询记录关联用户、数据范围、SQL、执行状态和结果规模。
- 指标口径和数据字典由业务侧维护，不由模型自行定义正式指标。

可行性结论：有条件可行；需验证 AST 校验覆盖范围、权限条件注入正确性、只读账号授权边界和查询资源控制。

## 六、统一数据存储与数据职责

| 存储组件 | 主要数据 | 不承担的职责 |
|---|---|---|
| MySQL | 用户、组织、权限、人才主档案、岗位、测评、面试、任务、业务状态、审计元数据 | 不承担向量近邻检索的主要职责 |
| Milvus | 人才、岗位等语义向量及检索索引 | 不作为人才正式档案权威数据源 |
| Neo4j | 经确认有价值的人才及业务关系图 | 不替代 MySQL 业务事务和主数据管理 |

| Ollama 模型服务 | 模型推理能力 | 不作为业务数据持久化系统 |

数据一致性原则：
1. MySQL 作为核心业务结构化数据的权威来源。
2. 向量和图数据应可由权威业务数据重建或校验。
3. 数据更新、删除和重建应有可追踪任务。
4. 文件元数据与文件原件之间保持可核验关联。
5. AI 生成内容与正式业务数据分开管理。
6. 重要跨存储流程需要记录失败状态、重试和补偿方式。

## 七、统一权限、安全与审计基线

### 7.1 身份认证与 RBAC

- 用户名密码认证。
- JWT + Refresh Token。
- 密码安全哈希存储。
- 统一 RBAC 权限中心。
- 后端统一校验菜单、接口和业务操作权限。
- 数据范围包括全部数据、部门数据和个人数据。
- 字段级权限与业务对象权限在后端执行。

### 7.2 个人信息保护

已确认身份证号、手机号等敏感字段脱敏展示。该选择不等于其他个人信息可以不受保护。

详细设计必须明确数据分类、最小权限、访问审计、传输和存储保护、保存期限及删除机制。

### 7.3 文件上传安全

当前确认的文件限制：
- PDF、DOCX、DOC、TXT、图片。
- 单次最多 20 份。
- 单份最大 20MB。

综合确认采用增强型安全基线：
1. 扩展名检查。
2. 文件头及真实类型校验。
3. 恶意文件扫描。
4. 隔离区检查。
5. 通过检查后再交给解析器。
6. 文件与 Web 可执行目录隔离。
7. 文件下载和解析前执行权限检查。
8. 限制解析时长、页数、图片像素、解压深度及临时资源。
9. 记录上传、下载、解析、删除和失败事件。

### 7.4 AI 输入输出与日志留存

保留完整 AI 调用记录的审计能力，但必须落实：
- 访问角色和最小权限。
- 敏感信息识别、脱敏及必要加密。
- 保存目的和数据范围。
- 保存期限、归档和删除机制。
- 日志查看、检索、下载和导出审计。
- 密码、令牌、密钥等认证凭据不得作为普通日志内容保存。

### 7.5 Agent、数字员工和 NL2SQL 权限

- 工具白名单和角色授权。
- 参数 Schema 校验。
- 执行前权限检查。
- 数字员工继承发起用户权限并叠加职责范围。
- 敏感操作按风险配置人工确认。
- NL2SQL 使用独立只读账号、AST 校验、表字段白名单和数据范围过滤。
- 任何 AI 执行都不能绕过业务服务和后端权限中心。

### 7.6 密钥管理

开发阶段可使用 `.env`，但必须：
- `.env` 加入 `.gitignore`。
- `.env.example` 只保存变量名和占位值。
- 限制文件系统访问权限。
- 禁止日志和 API 输出密钥。
- 支持泄露后的轮换和撤销。
- 不同环境使用不同密钥。

生产部署前重新评估专用密钥管理和安全注入方式。

## 八、任务执行、可靠性与性能基线

### 8.1 任务执行可靠性

所有耗时任务应具备：
- 持久化任务状态。
- 明确的任务生命周期。
- 原子认领和并发控制。
- 幂等键或等效重复执行防护。
- 超时、重试和失败状态。
- Worker 异常退出后的恢复策略。
- 权限复核和授权撤销处理。
- 执行日志和可追踪关联 ID。

### 8.2 超时策略

第 13 项选择 B：统一设置一个超时时间，所有请求和任务使用相同限制。

本报告保留该用户决策，但标记为技术限制项。API、数据库、模型推理和长时间批量任务的耗时特征不同，统一超时值可能导致短请求等待过长或长任务被提前终止。

详细设计必须明确统一超时值、适用边界、超时后的资源释放、任务状态和重试行为。分层超时可作为后续优化建议，不记为已确认决策。

### 8.3 备份与恢复

采用自动备份、定期恢复演练、任务异常恢复和核心服务降级机制。

备份范围至少评估：
- MySQL 业务数据。
- 简历和业务文件原件。
- Agent、Workflow 和数字员工配置。
- 数据字典和指标定义。
- 必要的任务及审计记录。

需要确定备份频率、保留周期、独立存储、恢复顺序和恢复目标；恢复演练应验证可用性和数据一致性。

### 8.4 性能测试

统一测试：
- 并发用户和请求吞吐量。
- API 平均、P95、P99 响应时间。
- 数据库查询、慢查询和连接池。
- 模型首 token 时间、完整响应时间和超时率。
- 异步任务排队时间、执行时间、成功率和重试率。
- Worker 数量、队列积压和恢复时间。
- CPU、内存、GPU 显存、磁盘和网络。
- 长时间运行稳定性。

本次没有确认具体量化阈值。应在详细设计和基线测试中结合真实部署环境、业务规模和硬件资源确定，不虚构验收数值。
