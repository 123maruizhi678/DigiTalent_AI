## 一、评估目标与范围

本步骤判断数字员工能否通过职责配置、Agent 和 Workflow 关联、任务触发及调度机制，形成可管理、可执行、可追踪的数字化执行主体。

按照第二阶段总流程，本步骤正式评估 11 项：

1. 数字员工注册、启用、停用和管理。
2. 数字员工职责描述与职责边界。
3. 数字员工与多个 Agent、Workflow 的关联关系。
4. 职责流程的定义和执行方式。
5. 定时、周期、手动及业务事件触发方式。
6. 任务分配、认领、排队和执行状态管理。
7. 异步任务、并发控制和资源限制。
8. 任务失败、超时、重试和人工介入机制。
9. 数字员工执行记录和结果追踪。
10. 成员即时通信账号关联的技术可行性及边界。
11. 数字员工的身份、权限和操作审计。

本报告不提前开发数字员工业务功能，不将即时通信平台接入设为初期运行前提，也不擅自扩展数字员工的业务职责。

## 二、业务概念与职责边界

### 2.1 核心概念

| 对象 | 职责 |
|---|---|
| 数字员工 | 承担明确业务职责，组织任务并选择已授权的 Agent、Workflow |
| Agent | 提供边界明确的专业任务能力 |
| Workflow | 定义具体任务的节点、条件、分支、人工确认和执行顺序 |
| 任务中心 | 统一创建、排队、分配、执行及追踪任务 |
| Scheduler | 根据定时、周期或事件规则创建任务 |
| Worker | 认领并执行耗时任务，更新任务状态 |
| 业务服务 | 执行业务规则、权限校验及正式业务数据写入 |

### 2.2 三者关系

数字员工不是单个 Agent，也不是 Workflow 的别名：

- 数字员工定义“谁负责什么业务”。
- Workflow 定义“具体任务按什么步骤执行”。
- Agent 定义“某个专业步骤由什么能力完成”。

一个数字员工可以关联多个 Agent 和多个 Workflow。每次执行应明确使用的数字员工配置版本、Workflow 版本和 Agent 版本。

### 2.3 当前业务依据

已确认的业务对象与流程文件明确包含数字员工注册管理、业务职责管理、职责流程配置、一个或多个 Agent/Workflow 关联、定时/周期/手动/业务事件触发、执行状态及异常监控等能力。

该业务文件同时明确：即时通信账号关联为可选扩展能力，当前以平台内部工作台使用为主，不将外部即时通信平台作为运行前提。

## 四、数字员工注册、生命周期与版本管理

### 4.1 用户确认方案

后台统一创建和管理数字员工，支持：
- 草稿。
- 启用。
- 停用。
- 编辑。
- 版本管理。

### 4.2 建议配置字段

| 字段 | 说明 |
|---|---|
| digital_employee_id | 数字员工唯一标识 |
| name | 数字员工名称 |
| description | 职责说明 |
| business_scope | 业务范围 |
| task_scope | 可执行任务类型 |
| permission_policy_id | 权限策略引用 |
| status | 草稿、启用、停用等状态 |
| version | 配置版本 |
| created_by / updated_by | 创建人及修改人 |
| created_at / updated_at | 创建和更新时间 |

### 4.3 生命周期建议

```text
草稿
  ↓
配置完成
  ↓
测试 / 校验
  ↓
启用
  ↓
运行中
  ↓
停用
```

状态转换条件、是否需要审批以及版本发布流程，应在详细设计阶段进一步明确。已启用配置不宜直接覆盖；运行任务应绑定启动时使用的配置版本，避免配置修改改变历史任务含义。

### 4.4 可行性判断

采用 FastAPI 管理接口、Pydantic 参数校验和 MySQL 配置表即可实现。无需为数字员工注册管理单独引入新的基础设施。

**结论：可行。** 生命周期细节及版本回滚规则待详细设计。

## 五、数字员工职责定义与边界

### 5.1 用户确认方案

每个数字员工配置：
- 名称。
- 职责说明。
- 业务范围。
- 可执行任务。
- 权限边界。

### 5.2 职责分层

| 层次 | 需要定义的内容 |
|---|---|
| 业务职责 | 该数字员工负责的业务目标 |
| 业务范围 | 允许处理的项目、人才或业务领域 |
| 任务范围 | 允许接收的任务类型 |
| 能力范围 | 可以调用的 Agent 和 Workflow |
| 权限范围 | 可读取、处理、提交哪些业务数据 |
| 人工边界 | 哪些操作必须由用户或授权人员确认 |

数字员工的职责配置不能替代用户、角色和业务数据权限。即使数字员工关联某个 Agent，也不意味着它自动获得该 Agent 的全部工具权限。

### 5.3 可行性判断

职责信息可采用结构化配置和权限策略引用实现。对于自然语言职责描述，可用于管理展示和辅助理解，但实际执行权限必须由结构化策略控制。

**结论：可行。** 具体业务职责仍以业务需求文件和后续业务设计为准，不在本报告中自行扩展。

## 六、数字员工与 Agent、Workflow 关联

### 6.1 用户确认方案

一个数字员工可关联多个 Agent 和多个 Workflow，并分别配置：
- 调用权限。
- 适用场景。
- 关联状态。
- 版本引用。

### 6.2 关系模型建议

```text
数字员工
  ├── 数字员工-Agent 关联
  │      ├── Agent 标识及版本
  │      ├── 允许任务类型
  │      └── 调用权限
  │
  └── 数字员工-Workflow 关联
         ├── Workflow 标识及版本
         ├── 适用场景
         └── 启用状态
```

建议采用独立关联表实现多对多关系，不在数字员工主表中硬编码 Agent 或 Workflow 列表。

### 6.3 执行约束

- 只能调用已关联且处于可用状态的 Agent、Workflow。
- 任务创建时确定版本引用。
- 运行期间不因后台配置变化而静默切换版本。
- 执行时再次检查当前用户、任务和数字员工的授权范围。
- Agent 的工具权限仍遵循第五步 AI Agent 与 Workflow 评估中确认的分层授权原则。

### 6.4 可行性判断

通过 MySQL 关联表、FastAPI 管理接口和第五步已确认的 Agent/Workflow 注册管理能力即可实现。

**结论：可行。**

## 七、职责流程定义与执行

### 7.1 用户确认方案

通过 Workflow 定义数字员工的职责流程。数字员工负责选择并执行已关联的 Workflow，不在数字员工配置中重复定义完整流程。

### 7.2 执行关系

```text
任务进入
   ↓
识别目标数字员工
   ↓
校验数字员工状态及任务范围
   ↓
选择已关联且适用的 Workflow
   ↓
绑定 Workflow 版本
   ↓
创建执行实例
   ↓
LangGraph 执行节点
   ↓
调用已授权 Agent / 业务服务
   ↓
保存执行状态及结果
```

### 7.3 技术职责

| 组件 | 职责 |
|---|---|
| FastAPI | 接收请求、鉴权、创建任务 |
| 数字员工管理模块 | 校验数字员工状态、职责和关联配置 |
| Workflow 管理模块 | 提供已发布流程定义及版本 |
| LangGraph | 执行流程节点、分支、中断和恢复 |
| Agent Runtime | 执行专业 Agent |
| 业务服务 | 校验业务规则并处理正式数据 |

### 7.4 可行性判断

第五步已确认 LangGraph 负责 Workflow 执行，数字员工通过受控关联选择 Workflow，技术路线一致，不需要另建一套流程引擎。

**结论：可行。** Workflow 动态配置转换、版本绑定和人工节点恢复仍需集成测试。

## 八、任务触发方式

### 8.1 用户确认方案

支持四种触发方式：

1. 手动触发。
2. 定时触发。
3. 周期触发。
4. 业务事件触发。

### 8.2 触发机制建议

| 触发方式 | 实现建议 | 关键控制 |
|---|---|---|
| 手动触发 | FastAPI 接口创建任务 | 身份、角色、业务范围和重复提交校验 |
| 定时触发 | APScheduler 到期后创建任务记录 | 调度记录、时区、重复触发防护 |
| 周期触发 | APScheduler 根据周期规则创建任务记录 | 周期规则、暂停、恢复和防重复 |
| 业务事件触发 | 业务服务在事件发生后调用内部事件入口或写入可靠事件记录 | 事件 ID、幂等、重放和失败补偿 |

### 8.3 APScheduler 边界

沿用基础技术组件评估的确认结果：
- APScheduler 负责定时和周期触发。
- APScheduler 不直接执行耗时 AI 任务。
- 调度器创建任务记录。
- Worker 负责执行任务。
- 多进程/多实例防重复触发和故障恢复需要专项验证。

业务事件触发不应简单等同于 APScheduler 定时扫描。应由业务事件入口产生任务，必要时通过可靠事件记录或事务性写入策略避免业务事务成功但任务未创建的问题。

### 8.4 可行性判断

四种触发方式均有明确实现路径。初期不需要额外引入消息队列，但 MySQL 任务记录、事件幂等及调度器多实例协调必须设计和测试。

**结论：有条件可行。** APScheduler 多实例和业务事件可靠投递是待验证重点。

## 九、任务中心、分配、认领与状态管理

### 9.1 用户确认方案

建设统一任务中心，支持：
- 任务创建。
- 任务分配。
- 任务排队。
- Worker 认领。
- 任务执行。
- 状态追踪。

### 9.2 任务中心建议字段

| 字段 | 说明 |
|---|---|
| task_id | 任务唯一标识 |
| task_type | 任务类型 |
| trigger_type | 手动、定时、周期或业务事件 |
| digital_employee_id | 执行数字员工 |
| digital_employee_version | 数字员工配置版本 |
| workflow_id / workflow_version | Workflow 及版本 |
| priority | 任务优先级 |
| status | 任务状态 |
| scheduled_at | 计划触发时间 |
| claimed_by | 认领 Worker |
| lease_expires_at | 认领租约到期时间 |
| attempt_count | 已执行次数 |
| max_attempts | 最大尝试次数 |
| idempotency_key | 幂等键 |
| started_at / finished_at | 开始及结束时间 |
| result_ref | 结果引用 |
| error_code / error_summary | 错误代码及摘要 |

### 9.3 任务状态建议

```text
PENDING
   ↓
QUEUED
   ↓
RUNNING
   ├── SUCCEEDED
   ├── RETRY_WAIT
   ├── WAITING_HUMAN
   ├── FAILED
   └── CANCELLED
```

具体状态及转换规则在详细设计时统一。任务状态变更应有合法转换校验和状态历史记录。

### 9.4 Worker 认领机制

MySQL 持久化任务表 + 独立 Worker 是已确认的基础方案。实施时需设计：
- 原子认领，避免多个 Worker 同时领取同一任务。
- 认领租约及过期回收。
- Worker 心跳或执行存活判断。
- 幂等键和重复执行防护。
- 状态更新事务。
- 失败任务重新进入队列的规则。

不要只使用“先查询 PENDING、再更新 RUNNING”的非原子流程，否则并发 Worker 可能重复认领同一任务。

### 9.5 可行性判断

MySQL 任务表和独立 Worker 可支撑初期任务中心，不需要立即引入 Redis 或独立消息队列。

**结论：有条件可行。** 原子认领、租约、幂等和故障恢复需要通过并发及故障注入测试。

## 十、异步任务、并发控制和资源限制

### 10.1 用户确认方案

- 采用异步任务执行。
- 耗时任务进入任务中心，由 Worker 后台处理。
- 统一任务中心实施全局、数字员工和任务类型三级并发限制。
- 统一管理任务优先级、超时时间、重试次数、模型并发及资源使用限制。

### 10.2 异步执行流程

```text
API 接收请求
   ↓
校验并创建任务
   ↓
MySQL 保存任务
   ↓
返回 task_id
   ↓
Worker 后台认领任务
   ↓
执行 Workflow / Agent
   ↓
更新任务状态及结果
   ↓
前端查询任务进度
```

API 不应长期占用 HTTP 请求等待整个 AI 任务结束。任务状态通过查询接口或平台内部通知反馈。

### 10.3 三级并发控制

| 层级 | 控制范围 | 示例 |
|---|---|---|
| 全局并发 | 平台全部任务总量 | 限制所有 Worker 同时执行数 |
| 数字员工并发 | 单个数字员工的同时执行量 | 限制某数字员工并行处理任务数 |
| 任务类型并发 | 同类任务的同时执行量 | 简历解析和画像生成分别限流 |

并发额度应在任务认领和释放时可靠维护，不能仅依赖前端限制。

### 10.4 资源管理

建议分别控制：
- Worker 任务并发。
- 模型推理并发。
- 单任务超时时间。
- 单任务最大重试次数。
- 任务优先级及排队策略。
- 单个数字员工并发上限。
- 单类任务并发上限。
- 模型服务超时和资源保护。

Worker 并发与 Ollama 模型推理并发不是同一指标，应分开设置。具体阈值须根据实际 CPU、内存、GPU 显存、模型大小和业务负载测试确定，不在可行性阶段虚构固定数值。

### 10.5 可行性判断

采用 MySQL 任务表、独立 Worker 和受控并发策略可以实现。初期不引入 Redis，与已确认基础技术基线一致。

**结论：有条件可行。** 多级并发额度的一致性、任务公平性及本地模型资源上限需要测试。

## 十一、失败、超时、重试与人工介入

### 11.1 用户确认方案

自动重试；超过重试次数后转人工处理；支持暂停、取消和人工重新执行。

### 11.2 异常处理分类

| 异常类型 | 建议处理 |
|---|---|
| 暂时性网络错误 | 有限次数自动重试 |
| 模型服务暂时不可用 | 退避重试，超限后转人工处理 |
| 模型输出结构不合规 | 有限修复或重新请求，仍失败则转人工 |
| 参数校验失败 | 不盲目重试，修正参数后重新执行 |
| 权限不足 | 立即拒绝，不自动重试 |
| 业务规则不满足 | 进入业务分支，不作为系统故障处理 |
| Worker 意外退出 | 通过租约超时识别任务并按恢复规则处理 |
| 外部副作用结果不确定 | 先查询或核对执行结果，再决定是否重试 |

### 11.3 重试机制

应配置：
- 最大重试次数。
- 重试间隔和退避策略。
- 可重试与不可重试错误分类。
- 单次执行超时。
- 幂等键。
- 人工重新执行权限。
- 每次尝试的执行记录。

对创建档案、发送通知、提交测评结果等有副作用的操作，不能不加判断地自动重试。应先验证上一次操作是否已经成功，避免重复执行。

### 11.4 暂停、取消和人工重新执行

- 暂停：阻止后续节点或任务继续调度；正在运行的模型调用能否即时中止取决于执行组件。
- 取消：标记任务取消并阻止未开始的后续操作；对已经完成的外部副作用不能简单视为撤销。
- 人工重新执行：保留原任务和尝试记录，创建新的执行尝试或受控重跑记录，不覆盖历史结果。
- 超限转人工：保存异常原因、最近执行节点和必要上下文，等待有权限人员处理。

### 11.5 可行性判断

技术路径明确，可由任务中心、Worker 和 LangGraph 执行状态协同实现。

**结论：有条件可行。** 暂停/取消语义、幂等和副作用恢复需要端到端验证。

## 十四、数字员工身份、权限和操作审计

### 14.1 用户确认方案

数字员工继承用户、角色及业务任务授权；执行前校验权限；记录完整操作审计。

### 14.2 权限判断原则

数字员工不是独立的人类用户身份，也不能自行获得系统管理员权限。每次执行必须有可追溯的发起主体和授权上下文。

建议权限判断综合考虑：
- 发起用户身份。
- 用户角色。
- 用户所属组织及数据范围。
- 业务任务授权。
- 数字员工职责范围。
- Workflow 允许的操作。
- Agent 和 Tool 的细粒度权限。

有效权限应取各层授权约束后的交集，不允许下层配置扩大上层授权范围。

### 14.3 执行前权限校验

```text
任务发起人
   ↓
用户身份认证
   ↓
角色与组织权限校验
   ↓
业务数据范围校验
   ↓
数字员工职责校验
   ↓
Workflow / Agent / Tool 权限校验
   ↓
执行操作
   ↓
记录审计结果
```

涉及正式业务数据写入的操作，仍由业务服务再次执行权限和业务规则校验。该原则与第五步 AI 中台数据边界方案保持一致。

### 14.4 审计内容

至少记录：
- 操作人及角色。
- 数字员工标识及版本。
- 任务编号。
- 操作类型。
- 目标业务对象。
- 权限检查结果。
- Workflow、Agent 和 Tool 版本引用。
- 操作时间。
- 执行结果。
- 失败或拒绝原因。

### 14.5 可行性判断

可复用平台用户、角色、组织和数据范围权限体系，并增加数字员工职责及任务授权校验。无需另建一套与平台用户体系隔离的权限系统。

**结论：有条件可行。** 需要在后续安全专项中验证权限继承、跨组织数据隔离、越权拒绝和审计完整性。
