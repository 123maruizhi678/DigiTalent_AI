## 一、设计目标与范围

本文档依据第四阶段第05步五批共30项确认结果，明确后端整体架构、代码分层、七大业务模块组织、数据访问边界、数据库
Session 与事务管理、LangChain 和 LangGraph 的职责、Agent 与 Tools
的调用约束，以及异常、日志、配置、安全和测试规范。

本文件属于后端概要架构设计，不等同于详细接口设计或完整代码实现。具体 API
路径、请求响应字段、数据库表结构、Agent/Workflow
节点定义、权限矩阵和测试用例，应在后续详细设计与开发阶段继续明确。

### 1.1 业务范围

后端架构覆盖平台七大业务模块：

1.  人才选拔。
2.  人才档案与人才画像。
3.  智能测评与面试。
4.  AI Agent 与工作流管理。
5.  数字员工与任务调度。
6.  数据智能与运营决策。
7.  用户、组织与权限管理。

当前不纳入业务范围：岗前培养与培训课程、企业知识库。

### 1.2 已确认技术基线

  技术或组件     已确认用途
  -------------- ------------------------------------------------
  FastAPI        后端 Web/API 框架
  Pydantic       请求、响应及数据结构验证
  SQLAlchemy     ORM、数据库访问、Session 和事务管理
  PyMySQL        MySQL 驱动
  MySQL 8.0.44   核心关系型数据库
  LangChain      模型调用、Prompt、Tools、结构化输出及检索能力
  LangGraph      多步骤 AI 工作流、状态管理、暂停恢复和人工介入
  Milvus         向量数据与相似度检索
  Vue 3          前端技术基线，前后端通过 API 协作

当前暂不使用
Redis。消息队列尚未确认选型，不应在实现中默认依赖某种消息中间件。

### 1.3 总体设计原则

-   采用模块化单体架构，不在初期拆分微服务。
-   使用统一 FastAPI 应用入口和路由注册机制。
-   七大业务模块独立组织，每个模块内部遵循统一分层。
-   API、Schema、Service、Repository、Model 职责清晰。
-   SQLAlchemy Model 与 Pydantic Schema 独立定义。
-   Repository 只负责数据访问；Service 承载业务规则和业务流程。
-   数据库 Session 通过 FastAPI 依赖注入管理。
-   事务由业务 Service 或明确的事务协调器管理。
-   跨模块通过公开 Service 接口协作，避免直接访问其他模块 Repository。
-   LangChain 负责模型与工具能力，LangGraph 负责复杂工作流编排。
-   Agent 和 Tools 不得绕过权限与业务 Service 直接修改核心业务数据。
-   异常、日志、配置、认证和测试采用统一工程规范。

### 2.3 第三批：数据访问、业务服务与事务管理

  ------------------------------------------------------------------------------------
  项目                    选择                    最终确认结果
  ----------------------- ----------------------- ------------------------------------
  13\. Repository 职责    A                       只负责数据访问，不承载业务规则

  14\. Service 职责       A                       负责业务规则、业务流程和模块内协调

  15\. Session 管理       A                       FastAPI 依赖注入创建请求级
                                                  Session，请求结束后释放

  16\. 事务管理位置       A                       由业务 Service 或事务协调器统一管理

  17\. 跨模块调用         A                       通过其他模块公开的 Service 接口协作

  18\. 长流程与业务事件   A                       同步 Service
                                                  调用与异步事件结合，复杂流程由
                                                  LangGraph 或业务协调机制管理
  ------------------------------------------------------------------------------------

整合结论： - Repository 封装 SQLAlchemy
查询和持久化，不实现复杂业务判断，也不随意调用其他模块 Service。 -
Service 组织业务规则、多个 Repository
操作、必要的跨模块调用和事务协调，不处理 HTTP 协议细节。 - FastAPI
Dependency 创建请求级 Session；同一业务操作涉及的 Repository
使用相同事务上下文；请求结束后关闭 Session。 - Repository
不自行随意提交事务，避免事务边界分散。 - 跨模块通过公开 Service
接口协作，禁止随意跨模块修改核心业务表。 -
简单业务操作采用同步调用；需要解耦的状态变化可采用业务事件；长时间 AI
流程由 LangGraph 管理。 -
当前没有确认消息队列选型。事件持久化、可靠投递、重试和失败补偿需在后续事件机制详细设计中确定，不能默认依赖
Redis 或其他未选型中间件。

### 2.4 第四批：Agent、Workflow 与后端业务集成

  --------------------------------------------------------------------------------------------------------
  项目                    选择                    最终确认结果
  ----------------------- ----------------------- --------------------------------------------------------
  19\. LangChain 职责     A                       模型调用、Prompt、Tools、结构化输出和检索能力

  20\. LangGraph 职责     A                       管理多步骤、分支、状态、暂停恢复和人工介入的复杂工作流

  21\. Agent 定位         A                       可复用智能能力单元，由 Service 或 Workflow 调用

  22\. Workflow 组织      A                       按业务场景定义独立 Workflow，由 LangGraph 管理执行

  23\. Tools 组织         A                       按业务模块封装，Agent 只能调用授权工具

  24\. AI 结果处理        A                       AI 输出经过业务 Service 校验后再写入正式业务数据
  --------------------------------------------------------------------------------------------------------

整合结论： - LangChain
是模型和工具能力集成层，负责模型调用、Prompt、Tools
封装、结构化输出及必要的检索能力。 - LangGraph 是复杂 AI
工作流编排层，负责多步骤执行、条件分支、状态管理、暂停恢复、人工介入和
Checkpoint。 - Agent 是可复用的智能能力单元，由业务 Service 或 Workflow
按需调用；不直接管理核心业务数据库事务。 - Workflow
按业务场景拆分，例如简历筛选、岗位人才匹配、测评执行、面试辅助和数字员工任务执行。 -
Tools 按业务模块封装，明确工具输入输出、授权范围和权限校验。 - AI
输出必须经过格式校验、业务规则校验和权限校验；必要时经过人工确认，再由业务
Service 决定是否持久化。 - 模型返回成功不等于业务操作成功。

## 三、后端整体架构

### 3.1 架构模式

采用模块化单体（Modular Monolith）：

-   一个 FastAPI 应用统一启动和部署。
-   七大业务模块在同一应用中独立组织。
-   模块拥有清晰的业务职责和数据访问边界。
-   模块间通过公开 Service 接口协作。
-   不在初期引入微服务拆分带来的网络通信、部署和运维复杂度。
-   后续是否拆分服务，由实际业务规模、团队协作和运行瓶颈决定。

### 3.2 总体调用关系

``` mermaid
flowchart TB
    Client[Vue 3 前端 / 外部调用方]
    API[FastAPI API 层]
    Schema[Pydantic Schema]
    Service[业务 Service 层]
    Repo[Repository 层]
    Model[SQLAlchemy Model]
    DB[(MySQL)]
    LC[LangChain 能力层]
    LG[LangGraph 工作流层]
    Agent[Agent 与 Tools]
    Milvus[(Milvus)]
    File[文件存储系统]

    Client --> API
    API --> Schema
    API --> Service
    Service --> Repo
    Repo --> Model
    Model --> DB
    Service --> LC
    Service --> LG
    LG --> Agent
    Agent --> LC
    Agent --> Service
    Service --> Milvus
    Service --> File
```

说明： - Schema 是 API
输入输出的数据结构定义，不是必须逐层调用的独立运行层。 - Agent 通过受控
Tools 使用业务能力，不能绕过 Service 直接修改核心业务数据。 - MySQL
保存权威业务数据；Milvus 负责向量检索；文件本体由文件存储系统保存。

### 3.3 五层职责

  ---------------------------------------------------------------------------------------------
  层                      主要职责                                 不应承担的职责
  ----------------------- ---------------------------------------- ----------------------------
  API                     HTTP                                     复杂业务规则和直接编写大量
                          路由、依赖注入、认证授权入口、请求响应   SQL

  Schema                  请求、响应、数据结构和格式验证           数据库持久化和业务流程编排

  Service                 业务规则、业务流程、模块协调、事务边界   HTTP 协议处理和底层 SQL 细节

  Repository              数据查询、增删改、持久化                 业务决策和跨模块流程编排

  Model                   SQLAlchemy 数据库实体映射                API
                                                                   请求响应模型和前端数据契约
  ---------------------------------------------------------------------------------------------

## 五、七大业务模块职责与边界

### 5.1 人才选拔 `candidate`

负责： - 招聘需求及岗位信息。 - 候选人管理。 - 简历上传和关联。 -
简历解析结果的业务接收与筛选。 - 岗位与人才匹配业务流程。 -
选拔过程及状态管理。

不负责： - 正式人才档案的权威管理。 -
测评评分规则和面试报告的权威管理。 - 通用 Agent/Workflow 引擎实现。

### 5.2 人才档案与画像 `talent`

负责： - 正式人才档案。 - 教育经历和工作经历。 -
技能、标签和人才画像。 - 人才档案历史和必要版本信息。

候选人转为正式人才时，通过 talent 模块公开 Service 创建或关联档案。

### 5.3 智能测评与面试 `assessment`

负责： - 测评方案和题目。 - 测评任务和答题记录。 - 评分及测评报告。 -
面试安排、面试记录和辅助评价。 - 测评与面试过程状态。

测评结果可以提供给人才画像流程使用，但其原始业务记录仍由 assessment
管理。

### 5.4 AI Agent 与工作流 `agent`

负责： - Agent 定义和配置。 - Prompt 管理。 - Tools 注册和授权。 -
Workflow 定义及版本。 - LangGraph 执行、Checkpoint 和运行记录。 -
模型调用适配和 AI 执行观测所需的业务记录。

不负责： - 直接替代各业务模块的核心 Service。 -
绕过业务权限和事务规则写入业务数据。

### 5.5 数字员工与任务调度 `employee`

负责： - 数字员工定义和业务身份。 - 能力配置。 - 任务分配与调度。 -
执行状态和记录。 - 调用 Agent/Workflow 完成任务的业务协调。

Agent 是可调用的智能能力；数字员工是承载任务和能力配置的业务对象。

### 5.6 数据智能与运营决策 `analytics`

负责： - 指标定义。 - 统计任务。 - 运营分析。 - 报表和决策支持。 -
必要的汇总结果和报告元数据。

统计分析通过授权的数据服务读取各模块数据，避免任意跨模块修改业务表。

### 5.7 用户、组织与权限 `system`

负责： - 用户和账号。 - 组织及组织关系。 - 角色和权限。 -
认证、授权及组织数据范围。 - 关键安全操作审计。

账号策略遵循此前确认的邀请制和后台创建原则；具体认证协议、令牌策略和权限矩阵在后续安全及权限详细设计中明确。

## 六、Repository、Service 与跨模块协作

### 6.1 Repository 规则

-   只负责持久化和查询。
-   接收必要的 Session 或事务上下文。
-   不在 Repository 内部随意创建全局 Session。
-   不自行决定跨模块业务流程。
-   不在 Repository 中随意提交事务。
-   复杂查询可以封装在 Repository，但业务含义和决策由 Service 负责。

### 6.2 Service 规则

-   负责业务规则和流程。
-   组织本模块多个 Repository 操作。
-   调用其他模块公开 Service。
-   协调事务和必要的外部能力。
-   对 AI 输出进行业务校验。
-   不依赖 FastAPI Request/Response 等 HTTP 对象作为核心业务输入。

### 6.3 跨模块依赖

推荐调用关系示意：

``` mermaid
flowchart LR
    Candidate[candidate Service]
    Talent[talent Service]
    Assessment[assessment Service]
    Agent[agent Service]
    Employee[employee Service]
    Analytics[analytics Service]
    System[system Service]

    Candidate --> Talent
    Candidate --> Assessment
    Employee --> Agent
    Analytics --> Candidate
    Analytics --> Talent
    Analytics --> Assessment
    System --> Candidate
    System --> Talent
    System --> Assessment
    System --> Agent
    System --> Employee
```

此图表示可能的服务协作方向，不代表所有调用都必须实现，也不构成允许循环依赖的依据。详细设计时应逐项确认依赖方向，避免环形依赖。

### 6.4 业务事件

需要解耦的状态变化可通过业务事件通知其他模块。当前尚未选定消息中间件，因此事件机制的初期实现方式、持久化、投递保证、重试和补偿仍需单独设计。重要事件不能仅依赖进程内临时回调而假定具备可靠投递能力。

## 七、数据库 Session 与事务管理

### 7.1 请求级 Session

使用 FastAPI Dependency 创建请求级 SQLAlchemy
Session，并在请求处理结束后释放。

基本调用关系：

``` text
HTTP 请求
  -> FastAPI Dependency 创建 Session
  -> API 调用 Service
  -> Service 调用 Repository
  -> Repository 使用同一 Session 访问 MySQL
  -> 业务操作结束
  -> 提交或回滚
  -> 关闭 Session
```

不得将一个 SQLAlchemy Session 实例作为全局共享对象供并发请求使用。

### 7.2 事务边界

-   由业务 Service 或明确的事务协调器管理事务。
-   一个业务操作涉及多个 Repository 时，应共享合理的事务上下文。
-   成功提交，异常回滚。
-   Repository 不自行随意提交。
-   不在耗时模型调用、人工等待或长时间 Workflow 执行期间持有数据库事务。
-   跨模块长流程采用分阶段持久化、状态推进和事件协调。

### 7.3 后台任务与 Workflow Session

后台任务和 LangGraph 执行不应持有来自 HTTP 请求的 Session
长时间运行。后台执行需要在每个短事务操作时创建和释放自己的数据库会话，并明确任务状态持久化与失败恢复策略。

## 八、LangChain、LangGraph、Agent 与 Tools 集成

### 8.1 职责划分

  ------------------------------------------------------------------------------------------
  组件                                职责
  ----------------------------------- ------------------------------------------------------
  LangChain                           模型调用、Prompt、Tools 封装、结构化输出及必要检索

  LangGraph                           多步骤流程、条件分支、状态管理、暂停恢复、人工介入和
                                      Checkpoint

  Agent                               可复用智能能力单元，执行推理和授权工具调用

  Tools                               向 Agent 提供受控业务能力

  Service                             业务规则、权限后的业务操作、结果校验和事务

  Repository                          正式业务数据持久化
  ------------------------------------------------------------------------------------------

### 8.2 Workflow 按场景组织

建议的 Workflow 场景包括： - 简历筛选 Workflow。 - 岗位人才匹配
Workflow。 - 智能测评执行 Workflow。 - 面试辅助 Workflow。 -
数字员工任务执行 Workflow。

以上为规划场景，具体 Workflow
数量、节点、状态和调用关系应在工作流详细设计中确定。

### 8.3 Tools 设计规范

Tools 按业务模块组织，例如：

``` text
agent/
└── tools/
    ├── candidate/
    ├── talent/
    ├── assessment/
    ├── employee/
    └── analytics/
```

每个 Tool 应明确： - 工具名称和用途。 - 输入参数 Schema。 - 输出结构。 -
调用主体和授权范围。 - 权限检查。 - 超时与异常处理。 -
是否具有写操作副作用。 - 幂等要求和审计要求。

禁止向 Agent 暴露任意 Python 执行、任意 SQL 执行或不受控的文件系统操作。

### 8.4 AI 输出进入业务系统的流程

``` mermaid
flowchart TD
    Start[Service 或 Workflow 发起 AI 任务]
    Agent[Agent / LangChain 执行]
    Output[生成结构化输出]
    Schema[Schema 格式校验]
    Rule[Service 业务规则校验]
    Auth[权限与数据范围校验]
    Human{是否需要人工确认}
    Persist[Repository 持久化]
    Result[返回业务结果]
    Reject[拒绝、修正或记录失败]

    Start --> Agent --> Output --> Schema
    Schema --> Rule
    Rule --> Auth
    Auth --> Human
    Human -->|需要| Review[人工审核]
    Review -->|通过| Persist
    Review -->|拒绝| Reject
    Human -->|不需要| Persist
    Persist --> Result
    Schema -->|失败| Reject
    Rule -->|失败| Reject
    Auth -->|失败| Reject
```

模型输出不能直接视为业务成功。所有写入必须经过业务
Service，必要时要求人工确认。

## 九、统一异常处理

### 9.1 异常分类

建议至少区分： - 参数验证异常。 - 认证异常。 - 授权异常。 -
业务规则异常。 - 数据不存在或状态冲突异常。 - 数据库访问异常。 -
外部服务异常。 - AI 模型调用异常。 - Workflow 执行异常。 -
未预期系统异常。

### 9.2 统一错误响应

全局异常处理器将异常转换为统一 API 错误结构。建议包含： - 错误编码。 -
面向调用方的安全错误消息。 - 请求追踪标识。 - 必要的字段验证详情。

不得向前端返回数据库密码、SQL
参数、堆栈、内部文件路径或密钥等敏感内部信息。详细错误信息写入受控日志。

## 十、统一日志与请求追踪

### 10.1 日志规范

建立统一日志模块，支持： - DEBUG、INFO、WARNING、ERROR 等级。 -
结构化日志字段。 - 请求 ID 或 Trace ID。 -
用户或任务关联标识（遵循最小必要原则）。 - 异常堆栈记录。 -
敏感信息脱敏。

### 10.2 日志分类

建议区分： - 应用运行日志。 - API 请求日志。 - 业务操作日志。 -
安全审计日志。 - 数据库异常与慢查询相关日志。 - Agent/Workflow
执行日志。

AI 执行日志应记录必要的执行状态、耗时、模型或 Workflow
标识和错误信息；不得无差别记录完整简历、身份证号、密码、API Key
或其他敏感内容。

## 十一、配置管理与环境隔离

### 11.1 配置方式

使用 Pydantic Settings 统一读取环境变量和
`.env`，按开发、测试和生产环境区分配置。

配置类别包括： - 应用名称、环境和调试开关。 - MySQL 连接。 - Milvus
连接。 - Ollama 或云端模型服务连接。 - MinerU 服务地址。 -
文件存储配置。 - 日志配置。 - 安全认证配置。 - 外部服务超时和重试参数。

### 11.2 安全要求

-   真实密码和 API Key 不写入源代码。
-   `.env` 不提交到 Git。
-   `.env.example` 只保留变量名称和非敏感示例值。
-   不同环境使用不同凭据。
-   配置启动时进行类型和必要性校验。
-   生产环境关闭调试模式。

## 十二、身份认证、权限与 API 安全

### 12.1 统一认证与授权

建立统一认证和权限依赖机制，API 请求应根据当前用户身份进行： -
身份认证。 - 角色和操作权限检查。 - 组织数据范围检查。 -
资源归属检查。 - 敏感操作审计。

### 12.2 前后端权限边界

前端菜单和按钮权限只用于界面展示，不构成真正的安全边界。所有权限必须在后端
API 或业务 Service 层进行校验。

### 12.3 Agent Tools 权限

Agent Tools 必须继承或显式验证调用主体的权限上下文，不得因为调用来自
Agent 而绕过用户、组织或资源权限。

### 12.4 认证细节待后续确定

认证协议、令牌类型与有效期、刷新策略、会话撤销、密码策略、组织数据范围规则和权限矩阵，应在后续认证与权限详细设计中确定。

## 十三、测试与质量管理

### 13.1 测试分层

  测试类型          主要覆盖内容
  ----------------- ----------------------------------------------------
  单元测试          Service 业务规则、工具函数、状态转换
  API 测试          路由、参数验证、响应结构、认证授权
  Repository 测试   查询、持久化、唯一约束和外键行为
  数据库集成测试    Session、事务提交、回滚和并发冲突
  AI 能力测试       Prompt、结构化输出、Tools 输入输出
  Workflow 测试     节点执行、条件分支、Checkpoint、暂停恢复和失败路径
  业务流程测试      简历筛选、人才匹配、测评面试、任务执行等端到端流程

### 13.2 测试原则

-   使用 pytest 建立自动化测试体系。
-   测试环境与开发环境数据隔离。
-   测试不依赖生产真实个人信息。
-   外部模型调用应具备可控测试替代方式或固定测试样例。
-   对 AI
    非确定性输出，优先验证结构、约束和业务结果，不只依赖某一句固定文本。
-   对权限、事务、失败重试和数据一致性进行专项测试。

### 13.3 代码质量

后续应结合项目实际配置代码格式化、静态检查、类型检查和自动化测试。具体工具及质量门槛在工程规范或开发规范中确认。
