## 3. 当前设计基线

### 3.1 核心数据模型

- `sys_user`：19列，18个普通字段及1个生成列。
- `sys_organization`：10列，9个普通字段及1个生成列。组织与部门统一建模，不建立独立`sys_department`。
- `sys_user_organization`：9列，7个普通字段及2个生成列。用户与组织节点为多对多关系。
- 总计38列、14个索引、3个外键、12个CHECK约束、3个不可恢复触发器。

### 3.2 关键业务规则

- UUID数据库存储为`CHAR(32)`；不修改公共Base、Mixin和UUID类型。
- 用户状态为`active/inactive/locked`；组织状态为`active/inactive`。
- 用户名、邮箱、电话及组织编码仅对未删除记录执行有效唯一约束；逻辑删除释放唯一值。
- 每个用户可关联多个组织/部门，可同时关联父组织及下属部门；最多一个有效主要归属，也允许没有主要归属。
- 组织树允许`group`和`company`作为根，`department`不能作为根；非根合法关系为`group→company`、`company→department`、`department→department`。
- 逻辑删除不可恢复；用户删除与关联删除在统一事务中完成；组织存在有效下级或用户关联时禁止删除。
- 不引入Redis，不新增独立邀请表、部门表或审计数据库表。

### 3.3 技术与事务规则

- MySQL使用InnoDB、utf8mb4及`utf8mb4_0900_bin`；目标版本为MySQL 8.0.17及以上。
- 外键采用RESTRICT；有效唯一由生成列及唯一索引实现；树结构写操作使用统一锁协议及事务校验。
- 邀请Token只保存SHA-256摘要；当前邀请状态保存在用户表，过程事件写结构化审计日志。
- 审计日志采用每进程唯一写入器和线程锁；序号分配、单行写入、flush/fsync及轮转在同一文件临界区内完成。文件日志与MySQL事务不具备跨介质原子性，未知提交结果必须保留为UNKNOWN并按真实数据库状态核查。
- 批量组织树调整须校验最终图及每一步中间状态；无法形成安全执行序列时整批拒绝。

## 5. 开发实施前置条件

以下属于实施验证，不属于待用户确认的业务决策：

1. 开发前检查实际MySQL版本、SQL模式、CHECK执行能力、排序规则及数据库身份。
2. ORM模型必须复用项目统一Base、UUID Mixin、时间字段Mixin和状态Mixin，所有模型注册到统一metadata。
3. 建表 SQL 需显式管理生成列、CHECK、外键、索引及3个不可恢复触发器。
4. 在隔离MySQL环境验证38列、14索引、3外键、12个CHECK及3个触发器。
5. 对邀请并发、组织树并发、批量树调整、审计文件短写/fsync失败、轮转、重启及数据库提交未知等场景进行测试。
6. 存量数据库必须先盘点表结构、历史数据和外部引用；不得将开发目录无模型推断为数据库为空。历史数据清洗、生产切换和运维操作需按具体环境另行授权。
