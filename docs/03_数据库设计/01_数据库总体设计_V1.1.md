## 一、设计目标与范围

本文件依据第四阶段第04步五批共30项确认结果，明确 AI
数字化人才平台的数据库总体架构、命名规范、主键与业务标识、字段类型、约束、索引、查询、文件存储、连接池、事务、并发、安全、备份、迁移、监控、归档、扩展及验收原则。

本文件属于数据库总体设计，不等同于最终数据库详细设计或数据库初始化脚本。具体表清单、字段长度、精度、默认值、索引组合、外键名称、结构变更 SQL 和
SQL DDL，应在后续数据库详细设计及开发阶段逐项确定。

### 1.1 业务范围

数据库设计覆盖平台七大业务模块：

1.  人才选拔。
2.  人才档案与人才画像。
3.  智能测评与面试。
4.  AI Agent 与工作流管理。
5.  数字员工与任务调度。
6.  数据智能与运营决策。
7.  用户、组织与权限管理。

同时覆盖文件、通知、审计、业务事件及导入导出等公共数据能力。

当前不纳入业务范围：岗前培养与培训课程、企业知识库。

### 1.2 已确认技术基线

  项目           确认方案
  -------------- ---------------------------------------------------------
  关系型数据库   MySQL 8.0.44
  业务数据库     `agent_service`（此前确认的数据库名称，实施前核对配置）
  ORM            SQLAlchemy
  MySQL 驱动     PyMySQL
  数据库结构变更 人工维护的 SQL 文件
  时间字段       `DATETIME`，按 UTC 保存
  主键存储       `CHAR(32)` UUID
  业务唯一标识   UUID 字符串
  缓存           暂不使用 Redis
  向量数据库     Milvus，职责与 MySQL 分离

### 1.3 设计原则

-   一个 MySQL 业务数据库统一管理业务数据，按模块划分表和数据归属。
-   表名、字段名统一采用小写英文和下划线命名。
-   数据库主键与业务唯一标识分开设计。
-   核心业务数据优先结构化存储，JSON 仅用于灵活配置和非固定结构数据。
-   根据实际查询场景建立索引，不盲目增加索引。
-   核心业务表建立必要的外键约束。
-   模块通过自身 Repository/DAO 和 Service 管理数据访问。
-   事务以业务服务操作为边界，使用 SQLAlchemy Session 管理。
-   MySQL 保存权威业务数据，Milvus 负责向量数据和相似度检索。
-   数据库结构版本由人工维护的 SQL 文件管理，结构变更须经人工审核与授权后执行。
-   根据数据类型制定归档、保留和删除策略。

## 三、数据库整体架构

### 3.1 总体结构

采用单 MySQL
业务数据库，按模块前缀组织数据表。各业务模块在应用层保持数据访问边界。

``` mermaid
flowchart TB
    API[FastAPI API 层]
    SVC[业务 Service 层]
    REPO[模块 Repository / DAO]
    DB[(MySQL 业务数据库)]
    FILE[文件存储系统]
    MILVUS[(Milvus 向量数据库)]

    API --> SVC
    SVC --> REPO
    REPO --> DB
    SVC --> FILE
    SVC --> MILVUS
```

### 3.2 数据库与存储职责

  ----------------------------------------------------------------------------------------------------------------
  存储组件                权威数据或职责                              不承担的职责
  ----------------------- ------------------------------------------- --------------------------------------------
  MySQL                   用户、组织、候选人、人才档案、测评、Agent   不承担大规模原始文件存储和向量相似度检索
                          配置、任务、指标、报告等结构化业务数据      

  文件存储系统            简历、附件、报告文件等文件本体              不替代 MySQL 中的业务元数据和权限关系

  Milvus                  Embedding 向量、向量检索及相似度匹配        不作为人才档案或其他核心业务数据的权威来源
  ----------------------------------------------------------------------------------------------------------------

Milvus 中的向量记录应保留可关联到 MySQL
业务对象的标识。向量数据应支持根据权威业务数据重新生成或重建。

### 3.3 数据库部署演进

初期采用单 MySQL
实例，不提前引入复杂集群、分库分表架构。根据实际数据量、并发量、慢查询和资源指标，逐步评估：

1.  SQL 和索引优化。
2.  MySQL 实例资源纵向扩展。
3.  统计查询汇总或预计算。
4.  读写分离。
5.  表分区或分库分表。

是否采用后续扩展方案必须由实际瓶颈和容量评估驱动。

## 四、数据库命名规范

### 4.1 数据库名称

当前沿用已确认的数据库名称：

`agent_service`

实施前应核对项目当前
`.env`、数据库实例和数据库配置，避免因项目名称调整造成数据库名称不一致。

### 4.2 表名前缀

  -----------------------------------------------------------------------------------------
  前缀                    模块                    示例
  ----------------------- ----------------------- -----------------------------------------
  `candidate_`            人才选拔                `candidate_profile`、`candidate_resume`

  `talent_`               人才档案与人才画像      `talent_profile`、`talent_skill`

  `assess_`               智能测评与面试          `assess_task`、`assess_report`

  `agent_`                AI Agent 与工作流       `agent_config`、`agent_workflow`

  `employee_`             数字员工与任务调度      `employee_profile`、`employee_task`

  `analytics_`            数据智能与运营决策      `analytics_metric`、`analytics_report`

  `sys_`                  用户、组织与权限管理    `sys_user`、`sys_role`
  -----------------------------------------------------------------------------------------

公共业务对象的最终前缀和归属模块应在详细表设计中确定，避免公共表在多个模块重复创建。

### 4.3 表名与字段名

-   统一小写英文。
-   单词之间使用下划线。
-   避免拼音和中文字段名。
-   避免使用 MySQL 保留字。
-   名称应表达稳定的业务含义。
-   关联表名称应体现双方对象或业务关系。

### 4.4 常用字段命名

  字段           含义
  -------------- ------------------------
  `id`           数据库主键
  `created_at`   创建时间
  `updated_at`   更新时间
  `deleted_at`   逻辑删除时间
  `created_by`   创建人标识
  `updated_by`   最后更新人标识
  `status`       所属对象的业务状态
  `version`      乐观锁版本号（适用时）

并非所有表都必须包含完全相同的字段，应根据对象性质确定；审计类、事件类和只追加记录类数据需要采用适合自身的数据模型。

## 五、主键与业务唯一标识设计

### 5.1 双标识原则

数据库主键和业务唯一标识分开设计：

  ------------------------------------------------------------------------------------------------------------
  标识                    用途                             示例字段
  ----------------------- -------------------------------- ---------------------------------------------------
  数据库主键              表内唯一标识及数据库关系         `id`

  业务唯一标识            业务识别、跨模块引用和接口交互   `talent_id`、`candidate_id`、`assessment_task_id`
  ------------------------------------------------------------------------------------------------------------

两类标识均应使用统一的 UUID
字符串规则，但必须分别生成，不能把同一个字段同时当作数据库主键和业务标识。

### 5.2 存储格式

-   数据库主键采用 `CHAR(32)`。
-   业务唯一标识采用 UUID 字符串。
-   对业务唯一标识按对象范围建立唯一约束。
-   统一 UUID 格式、大小写和连字符规则。
-   生成方式由应用层统一封装，禁止各模块自行采用不同生成规则。

### 5.3 业务标识使用规则

-   手机号、邮箱、身份证号等个人信息不得作为主键。
-   业务标识不应承载可推断的个人敏感信息。
-   外部接口应进行身份认证和权限校验，UUID 不等同于访问授权。
-   关联表应明确使用数据库主键还是业务标识，优先在数据库内部使用主键建立外键关系。

## 六、字段类型与数据完整性规范

### 6.1 常用字段类型建议

  ---------------------------------------------------------------------------------------
  数据类型                建议用途                   设计注意事项
  ----------------------- -------------------------- ------------------------------------
  `CHAR(32)`              UUID 主键及 UUID 业务标识  统一格式和大小写

  `VARCHAR(n)`            名称、编码、状态、短文本   根据业务长度确定 n

  `TEXT`                  较长文本内容               评估检索和索引需求

  `BIGINT`                数量、计数或较大整数       根据范围选择有符号或无符号

  `INT`                   版本号、较小整数           版本字段通常非负

  `DECIMAL(p,s)`          需要精确计算的数值         不使用浮点数保存要求精确的业务数值

  `TINYINT`               明确的布尔或小范围标志     在应用层统一语义

  `DATETIME`              时间字段                   按 UTC 保存

  `JSON`                  灵活配置和非固定结构       不替代核心关系字段和高频检索字段
  ---------------------------------------------------------------------------------------

最终长度、精度和可空性在详细表结构设计时确定。

### 6.2 外键约束

核心业务表建立必要的外键约束，特别是：

-   多对多关联表的双方关系。
-   人才经历与人才档案关系。
-   测评任务与测评方案关系。
-   Workflow 执行与 Workflow 版本关系。
-   任务执行与任务关系。
-   用户角色和角色权限关系。
-   报告与指标引用关系。

删除策略应保护历史业务记录，避免不加区分地使用
`ON DELETE CASCADE`。对需要保留的业务历史，优先使用停用、归档或受控删除。

### 6.3 唯一约束与非空约束

-   每张核心表必须有主键。
-   业务唯一标识按业务对象建立唯一约束。
-   必填业务属性设置非空约束。
-   关联表应防止重复关系记录。
-   对有明确业务范围的唯一性，使用组合唯一约束。
-   约束定义应与业务规则一致，不能仅为技术方便而增加不合理限制。

### 6.4 时间字段

统一使用 `DATETIME`，按 UTC 保存。

常用字段： - `created_at` - `updated_at` - `deleted_at` - `started_at` -
`completed_at`

应用层负责将用户本地时间转换为 UTC 或将 UTC
转换为展示时区。业务发生时间应根据具体业务语义单独命名。

### 6.5 状态字段

使用 `VARCHAR` 保存业务状态编码，由所属模块定义状态集合和合法流转规则。

示例值仅用于说明编码形式：

-   `pending`
-   `running`
-   `completed`
-   `failed`
-   `cancelled`

不同对象可以有不同状态集合，不将上述示例视为全平台统一状态枚举。

### 6.6 JSON 字段

适合使用 JSON 的场景： - Agent 灵活配置。 - Workflow 节点参数。 -
模型调用的非固定参数。 - 不适合拆分为稳定字段的扩展配置。

不适合整体使用 JSON 的场景： - 人才核心身份和档案字段。 -
高频检索的技能、标签和经历。 - 需要外键关联的业务对象。 -
需要强唯一约束和精确筛选的字段。

## 七、索引与查询设计

### 7.1 索引优先级

1.  主键索引。
2.  业务唯一标识唯一索引。
3.  核心外键字段索引。
4.  高频过滤字段索引。
5.  高频排序字段索引。
6.  根据真实查询模式建立联合索引。

不为所有字段机械地创建索引。索引会增加写入、更新和存储成本，应综合查询收益评估。

### 7.2 联合索引

联合索引应根据真实 SQL 查询条件、排序条件和过滤条件设计，遵循 MySQL
联合索引最左前缀等规则。

示例仅用于说明设计方式：

``` sql
CREATE INDEX idx_candidate_status_created
ON candidate_profile (status, created_at);
```

实际索引应在对应表结构和查询语句明确后确定，不应直接将示例当作最终 DDL。

### 7.3 分页策略

  场景               建议分页方式
  ------------------ ------------------
  普通人才列表       `LIMIT/OFFSET`
  普通候选人列表     `LIMIT/OFFSET`
  后台管理列表       `LIMIT/OFFSET`
  大量任务执行记录   游标分页
  大规模审计记录     游标分页
  深分页场景         优先评估游标分页

分页必须使用稳定排序字段。游标分页应使用唯一且稳定的排序键，必要时组合时间字段与主键。

### 7.4 查询优化

-   使用 `EXPLAIN` 分析执行计划。
-   开启并分析 MySQL 慢查询日志。
-   检查全表扫描和索引使用情况。
-   避免 ORM N+1 查询。
-   只读取业务所需字段。
-   对高频查询建立专项优化记录。
-   复杂统计查询不得无评估地影响核心业务请求。

## 八、文件与大字段存储

### 8.1 存储原则

数据库保存文件元数据和存储引用，文件本体存放在文件存储系统。

MySQL 文件记录可包含： - 文件数据库主键和业务标识。 - 原始文件名。 -
文件类型和 MIME 类型。 - 文件大小。 - 存储系统或存储位置引用。 -
上传主体和上传时间。 - 文件校验信息。 - 文件状态及必要的访问控制信息。

### 8.2 文件与业务对象关联

通过独立的文件业务关联对象连接候选人、简历、人才档案、测评报告等业务对象。文件访问必须经过业务权限校验，不能仅凭存储路径访问。

### 8.3 文件删除

删除文件前检查： - 是否仍被业务对象引用。 -
是否属于需要保留的历史材料。 - 当前操作者是否有删除权限。 -
是否满足数据保留和审计要求。

## 九、模块数据访问边界

### 9.1 模块访问原则

各模块通过自身 Repository/DAO 和 Service
管理数据访问。其他模块通过公开业务接口或专门查询服务获取数据。

  ---------------------------------------------------------------------------------
  模块                                权威管理的数据示例
  ----------------------------------- ---------------------------------------------
  人才选拔                            招聘需求、候选人、简历、选拔记录、匹配结果

  人才档案与画像                      正式人才档案、经历、技能、标签、人才画像

  智能测评与面试                      测评方案、测评任务、答题、评分、面试和报告

  Agent 与工作流                      模型配置关联、Agent、Prompt、Tool、Workflow
                                      及执行实例

  数字员工与任务调度                  数字员工、任务、分配和执行记录

  数据智能与运营决策                  指标定义、统计结果、分析任务和分析报告

  用户、组织与权限                    用户、组织、角色、权限和授权关系
  ---------------------------------------------------------------------------------

### 9.2 跨模块读取与修改

-   模块可以通过服务接口获取其他模块授权提供的数据。
-   模块不得随意直接修改其他模块的核心业务表。
-   允许建立只读查询或专门查询服务满足跨模块展示和分析需要。
-   跨模块操作应明确发起方、数据提供方和处理结果。
-   重要状态变化通过业务事件通知相关模块。
-   事件的幂等、重试、失败补偿和持久化策略在后续详细设计中确定。

## 十、事务与并发控制

### 10.1 事务边界

使用 SQLAlchemy Session 管理事务，以业务服务操作为事务边界。

-   同一业务操作涉及多张表时，在合理范围内统一提交。
-   发生异常时回滚。
-   请求或业务操作结束后释放 Session。
-   不在耗时的 AI 模型调用或长流程等待期间持有数据库事务。
-   跨模块长流程采用分阶段操作和业务事件协调，不使用跨整个流程的长事务。

### 10.2 乐观锁

对于可能发生并发修改且不希望互相覆盖的对象，可增加 `version` 字段。

更新时校验版本号： - 版本一致时允许更新并递增版本。 -
版本不一致时拒绝覆盖，返回并发冲突。 -
由业务层决定提示用户刷新、重新提交或进行冲突处理。

### 10.3 悲观锁

任务抢占、关键资源竞争等确实需要串行化的场景，可以使用 MySQL
行锁。应控制锁定范围和持有时间，并处理死锁重试，避免滥用锁影响吞吐量。

## 十一、数据安全与审计

### 11.1 敏感数据分级保护

重点关注： - 候选人和人才个人信息。 - 简历原始文件。 -
测评答题、评分和面试信息。 - 用户认证信息。 - 模型供应商 API
密钥及系统密钥。

根据数据敏感程度采取字段加密、文件访问控制、最小权限和审计措施。

### 11.2 密码与密钥

-   用户密码使用适当的密码哈希算法保存，不可明文存储。
-   模型 API 密钥、数据库密码等机密不写入代码仓库。
-   加密密钥与被加密的数据分离保存。
-   对密钥读取和使用实施权限控制。

### 11.3 审计

关键操作记录： - 操作主体。 - 操作对象及标识。 - 操作类型。 -
操作时间。 - 操作结果。 - 必要的来源信息。

审计记录应避免保存不必要的敏感明文。

------------------------------------------------------------------------

## 十二、备份与恢复

### 12.1 备份策略

-   定期执行全量备份。
-   根据恢复目标启用和保留 MySQL Binlog。
-   备份文件与数据库运行环境分离存放。
-   对备份文件实施访问控制。
-   定期验证备份文件完整性和可恢复性。

### 12.2 恢复能力

根据业务恢复目标评估： - RPO：可接受的数据恢复点目标。 -
RTO：可接受的服务恢复时间目标。 - 全量备份恢复。 - 基于 Binlog
的时间点恢复。

具体备份频率、保留期限、RPO 和 RTO
不在本总体设计阶段臆定，应结合实际运行要求确定。

------------------------------------------------------------------------

## 十三、数据库结构变更管理

### 13.1 人工维护 SQL 方案

数据库结构变更全部通过人工编写、人工审核、人工执行的 SQL 文件完成。

主要要求：

- 数据库初始化使用人工维护的初始化 SQL 文件（`sql/init.sql`），建表语句依据 SQLAlchemy ORM 定义人工编写，不由代码自动生成。
- 增量结构变更 SQL 放在 `sql/changes/`，按日期与用途命名，纳入版本控制。
- 每个变更 SQL 必须经人工审核与授权后方可执行，执行前说明目标数据库、影响范围和回滚方式。
- 开发、测试、生产环境按同一份已审核 SQL 推进，不使用自动升级或自动回滚机制。
- 变更前评估数据兼容性与执行风险；重要变更先备份，再执行，必要时由人工编写前向修复或回退 SQL。
- 不允许只修改数据库而不维护对应 SQL 文件和 ORM 模型；ORM 模型与 SQL 结构必须保持同步。

### 13.2 SQLAlchemy 职责

SQLAlchemy 负责 ORM 映射、查询、连接池和事务管理，不承担结构版本演进。不得使用 `metadata.create_all()` 自动建表替代人工审核的 SQL，也不得将开发环境的自动建表能力当作生产环境建库方案。

### 13.3 测试数据库隔离

- 开发、测试、生产环境统一使用 MySQL，数据库相关测试在独立的 MySQL 测试库中执行。
- pytest 连接独立的 MySQL 测试数据库，与开发库、生产库严格隔离：独立的库名、独立的连接配置、独立的凭据，不复用开发库或生产库。
- 测试库表结构同样通过人工维护并审核的 SQL 文件初始化，与开发库、生产库保持同一份结构基线。
- 禁止测试代码自动连接或修改生产数据库；测试配置中不得出现生产库地址。
- 涉及 MySQL 特性的约束（生成列、排序规则、并发、触发器、DDL 行为）只在 MySQL 环境验证并留证。

## 十四、连接池与运行监控

### 14.1 SQLAlchemy 连接池

统一通过 SQLAlchemy 管理连接池。需要配置和评估：

-   `pool_size`
-   `max_overflow`
-   `pool_timeout`
-   `pool_recycle`
-   `pool_pre_ping`

具体数值根据 MySQL
连接上限、应用并发、运行环境和压力测试确定，不在总体设计阶段固定。

### 14.2 监控内容

  类别       监控内容
  ---------- --------------------------------------------
  服务状态   MySQL 可用性、连接失败
  连接池     活跃连接、等待连接、连接超时
  查询性能   慢 SQL、执行时间、扫描行数
  事务       事务异常、长事务、回滚
  并发       死锁、锁等待、冲突
  资源       CPU、内存、磁盘、存储增长
  备份       备份任务状态、备份文件完整性、恢复验证结果

## 十五、历史数据归档与容量扩展

### 15.1 归档原则

按业务对象和数据类型制定归档策略，不统一采用永久保留或定期物理删除。

  数据类别             归档与保留方向
  -------------------- --------------------------------------
  候选人与选拔记录     按业务和合规要求保留，重要过程可归档
  人才档案             按人才档案管理和数据保留要求处理
  测评与面试记录       保留必要的业务追溯信息
  Workflow 执行记录    按执行追溯和运维分析需要归档
  任务执行记录         按任务审计和追溯要求归档
  审计日志             按安全审计和组织制度保留
  通知发送记录         按业务追溯需要保留或归档
  指标统计结果和报告   保留必要的历史统计结果和报告版本

实际保留期限、个人信息处理和物理删除条件，应依据适用法律法规及组织制度另行确定。

### 15.2 容量增长

初期采用单 MySQL 实例。优先通过索引优化、SQL
优化、资源扩容和统计查询分离解决性能问题。

达到明确瓶颈后再评估读写分离、分区、分库分表等方案，不提前引入不必要的分布式复杂度。

## 十六、统计分析数据设计

初期使用 MySQL
支持业务统计和运营分析，但应将日常业务查询与复杂统计查询适当分离。

建议原则： - 业务模块提供经过授权的数据服务。 -
指标定义和指标统计结果分开管理。 -
复杂统计尽量不直接压迫高频业务事务。 - 必要时使用汇总表或预计算结果。 -
报告记录统计周期、指标口径和数据来源。 - 初期不强制引入独立数据仓库。
