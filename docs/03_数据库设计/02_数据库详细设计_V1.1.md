## 1. 设计目标与总原则

本文件汇总第五阶段第03步全量重新评估的六批确认结果，形成数据库实施基线。总原则为：**按数据性质选择存储方式**。业务对象独立不代表必须一对象一表；静态配置、动态业务数据、运行数据、文件本体和向量数据分别选择适合的存储介质。

覆盖七大模块：人才选拔、人才档案与人才画像、智能测评与面试、AI
Agent与工作流管理、数字员工与任务调度、数据智能与运营决策、用户组织与权限管理，以及公共数据。

## 2. 全局存储架构

  --------------------------------------------------------------------------------------------------------------------------
  存储介质               存储内容                                                                   边界
  ---------------------- -------------------------------------------------------------------------- ------------------------
  MySQL                  动态业务数据、关系数据、正式业务结果、必要运行记录、用户权限、文件元数据   结构化查询、事务和约束

  YAML/JSON配置          模型参数、静态规则、Agent/Tool/Workflow配置                                不保存明文密钥

  Python代码             Agent、Tool实现、Workflow图结构、固定指标计算逻辑                          Git管理和代码评审

  Markdown               Prompt正文及说明文档                                                       Git管理

  Git                    配置与代码版本                                                             提交记录、分支、标签

  本地文件系统           简历、简历版本、附件、报告、导入导出文件、日志                             文件本体不入MySQL

  Milvus                 Embedding向量和向量检索数据                                                不作为业务数据权威来源

  独立Checkpoint持久化   LangGraph中断恢复状态                                                      后端需专项验证
  --------------------------------------------------------------------------------------------------------------------------

配置定义与运行数据分离：模型、Agent、Prompt、Tools、Workflow定义不建立MySQL配置表；Agent/Workflow执行记录存MySQL；Checkpoint独立持久化。密钥、密码、令牌通过环境变量或安全凭据注入，不提交Git、不写普通日志。

**存储决策优先级：**
第一批确定模块级存储原则；最后一批第33、35、36项对邀请/登录、通知/事件/导入导出、审计/系统日志作出更具体的文件化决定，具体记录方式以这些细化决定为准。

## 3. 数据库总体规范

  项目       规范
  ---------- ----------------------------------------
  数据库     MySQL，`agent_service`
  字符集     `utf8mb4`
  表名       小写英文和下划线
  主键       `CHAR(32)` UUID
  业务标识   需要跨系统或对外引用时设置独立业务UUID
  时间       `DATETIME`，统一UTC
  状态       `VARCHAR`，使用明确状态集合
  JSON       仅用于动态结构，不替代核心关系字段
  外键       核心业务关系建立必要外键
  ORM/结构变更 SQLAlchemy / 人工维护 SQL

通用字段按需采用：`id`、`business_id`、`status`、`created_at`、`created_by`、`updated_at`、`updated_by`、`is_deleted`、`version_no`。不要求所有表机械地包含全部字段。金额和分值使用适当DECIMAL类型；JSON字段定义结构版本；关键数据优先逻辑删除；并发编辑使用更新时间或版本号控制。

## 11. 风险与待验证事项

  -------------------------------------------------------------------------------------------------------------------------------------
  编号   风险                     影响                                   建议处理
  ------ ------------------------ -------------------------------------- --------------------------------------------------------------
  R01    邀请和登录只写日志       不便查询邀请历史、有效期及登录统计     当前状态由用户业务字段承载；事件日志追溯；不记录明文邀请令牌

  R02    通知记录不入库           难以查询通知历史、已读状态和失败重试   若需要通知中心，重新评估持久化方案

  R04    导入导出记录文件化       后台难以查询任务状态和历史             文件记录状态；需要任务中心时重新评估MySQL

  R05    操作审计文件化           日志可能丢失、被篡改                   独立目录、最小权限、备份和完整性校验

  R09    题库和试题合并           不同题型字段差异                       类型字段和类型专属Schema校验

### 16.4 MySQL记录与日志文件的关联

MySQL摘要记录和日志文件通过稳定标识关联：

-   `execution_id`：一次Agent、Workflow或任务执行的唯一标识；
-   `business_id`：关联的人才、招聘、测评等业务对象；
-   `correlation_id`：跨Agent、Workflow、Tool和Worker的链路关联标识；
-   `log_file_ref`或日志查询定位信息：用于定位对应日志文件或日志分片。

日志定位字段不应存储临时绝对路径作为唯一依据。建议以日志类别、日期分区、执行ID和文件分片规则定位，并允许日志轮转归档后更新索引或归档映射。

### 16.5 明确的存储边界

**进入MySQL：**

-   当前执行状态及可查询的执行摘要；
-   任务执行实例、重试次数及必要状态；
-   Workflow整体执行状态；
-   正式业务结果及后续流程需要引用的结果；
-   分析任务状态及正式分析结果引用。

**进入日志文件：**

-   Workflow节点级执行过程；
-   Agent模型调用和Tool调用详细过程；
-   Worker内部步骤和详细输出；
-   分析计算过程；
-   中间状态、调试信息、耗时明细和异常堆栈。

**不得仅写入普通日志的内容：**

-   人才正式档案和画像；
-   测评答题、评分及正式报告的业务引用；
-   后续业务流程必须读取的正式任务结果；
-   用户、角色、权限和数据范围；
-   必须支持事务一致性或可靠恢复的当前业务状态。

### 16.6 日志安全与可靠性要求

-   不记录明文密码、访问令牌、API Key、邀请密钥或完整认证头。
-   Prompt、模型输入输出和Tool参数可能包含个人信息；默认记录摘要和必要元数据，完整内容必须经过脱敏、权限和保留策略评估。
-   日志按类别和日期分区，设置轮转、保留、归档和清理策略。
-   对关键日志实施最小访问权限、备份和完整性校验。
-   日志写入失败、磁盘空间不足和日志队列积压必须产生可观测告警。
-   通过`execution_id`、`business_id`和`correlation_id`支持检索。
-   对要求事务一致性的业务事件，不能把普通文件日志当作事务提交的替代品；应采用可重试、幂等或经专项评估的可靠事件机制。
-   日志文件不是Checkpoint。Workflow恢复必须使用独立Checkpoint持久化机制。

### 16.7 本轮对原文档的结构性更新

1.  `workflow_node_execution`从MySQL表清单中移除。
2.  Workflow节点执行过程调整为结构化日志。
3.  `agent_execution`、`workflow_execution`、`task_execution`和`analytics_job`保留，但仅存摘要和状态。
4.  `task_result`只承载正式业务结果，不承担中间运行日志功能。
5.  Agent、Workflow、Task和Analytics日志类别纳入日志目录及日志规范。
6.  本节六项确认结果作为数据库详细设计的正式补充确认。

### 16.8 本轮最终结论

运行记录采用"**MySQL保存可查询状态和正式业务结果，日志文件保存详细执行过程**"的双层存储架构。该方案减少高频、细粒度运行明细对MySQL的写入和存储压力，同时保留业务状态查询、任务重试和执行追踪能力。

本轮六项确认全部选择A，整合评估完成。
