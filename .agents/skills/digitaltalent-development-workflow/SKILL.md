# 数字化人才平台标准开发工作流

本 Skill 规定项目开发任务的通用执行方式，不定义具体业务方案。业务目标、范围、设计依据、交付物和特殊限制以用户当前任务提示词为准。

## 0. 规则层级与授权

| 来源 | 负责内容 |
|---|---|
| 系统及更高层级指令 | 必须遵守，不得被项目规则或任务提示词覆盖 |
| 项目根目录 `AGENTS.md` | 项目长期约定、安全边界、技术规范 |
| 本 Skill 及 `references/` | 通用开发流程、检查、测试与验收 |
| 当前任务提示词 | 本次目标、范围、设计依据、交付物和特殊授权 |

执行规则：

1. 遵守系统及更高层级指令。
2. 默认遵守 `AGENTS.md` 和本 Skill；用户可在其权限范围内明确授权调整项目约定或流程。
3. 授权只适用于明确事项和范围，不自动扩展到其他文件、任务或后续任务。
4. 授权来源、事项和适用范围应记录在验收结果中；授权不明确时先询问。
5. 不因调用 Skill 而扩大任务范围，不自动开始下一项任务。
6. 分析、命令、测试和验收结论必须有真实证据，不得推测或编造。

## 1. 执行效率与上下文复用

### 1.1 基本原则

采用“已有信息优先、按需检查、增量执行”的方式。禁止每次任务启动时无差别地完整扫描项目、重读全部文档或检查所有运行环境。

### 1.2 上下文复用

1. 优先复用当前对话、当前任务已提供的设计文件、`AGENTS.md`、近期验收报告及真实命令输出。
2. 已有信息只有在与当前任务直接相关、来源明确且未显示过期时才可复用。
3. 不重复读取与当前任务无关的文档，不为了解背景递归扫描整个项目。
4. 若信息缺失、相互矛盾、涉及重大决策或可能已变化，只核实对应部分。
5. 不把历史报告中的“曾经通过”当作本次代码状态的测试证据。
6. 环境事实可复用作背景；本次执行 Python 命令前，若当前会话没有可信的环境验证结果，进行最小必要验证。

### 1.3 按任务分级

| 等级 | 典型任务 | 检查深度 |
|---|---|---|
| 轻量 | 单文件局部逻辑、文案或小范围 Bug 修复 | 检查目标文件、直接调用方和相关测试；不做全项目扫描 |
| 标准 | 多文件业务逻辑、API、ORM 模型、配置或跨模块调整 | 检查相关模块、依赖关系、共享文件及关联回归 |
| 完整 | 基础架构、公共配置、数据库基础设施、安全边界、跨模块重构 | 完整影响分析、必要环境核验、跨模块回归和风险评估 |

执行者应根据实际影响选择等级，并在复杂任务中说明理由。不得为了节省时间省略安全授权、Git 基线或必要测试。

### 1.4 环境检查按需执行

1. 仅检查本次任务实际使用的环境和工具。
2. Python 开发、测试、静态检查及依赖管理仍必须通过 Conda `feiyu` 环境执行。
3. 不涉及 Python 的纯文档任务，不检查 Python、Conda、MySQL、Ollama、GPU 等环境。
4. 不涉及数据库的任务，不检查或连接 MySQL。
5. 不涉及模型服务的任务，不检查 Ollama、Embedding 或 GPU。
6. 不涉及前端的任务，不检查 Node/npm。
7. 如果任务依赖某环境但已有证据可能过期，只重新核验该环境，不做无关检查。

## 2. 开发前检查

根据任务等级执行 `references/development-checklist.md` 中适用的项目。至少确认：

1. 项目根目录及任务范围。
2. `AGENTS.md` 中与本次任务相关的约定。
3. Git 工作区基线及用户已有修改。
4. 当前任务的前置依赖和相关实现。
5. 将修改、新增及明确不修改的文件。
6. 本次任务的完成标准和禁止事项。

不得为了“了解项目背景”扫描整个项目。目录访问必须有任务必要性，并遵守 `AGENTS.md` 的访问限制。当前任务明确要求整理或修改 `docs/` 时，按该任务授权范围访问，不得扩展到无关目录。

## 3. Python 环境规范

所有 Python 程序、测试、静态检查及依赖管理命令必须通过 Conda 环境 `feiyu` 执行。

当前项目约定的最小核验命令：

```powershell
conda run -n feiyu python --version
conda run -n feiyu python -c "import sys; print(sys.executable)"
conda run -n feiyu python -m pip --version
```

预期环境为 Python 3.11.x，解释器位于 `D:\anaconda3\envs\feiyu\python.exe`，pip 来自该环境。

若 `conda` 不在 PATH，可使用已确认的 Conda 路径：

```powershell
D:\anaconda3\Scripts\conda.exe run -n feiyu python --version
```

并通过同一 Conda 调用方式核验解释器和 pip。不得直接调用解释器绝对路径执行 Python 命令。

Conda 不可用、`feiyu` 不存在或核验失败时，停止相关 Python 开发和测试；不安装依赖、不切换 base、不调用其他 Python、不自动创建环境，报告失败原因并等待指示。

## 4. 前置依赖与现状核验

1. 只核验当前任务声明或实际依赖的前置任务。
2. 依据代码、配置、模型、SQL、测试或执行结果判断，不凭任务编号或文件名认定完成。
3. 状态使用：`已完成` / `部分完成` / `未完成` / `阻塞`。
4. 前置任务阻塞时，先报告影响，不擅自绕过或顺手补齐。
5. 搜索已有实现，避免重复实现；只查看与当前任务相关的调用关系。

## 5. 文件职责与共享文件

按任务等级使用 `references/file-responsibility-guide.md`：

- 轻量任务：识别目标文件职责及直接影响。
- 标准任务：列出修改文件、关联调用方、注册入口和关联测试。
- 完整任务：对公共文件执行完整历史、调用关系、修改顺序和回归分析。

共享文件修改必须最小化、增量化。此处“增量”指局部修改，不指在正式文档末尾追加补充说明；文档维护遵循 §8.1。不得无关重排、重写、格式化或重命名。已有未提交修改时不得覆盖；大范围冲突先向用户说明。

## 6. 技术方案与开发边界

复杂任务在编码前说明：实现方案、子任务、模块职责、数据流、接口关系、文件修改顺序、依赖/配置变化、风险和回退方式。简单任务可简要说明。

以下重大事项必须遵循已确认设计或取得用户明确授权：数据库/ORM 变更、公共数据结构、API 契约、认证授权方案、模型服务、向量库、缓存/消息队列/对象存储、核心依赖升级、目录边界调整。

项目当前数据库规范：

- MySQL 是唯一关系型数据库。
- SQLAlchemy 负责 ORM 模型定义和数据库访问。
- 数据库初始化及结构变更使用人工编写、审核和执行的 SQL 文件。
- 不使用自动数据库迁移框架。
- 数据库测试使用独立 MySQL 测试数据库，不使用其他数据库替代。
- 测试数据库与开发、生产数据库严格隔离。
- 未经明确授权，不创建/删除数据库，不执行 DDL/DML，不清空或重建表。

不得自行改变上述技术选型。

## 7. 编码与依赖管理

1. 优先小范围增量修改，不做无关重构。
2. 复用已有公共能力，不复制第二套实现。
3. 不删除测试、不降低断言、不通过放宽测试迁就实现。
4. Python 代码遵循项目 `pyproject.toml` 中的 Ruff 规范。
5. 新增或修改配置项时，遵守 `AGENTS.md` 的中文说明要求，并同步相关示例配置。
6. 未经用户授权，不安装、卸载或升级依赖。
7. 依赖仅维护在项目现有 `requirements/` 结构中，不另建依赖管理机制。
8. 不在代码、配置、日志或报告中写入真实密码、Token、API Key。

## 8. 测试验证

根据任务性质选择测试类型，具体要求见 `references/testing-checklist.md`。

项目数据库测试规范：

- 数据库相关测试使用隔离的 MySQL 测试数据库。
- 测试所需结构通过已审核的人工 SQL 文件准备。
- 不使用其他数据库替代 MySQL。
- 未经明确授权，不执行测试所需 DDL、DML、建库、删库或清理操作。
- 不存在可用隔离测试库或授权时，记录为未执行，不得擅自连接业务库。

不得用一种测试通过冒充另一种测试通过。报告必须区分已执行、失败、未执行和未验证项目。测试失败后保留原始错误，定位原因并重跑相关测试。

### 8.1 通用问题处理与文档更新

适用于所有开发任务、代码实现、测试、数据库实施、技术审核及验收过程。统一原则：问题发生时及时记录；解决并验证后直接修订原有内容，以最终正确情况维护当前有效文档，不以追加说明代替原文更新。

**发现与处理：**

1. 优先在已有开发记录、问题清单或任务文档的对应位置，记录问题现象、位置、影响范围、原因（未知时写“待分析”）、当前处理状态及是否影响后续开发。不随意新建问题记录文件。
2. 分析根因 → 确定方案 → 实施修复 → 执行必要验证 → 确认是否真正解决。尚未验证、验证失败或必要验证未执行时，不得标记为已解决；保留实际问题及后续影响。
3. 解决且验证通过后，在原有对应位置更新实现、原因、方案、状态、完成度及验收结论；正式文档只保留当前有效描述。必要的最终根因和验证证据可在对应字段中保留。

| 文档内容 | 问题未解决时 | 解决并验证后 |
|---|---|---|
| 问题描述 | 记录当前问题 | 更新为最终正确情况 |
| 原因分析 | 待分析或记录根因 | 必要时保留最终确认的根因 |
| 解决方案 | 记录待实施方案 | 更新为实际采用的方案 |
| 任务状态 | 处理中或待解决 | 更新为实际完成状态，不扩大完成范围 |
| 验收结果 | 未通过或待确认 | 更新为最新验证结论 |
| 临时问题清单 | 保留未解决问题 | 删除已解决临时条目；正式问题状态可更新为已解决 |

**正式文档与历史证据：**

- 持续维护的设计文档、开发实施方案、任务拆分与排期、开发进度、验收标准、当前开发记录、问题清单及未签署未归档的当前验收报告，均应直接更新原有内容。
- 已签署的正式验收报告、已归档执行日志及必须保持原始状态的审计记录属于历史证据，不得篡改。最新状态应写入当前有效任务记录或正式状态文件，必要时引用历史证据，并明确适用时间及版本。
- 原始失败输出、执行命令、退出码及测试证据是真实执行事实，不因问题解决而删除或改写为成功。将当前结论更新为最新验证结果，并使其与有明确时间/轮次的历史证据区分。

**跨文档同步与权限：**

- 仅检查并同步直接受影响、且已获访问和修改授权的设计与实现说明、任务状态、测试覆盖、验收报告和阶段进度。使实现情况、完成度及验证结论一致，避免修复后仍写有问题、重测通过仍保留过期失败结论、方案已变更仍描述旧方案、任务已完成仍显示处理中。
- 同一问题优先维护一个已有主记录；相关文档按职责更新当前结论，必要时引用主记录，避免重复描述互相矛盾。不为保留历史叙述而在正式文档中长期保留错误方案、临时结论或过期状态。
- 文档更新义务不扩大设计变更或文件访问权限。涉及授权范围外文档时，先在已授权的对应记录或当前回复中说明待同步文件、影响和所需授权，再请求授权；未经授权不得扫描或修改，也不得声称同步已完成。

禁止在原问题后持续追加解决说明，禁止新增“问题处理补充说明”“问题修复记录”“问题解决补充记录”等章节或文件代替原文修订。不得删除仍有效的问题、风险或必要测试证据，不得将未经验证的问题标记为已解决，不得修改须保持真实性的历史记录，不得重写无关文档。

## 9. 验收报告

每项开发任务完成后，按 `references/acceptance-report-template.md` 输出验收报告。

- 报告内容必须来自真实命令输出。
- 不适用章节可标记“不适用”，不编造内容。
- 报告路径由当前任务提示词指定；未获授权不得自行写入 `docs/`。
- 最终状态只能为：`已完成` / `部分完成` / `阻塞`。
- 开发完成不等于验收完成；必要验证未执行时如实判定。
- 明确列出遗留问题、风险和待人工确认事项。
- 已有当前有效报告时按 §8.1 修订原有实现说明、验证结果及结论，不另建重复报告或追加补充记录；已签署或归档的历史报告保持原样。

## 10. 任务收尾

1. 对照开发前 Git 基线复核本次改动。
2. 区分开发前已有修改与本次修改。
3. 执行适用的 `git diff --check`，必要时检查 `git status --short` 和 `git diff --stat`。
4. 不覆盖用户未提交修改，不擅自清理无关变更。
5. 不擅自执行 `git add`、`git commit`、`git push`、`git reset --hard`、`git clean`。
6. 按 §8.1 核对直接受影响文档的一致性，在授权范围内更新原文；输出或更新验收报告并说明开发完成/验收完成状态及尚待授权的同步项。
7. 停止并等待用户审核，不自动开始下一项任务。

## 11. 禁止事项速查

- 因 Skill 触发而扩大任务范围。
- 无差别扫描整个项目或读取无关目录。
- 使用非 `feiyu` 环境执行 Python。
- 未经授权改变技术选型、安装/升级依赖或执行数据库操作。
- 使用非 MySQL 数据库作为项目数据库测试替代。
- 覆盖用户未提交修改、擅自提交或重置工作区。
- 删除测试或降低断言标准。
- 将未执行的测试描述为通过。
- 任务完成后自动进入下一阶段。
